## 一路撞出来的两个坑（都已写进镜像/脚本）

1. **`zeroize 1.9.0` 要 `edition2024`**——Rust 1.83.0 的 Cargo 直接 `error: failed to parse manifest`。
   workspace 声明的 `rust-version = 1.80` 早已编不动 `Cargo.lock` 的实际内容。镜像默认版本提到 **1.90.0**。
2. **`centos:7` 的 manifest 在 Docker Desktop 上首次拉取失败**（`failed size validation`），
   单独 `docker pull --platform linux/amd64 centos:7` 后正常。属本地缓存打嗝，非脚本问题，未加规避代码。

顺带把 `Cargo.toml` 的 `rust-version` 由 `1.80` 改成 `1.85`、README 的「构建机需要 Rust 1.80+」一并改掉——
那两处声明在 `Cargo.lock` 现有内容下早已是假的，跟 CentOS 无关，普通构建路径上同样成立。

## 判据

### 1. GLIBC 符号上界（构建期静态核对，`objdump -T`）

```
db-qbs-sink:       GLIBC_2.16
db-qbs-source:     GLIBC_2.16
db-qbs-source-run: GLIBC_2.16
```

三个都低于 CentOS 7 的 2.17。

### 2. 干净 `centos:7`（glibc 2.17）上直接启动

三个二进制都因缺 `--config` 报用法并以 **exit 1** 退出——也就是**进程真的起来了**，
无 `GLIBC_2.xx not found`、无 `error while loading shared libraries`：

```
{"level":"error","event":"sink_unavailable","message":"用法：db-qbs-sink --config <sink.toml>"}
{"level":"error","event":"source_config_failed","message":"用法：db-qbs-source --config <source.toml>"}
{"level":"error","event":"cli_failed","failure_kind":"CONFIG","message":"missing required --config"}
```

### 3. glibc 动态链接（保住 OCI 加载 Instant Client 的前提）

`ldd` 三个产物一致，全部解析到位，无 `not found`：

```
libgcc_s.so.1 librt.so.1 libpthread.so.0 libm.so.6 libdl.so.2 libc.so.6
/lib64/ld-linux-x86-64.so.2
```

### 4. `cargo test --workspace`

mac 原生跑，**exit 0**，各 target `test result: ok`，**0 failed**（本票只加构建环境，不碰 `crates/` 与 `web/src/` 的代码）。

### 5. `verify.sh` 单跑

不带参数跑 `packaging/centos7/verify.sh`，平台取 `out/platform`（`linux/amd64`），**exit 0**。
