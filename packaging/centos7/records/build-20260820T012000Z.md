## arm64 这一路撞出来的两个坑（都已写进脚本/镜像）

1. **`centos:7` 的 manifest 解析在 buildkit 里偶发 `failed size validation`**——两个平台各撞过一次，
   而 `docker pull` 走的是另一条路、拉得下来。脚本改成**每个平台先 `docker pull --platform` 再 `docker build`**。
2. **altarch 的包用另一把签名 key**（`RPM-GPG-KEY-CentOS-7-aarch64`，key ID `305d49d6`），
   原来的 repo 只列了 x86_64 那把，`yum install` 直接 `Public key ... is not installed` 失败。
   镜像改成**把 `/etc/pki/rpm-gpg/RPM-GPG-KEY-CentOS-7*` 全部导入、全部列进 `gpgkey`**——
   没有关掉 `gpgcheck`：那是装到客户机上的东西的来源凭证。

## 判据

### 1. GLIBC 符号上界（构建期静态核对，`objdump -T`）

| 平台 | `db-qbs-sink` | `db-qbs-source` | `db-qbs-source-run` |
| --- | --- | --- | --- |
| `linux/amd64` | `GLIBC_2.16` | `GLIBC_2.16` | `GLIBC_2.16` |
| `linux/arm64` | `GLIBC_2.17` | `GLIBC_2.17` | `GLIBC_2.17` |

六个产物都不高于 CentOS 7 的 2.17（aarch64 侧正好压在 2.17 —— glibc 2.17 是 aarch64 的首发版本，
`GLIBC_2.17` 就是它能有的最低符号版本，不是越界）。

### 2. 各自架构的干净 `centos:7`（glibc 2.17）上直接启动

两个平台各三个二进制，全部因缺 `--config` 报用法并以 **exit 1** 退出——进程真起来了，
无 `GLIBC_2.xx not found`、无 `error while loading shared libraries`：

```
容器 x86_64 / ldd 2.17：sink_unavailable / source_config_failed / cli_failed(CONFIG) 三条用法，exit 1
容器 aarch64 / ldd 2.17：同上三条，exit 1
```

### 3. glibc 动态链接（保住 OCI 加载 Instant Client 的前提）

两边 `ldd` 全解析到位、无 `not found`，`libc.so.6` 在；`file` 认得出各自的解释器：

```
linux-amd64/db-qbs-source: ELF 64-bit LSB pie executable, x86-64,      interpreter /lib64/ld-linux-x86-64.so.2
linux-arm64/db-qbs-source: ELF 64-bit LSB pie executable, ARM aarch64, interpreter /lib/ld-linux-aarch64.so.1
```

### 4. `cargo test --workspace`

mac 原生跑：**28 个 `test result: ok`，0 个 `FAILED`**（本票只改构建环境，不碰 `crates/` 与 `web/src/` 的代码）。

### 5. `verify.sh` 单跑

不带参数跑 `packaging/centos7/verify.sh`，自动按 `out/bin/` 下的平台目录各验一遍，**exit 0**。
