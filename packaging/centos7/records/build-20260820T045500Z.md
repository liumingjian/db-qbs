# CentOS 7 构建镜像：yum 源加后备镜像 — 2026-08-20T04:55:00Z

[#151](https://github.com/liumingjian/db-qbs/issues/151) 的追加，起因是 [#154](https://github.com/liumingjian/db-qbs/issues/154)
实跑时踩到的那颗雷（见 `docs/spikes/fixtures/local-rig/rehearsal-preflight-20260820T035846Z.md`）。
**只改换源那一段**，不重编二进制——产物、GLIBC 上界、启动验证都不在本次范围内，
它们的实录是 [`build-20260820T012000Z.md`](build-20260820T012000Z.md)。

## 事情本身

2026-08-20 下午，`vault.centos.org` 前面那层 CDN 开始对 `*.sqlite.bz2` 回 **403**
（同一批 `*.xml.gz` 照常 200）。yum **优先取 sqlite 元数据**，于是那几个小时里
`yum install` 一律以 `No more mirrors to try` 收场——演练台上装 stunnel 全线失败，
而同一份换法也在这个构建镜像里，下一次构建会撞上同一堵墙。

**当晚 04:5x 复测：它自己好了**（同一个 URL 回 200，单源构建也重新成功）。
所以这不是一次永久性下线，而是一次抽风——**正因为它会自己好、也会自己再坏**，
单源就是一颗随时引爆的雷，而装机当天在客户现场引爆没有第二次机会。

## 改了什么

| 文件 | 改动 |
| --- | --- |
| `packaging/centos7/Dockerfile` | 新增 `ARG VAULT_MIRRORS`；`baseurl` 由 `VAULT_BASE` + 若干后备镜像拼成；加 `failovermethod=priority` |
| `packaging/centos7/build.sh` | 按平台算 `vault_leg`（`7.9.2009` / `altarch/7.9.2009`），base 与 mirrors 一起分腿，`--build-arg VAULT_MIRRORS=…` 传进去 |
| `docs/spikes/fixtures/local-rig/scripts/rehearsal-tunnel-up.sh` | 同一份换法的第三处，口径与注释对齐（后备镜像已在 #154 落地，本次补 `failovermethod=priority`） |
| `docs/spikes/fixtures/local-rig/scripts/test-rehearsal-tunnel.sh` | 第 11 条从「两处 vault 版本一致」扩到「三处后备镜像集合一致 + 两处都有 `failovermethod=priority`」 |

后备镜像取 `linuxsoft.cern.ch` 与 `archive.kernel.org` 的 centos-vault 树，两条腿的
altarch 路径都先探过（`repomd.xml` 与 `*.sqlite.bz2` 皆 200）。存档内容是冻结的，
镜像之间不会各说各话。

**`failovermethod=priority` 不能省**：yum 默认 `roundrobin`，从 URL 列表里**随机**挑起点，
「vault 优先、另两个才轮到」原本只是句愿望。

## 判据

### 1. 两个平台的构建镜像都建得出来

```
######## linux/amd64  base=http://vault.centos.org/7.9.2009
baseurl=http://vault.centos.org/7.9.2009/os/$basearch/ https://linuxsoft.cern.ch/centos-vault/7.9.2009/os/$basearch/ https://archive.kernel.org/centos-vault/7.9.2009/os/$basearch/
failovermethod=priority
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-CentOS-7
gcc-4.8.5-44.el7.x86_64 make-3.82-24.el7.x86_64 binutils-2.27-44.base.el7_9.1.x86_64 tar-1.26-35.el7.x86_64
x86_64 / ldd (GNU libc) 2.17 / rustc 1.90.0

######## linux/arm64  base=http://vault.centos.org/altarch/7.9.2009
baseurl=http://vault.centos.org/altarch/7.9.2009/os/$basearch/ https://linuxsoft.cern.ch/centos-vault/altarch/7.9.2009/os/$basearch/ https://archive.kernel.org/centos-vault/altarch/7.9.2009/os/$basearch/
failovermethod=priority
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-CentOS-7 file:///etc/pki/rpm-gpg/RPM-GPG-KEY-CentOS-7-aarch64
gcc-4.8.5-44.el7.aarch64 make-3.82-24.el7.aarch64 binutils-2.27-44.base.el7_9.1.aarch64 tar-1.26-35.el7.aarch64
aarch64 / ldd (GNU libc) 2.17 / rustc 1.90.0
```

altarch 那条腿的两把签名 key 照旧都在（`build-20260820T012000Z.md` 的第 2 个坑），
`gpgcheck` 没关。

### 2. failover 真的会轮到后备镜像（正/负对照）

vault 复原之后，「拿掉后备镜像看它红」这条负对照已经做不成了（单源也构建成功）。
所以改成**把第一个源故意指坏**，直接判机制本身：

| | 主源 | 后备镜像 | 结果 |
| --- | --- | --- | --- |
| 正对照 | `…/7.9.2009-no-such-tree`（404） | 有 | **构建成功**，日志里 `Trying other mirror.` |
| 负对照 | `…/7.9.2009-no-such-tree`（404） | 无 | **当场失败**：`repodata/repomd.xml from base: [Errno 256] No more mirrors to try.` |

负对照那一条同时说明：没有后备镜像时，主源一坏就是死路——这正是下午那几个小时的形状。

### 3. 三处换法不许各走各的

`test-rehearsal-tunnel.sh` 第 11 条扩写后，本机跑绿；并做了负向验：
从 Dockerfile 里删掉一个后备镜像 → 「后备镜像集合三处对不上」当场红；
删掉 `failovermethod=priority` → 「少了 failovermethod=priority」当场红。

## 没做的事（明写）

- **没有重编二进制**：本次只碰换源那一段，产物与 GLIBC 判据沿用
  [`build-20260820T012000Z.md`](build-20260820T012000Z.md)。要出新产物就跑 `build.sh`，
  它会连着 `verify.sh` 一起走。
- **没有把后备镜像塞进离线包**：现场那台机器多半连不上任何一个源，那条路是行李清单第 8 项
  （离线 rpm），不是 failover。
