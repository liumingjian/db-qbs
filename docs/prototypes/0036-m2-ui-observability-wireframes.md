# 原型（v2 定稿）：M2 Web UI 的观察面 —— 反推 M1 日志记什么

> **throwaway，不进 main。** 对应 issue #36。这里画的是**观察面**，不是 M2 的 UI 设计：
> 每一个格子存在的唯一理由，是它背后那一行「M1 运行期必须记下什么」。
> 不选框架、不定视觉、不碰 SQL 构建器交互。

## 五条约束（本票的真正产出 —— 「日志与可观测性的最小形态」那块雾的输入）

**A. 载体是 JSON Lines，不是人话文本。**
stdout 每行一个 JSON 对象，`source` 与 `sink` 同一套。理由是消费者定形态：这块雾的
消费者不是坐在终端前的人，是**排障时的 Agent 与 M2 的采集侧**——人话仍在 `message`
字段里，但**结构在字段上，不在排版上**。ADR-0016 §3「source 一次性进程」之后
stdout 就是全部取证面，把结构留在排版里等于要求下游写正则。

**B. 公共字段固定五个**：`ts`（UTC RFC3339）/ `level` / `event` / `run_id` / `task`。
`run_id` **可以是 `null`**——SQL 形状预检失败时 run 根本没发起（ADR-0016 §4），
字段缺席与「这个 run 没有 id」必须分得开。`task` 是任务绝对路径，
它是任务的唯一身份（`run_id` 里没有任务信息，ADR-0016）。

**C. 每批一行、全字段**：`seq` / `rows` / `bytes` / `written` / `ms`。
常态打，不挂开关。ADR-0011 验收要测批次字节分布、ADR-0007 要测 fetch 与推送耗时占比、
ADR-0015 要在 `sum(affected_rows) != rows.len()` 时点名第 `seq` 批——**这三条验收要求
在常态逐批日志下自动被满足**，不必另加一套只在验收时打开的埋点（开关是会忘记打开的东西）。
10 万行约 20–37 批，量级不构成理由。

**D. 失败定位打到列和值**：错误行带 `column` 与 `value`。
于是 #35 给 `ERROR 1292` 定的「点名是哪一列、哪个值」**不需要订正**。
代价必须写在明处：**日志文件因此含业务数据值**，权限口径跟 ADR-0016 的凭据同档（0600），
且这条要作为一句负面条款进规格——否则部署时日志会被随手 `chmod 644` 或采集到别处。

**E. 格式契约：字段集合稳定，排版不保证。**
`event` 取值与每个 `event` 必带的字段集合进规格；字段**只增不删、不改义**；
`message` 的文字随时可改。JSON 之后这条几乎是白拿的，而它决定了 M2 能不能靠采集
M1 的日志把面 2 拼出来——见冲突 C1。

## 数据项清单（每行都是一条对 M1 日志/协议的要求）

| # | 数据项 | 面 | M1 能不能提供 |
|---|--------|----|--------------|
| 1 | `run_id` | 1/2/3 | **能** —— 已定 stdout 单独一行（ADR-0016），另作公共字段 |
| 2 | 任务绝对路径 | 1/2/3 | **能** —— 已定进日志第一行（ADR-0016），升为公共字段 |
| 3 | 业务日期 | 1/2/3 | **要加埋点** —— 进 `run_start` |
| 4 | 当前阶段（五状态） | 1 | **要加埋点** —— 五个迁移点各一行 `phase_change` |
| 5 | 已推批次 `seq` | 1/3 | **能** —— ADR-0007 已要求 |
| 6 | 已推行数（累计） | 1 | **要加埋点** —— 累加器已存在，进 `batch_pushed` |
| 7 | 每批行数 / 字节数 | 1 | **要加埋点** —— 约束 C，常态打 |
| 8 | 每批耗时 | 1 | **要加埋点** —— 约束 C |
| 9 | run 起止墙钟时间 | 1/2 | **要加埋点** —— `run_start` / `run_end` |
| 10 | fetch / 推送 / commit 分段耗时 | 2 | **要加埋点** —— 进 `run_end`，兑现 ADR-0007 与 ADR-0010 的验收测量项 |
| 11 | 门禁四个数 + `sink_reported_rows` | 3 | **能** —— ADR-0013 已定进 `VERIFY_FAILED` 报文 |
| 12 | `purged_rows` | 2 | **能** —— ADR-0010 已在成功报文里 |
| 13 | 终态 `SWAPPED`/`DISCARDED` | 2/3 | **能，但有窗口** —— 只在 sink 最近 32 条墓碑内；进 `run_end` 后日志里就不受 32 条限制 |
| 14 | 失败 `code` + `message` | 3 | **能** —— ADR-0010 十码闭集 |
| 15 | 预检逐列报告 | 3 | **能** —— ADR-0009 §8 一次报全部列，每列一行 |
| 16 | 历史 run 列表（跨进程） | 2 | **M1 不提供**，但 JSON 日志被采集后可重建 —— 见 C1 |
| 17 | 按任务/日期查历史 | 2 | 同 16 —— `task` 与业务日期都在字段里，可被索引 |
| 18 | 定位到「哪一列、哪个值」 | 3 | **要加埋点** —— 约束 D，`column` + `value` |
| 19 | 进度百分比 | 1 | **不能** —— 总行数未知，结构性（ADR-0007 不预先 COUNT） |
| 20 | 实时推送（流式刷新） | 1 | **不能** —— source 无入站接口（ADR-0016 §3） |

**结论：8 项要加埋点、2 项结构性不能给（19/20）、2 项（16/17）从「不能」降级为「M2 靠采集重建」。**

## 冲突清单（留给 M2 地图）

| 冲突 | 撞上 | 留给 M2 的问题 |
|------|------|----------------|
| C1 历史运行列表 | ADR-0012 §2 状态不落盘；墓碑 32 条非状态存储 | M1 照实认零、不引入存储。JSON 日志 + 约束 E 把「采集日志重建历史」变成一条**可选路线**——M2 要在「引入运行历史存储」与「消费日志」之间选一次，这是 M2 地图的第一批票 |
| C2 进行中的实时观察 | ADR-0016 §3 source 一次性、无入站接口 | source 变长驻后进度从哪来？推还是拉？ |
| C3 校验失败的取证 | ADR-0013 暂存表失败即 DROP、不留现场 | 「差了哪几行」M2 要不要留？留在哪？ |
| C4 进度百分比 | ADR-0007 不预先 COUNT | M2 是否愿意为进度条付一次 COUNT 的钱？ |

**不构成冲突的一条**：约束 D 与 #35 的 `ERROR 1292` 措辞要求一致，不需要订正 —— 代价是
日志文件含业务数据值，权限须与凭据同档（0600）。
