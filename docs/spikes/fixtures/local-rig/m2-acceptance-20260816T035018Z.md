## 手工门禁 G1 —— 建表 SQL 生成器 ↔ 映射预检不漂移的第二遍

判据见 ADR-0028 §3.3：**真**在 MySQL 上执行生成的 DDL → **真** `describe` 出列元数据 →
**真**跑映射预检。以下是本次（2026-08-16，与上表同一台架实例）的实际观察，不是复述。

### 步骤 1：生成 —— 真 describe，70 列

`POST /api/columns`，源端 `t_m1_wide`（`row_id NUMBER(8)` + `d_biz DATE` + `c01–c68 VARCHAR2(48)`），
`target_table = G1_DDL_PROBE`。

```text
columns_http=200
columns_count=70
-- db-qbs 生成的目标表建表 SQL，请自行执行；产品不会替你建表。
-- 下面这条索引不是可选项：切换事务的 DELETE 会锁住目标表当日范围，
-- 业务日期列无索引时锁全表。
CREATE TABLE `G1_DDL_PROBE` (
  `ROW_ID` DECIMAL(8,0) NULL,
  `D_BIZ` DATETIME(0) NULL,
  `C01` VARCHAR(48) NULL,
  ...
  `C68` VARCHAR(48) NULL,
  KEY `idx_d_biz` (`D_BIZ`)
) DEFAULT CHARSET=utf8mb4;
```

### 步骤 2：真执行 —— 70 列这版被 MySQL 拒了

```text
ERROR 1118 (42000) at line 4: Row size too large (> 8126). Changing some columns to
TEXT or BLOB may help. In current row format, BLOB prefix of 0 bytes is stored inline.
information_schema.columns count for G1_DDL_PROBE = 0   （表根本没建出来）
```

`68 × 48 × 4 B（utf8mb4）= 13056 B > 8126 B`。**这不是生成器缺陷**——DDL 语法正确，
是目标端行宽上限拦下的。价值在于：ADR-0027 那条 `ERROR 1118` 静态提示不是理论关切，
**70 列 × `VARCHAR2(48)` 的宽表在 utf8mb4 下真的建不出来**；#2 的真实列清单里若有同等宽度，
行宽上限就是排在类型白名单之后的第二道墙。

### 步骤 2′：真执行 —— 收窄到 40 列后一次成功

同一生成器，源端改取 `row_id + d_biz + c01–c38`（40 列，`38 × 48 × 4 = 7296 B`）：

```text
step1_columns_count=40
step2_mysql_exit=0
DESCRIBE `G1_DDL_PROBE`:
Field   Type            Null  Key  Default  Extra
ROW_ID  decimal(8,0)    YES        NULL
D_BIZ   datetime        YES   MUL  NULL
C01     varchar(48)     YES        NULL
C02     varchar(48)     YES        NULL
C03     varchar(48)     YES        NULL
...
information_schema：40 列，其中 is_nullable=YES 的 40 列
```

`KEY idx_d_biz` 落成了 `D_BIZ` 上的 `MUL` 索引，与生成的 DDL 一致。

### 步骤 3：真跑映射预检（正面）

`POST /v1/runs` 直接打到运行中的 sink——由 sink 自己去 MySQL describe 目标表再跑
`precheck`，源端列取步骤 1′ 的 `describe` 输出：

```text
positive_open_http=200
{"run_id":"20260816041000_0a1b2c",
 "staging_table":"G1_DDL_PROBE__stg_20260816041000_0a1b2c",
 "columns_checked":40}
information_schema：G1_DDL_PROBE、G1_DDL_PROBE__stg_20260816041000_0a1b2c 两张表都在
```

40 列逐列过检、零 issue、暂存表真被建出来。**生成器与映射预检对同一批 describe 元数据零漂移。**

### 步骤 3′：真跑映射预检（反面对照）

只有正面会把「预检根本没在判」也判成通过，所以人为在目标表上制造两处偏离再跑一次：

```sql
ALTER TABLE `G1_DDL_PROBE` DROP COLUMN `C05`, MODIFY COLUMN `C07` varchar(8);
```

```text
negative_open_http=422
error.code = PRECHECK_FAILED
{"issues":[
  {"column":"C05","source":"VARCHAR2(48)","target":"<missing>","rule":"目标表缺少同名列"},
  {"column":"C07","source":"VARCHAR2(48)","target":"VARCHAR(8)",
   "rule":"目标 VARCHAR 长度必须大于或等于源 VARCHAR2 长度"}],
 "total":2}
```

两处偏离逐列点名、一次报全部，没有多报也没有漏报。

### 收尾

```text

DROP TABLE G1_DDL_PROBE → information_schema 中 G1_DDL_PROBE% 残留 0 张
```

### G1 结论

**通过。** 正面 40/40 列零 issue、反面两处偏离逐列点名，生成器出的 DDL 与映射预检读到的
目标端元数据是同一套判断。附带抓到一条与门禁无关但对上线有用的事实：70 列宽表撞 `ERROR 1118`。
