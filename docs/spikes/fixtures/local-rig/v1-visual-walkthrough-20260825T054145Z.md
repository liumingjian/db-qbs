## 一、X21（过滤条件 · WHERE 文本框）· 新增

打开构建器（源表模式）→ 读列 → 看「过滤条件」那张卡：

```
card_title:      过滤条件
card_subtitle:   留空就是整表取数；写什么就原样拼进 WHERE 后面
aria_label:      过滤条件（WHERE 之后的部分）
placeholder:     D_BIZ >= DATE '2026-08-01'
                   AND STATUS IN ('OK', 'WARN')
value_from_task: LOAD_DATE = DATE '2026-08-19'      ← 任务定义里那段字原样回显
note:            只写 WHERE 之后的部分，不用写 WHERE 这个词，也不要写分号。
                 本表可用的列：ID, C_NAME, LOAD_DATE, N_AMT
```

**旧的四格表单一个控件都没剩下**——这是本条最要紧的一半，因为「换了新的」与「旧的还在
角落里」在截图上看着一样：

```
leftover_selects:    0      ← 卡里一个 <select> 都没有（比较符 / 值类型下拉全没了）
leftover_add_button: false  ← 没有「添加条件」
rows_of_old_form:    0      ← 没有 .condition-row
```

占位符是**一条能直接改的真句子**，不是「请输入条件」：它带 `>=`（旧表单表达不出来的形态）、
带 `IN`、带日期字面量，是两行——照着改就能用。

往里写一段带四类记号的多行条件：

```
typed:              LOAD_DATE >= DATE '2026-08-01'
                      AND C_NAME IN ('SH', 'HZ') AND N_AMT > 100
value_after_typing: （逐字相同）
```

高亮层的实测：

```
present:          true
text_round_trips: true                  ← <pre> 的文本与 textarea 的值逐字相同
keyword:          rgb(124, 58, 237)     ← --sql-keyword，与自定义 SQL 那格同一批令牌
string:           rgb(15, 123, 79)
number:           rgb(180, 83, 9)
punct:            rgba(0, 0, 0, 0.65)
textarea_color:   rgba(0, 0, 0, 0)      ← 输入层的字是透明的，看到的是下面那层
ligatures:        none                  ← `>=` 按字面显示，没被画成 ≥
metrics_match:    true
  两层各自的六项：font ui-monospace…  size 12px  line 18.6px
                 pad 9px 10px  border 1px  ws pre
pre_box:          x 259  y 1162  w 922  h 94
textarea_box:     x 259  y 1162  w 922  h 94      ← 四个数逐个相同，光标不会飘
```

**`metrics_match` 与两个 box 全等是这一条真正买到的东西。** 颜色对不对肉眼能看，
两层错开半个像素肉眼看不出来——它只在你把光标移到第三行末尾时才现形。

生成的 SQL：

```
SELECT a.ID AS ID,
       a.C_NAME AS C_NAME,
       a.LOAD_DATE AS LOAD_DATE
  FROM APP.T_HOLDING a
 WHERE LOAD_DATE >= DATE '2026-08-01'
  AND C_NAME IN ('SH', 'HZ') AND N_AMT > 100
```

第二行前面那 2 格是**用户自己在文本框里敲的那 2 格**，生成器一格都没补。

**这一条是代码审查改出来的。** 先前那版把续行缩进重排成 7 格，看着确实齐；
但那**不是只动空白**——落在字符串字面量里的换行，插进去的空格会改掉那个字面量的值，
也就改掉了搬的数据。判定改成**一个字符不加不改**（ADR-0047 §1），
产品、三份桩、X21 的判据一起改，这一段是改完之后的复跑。看着不如对齐好看，
换来的是「预览的字与执行的字逐字相同」。

`run_parameter_block: false`——预览下面那块「运行参数」不再渲染，
它随 ADR-0047 §3 整条退役，不是「这次恰好没有参数」。

## 二、X9（重跑与并发拦截）· 后半再改判

前半（入口在抽屉底部、五种态各给什么）**逐条复核，与上一份实录一致**：

```
rows:  成功=客户订单增量  进行中=财务凭证  失败=结算对账
       结局不明=客户主数据  尚未运行=产品维表
drawer footer:
  失败      ["关闭", "重跑"]
  结局不明  ["关闭", "重跑"]
  进行中    ["关闭"]
  成功      ["关闭"]
  尚未运行  开不了抽屉，行内图标 disabled，
            aria-label「运行详情（不可用）：这个任务尚未运行过，没有可看的运行记录。」
```

后半是本次改判。点那条失败任务抽屉底部的「重跑」：

```
dialog_opened:        false        ← 没有对话框
drawer_closed:        true
landed_on_run_detail: true
breadcrumb:           数据导入 / 运行详情
start_error:          null
```

**点下去当场就跑，直接落到运行详情。** 原判那整段「按上次参数预填、参数全部可改、
填满后出并跑提示」在这一版没有对象——上一次运行没有留下任何需要带过来的取值。

并跑拦截**没有消失，换了落点**。去点那条名下已有运行在飞的任务（财务凭证）的行内
「发起运行」：

```
dialog_opened: false
notice:        财务凭证：该任务已有一次运行进行中 | 知道了
notice_colors: color rgba(0, 0, 0, 0.85)   bg rgb(255, 241, 240)
```

这句话落在**屏顶的 `.notice.is-error` 横幅**里，前缀是任务名（一屏可能连点好几个，
不写名字就不知道是哪一条），尾巴上一颗「知道了」把它收掉。**它是服务端真回的 409**，
不是客户端猜的——原来那条 `.stale-run-hint` 是发起之前的一次预读，与真正的闸门赛跑。

跑完这一趟之后的状态列：`["成功","进行中","失败","结局不明","成功","尚未运行","成功"]`
——重跑那一条把 `task-verify` 的最近一次换成了新的进行中记录，其余六行未被扰动。
