## 2. `oracle` crate / ODPI-C 类型保真度（#3）

**结论：通过。** `NUMBER` 能以字符串取到 38 位完整精度，ADR-0003 的硬前提成立。
台架覆盖到的每一种类型都能保真读出，**FAIL 0 项**。

> 跑法：`docs/spikes/fixtures/local-rig/scripts/run-odpi-probe.sh`（在 #9 台架上，
> arm64 原生 Instant Client 19.32 → amd64 模拟的 XE 11.2.0.2）。
> 探针源码 `docs/spikes/fixtures/local-rig/spike-odpi/`，一次性，不进主干。
> 期望值全部来自台架的 `t_canon_expected`，**没有硬编码在 Rust 里**。

### 2.1 闸门判据：`NUMBER` 完整精度

```
[PASS] n_int38 取成 String = "12345678901234567890123456789012345678"（38 位有效数字）
[PASS] n_bare  取成 String = "12345678901234567890123456789012345678"（38 位有效数字）
[对照] 同一值取成 f64     = 12345678901234568000000000000000000000  ← 精度已丢
```

`row.get::<_, String>()` 走的是 ODPI-C 的原生 bytes 路径，**不经过 `f64`、也不经过
`rust_decimal`**；同一行取成 `f64` 的对照数据就在上面，两者放一起即为 ADR-0003 的论据。

### 2.2 逐类型判定

| 类型 | 边界 | 结果 |
|---|---|---|
| `NUMBER`（无精度声明 / 38,0 / 38,10 / 18,2） | 38 位满精度正负、零与负零、尾零、高标度、小于 1 的小数 | PASS |
| `DATE` | 非零时分秒 | **M1 生效** | PASS（`2026-08-13 14:35:09`） |
| `TIMESTAMP(6)` | 固定 6 位补零 | PASS（`2026-08-13 14:35:09.120000`） |
| `VARCHAR2` / `NVARCHAR2` 中文 | UTF-8 往返 | PASS |
| `CHAR(10)` / `NCHAR(10)` | 尾部空格保留 | PASS（`"AB        "`、`"甲乙        "`） |
| `NULL` | 与非 NULL 可区分 | PASS |
| `RAW` / `BLOB` | 字节无损 | 读出正常（`DEADBEEF00` / `0001020304FF`），但 **V1 排除**（#11） |
| `CLOB` / `NCLOB` | 中文混合内容 | 读出正常，**V1 排除**（#11） |
| `LONG` / `LONG RAW` | 11g 遗留类型，ODPI-C 已知弱项 | **读出正常** —— 预想的坑没踩到；仍 **V1 排除**（#11） |
| `BINARY_FLOAT` / `BINARY_DOUBLE` | 值域 | 读出正常，但 **V1 排除**，见 2.4 |

汇总：`PASS 20 / FAIL 0 / EXCL 8 / OBS 100`（`t_canon_expected` 的 28 个单元格全部判定）。

> `EXCL` 是 [#11](https://github.com/liumingjian/db-qbs/issues/11) 结论落进台架后的产物：ADR-0003 白名单之外的类型不再判 PASS/FAIL，
> 只回报驱动取到了什么。首跑（#11 结论前）的数字是 `PASS 20 / FAIL 0 / UNSPEC 3`，
> 保真度判定本身没有变化 —— 变的是那几类从「ADR 未定义」改记为「V1 明确不支持」，
> 且覆盖从 3 个单元格补齐到 8 个（`NCLOB` / `BLOB` / `BINARY_DOUBLE` / `LONG` / `LONG RAW` 原先漏在期望表外）。

### 2.3 意外发现：驱动的 `NUMBER` 字符串已经就是规范形式

`0.5` / `-0.01` / `1.23`（源值 `1.2300000000`）/ `0`（源值 `-0`）——
**驱动给出的原始字符串与 ADR-0003 规范形式逐字节相同**，规范化函数在这些用例上是恒等变换。

这直接回答 [#10](https://github.com/liumingjian/db-qbs/issues/10)：
`sqlplus` 的 `TO_CHAR(0.5)` 返回 `.5`，但 **ODPI-C 返回 `0.5`（保留小数点前的 0）**。
两者不一致，说明「`TO_CHAR` 的行为」不能当成规范形式的依据。
按 ODPI-C 的输出定 ADR，规范化这一步在 `NUMBER` 上就退化成校验，实现风险最低。

### 2.4 曾经的 ADR 缺口 —— 已由 #11 收口为「V1 不支持」

`BINARY_DOUBLE` 的 `1.7976931348623157E+308` 取成字符串是 **309 位的十进制展开**
（`17976931348623157` 后跟 292 个 `0`），不是科学计数法。二进制浮点本身就不是十进制精确值，
「一律走字符串」对这两个类型**不构成无损往返的保证**；这个值落进 MySQL `DECIMAL` 也必然溢出。
`RAW` / `BLOB` / `CLOB` / `NCLOB` / `LONG` / `LONG RAW` 同样没有规范形式定义
（本报告按十六进制大写 / 原样文本表示，那只是回报用的可比对表示，不是规范形式）。

[#11](https://github.com/liumingjian/db-qbs/issues/11) **已结**：本条的先决输入本是 #2 的真实类型清单，
但客户环境不可达，故按默认答案收口 —— **ADR-0003 升格为白名单制**，
只有 `NUMBER` / `DATE` / `TIMESTAMP` / `VARCHAR2` / `NVARCHAR2` / `CHAR` / `NCHAR` / `NULL`
允许进入搬运链路，上述类型一律在**映射预检阶段报错拒绝**，不静默按某种默认形式搬过去。
理由是两种错法代价不对称：排错了当场报错，定错了会以「checksum 对不上」的形式在下游远处爆出来。
详见 ADR-0003「V1 类型白名单」一节。

台架已同步：这些单元格的期望值写成 `V1 排除：…`，探针判 `EXCL` 而非 `UNSPEC`。
**判据在数据里**（`t_canon_expected.note`），日后若决定纳入某一类，改期望表即可，不必动 Rust。

### 2.5 本条**没有**回答什么

1. **GBK 中文往返未测。** 台架 `NLS_CHARACTERSET` 是 `AL32UTF8` 且改不了（见台架 README 边界一节），
   本条测的是 UTF-8 路径。生产库若为 `ZHS16GBK`，仍需在客户环境复测 —— **M0 的已知缺口**。
2. **真实类型清单仍缺。** 本条覆盖的是 ADR-0003 的「类型面」，不是客户表的列清单（#2 的产出）。
   若 #2 扫出 `XMLType`、`INTERVAL`、`TIMESTAMP WITH TIME ZONE` 等台架未覆盖的类型，需补测。
   按 #11 的白名单决策，这类类型 V1 一律预检报错拒绝 —— 所以 #2 的类型普查
   （`fixtures/03-type-census.sql` 的「11g 遗留类型点名检查」一段）已从**阻塞项降级为验收项**：
   返回空则白名单成立，有命中则回炉重开 #11。
3. **吞吐与内存不在此列**（#5，且本台架测不了）。

因此本条**通过，但不单独关闭闸门** —— 闸门仍需 #5，以及在客户环境上复验 1 与 2。

## 3. `oracle-rs` 纯 Rust 类型保真度（#4）

**结论：未测，候选出局。** 不是"测了不通过"，是**前置条件不满足，测了也没有意义**。

`oracle-rs` 自己声明的服务端下限是 **Oracle 12.1**（纯 Rust 实现的 TNS 协议版本），
而 #6.3 确认客户源端是 **11g**。差的是协议版本，不是 API 覆盖度——
再怎么补功能也补不出一个 11g 能握手的实现。[#4](https://github.com/liumingjian/db-qbs/issues/4) 据此关闭，不产出实测数据。

**这一条改变了 M0 的性质**：ADR-0001 原本留的是「两个候选择优」，
11g 一出来就变成 **ODPI-C 单点验证——没有备胎**。所以 §2 的类型保真度若失败，
不是"换另一个 Rust 驱动"，而是直接触发 ADR-0001 复审、回退 Java。#1 的通过判据已按此改写。

> 留给未来的口子：客户若在 V1 之后把源端升到 12.1+，"免 Instant Client"这条路会重新打开，
> 届时值得重测一次——那是一次部署形态的简化，不是正确性问题。

## 4. 流式 fetch 吞吐与内存（#5）

**结论：台架能答的两条都过了。** 内存形状 —— 峰值随「批次大小 × 行宽」走，与总行数无关（4.2）；
客户端每行处理开销 —— 1.1 us/行（4 列），随行数线性，外推 70 列后 10 万行约 1.5 秒客户端 CPU（4.7）。
**只剩服务端吞吐的绝对秒数，台架不可信，已按 ADR-0005 转 #2 的上线前复验清单。**

> 跑法：内存形状 `.../scripts/run-bulk-probe.sh`，客户端 CPU `.../scripts/run-cpu-probe.sh`（#9 台架，
> arm64 原生 Instant Client 19.32 → amd64 模拟的 XE 11.2.0.2）。
> 探针源码 `docs/spikes/fixtures/local-rig/spike-bulk/`，一次性，不进主干。
> 数据源 `t_bulk_probe` 10 万行（`row_id` / `NUMBER(18,2)` / `VARCHAR2(200)` / `DATE`）。
>
> **一次进程只测一个配置** —— `/proc/self/status` 的 `VmHWM` 是进程存续期峰值，
> 同一进程里连测多个配置，后面的会被前面的污染。矩阵由 runner 脚本循环。
>
> **为什么这一节能在台架上做**：台架 README 判过「#5 不能在此测」，那说的是**吞吐**。
> 内存形状与客户端 CPU 都是驱动**客户端侧**的行为 —— 客户端跑在 arm64 原生上，没有模拟层，
> 与服务端快慢无关。下面凡是内存与 `getrusage` CPU 的数字都成立，凡是**墙钟**的数字都只用来看趋势
> （4.7 开头那条 dblink 对照实验，就是这个区分的实证）。

### 4.1 地板：Instant Client 常驻多少

只连库不查询，RSS 从 1.8 MB → **25.8 MB**。这 24 MB 是 ODPI-C `dlopen` 进来的
`libclntsh.so` 及其会话结构，**与数据量无关**，下面每一行的增量都是在它之上算的。

### 4.2 形状判据：峰值跟行数走还是跟批次走

批次固定 5000 行、`fetch_array_size=100`，行数走 ×10 阶梯：

| 行数 | `VmHWM` | 相对地板 |
|---|---|---|
| 1,000 | 26,496 kB | +716 kB |
| 10,000 | 27,656 kB | +1,876 kB |
| 100,000 | 27,656 kB | **+1,876 kB** |

**10k 与 100k 一字不差** —— 行数涨 10 倍，峰值一个字节没动。
（1k 那行低，是因为只有 1000 行、5000 的批次没攒满，量到的是半个批次。）

反证在同一段取值代码上做，只把「攒够一批就清空」换成「全部留在内存里」：

| 行数 | `VmHWM`（collect） | 相对地板 |
|---|---|---|
| 1,000 | 26,588 kB | +808 kB |
| 10,000 | 29,064 kB | +3,284 kB |
| 100,000 | 55,048 kB | **+29,268 kB** |

线性，约 **300 B/行**。这条反证是必要的：它证明测量手段对「内存随行数涨」是敏感的，
所以上表的「不涨」不是量不出来，是真没涨。

> 换句话说，**驱动没有在内部缓冲全量结果集**，流式读是真的。
> ADR-0001「同步阻塞 IO + 分批落库」的内存前提成立。

### 4.3 批次大小的代价

10 万行固定，`fetch_array_size=100`，批次走阶梯：

| 批次 | `VmHWM` | 相对地板 | 摊到每行 |
|---|---|---|---|
| 500 | 26,504 kB | +724 kB | — |
| 5,000 | 27,456 kB | +1,676 kB | ~0.33 kB |
| 20,000 | 32,008 kB | +6,228 kB | ~0.31 kB |
| 50,000 | 40,388 kB | +14,608 kB | ~0.29 kB |

摊到每行约 **300 B**，与 4.2 反证表的斜率一致 —— 因为它们是同一笔开销：
**批次缓冲就是「驻留在内存里的行数」**，只不过流式模式下这个行数被批次钉住了。
（500 那行摊下来偏高，是固定开销还没被摊薄，不是行变大了。）

结论的形式是：**峰值 ≈ 地板 + 批次行数 × 单行字节 + 取数缓冲**。
三项里没有总行数。

### 4.4 驱动取数参数

10 万行、批次 5000：

| `fetch_array_size` | `VmHWM` | 相对地板 | 耗时（趋势） |
|---|---|---|---|
| 10 | 27,528 kB | +1,748 kB | 773 ms |
| 100（默认） | 27,656 kB | +1,876 kB | 149 ms |
| 1,000 | 28,732 kB | +2,952 kB | 121 ms |
| 5,000 | 33,344 kB | +7,564 kB | 116 ms |

`fetch_array_size` 是 ODPI-C 一次网络往返取回的行数，缓冲约 **1.16 kB/行**。
趋势上 10 → 100 是 5 倍提速（往返次数少了 10 倍），100 → 1000 收益已经很薄，
1000 → 5000 基本平掉 —— 拐点在 100～1000 之间。**绝对秒数作废，拐点位置本身可信**
（往返次数是逻辑量，不受模拟层影响）。

`prefetch_rows` 取 0 / 2（默认）/ 1000，峰值 27,656 / 27,640 / 27,900 kB，
耗时 205 / 209 / 193 ms —— **三档都没有可辨识的差别**。它只影响 `execute` 那一次的预取，
真正的缓冲是 `fetch_array_size`。**这个参数不必调。**

### 4.5 走 dblink 的同一条链路

`t_bulk_probe@fa`（loopback dblink），其余参数不变：

| 取法 | `VmHWM` | 对照本地表 |
|---|---|---|
| `fetch_array_size=100` | 27,656 kB | **完全相同** |
| `fetch_array_size=1000` | 28,736 kB | 28,732 kB，差 4 kB（噪声） |

**dblink 不改变客户端的内存形状** —— 合理，远端拉回是服务端内部的事，
到客户端这一侧仍是同一条 SQL*Net 结果流。（耗时 664 / 414 ms 比本地表高 3～4 倍，
loopback 多一跳，但这是模拟层上的数字，只说明"有代价"，不说明代价多大。）

### 4.6 批次大小 5000 的建议

**维持 5000，但判据要从「行数」改成「字节数」。**

台架的 `t_bulk_probe` 只有 4 个窄列，约 300 B/行，批次 5000 → 1.7 MB，
连同地板和取数缓冲一共 27 MB，对内网机器毫无压力。但生产的 `t_r_fr_aststat`
是 **70 列**（#6 已按这个宽度建过 `t_wide_probe`），单行字节要大一个量级。
按 3 kB/行估，批次 5000 ≈ 15 MB，仍然安全；批次 50000 ≈ 150 MB，**越过 100 MB 的任务上限**。

所以给 M2/M3 的实现约束是：

- **批次大小 5000 作为默认值保留** —— 在 300 B/行 到 3 kB/行的范围内都落在安全区。
- **真正的上限是 `批次 × 单行字节`，不是批次行数。** 若 #2 拿回来的真实行宽远超 3 kB，
  批次要按字节反算下调，而不是继续用 5000。
- **`fetch_array_size` 设 100～1000**（默认 100 已在拐点上，1000 多花 1 MB 换一点余量）。
  **`prefetch_rows` 保持默认，不要调。**

### 4.7 客户端每行 CPU 开销（3b）

**问的不是"客户库快不快"，是"同步阻塞 IO 的_实现_会不会成为瓶颈"。** 前者是服务端吞吐，
台架答不了（已转 #2 清单第 4 项）；后者是我们这一侧每搬一行烧多少 CPU，台架能答。

计量用 `getrusage(RUSAGE_SELF)` 的 `ru_utime + ru_stime` —— **只计进程真正占用 CPU 的时间，
等服务端的时间不计入**，所以模拟层拖慢的是墙钟，不是这个数。跑法
`./scripts/run-cpu-probe.sh`（`REPS=7`，每档取中位数），探针的四个 `cpu*` 模式把取数路径
切成累进的四层，相邻两层相减即为该层的每行成本。

**先验计量本身**：同一条完整路径，本地表 vs loopback dblink ——

| 链路 | 墙钟中位数 | 客户端 CPU 中位数 |
|---|---|---|
| `t_bulk_probe` | 193 ms | 110.6 ms |
| `t_bulk_probe@fa` | 511 ms（**2.6 倍**） | 113.1 ms（差 2%，噪声内） |

**服务端慢了 2.6 倍，客户端 CPU 一动不动。** 这条对照就是「CPU 计量隔离掉了服务端」的证据，
也是这一小节能在模拟层台架上成立的理由。

#### 每行成本随行数线性

完整路径（4 列，批次 5000，`fetch_array_size=100`）：

| 行数 | 客户端 CPU | 每行 |
|---|---|---|
| 1,000 | 1,636 us | 1,636 ns |
| 10,000 | 12,187 us | 1,219 ns |
| 100,000 | 110,644 us | **1,106 ns** |

两段斜率：1k→100k 是 1,101 ns/行，10k→100k 是 1,094 ns/行 —— **相差 1%**，
截距（每次查询的固定开销）约 0.5 ms。每行成本是常数，**没有随行数增长的项**
（反复分配、累积拷贝这类实现缺陷会表现为超线性，这里没有）。

#### 成本分解：大头在驱动，不在我们的代码

10 万行、4 列，四个累进层级：

| 层 | 累计 CPU | 增量 | 每行增量 | 占比 |
|---|---|---|---|---|
| `cpu0` 迭代行、不取值 | 70,355 us | — | 704 ns | **64%** |
| `cpu1` 取原生类型 | 81,068 us | +10,713 us | 107 ns | 10% |
| `cpu2` → ADR-0003 规范形式文本 | 101,915 us | +20,847 us | 208 ns | 19% |
| `cpu3` 组 `Vec<String>` + 批次缓冲 | 110,644 us | +8,729 us | 87 ns | 8% |

**64% 花在「把行推过来」上** —— OCI/ODPI-C 解析 SQL*Net 协议、填内部缓冲，
这段代码不是我们的，改不动，只能靠**少取列**来避免。
我们自己能改的（文本化 + 组装 + 批次）合计约 27%，绝对值 295 ns/行。

#### 每单元格成本：往 70 列外推

台架表只有 4 列，生产 `t_r_fr_aststat` 是 70 列，所以要知道成本是按行摊还是按单元格摊。
完整路径、10 万行，只改取几列：

| 列数 | 每行 CPU |
|---|---|
| 1 | 455 ns |
| 2 | 579 ns |
| 3 | 838 ns |
| 4 | 1,106 ns |

线性拟合：**每多一列约 217 ns，另有与列数无关的每行固定开销约 238 ns。**
外推到 70 列：`238 + 70 x 217` ≈ **15.4 us/行**，10 万行 ≈ **1.5 秒**客户端 CPU；
按 300 ns/单元格的悲观值算也只有 2.1 秒。

#### 结论：同步 IO 的实现侧无罪

- 客户端侧的时间下界（10 万行 x 70 列）是 **1.5～2 秒**，ADR-0001 说的「几十秒」
  **远未触及** —— 单核客户端 CPU 撑得住约 65,000 行/秒（70 列）。
- 因此 **ADR-0001 不必因实现开销复审**。剩余风险全在服务端与网络，
  那正是 #2 清单第 4 项要量的东西。
- 给 M1 的指向：**别调代码，先减列。** 大头（64%）在驱动的协议解析里，
  只有少取列能省；我们自己的 295 ns/行即使优化掉一半，10 万行也只省 0.015 秒。

### 4.8 本条**没有**回答什么

- **吞吐的绝对数字。** 服务端在 Rosetta 模拟层上，10 万行 150～200 ms 这种数字不能引用，
  也不能拿来说"同步 IO 够快"。ADR-0001 的**内存**前提与**客户端实现开销**前提都已证实，
  **服务端吞吐**前提只能说「没有被证伪」—— 真实数字必须在客户环境上重测（#2 清单第 4 项）。
- **宽单元格的 CPU 成本。** 4.7 的 217 ns/单元格是在窄列上测的（约 300 B/行）；
  字符串分配与拷贝随字节数走，真实宽列会更贵。70 列的外推按「每单元格常数」做，
  真实行宽标定（#2 清单第 2 项）回来后应复算一次。
- **真实行宽。** 4.6 的批次建议建立在对 70 列宽表的**估算**上。`#2` 拿回
  `t_r_fr_aststat` 的真实列定义后，这个估算要用实测行宽替换。
- **跨机 dblink 的 RTT。** 台架是 loopback，4.5 的耗时对比只说明有代价，不说明有多大。
- **GBK 字符集下的行宽。** 台架是 `AL32UTF8`，中文 3 字节/字；生产 `ZHS16GBK` 是 2 字节，
  行宽会略小 —— 方向对我们有利，但同样待客户环境复验。

## 5. dblink 列投影下推（#6）

**结论：Oracle 自己会把列投影推到远端。ADR-0004 的「把投影写进内层子查询」是防御性建议，不是必需的。**
**绑定变量能穿过 dblink，ADR-0004 不需要改方案。**

在本地替身台架（`docs/spikes/fixtures/local-rig/`，loopback dblink `@fa` 指回同一 XE 11.2.0.2）上，
建了一张 70 列的 `t_wide_probe`（贴近生产 `t_r_fr_aststat` 的形状）灌 5000 行随机值实测。
探针脚本 `probes/dblink-pushdown{,-2,-3}.sql`，跑法 `./scripts/run-dblink-probe.sh [脚本名]`。

### 5.1 远端 SQL 里带没带列裁剪

关键证据是执行计划的 **Remote SQL Information** —— 那才是真正发到远端的 SQL。
要看到它，查询必须同时碰本地对象（纯远程查询会被判成 `fully remote statement`，整条语句发过去，
连 `REMOTE` 行源都没有）。因此对比在「远程宽表 join 一张本地小表」的混合形状上做：

| 形状 | 内层写法 | Plan hash | 发到远端的 SQL |
|---|---|---|---|
| A（生产原样） | `SELECT *` | 414720286 | `SELECT "ROW_ID","D_ASTSTAT","C01","C02" FROM "T_WIDE_PROBE" "A" WHERE "D_ASTSTAT"=TRUNC(:1-1)` |
| B（ADR-0004 建议） | 投影写进内层 | 414720286 | **完全相同** |
| A + `NO_MERGE` | `SELECT *`，禁止子查询合并 | 3814347444 | **完全相同** |

三点：

1. **70 列里只有 4 列过网络** —— 外层引用的 3 列，加上 WHERE 用到的 `D_ASTSTAT`。列投影下推成立。
2. **A 与 B 的计划完全一致**（同 plan hash、同远端 SQL）。改写不带来任何收益。
3. **连 `NO_MERGE` 都推不坏它** —— 加了 hint 后本地多一层 `VIEW`，但远端 SQL 一字不差。
   投影裁剪不依赖子查询合并，所以它不是「碰巧生效」。
4. 顺带：**WHERE 谓词也一并下推**了，不是拉回本地再过滤。

### 5.2 网络传输量实测

`v$mystat` 的 `bytes received via SQL*Net from dblink`，5000 行：

| 取法 | 收字节 | B/行 |
|---|---|---|
| 内层 `SELECT *`，外层 3 列 | 656,992 | 131.4 |
| 内层已投影，外层 3 列 | 656,595 | 131.3 |
| 混合（远程 join 本地），外层 3 列 + tag | 667,448 | 133.5 |
| **对照：真取全 70 列** | **20,830,956** | **4166.2** |

前两行差 0.06%，是噪声。对照行说明计数器对列宽完全敏感（32 倍差距），
所以前两行的「没差别」不是计数器不灵，是真没差别。

> 坑（留档）：第一轮测出来只有 12 B/行，因为填充数据每行同值，**SQL\*Net 会去重重复列值**。
> 第三轮改灌随机值才得到上面的数字。以后拿字节计数器做对比，填充数据不能同值。

### 5.3 绑定变量能否穿过 dblink（这条影响 ADR-0004）

**能。** `:biz_date` 到了远端仍是绑定变量，没有被拼成字面量：

```
Remote SQL Information:
   3 - SELECT "ROW_ID","D_ASTSTAT","C01" FROM "T_WIDE_PROBE" "A" WHERE "D_ASTSTAT"=:1
```

实跑 `WHERE a.d_aststat = TO_DATE(:biz_date,'YYYY-MM-DD')` 命中 5000 行。
（顺带印证反面：不参数化时 `TRUNC(SYSDATE-1)` 在远端变成 `TRUNC(:1-1)` ——
`SYSDATE` 在**本地**求值后当绑定值送过去，这正是 ADR-0004 要消灭的「运行时才求值」。）

### 5.4 dblink 故障的错误特征（M4 要能区分本地 / dblink 问题）

| 故障 | SQLCODE | 错误文本 |
|---|---|---|
| 监听端口不通 | `-12541` | `ORA-12541: TNS:no listener` |
| 主机名解析不了 | `-12154` | `ORA-12154: TNS:could not resolve the connect identifier specified` |
| 远端口令错 | `-1017` | `ORA-01017: invalid username/password; logon denied`<br>`ORA-02063: preceding line from FA_BAD_CRED` |
| 远端表不存在 | `-942` | `ORA-00942: table or view does not exist`<br>`ORA-02063: preceding line from FA` |
| 本地表不存在（对照） | `-942` | `ORA-00942: table or view does not exist` |

**判别规则给 M4：`ORA-02063: preceding line from <LINK_NAME>` 是 dblink 的签名。**
它带着 link 名，且只在远端报错时出现 —— 上表最后两行错误码完全相同，
唯一的区别就是有没有这一行。M4 的错误分类应当扫 `ORA-02063` 并抓出 link 名，
而不是去枚举 `ORA-125xx`（TNS 层错误压根不带 `ORA-02063`，要单独归一类「连不上远端」）。

另有 `v$dblink` 可查当前会话打开着哪些 dblink（`DB_LINK` / `IN_TRANSACTION`），排障时有用。

### 5.5 本条**没有**回答什么

- **台架是 loopback dblink**（指回同一实例），复现的是远程优化器路径的**形状**，不是跨机网络。
  字节数真实（走了本地 listener 的 TNS），**RTT 与吞吐不真实** —— 那是 #5 的事，且 #5 也测不了。
- **生产的 `@FA` 指向的远端库版本未知**。远端 SQL 的生成是本地 CBO 的行为，与远端版本无关，
  但若 `htbr45.t_r_fr_aststat` 在远端其实是**视图或同义词**，下推行为可能不同 ——
  这条要在 #2 拿到客户环境后复验一次。
- 生产查询是否也 join 本地对象未知。若它像台架的纯远程形状一样只碰 `@FA`，
  Oracle 会走 `fully remote statement`（整条语句发过去执行），那是更好的情况，投影问题不存在。

3. **因此 M0 从「两个候选择优」变成「ODPI-C 单点验证」**：#3 不通过就没有备胎，

   `LONG` / `LONG RAW` / `XMLType` 这类遗留类型在 11g 库里出现的概率更高，#2 的类型清单要重点扫。

## 7. 闸门决策（#8）

### 7.1 决策

**通过。继续 Rust，Oracle 驱动定 [`oracle`](https://crates.io/crates/oracle) crate（kubo/rust-oracle，封装 ODPI-C → 官方 OCI）。**

**理由不是"它表现好"，是"判据逐条成立且没有备胎"**：11g 把 `oracle-rs` 挡在门外（§3），
M0 从"两个候选择优"塌缩成"ODPI-C 单点验证"——所以下面每一条都是必要条件，
任何一条不成立都直接回退 Java，不存在换个 Rust 驱动再试的选项。

**ADR-0001「同步阻塞 IO」的两个前提中，客户端侧的两个都被证实**：内存不随行数涨（§4.2），
每行 CPU 常数且远低于预算（§4.7）。**服务端吞吐前提只能说"没有被证伪"**——它在台架上不可测，
已按 [ADR-0005](../adr/0005-local-rig-as-v1-verification-baseline.md) 转 #2 上线前复验。

### 7.3 类型映射表草案（M1 / M3 的直接输入）

**范围声明**：本表覆盖的是 **ADR-0003 的 V1 白名单**，不是"生产表实际出现的全部类型"——
后者是 #2 的产出，客户环境不可达（ADR-0005）。白名单之外的类型**在映射预检阶段报错拒绝**，
所以本表不完整不会变成"搬错"，只会变成"跑不起来"，这是 #11 刻意选的代价。

目标端统一 `utf8mb4` / `utf8mb4_0900_ai_ci`（**NO PAD 排序规则，尾部空格参与比较**——7.4 要用到）。

| Oracle 类型 | 规范形式（ADR-0003） | MySQL 8.0 目标类型 | M1 / M3 | 判据与坑 |
|---|---|---|---|---|
| `NUMBER(p,s)`，`0 ≤ s ≤ p ≤ 38` | 十进制字符串，去整数前导零与小数尾零，`\|x\|<1` 保留 `0.` | `DECIMAL(p,s)` | **M1 生效** | 目标形状必须**逐位相等**：`p' == p && s' == s`，不是"够大就行"；**标度不足是静默舍入，严格模式也不拦**（§7.8 组 2 实测） |
| `NUMBER(p,s)`，`s > p`（纯小数） | 同上 | `DECIMAL(s,s)` | M3 | 目标形状必须精确为 `(s,s)`：`p' == s && s' == s`；Oracle 允许 `NUMBER(4,6)`（值域 `\|x\| < 0.01`），MySQL 无 `s>p` 写法 |
| `NUMBER(p,s)`，`s < 0`（负标度） | 同上（整数，无小数点） | `DECIMAL(p+\|s\|, 0)` | M3 | 目标形状必须精确为 `(p+\|s\|,0)`：`p' == p+\|s\| && s' == 0`；`NUMBER(8,-2)` 存的是百位对齐的整数，最大 10 位 |
| `NUMBER`（无精度声明） | 同上 | **必须人工指定 `DECIMAL(p,s)`** | M3 | 元数据里 `p`/`s` 皆为 `NULL`，推不出目标精度。预检**不猜**，未指定即拒绝，见 7.4 第 2 条 |
| `DATE` | `YYYY-MM-DD HH:MM:SS` | **`DATETIME`**（即 `DATETIME(0)`） | **M1 生效** | **不能用 `TIMESTAMP`**，见 7.4 第 3 条；往返已实测（§7.8 组 3） |
| `TIMESTAMP(n)`，`n ≤ 6` | `YYYY-MM-DD HH:MM:SS.ffffff`（定长 6 位） | `DATETIME(6)` | M3 | `n > 6` 是 ADR-0003 的缺口，见 7.4 第 4 条；**写进 `DATETIME(0)` 会静默舍掉小数秒**（§7.8 组 3） |
| `VARCHAR2(n CHAR)` / `NVARCHAR2(n)` | 原样 UTF-8 | `VARCHAR(n)` | **M1 生效** | `n` 已是字符数，直接对齐 |
| `VARCHAR2(n BYTE)` | 原样 UTF-8 | `VARCHAR(n)` | **M1 生效** | 字节语义：`ZHS16GBK` 下 `n` 字节至多 `n` 个字符，故 `VARCHAR(n)` **必然够**（偏松，不会截断） |
| `CHAR(n)` / `NCHAR(n)` | 原样 UTF-8，**保留尾部空格** | **`VARCHAR(n)`** | M3 | **不能用 `CHAR(n)`**——已实测（§7.8 组 1），见 7.4 第 5 条 |
| `NULL`（任意列上的空值） | 专用标记，与空串区分 | 目标列**必须可空** | **M1 生效** | MySQL 区分 `NULL` 与 `''`；预检不得给目标列自动加 `NOT NULL` |

> **「M1 / M3」列（2026-08-13 加，[#25](https://github.com/liumingjian/db-qbs/issues/25) /
> [ADR-0009](../adr/0009-m1-mapping-precheck-rules.md)）**：标 **M1 生效** 的行是 M1 白名单
> —— `NUMBER(p,s)`（常规形态 `0 ≤ s ≤ p ≤ 38`）/ `VARCHAR2` / `DATE` 三种，加上 NULL 的可空性要求。
> 标 **M3** 的行**映射规则本身没有作废**（都是实测或文档坐实的结论），只是 M1 的预检**一律拒绝**
> 这些类型、不许跑。判定式、拒绝清单与错误信息形态见 ADR-0009。

**V1 明确排除**（#11 / ADR-0003 白名单制，预检报错拒绝，不静默搬运）：

| 排除的类型 | 一句话理由（详见 ADR-0003） |
|---|---|
| `BINARY_FLOAT` / `BINARY_DOUBLE` | 二进制浮点不是十进制精确值，"一律走字符串"对它不构成无损保证（§2.4 实测 309 位十进制展开） |
| `RAW` / `LONG RAW` / `BLOB` | 字节表示法未钉死；`BLOB` 与"行 checksum = 各列拼接"的内存模型冲突 |
| `CLOB` / `NCLOB` / `LONG` | 超长值打破行拼接 checksum 模型；目标端 `TEXT`/`LONGTEXT` 上"比对 `DECIMAL(p,s)` 精度"那套预检规则不适用 |
| 台架未覆盖的其余类型（`XMLType`、`INTERVAL`、`TIMESTAMP WITH TIME ZONE`、对象类型…） | 白名单外一律拒绝。#2 的类型普查若扫出命中，回炉重开 #11 |

### 7.4 本表推出的硬约束（M1 / M3 必须落实）

这一节是做映射表时**新暴露**的，不在前六节的实测范围内——它们不是驱动的问题，
是"规范形式写进 MySQL 之后还是不是同一个值"的问题。**这些是正确性约束，不是优化建议。**

> **2026-08-13 修订（[ADR-0006](../adr/0006-count-only-verification-in-v1.md)）**：
> V1 的校验只比行数，不做行 checksum。本节六条**一条都不能少，且分量更重了**——
> 原先它们是"为了让两端 checksum 可比"的推论，现在它们**就是防线本身**：
> 值被悄悄改掉这件事，V1 没有任何下游机制会发现，全靠这六条在映射预检与建表规则里挡住。
> 第 1 条的两条出路里"目标端重规范化"随 checksum 一起推迟到 V2，**只剩预检强制精度逐位相等**。

1. **`DECIMAL` 的目标形状必须与源类型推导结果逐位相等。** 规范形式 `1.23` 落进
   `DECIMAL(18,6)`，目标端读回来是 `1.230000`——尾零会被补回；反方向上，目标标度不足会
   **静默舍入**。因此 [#19](https://github.com/liumingjian/db-qbs/issues/19) 定案：预检要求目标
   `(p',s')` 精确等于 §7.3 三条 NUMBER 规则推导出的形状。常规形态是 `(p,s)`，纯小数是
   `(s,s)`，负标度是 `(p+|s|,0)`；后两条在 M3 生效。生产 70+ 列一次检查完、一次报告全部，
   具体决策与运维代价见 ADR-0003「`DECIMAL` 精度与标度」增补。
   > **2026-08-13 已实测（[#13](https://github.com/liumingjian/db-qbs/issues/13)，见 §7.8 组 2）。**
   > 补尾零成立；更危险的是**反方向**——标度**更小**时 MySQL **静默舍入**（`0.5` → `1`），
   > `STRICT_ALL_TABLES` 下只给一条 `Note 1265`，语句照样成功。V1 只比行数，这条无人兜底，
   > **预检必须强制目标标度不小于源标度**。
   > 同时实测**推翻了「逐位相等即可让两端 checksum 可比」**：`0.5` 写进 `DECIMAL(38,2)`
   > 读回 `0.50`，逐位相等只保**值**不保**字节**。V2 的目标端 checksum **必须重规范化**，
   > 上面这条出路对 V2 不成立（对 V1 的保值目的仍然成立）。
   > **V1 / V2 边界**：逐位相等只保值、不保读回字节。V1 不做行 checksum，故不做目标端
   > 重规范化；V2 若计算目标端 checksum，仍必须去尾零。重规范化发生在写入之后，不能挽回
   > 较小标度已经造成的舍入，因而不能代替映射门禁。
2. **无精度声明的 `NUMBER` 是预检必须拦下的一类。** 它在生产 11g 库里很常见，
   而元数据给不出 `(p,s)`。V1 要求任务定义显式给出目标 `DECIMAL(p,s)`，
   并**在预检时按源端实际值域采样校核**（`MAX(LENGTH(TO_CHAR(...)))` 一类）；不给就拒绝跑。
   注意 MySQL `DECIMAL` 上限是 `(65,30)`，而 Oracle `NUMBER` 的标度可到 127——
   超出 MySQL 表达能力的必须拒绝，不能截。
3. **`DATE` 的目标类型是 `DATETIME`，不是 `TIMESTAMP`。** MySQL `TIMESTAMP` 有两处会静默改值：
   值域只到 2038（Oracle `DATE` 到 9999），且**按会话时区做转换**——搬运链路里出现时区转换，
   等于在正确性单点上引入一个环境依赖变量。`DATETIME` 无时区、无 2038 限制，原样存取。
4. **ADR-0003 的 `TIMESTAMP` 白名单行没有标度上限——这是缺口。** 规范形式定死 6 位小数，
   而 Oracle `TIMESTAMP` 最高 `(9)`。`TIMESTAMP(9)` 搬过来会**静默丢 3 位**，
   正是白名单制要消灭的那种错法。已开 [#12](https://github.com/liumingjian/db-qbs/issues/12) 单独决策（拒绝 vs 截断），**M1 实现前必须有结论**。
5. **`CHAR(n)` 的目标类型是 `VARCHAR(n)`，不是 `CHAR(n)`。** ADR-0003 要求 `CHAR` 保留尾部空格
   （§2.2 实测驱动确实给出 `"AB        "`），而 **MySQL `CHAR` 在读取时会剥掉尾部空格**
   （非 `PAD_CHAR_TO_FULL_LENGTH` 模式下），目标端 checksum 因此与源端不同。
   `VARCHAR` 原样保留，且 `utf8mb4_0900_ai_ci` 是 NO PAD 排序规则，比较时尾空格也算数。
   > **2026-08-13 已实测坐实（[#13](https://github.com/liumingjian/db-qbs/issues/13)，见 §7.8 组 1、组 4），
   > 本条从建议升为无条件硬约束**：`CHAR(10)` 里 `"AB        "` 读回只剩 `4142`，全空格值读回长度为 0；
   > `CAST(... AS BINARY)` 救不回，`PAD_CHAR_TO_FULL_LENGTH` 不但救不回还会**凭空补出源端没有的空格**
   > （且在 8.0.46 上已 deprecated）。`VARCHAR(10)` 五种输入全部逐字节原样。
   > 另有独立的第二条理由：`CHAR` 上**空串与全空格读回来会碰撞**，值的可区分性都保不住。
   > **生成建表 SQL 时目标端不得出现 `CHAR`。**
   > **2026-08-13 定案（[ADR-0009](../adr/0009-m1-mapping-precheck-rules.md)）**：本条硬约束不变，
   > 但 **M1 的预检直接拒绝源端 `CHAR`/`NCHAR`**——映射是对的，只是不在 M1 白名单里，转 M3。
6. **`utf8mb4` 下的行长上限要预检算一遍。** MySQL 单行上限 65,535 字节，
   `VARCHAR(n)` 在 `utf8mb4` 下按 `4n` 计。生产表 70 列，若字符列宽度普遍较大，
   建表可能直接失败（`Row size too large`）。这是**建表 SQL 生成**（V1 只生成不执行）要提前算的，
   不是跑起来才发现。
   > **2026-08-13 订正（[ADR-0009](../adr/0009-m1-mapping-precheck-rules.md)）**：暂存表
   > `<target>__stg_<run_id>` 是 db-qbs **真的去执行建的**，所以这条在 M1 会真炸。
   > 但**预检不预先算** —— 自己实现的近似式算松了照样炸、算紧了误拒。
   > 改为要求 **`ERROR 1118` 必须被显式识别并翻成人话**。

### 7.8 目标端往返实测（[#13](https://github.com/liumingjian/db-qbs/issues/13)，2026-08-13）

§7.4 第 1、5 条原本是**按 MySQL 文档推出来的**，标着「待实测」。这一节把它们跑掉了。

**问的是什么**：前六节验的是**源端**——驱动能不能把值原样取成规范形式（`FAIL 0`）。
这一节验**目标端**——同一个规范形式字符串写进 MySQL 列、再读回来，还是不是同一串字节。
不需要 Oracle 参与：规范形式是**已知的输入字符串**。

**怎么跑**：`./scripts/run-mysql-roundtrip-probe.sh`（只起 MySQL 8.0.46 / arm64 原生，
`utf8mb4` / `utf8mb4_0900_ai_ci`，`sql_mode=STRICT_ALL_TABLES`）。
判定一律用 `HEX()` **逐字节比对**，不用字符串相等——排序规则与 PAD 语义不参与判定。

> **计量前提**：`mysql` 客户端在容器里默认落到 `latin1`，中文会**双重编码**进库，
> 整组中文结论作废。探针显式 `SET NAMES utf8mb4` 且客户端带 `--default-character-set=utf8mb4`，
> 并把 `@@character_set_connection` 打进输出当证据。第一轮就是这么踩到的。

#### 组 1：`CHAR` vs `VARCHAR` —— 尾空格（§7.4 第 5 条取证）

| 输入（规范形式） | `src` HEX | `CHAR(10)` 读回 HEX | 判定 | `VARCHAR(10)` 读回 HEX | 判定 |
|---|---|---|---|---|---|
| `AB` + 8 空格 | `41422020202020202020` | `4142` | **FAIL** | `41422020202020202020` | PASS |
| `甲乙` + 8 空格 | `E794B2E4B999` + 8×`20` | `E794B2E4B999` | **FAIL** | `E794B2E4B999` + 8×`20` | PASS |
| 10 个空格 | `20202020202020202020` | *（空）* | **FAIL** | `20202020202020202020` | PASS |
| 空串 | *（空）* | *（空）* | PASS | *（空）* | PASS |
| `ABCD`（无尾空格） | `41424344` | `41424344` | PASS | `41424344` | PASS |

**`CHAR` 剥尾空格已实测坐实**，不再是「文档说」：`CHAR_LENGTH` 从 10 掉到 2，
全空格值直接变成 0 长度。**`VARCHAR` 五种输入全部逐字节原样**。

`CAST(char_col AS BINARY)` **救不回来**——读回的值已经丢了填充，转二进制只是把已丢的东西再转一遍。

`PAD_CHAR_TO_FULL_LENGTH` 更**救不回来，还会造假**：它补到定长而不是还原原值——
`ABCD` 变成 `ABCD` + 6 空格（源端没有的空格被凭空加上），空串变成 10 个空格。
它只在「原值恰好占满定长」时碰巧对上。**这个 `sql_mode` 在 MySQL 8.0.46 上已标记 deprecated**，
更不能当作出路。

`utf8mb4_0900_ai_ci` 的 NO PAD 语义同步验了：`'AB' = 'AB        '` 返回 **0**
（对照 `utf8mb4_general_ci` 返回 1），§7.3 的前提成立。

#### 组 2：`DECIMAL` 标度（§7.4 第 1 条取证）

同一个规范形式分别写进四种标度的列，读回值（`CAST(... AS CHAR)`）：

| 规范形式 | `DECIMAL(38,0)` | `DECIMAL(38,2)` | `DECIMAL(38,6)` | `DECIMAL(65,20)` |
|---|---|---|---|---|
| `1.23` | **`1`** ⚠ | `1.23` ✓ | `1.230000` | `1.23000000000000000000` |
| `0.5` | **`1`** ⚠ | `0.50` | `0.500000` | `0.50000000000000000000` |
| `-0.01` | **`0`** ⚠ | `-0.01` ✓ | `-0.010000` | `-0.01000000000000000000` |
| `0` | `0` ✓ | `0.00` | `0.000000` | `0.00000000000000000000` |
| 38 位整数 | 原样 ✓ | **ERROR 1264** | ERROR 1264 | ERROR 1264 |

三条结论，一条比一条重要：

1. **标度更大 → 尾零被补回来**，§7.4 第 1 条的原判成立（`1.23` → `1.230000`）。
   值没变，字节变了。
2. **标度更小 → 静默舍入，`STRICT_ALL_TABLES` 也拦不住。** `0.5` 写进 `DECIMAL(38,0)`
   读回 `1`，`1.23` 读回 `1`，`-0.01` 读回 `0` —— MySQL 只给一条
   **`Note (Code 1265) Data truncated`**，*不是* warning，*不是* error，语句成功提交。
   **这是 V1 最危险的一条**：ADR-0006 之后校验只比行数，行数完全对得上，值已经被改掉，
   没有任何下游机制会发现。（对照：整数位不够是硬 `ERROR 1264 Out of range`，会当场炸——
   **危险的从来是标度，不是精度**。）
3. **「精度逐位相等」保值，但不保字节。** 看 `0.5` 那一行：即使目标列就是源列声明的
   `NUMBER(38,2)` → `DECIMAL(38,2)`，读回来也是 `0.50` 而不是规范形式 `0.5` ——
   因为规范形式**去尾零**，而 `DECIMAL` **总是补齐到声明标度**。
   逐位相等只保证「读回的**数**等于源值」，不保证「读回的**字符串**等于规范形式」；
   只有当某个值的实际标度恰好等于列标度时两者才重合。

第 3 条推翻了 §7.4 第 1 条给 V2 留的那条出路：**V2 的目标端 checksum 不可能靠
「预检强制精度逐位相等」实现**，必须在目标端重新规范化（去尾零）。这条现在只是 V2 的债，
V1 不受影响（V1 不比 checksum）——但不能让它以「已解决」的样子留在文档里。

#### 组 3：`DATETIME` / `DATETIME(6)`

| 规范形式 | `DATETIME` 读回 | 判定 | `DATETIME(6)` 读回 | 判定 |
|---|---|---|---|---|
| `2026-08-13 14:35:09`（DATE） | `2026-08-13 14:35:09` | PASS | `2026-08-13 14:35:09.000000` | FAIL |
| `2026-08-13 14:35:09.120000`（TIMESTAMP） | **`2026-08-13 14:35:09`** ⚠ | FAIL | `2026-08-13 14:35:09.120000` | PASS |

§7.3 的映射**双向都验上了**：`DATE` → `DATETIME(0)`、`TIMESTAMP` → `DATETIME(6)`，
**错配任一方向都不成立**。注意第二行：小数秒写进 `DATETIME(0)` 被**静默舍掉，一条 Note 都没有**——
与组 2 第 2 条同一类失效模式（静默改值），预检必须把标度对齐当硬约束。

#### 组 4：`NULL` 与空串

| 输入 | `IS NULL` | `= ''` | `VARCHAR` 读回 HEX | 长度 | `CHAR(10)` 读回 HEX |
|---|---|---|---|---|---|
| SQL `NULL` | 1 | NULL | NULL | NULL | NULL |
| 空串 | 0 | 1 | *（空）* | 0 | *（空）* |
| 10 个空格 | 0 | 0 | `20202020202020202020` | 10 | *（空）* |
| 字面量 `NULL` 三字母 | 0 | 0 | `4E554C4C` | 4 | `4E554C4C` |

**`VARCHAR` 上四者两两可区分**（3 个非空值 `COUNT(DISTINCT)` = 3，`BINARY` 下同样是 3），
ADR-0003「NULL 专用标记与空串区分」在目标端成立。

**`CHAR` 上不成立**：空串与 10 个空格读回来都是空，**直接碰撞**；
开了 `PAD_CHAR_TO_FULL_LENGTH` 也一样碰撞（两者都变成 10 个空格）。
这是禁用 `CHAR` 的第二条独立理由——不只是尾空格，是**值的可区分性**。

#### 落回映射规则

| # | 原状态 | 实测后 |
|---|---|---|
| §7.4 第 5 条 | 「文档行为，尚未实测」 | **已实测坐实，`CHAR(n)` → `VARCHAR(n)` 升为硬约束**（无条件，不再以「若剥空格被证实」为前提） |
| §7.4 第 1 条 | 「标度更大会补尾零」 | 成立；**新增更危险的一条：标度更小静默舍入，严格模式不拦**；并推翻了「V2 靠逐位相等即可」的说法 |
| §7.3 `DATE` / `TIMESTAMP` 行 | 按文档 | 双向实测通过 |
| ADR-0003 NULL 标记 | 按文档 | 目标端 `VARCHAR` 上可区分，成立 |

**给映射预检的硬约束（M1 / M3 必须落实）**
（M1 的具体判定式见 [ADR-0009](../adr/0009-m1-mapping-precheck-rules.md)）：

- **目标列标度必须 ≥ 源列标度**，且整数位 `p−s` 必须 ≥ 源列 `p−s`。标度不足是静默失效，
  没有任何运行期机制能发现，**只能在预检拦**。默认仍取「逐位相等」（最简单、也最严），
  但要知道它的作用是**保值**，不是保字节。
- **`CHAR(n)` / `NCHAR(n)` 一律映射到 `VARCHAR(n)`**；生成建表 SQL 时目标端**不得出现 `CHAR`**。
- **`DATE` → `DATETIME(0)`，`TIMESTAMP(n)` → `DATETIME(6)`，不得交叉**。
- 目标列**必须可空**，预检不得自动加 `NOT NULL`（否则 NULL 与空串在目标端塌成一个）。

探针与脚本：`docs/spikes/fixtures/local-rig/probes/mysql-roundtrip.sql`、
`scripts/run-mysql-roundtrip-probe.sh`（一次性，不进主干；可重复执行）。

### 7.9 `DATETIME` 值域实测（[#35](https://github.com/liumingjian/db-qbs/issues/35)，2026-08-13）

**问的是什么**：Oracle `DATE` 的域从公元前 4712 起，MySQL `DATETIME` 的**文档域**从
`1000-01-01` 起（文档原话是 *supported range*，更早的值「可能能用但不保证」）。
ADR-0009 的 `DATE` 规则只判 `fsp == 0`，**没判值域**——因为值域是**值**的性质，
预检看列元数据看不见它。域外的值写进去到底是**静默写进去**（那就是 ADR-0006 那张
「行数相等但值被静默改掉」表上的新一行）还是**报错**（那就落在既有的「失败即整 run 失败」形状里）？

**怎么跑**：`./scripts/run-mysql-datetime-domain-probe.sh`（只起 MySQL 8.0.46 / arm64 原生）。
`sql_mode` 取 **ADR-0015 开连接仪式写死的那串 `STRICT_ALL_TABLES`**，不是 MySQL 默认串——
默认串含 `NO_ZERO_DATE` / `NO_ZERO_IN_DATE`，仪式那串没有，两者行为不同。
判定用 `HEX()` 逐字节比对，与 §7.8 同一口径。

#### 组 A：`STRICT_ALL_TABLES` 下写进 `DATETIME`，逐字节读回

| 输入串 | 结果 | `HEX` 逐字节往返 |
|---|---|---|
| `0001-01-01 00:00:00` | 接受，**零 warning** | ✓ 相同 |
| `0999-12-31 23:59:59` | 接受，**零 warning** | ✓ 相同 |
| `1000-01-01 00:00:00` | 接受 | ✓ 相同 |
| `9999-12-31 23:59:59` | 接受 | ✓ 相同 |
| `0000-01-01 00:00:00` | 接受 | ✓ 相同 |
| `0000-00-00 00:00:00` | 接受 | ✓ 相同 |
| `4712-01-01 00:00:00` | 接受 | ✓ 相同 |

**公元 1–999 不是静默改值，是原样存住、原样读回。** 文档说的 `1000-01-01` 下限在
8.0.46 上是保守值，实测全域字节相等。多值 `INSERT`（ADR-0015 §2 的写法）里混一个
`0001-01-01`，三行**全部写入**，不连坐。

`0000-00-00` 被接受是**仪式那串 `sql_mode` 的直接后果**（默认串的 `NO_ZERO_DATE` 会拦）。
对 M1 无影响：源端是 Oracle `DATE`，产不出零日期。

#### 组 B：格式化后仍越界的形态

| 输入串 | `STRICT_ALL_TABLES` | `sql_mode=''` 对照 |
|---|---|---|
| `-4712-01-01 00:00:00`（驱动给了带符号的年） | **`ERROR 1292`** 硬报错，行未写入 | **静默变 `0000-00-00 00:00:00`**，只给 `Warning 1265` |
| `-0001-01-01 00:00:00` | **`ERROR 1292`** | — |
| `10000-01-01 00:00:00`（五位年上溢） | **`ERROR 1292`** | **静默变 `0000-00-00 00:00:00`**，`Warning 1265` |

**「硬报错」这件事是 ADR-0015 那条 `sql_mode` 断言买来的，不是 MySQL 自带的。**
非严格模式下同样的输入静默塌成零日期，且给的是 `Warning 1265`——
与 §7.8 组 2 标度舍入同一个码，也正是 ADR-0010 `INTERNAL_PRECHECK_ESCAPE` 盯的那个哨兵。

#### 结论落回规则

1. **MySQL 侧不存在「公元 1–9999 静默改值」**，ADR-0006 的静默清单上没有这一行，
   `DATE` 值域检查**不进 M1 预检**（裁定见 ADR-0009 §10）。
2. **越界形态在严格模式下当场炸**，落在「失败即整 run 失败」的既有形状里，不需要新防线。
3. **真正的静默口子挪到了源端**：`canon_date` 从驱动时间分量格式化（ADR-0014 §3），
   若驱动对公元前日期把 `year` 给成正数（丢掉纪元），公元前 4712 年会变成上表第 7 行
   那个**完全合法**的 `4712-01-01`，MySQL 欣然接受。这条 MySQL 侧看不见，
   记进 ADR-0006 静默清单且**防线栏是空的**。

探针与脚本：`docs/spikes/fixtures/local-rig/probes/mysql-datetime-domain.sql`、
`scripts/run-mysql-datetime-domain-probe.sh`（一次性，可重复执行）。
