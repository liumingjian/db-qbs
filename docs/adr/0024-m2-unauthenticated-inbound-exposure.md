# ADR-0024: 无鉴权入站面的定价——端口即凭据，兜底是部署形态而非产品

**状态**: 已接受
**日期**: 2026-08-15
**来源**: [#54](https://github.com/liumingjian/db-qbs/issues/54)（地图 [#47](https://github.com/liumingjian/db-qbs/issues/47)）
**关联**: [ADR-0016](0016-task-definition-form.md)（**§8 凭据明文的兜底理由由本 ADR 改写**）、
[ADR-0017](0017-run-log-format-and-contract.md)（**§4 的时效条目由本 ADR 补充**）、
[ADR-0021](0021-m2-log-collection-boundary.md)（**§2 的暴露面表述与 §4 的启动 `warn` 措辞由本 ADR 加码**）、
[ADR-0019](0019-m2-source-process-topology.md)（source 长驻并第一次有入站面）、
[ADR-0023](0023-m2-sql-builder-boundary.md)（§ 构建器只生成 `source_sql` 文本且人可手改——本 ADR §1 的前半句）、
[ADR-0002](0002-staging-table-atomic-swap.md)（切换是目标表上的 `DELETE` + `INSERT`——本 ADR §1 的后半句）

## 背景

地图 [#47](https://github.com/liumingjian/db-qbs/issues/47) 的收窄 2 已定：**M2 不做鉴权**（V1 非目标）。
本 ADR **不重开这个决策**，重开的是它的**兜底前提**。

M1 有两处「明知的缺口靠文件权限兜底」——ADR-0016 §8 凭据明文 0600、ADR-0017 §4 日志含业务值 0600。
两处的兜底之所以成立，是因为 **M1 的 source 没有入站接口**（ADR-0016 §3）：够到那两个文件，
先得够到那台机器。**source 一旦监听入站端口，这个前提就没了。**

其中「业务值」这一侧，[ADR-0021](0021-m2-log-collection-boundary.md) §2 已经定完：
兜底从文件权限换成主机边界与 `listen` 可达范围，并写下「可达范围即暴露范围」。
**本 ADR 补的是另一侧，也是真正没人算过的那笔账：凭据的「权限」，而不是凭据这个字符串。**

## 决策

### 1. 暴露面写成权限等价，不写成「能读到几个值」

> **能连上 `source` 服务端口的人，等价于持有该 `source` 的 Oracle 凭据与目标端写权限——
> 可对源库（含 dblink 指向的更远端库）跑任意 SQL，可清空并重写任意已配置的目标表。**

这句话是可判断的：部署者读完就知道该把这个端口放在哪。它的两个来源都在明处，不是推测：

- **任意 SQL**：ADR-0023 定构建器只生成 `source_sql` **文本**、且**人可手改**。
  一个能建任务的 UI，因此就是一个对 Oracle 的 SQL 控制台。
- **清空目标表**：ADR-0002 的切换路径是目标表上的 `DELETE` + `INSERT`。
  发起一次 run 就能把一张已配置的目标表整段重写。

**「日志含业务值」是这句话的子集，不是并列项。** ADR-0021 §2 那句「任何能连上 source 服务端口的人，
都能在运行历史里读到源库的真实业务值」**仍然成立且不撤销**，但它只覆盖**读**；
本节把它升级成覆盖**能做什么**。凡引用暴露面的地方，以本节这句为准。

### 2. 凭据明文在 M2 没有新增泄露路径，但要写死一条负面条款堵住唯一的口子

配置文件仍是 `--config` 显式指定、仍 0600、端口本身不暴露文件内容。M2 唯一可能新增的泄露路径，
是 UI 顺手长出一个「连接配置管理页」。**堵死：**

> **连接配置在 M2 仍只走 `--config` 文件。`/api/*` 的任何响应不得回传口令，
> UI 不提供连接配置的读写面。**

这条同时约束 [#57](https://github.com/liumingjian/db-qbs/issues/57) 与
[#58](https://github.com/liumingjian/db-qbs/issues/58) 的原型：**没有连接管理页，不是还没画，是不画。**

**注意它与 §1 的关系**：堵住这个口子并不降低 §1 的暴露面——端口已经等价于凭据的权限了。
它防的是**另一件事**：口令本身泄露出去之后可以**脱离本服务**直连数据库、可跨主机横向使用，
那是比「通过本应用作恶」更大的一档。两者不可互相抵消。

### 3. sink 那个 M1 就有的无鉴权入站面，本 ADR 首次成文，但不算 M2 新增缺口

`crates/sink` 有 `listen`、**零鉴权代码**。按 `CONTEXT.md`，离线只约束数据库主机，
两个服务进程**跨互联网**通信——所以 sink 是一个可能暴露在更宽网络上的无鉴权面，
而且它才是真正握着 `DELETE` 的那一端。

**分级认账：**

- **source 侧**：M2 新增缺口（M1 根本没有入站面），进 `CONTEXT.md` 缺口清单。
- **sink 侧**：**M1 既有、本 ADR 首次成文**。不是本图引入的，但「暴露面成文」如果只写 source，
  写出来的就是一句假话。

两者**同一个重开条件**（§6）。**不为 sink 单开票**——它没有独立的决策要做，
需要的只是被写出来。

### 4. 部署前提：默认只绑回环；要多人访问，鉴权由部署者在反向代理上做

ADR-0021 §4 已定 `listen` **必填、允许非回环、非回环时启动打 `warn`**，本 ADR 不改这三条。
本 ADR 加的是**推荐形态**，并写清它的归属：

> **默认形态：`listen` 只绑回环，本机访问。**
> **需要多人访问时，由部署者在前面放反向代理，并在那里做鉴权与 TLS。**
> **产品对此零感知、零校验，且不因其存在而放宽任何内部约束。**

**这不擦收窄 2 的边**：收窄 2 挡的是**产品实现鉴权**，不是**部署者在外层做鉴权**。
区别是可判断的——产品里不会出现任何一行读取 `X-Forwarded-User`、
不会有「已在代理后」这种配置开关、不会有任何代码路径因为「前面有代理」而少做一件事。
**代理存不存在，本进程的行为一字不差。**

因此本条是**部署者责任**，不是产品特性。它写进部署前提文字，**不进部署形态图**——
画进图就会被读成产品的一部分。

### 5. 最小动作三条：不做鉴权 ≠ 做零

收窄 2 挡住的是「做鉴权」，本 ADR 要做的是把已经存在的事实**摆到部署者面前**。三条，都不涉及鉴权：

**(a) UI / API 不回显凭据** —— §2 那条负面条款。

**(b) 启动横幅的 `warn` 措辞加码，两端都打。**
ADR-0021 §4 那条 `warn` 原本只说「运行历史含源库业务数据值」，按 §1 它说轻了。
措辞改为点名**权限等价**：本服务无鉴权、能连上者可对源库跑任意 SQL 并清空重写目标表、
运行历史含源库真实业务值、当前监听地址。

**sink 同样加一条同形状的启动横幅**（无鉴权、能连上者可清空并重写任意暂存表与目标表、当前监听地址）。
这要动 M1 的二进制——**正面认账**：理由与 ADR-0021 §3 破例同款，改的是**日志侧**不是搬运逻辑
（收窄 1 管的是搬运语义，此处没碰），且 ADR-0017 §5 明确允许新增。
**这是「搬运链路零改动」之后对 M1 二进制的第二次日志侧改动**（第一次是 `component`）。

`source` 侧非回环时才打 `warn` 的条件不变；**sink 侧无条件打**——sink 本来就没有「只给本机用」这种形态。

**(c) `CONTEXT.md` 部署形态图补两处最小标注** —— 见 §7。

**否掉「出一份部署检查清单文档」**：它是文档不是规格，本图没有一票依赖它，
写不写不改变任何人的行为——真正会被读到的是 (b) 那条启动横幅。要写可以顺手写，不进本票验收。

**否掉「什么都不加」**：§1 那句话如果只活在 ADR 里，部署者永远读不到它。
缺口的价值全在**被拆掉的那一刻留痕**，这一点与 ADR-0021 §4 同理。

### 6. 重开条件：三条，可判断

本条定价在下列**任一**条件成立时失效，必须真的引入鉴权，
并与 ADR-0016 §8（凭据明文）、ADR-0017 §4 / ADR-0021 §2（业务值）**一并重开**：

1. **出现「`source` 需要被多个不在同一信任域的人访问」的实际部署。**
   ——反向代理那层是把信任域收窄到「代理背后的人」；一旦这些人本身互不信任，代理就兜不住了。
2. **同一进程内出现第二套目标端凭据或第二个租户。**
   ——多租户一来，「可达即全权」立刻不成立：进程内没有任何东西能区分 A 租户与 B 租户的请求。
3. **任何一票要求 `/api/*` 承载凭据流转**（而不仅是写操作）。
   ——那会直接推翻 §2。

### 7. `CONTEXT.md` 的两处订正

**(1) 部署形态图**：`source` 框标 `listen`（入站面，**M2 新增**），`sink` 框标 `listen`（**M1 既有**），
两处各挂一句「无鉴权 → 可达范围即权限暴露范围」。§4 的反向代理写在图**下方**的文字里，不进图。

**(2) 明知的缺口清单：4 条 → 5 条，且第 1 条改写。**

- **新增第 5 条**「无鉴权入站面 = 凭据权限等价暴露」，source 与 sink 并入，分级如 §3。
  **必须独立成条**——M1 没有 source 入站面，这条是**从无到有**，塞进别条会被漏读。
- **第 1 条（凭据明文）改写理由段**。原文的理由是「V1 无鉴权，单给凭据加一层是零收益」；
  在 M2 这句**不再成立**——不是「加一层没收益」，而是**「加了也没用，因为端口本身已经等价于凭据」**。
  理由变了就得改写，否则后人会以为这条一动没动。

## 后果

- **M2 第一次有了一句部署者读得懂、判得动的暴露面**：不是「注意安全」，是「端口 = 凭据 + 目标端写权限」。
- **`CONTEXT.md` 明知的缺口从 4 条变 5 条**，且第 1 条的**理由**（不是结论）被改写。
- **UI 的范围被砍掉一块**：连接配置管理页在 M2 明确不做，#57 / #58 的原型不得长出来。
- **M1 的 sink 二进制要改一行**（启动横幅），这是本图第二次、也是目前最后一次动 M1 二进制。
- **反向代理进了部署前提但没进产品**：产品侧不会出现任何「已在代理后」的开关或代码路径——
  这条是可验证的，不是口头承诺。
- **鉴权的重开条件第一次可判断**：三条，各自是能在部署现场当场判定的事实，
  而不是「等安全要求提高了再说」。

## 时效

- **§1 / §4 / §5 整体在 §6 三条任一成立时重开**，与 ADR-0016 §8、ADR-0017 §4 / ADR-0021 §2 一并处理。
- **§2 的负面条款**在「凭据需要在运行时轮换」这类需求出现时重开——那时口令必然要有一条流转路径。
- **§3 的 sink 分级**：若将来 sink 也长出入站的**管理面**（而不只是接批次），
  它就从「M1 既有」变成新缺口，本节重判。
