# ADR-0036: 任务定义改为结构化规格，SQL 降级为只读派生；v1 不支持手改 SQL

**状态**: 已接受
**日期**: 2026-08-18
**来源**: [#121](https://github.com/liumingjian/db-qbs/issues/121)（地图 [#117](https://github.com/liumingjian/db-qbs/issues/117)）
**关联**: [ADR-0035](0035-upsert-write-model.md)（业务日期降级与运行参数——**本 ADR 是它落到任务定义上的承载点，不重开它的语义**）、
[ADR-0016](0016-task-definition-form.md)（四字段任务定义；**§2 §4 §6 由本 ADR 宣告退役**）、
[ADR-0023](0023-m2-sql-builder-boundary.md)（构建器边界；**§2 §5 §6 §8 §9 由本 ADR 宣告退役**）、
[ADR-0004](0004-parameterized-business-date.md)（相对时间禁令维持，「粘现成 SQL 是主路径」在 v1 不再成立）、
[ADR-0009](0009-m1-mapping-precheck-rules.md)（映射预检**一个字不动**）、
[ADR-0027](0027-target-ddl-generation-and-cross-end-metadata.md)（§7 不缓存，由本 ADR §6 加强）、
[ADR-0034](0034-v1-scope-from-customer-needs.md)（§1 要求收窄与丢弃显式记账）

## 背景

[ADR-0035](0035-upsert-write-model.md) §3 把「业务日期」这个一等概念判废：过滤降级成普通条件
（「字段 + 比较符 + 值」），运行期传参改成每条条件「常量 or 运行时填」二选一，
并发互斥键改成 `task_id + 本次运行参数集`。它明写「本 ADR 只定语义」，控件与 SQL 生成归 #121。

这些语义落到**任务定义**上时，[ADR-0016](0016-task-definition-form.md) §2 的四字段撑不住了：

- `source_sql` 是**一段自由文本**，其中 `:biz_date` 是唯一参数，形状由 SQL 形状预检强收。
  ADR-0035 §3 要求发起时**逐条列出运行参数并取值**——一段自由文本推不出参数清单，
  除非去解析它，而解析任意 Oracle SQL 正是 ADR-0023 §2 否掉方案 C 的那件事。
- `source_date_col` / `target_date_col` 随「业务日期」这个概念一并失去意义
  （ADR-0035 §3 的表已把依赖它们的四处逻辑判掉）。

[ADR-0023](0023-m2-sql-builder-boundary.md) §2 当年判「构建器是一次性脚手架，选择状态不进任务定义，
**SQL 文本是权威**」，其论证支点是 ADR-0004 认定的现实用法：
**真实主路径是粘一条现成 SQL 改一改就用**，构建器只是给不会写的人的辅助入口。
所有者 2026-08-18 的裁定 6 已经推翻这个支点：**构建器选择态进任务定义**。

本 ADR 定的是**任务定义的形态与真相源**，不重开 ADR-0035 的搬运语义。

## 决策

### 1. 结构化规格是唯一真相源；v1 不支持手改 SQL

三种形态（沿用 ADR-0023 §2 的分法）：

| | 形态 | 判决 |
|---|---|---|
| A | 一次性脚手架：向导吐出 SQL 文本，选择态不留存，文本是权威 | **退役**（ADR-0023 §2 原判） |
| **B** | **结构化规格是权威**：任务定义存表 / 列 / 条件 / 排序 / 主键，SQL 由它生成 | **采纳** |
| C | 双向同步：手改后反解析回结构化模型 | 否（要写 Oracle SQL 解析器，ADR-0023 §2 的理由一字不改） |

**SQL 在界面上只读展示，v1 不提供任何编辑入口。**

**这是一次明确的能力收窄，按 [ADR-0034](0034-v1-scope-from-customer-needs.md) §1 的规矩在此显式记账**：
收掉的是 ADR-0023 §2 与 ADR-0004 共同认定的「粘一条现成 SQL 改一改就用」这条主路径。
**代价明写**：生产上那条 70+ 列、带 dblink 的现成查询在 v1 **不能直接粘进来跑**，
只能用构建器重建；构建器表达不了的查询（多表 join、子查询、表达式列）在 v1 **没有出路**。见「时效」。

**被否掉的中间路线**：存一份 SQL 文本但设为只读（即「只读的自由文本」）。
它保留了「任务定义里躺着一份不可再生的 SQL」这个形态，于是参数清单照样推不出来、
条件形状照样不可知——**手改的全部代价都留下了，却一点自由都没给**。

采纳 B 的三条理由：

1. ADR-0035 §3 的「运行时填」要求发起时能逐条列出参数并取值，**只有结构声明的参数清单做得到**。
2. 只要允许手改，结构与文本**必然漂移**，且「谁权威」要在每一处判定上重问一遍。
3. 所有者裁定 6 已把构建器选择态放进任务定义，B 是它的直接后果，不是新增判断。

**推论**：裁定 6 的后半句「手改 SQL 后向导态标失效」在 v1 **前提不成立**——根本不存在手改这个动作。
**这是前提消失，不是裁定被推翻**；将来恢复手改时它自动重新生效。

### 2. SQL 不进任务定义、现算；每次运行的历史里钉一份当次执行的 SQL

- **任务定义只存规格**。展示与发起时由规格现生成 SQL。
- **每条运行记录存一份当次实际执行的 SQL 文本快照。**

两份 SQL 性质根本不同：任务定义里的那份回答「**现在会生成什么**」，
历史里的那份回答「**当时执行了什么**」。后者是审计事实，规格改了它也不能跟着变。

**否掉「任务定义里存一份、规格改动时重算覆盖」**：那正是本 ADR 刚消灭的漂移面——
生成器逻辑一升级，存下来的那份就与规格对不上，而**没有任何手段能检测到**。

历史里那份快照存**未绑定的语句文本**，参数值不内联进去：值本来就由「运行参数」列
（ADR-0035 §3）负责展示，内联会让同一份事实在两处重复，还平白引入一层拼串转义面。

### 3. 不给「以后恢复手改」预留任何结构位

不加 `sql_provenance` 之类的标记字段，不留只读的第二分支。

§4 已判旧任务定义直接丢弃换 schema，说明此刻改数据结构的代价被接受为低；
一个只有单一取值的字段**既挡不住**将来真做手改时数据形状还得再变一次，
**又会让**读代码的人以为系统里存在两种任务形态。保留分支代码则要为一条走不到的路径养测试。

### 4. 已有的任务定义直接丢弃，换新数据结构

不做就地翻译（要写 Oracle SQL 解析器做反解析，与 ADR-0023 §2 否掉 C 是同一条理由），
不做 legacy 只读并存（会把「两种任务形态」这个偶然复杂度永久焊进发起链路）。

前提是第一版尚无真实用户数据。按 [ADR-0034](0034-v1-scope-from-customer-needs.md) §1 的规矩，
**丢弃这件事在此显式记账，不许在实现票里悄悄生效**。

#### 2026-08-19 增补（实现期，[#121](https://github.com/liumingjian/db-qbs/issues/121)）

**运行历史表同样整表 DROP，与任务定义同一条理由。** 本节原文只写了任务定义，
实现时发现历史绕不过去：历史行上原本钉的是 `biz_date`，新模型里那一格是**运行参数集**
（参数名由用户在条件里自己定）。把旧的 `biz_date` 翻成某个参数名的运行参数是**编事实**——
而历史数据的全部价值就在于它是事实。同一份「尚无真实用户数据」的前提在这里也成立，
所以选择丢弃而不是伪造。落点：`crates/source/src/run_history.rs` 的 `drop_legacy_history_table`。

### 5. SQL 形状预检整段取消

`crates/source/src/lib.rs:186` 那六条规则（出处见 ADR-0016 §4 表、ADR-0023 §5 表）的去向：

| # | 规则 | 去向 |
|---|---|---|
| 1 | `:biz_date` 恰好两次、构成半开区间 | **随 ADR-0035 §3 退役**（业务日期不再是一等概念） |
| 2 | WHERE 中不存在其他谓词 | **随之退役**——WHERE 现在正是装用户条件的地方 |
| 3 | `upper(target_date_col) == upper(source_date_col)` | **随这两个字段一并退役** |
| 4 | 无相对时间函数（`SYSDATE` 等） | 生成器**结构性不产出**，取消 |
| 5 | 每列必须显式命名 | 生成器**结构性保证**（只选真列、一律带 `AS`），取消 |
| 6 | 表达式列 / 精度不确定的列一律拒绝 | **不由生成器保证，仍然取消**——见下 |

第 6 条是六条里**唯一还有真实判定力**的一条：精度确定性取决于源表实际怎么建的，
同一份规格换一张源表就可能不成立。取消它意味着**精度不确定的列在发起前不再被拦截**。
这与所有者「精度判定降级」的既有裁定一致，故按裁定执行；
**后果明写在此不留悬案**：这类问题只会在真跑时暴露，或者静默丢精度。

**注意判定并未全部消失**：[ADR-0009](0009-m1-mapping-precheck-rules.md) 的**映射预检**不受本 ADR 影响——
它在 sink 侧、走游标 describe 而非数据字典，白名单外类型、精度不足的 `DECIMAL`、
无精度声明的 `NUMBER` 仍由它**硬拒**。本节取消的只是 source 本地那一段**SQL 文本形状**门禁。
[ADR-0010](0010-http-protocol-contract.md) §3.1 经 ADR-0016 §4 收窄的措辞
（「**逐列类型判定** source 一个都不做」）随之回到字面成立。

**ADR-0023 §8「每次发起无条件重跑形状预检」整条退役**——它的存在理由原话是
「SQL 可手改，发起时那份文本与是否由构建器生成结构性不可区分」，这个前提没了。

### 6. 派生面定形：恰好三样

从任务定义算出来的东西**只有三样**：

1. **源端 SQL**；
2. **运行参数清单与取值**；
3. **报文里来自任务定义的那些字段**。

**明确不在派生面里的**：目标表 DDL 生成（`generate_target_ddl`，
`crates/source/src/target_ddl.rs:43`）与 `OpenRunRequest`。两者吃的都是
**游标 describe 回来的源列**（类型 / 精度 / fsp），任务定义里根本没有这些信息——
它们属于「取列」那条链，不是任务定义的派生。
把它们吸进来等于把**瞬态**的取列结果粘进**持久**的任务定义，与
[ADR-0027](0027-target-ddl-generation-and-cross-end-metadata.md) §7「元数据不缓存」正面冲突。

（定稿过程中一度还有第四样「形状校验的输入」，随 §5 一起消失。）

### 7. 互斥键里「运行参数集」的规范形式

ADR-0035 §3 把互斥键定为 `task_id + 本次运行参数集`，但没定这个集合怎么算。定为
**参数名 → 值的规范化 map**（按参数名排序，值原样取字符串）。

- **否掉「渲染后的 SQL 文本哈希」**：ADR-0035 §3 把历史表改成了「运行参数」列，
  要展示的就是这个 map，SQL 哈希展示不出来；且生成器改一个空格就会被判成「不同的一次运行」，
  凭空放行一次本该被挡的重复运行。
- **否掉「参数值按声明顺序串接」**：增删一个参数会让此前所有历史键对不上。

无参数时退化成「同任务不许并跑」，与 ADR-0035 §3 表里那句一致。

## 后果

- **[ADR-0016](0016-task-definition-form.md) §2（四字段清单）与 §6（未知字段严拒对那四个字段的表述）退役**；
  §4 的 SQL 形状预检随本 ADR §5 退役。§1 的 TOML 形式早已由 ADR-0019 的 M2 形态取代，本 ADR 不再重复处置。
- **[ADR-0023](0023-m2-sql-builder-boundary.md) §2 退役**（一次性脚手架 / 选择态不留存 / SQL 文本权威）；
  §5 §6 §8 随形状预检退役；§9 的输入输出定形作废（输出不再是那四个字段）。
  §1「选条件坐实收窄」早已被 ADR-0035 §3 推翻。
  **§3（dblink）、§4（只亮不判）、§7（目标端两字段人手填）、§10（不做数据预览）一个字不动。**
- **[ADR-0004](0004-parameterized-business-date.md) 的相对时间禁令维持**（ADR-0035 §3 已重申），
  但它认定的「主路径是粘现成 SQL」在 v1 不再成立——那正是 §1 记的这次收窄。
- **[ADR-0009](0009-m1-mapping-precheck-rules.md) 的映射预检、判定式、不缓存一个字不动。**
- **[ADR-0027](0027-target-ddl-generation-and-cross-end-metadata.md) §7 的不缓存被加强**：
  §6 明确 describe 结果不得进任务定义。
- **所有者裁定 6 的后半句是前提消失，不是被推翻**（§1 推论）。这一句必须留着，
  否则下次读裁定的人会以为它被反向重开了。
- **`CONTEXT.md` 三处要改**：术语表「任务定义」、术语表「SQL 形状预检」、
  V1 范围里 ADR-0023 §1 改写的那句「选表 / 选字段 / 指定日期列」。
- **[#121](https://github.com/liumingjian/db-qbs/issues/121) 正文三条陈旧论断作废**
  （倾向自由文本 WHERE 片段 / 业务日期谓词强制保留 / 与清除条件的等价性），收口时订正。
- 实现与验收台架归 #121 / [#122](https://github.com/liumingjian/db-qbs/issues/122)。
  **在跑之前，任何报告不许写「通过」**（ADR-0035 §5 原话）。

## 时效

1. **手改 SQL —— v1 明确不做。** 出现「构建器表达不了、但业务上必须搬」的真实查询时重估；
   届时裁定 6 的后半句自动重新生效，且必须一并回答本 ADR §2 遗留的问题：
   手改之后，历史里那份 SQL 快照与规格是什么关系。
2. **精度确定性判定 —— §5 取消它是在执行既有的降级裁定。** 出现真实的静默精度丢失时重估，
   正解大概率是把它挪进映射预检（那一端本来就握着 describe 的精度信息），而不是把形状预检整段搬回来。
3. **构建器表达力** —— 多表 join / 子查询 / 表达式列在 v1 无出路，
   与 ADR-0035 时效 2（过滤条件表达力）同源，一并重估。
