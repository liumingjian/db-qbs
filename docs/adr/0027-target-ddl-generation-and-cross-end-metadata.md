## 背景

`CONTEXT.md` V1 范围写着「不自动建目标表，**只生成建表 SQL 给人执行**」。
这句话在 M1 无处落地——M1 没有 UI，人是拿着预检报错自己改表的。
M2 有了 UI，它必须有一个具体的落点。

ADR-0023 §7 把一条路明确推给了本票：新开一条 `source → sink` 的**目标端元数据查询接口**，
让构建器也能列目标表、目标列、甚至直接生成建表 SQL。它要给 ADR-0010 的接口闭集
加一类**不属于任何 run 的元数据查询**，是真正的协议扩面。

本 ADR 判掉这条路，并把建表 SQL 的整条回路定形。

### 三条改变问法的事实

**事实 1——生成目标表建表 SQL 结构性地不需要目标端元数据。**
ADR-0009 §2 的三条判定式**可逆且唯一确定**：

| 判定式（预检方向） | 正向推导（生成方向） |
|---|---|
| `NUMBER(p,s) → DECIMAL(p',s')`，逐位相等 `p'==p && s'==s` | 唯一解 `DECIMAL(p,s)` |
| `VARCHAR2(n) → VARCHAR(n')`，下界 `n' >= n` | 最小解 `VARCHAR(n)` |
| `DATE → DATETIME(fsp)`，严格 `fsp == 0` | 唯一解 `DATETIME(0)` |

加上 ADR-0009 §5「目标表已有 `NOT NULL` 列一律拒」，生成的表必须**全列可空**。
**输入只有源列元数据，零目标端输入**——因为表还不存在，那边没有任何东西可查。
ADR-0010 §3.1「逐列类型判定集中在 sink」的论证前提是「**需要目标端元数据做逐列比对**」，
在这件事上不成立：这不是比对，是单向推导。

**事实 2——ADR-0002 增补把两个 DDL 生成器当成了同一个（本 ADR §6 订正）。**

**事实 3——建表 SQL 若从数据字典生成，它就是非权威的。**
ADR-0009 §1 定死源列权威来源是**游标 describe** 不是数据字典；ADR-0023 §4 让构建器读字典但**只亮不判**，
理由是视图 / dblink / 同义词之下两者可以不一致。按字典生成的 `CREATE TABLE`，
人老老实实建完，预检拿 describe 一比照样可能不过——**这正是「构建器放行了、预检却拒」，
而且这次人已经付出了建表的真实代价**。

## 决策

### 1. 建表 SQL 由 `source` 生成，不由 `sink` 生成

事实 1 说 `source` 手上的信息已经够了。

**反方论据只有一条，但它不轻**：判定规则会有两份实现——`source` 侧的正向生成器与
`sink` 侧的逐列比对器，两边漂移了就是「生成的表建出来预检不过」，
而这恰恰是最难排的一类错（人已经付了建表的代价，产品却说不行）。

**仍然选 source，两条理由**：

1. 漂移的解法不是把生成搬到 sink——那要付一条全新的协议扩面（见 §3）——
   而是**把这三行判定式当成一条规格，用 [ADR-0014](0014-canonical-form-boundary-test-suite.md)
   那套边界测试套件在两端各钉一遍**。规则只有三行且无边界推理，这件事是做得到的。
2. 搬到 sink **消不掉**两份实现：sink 那边仍然是「比对」与「生成」两段代码。
   换来的只是两份实现在同一个进程里，而它们仍会漂移。

### 2. 源列元数据取 describe，为此新增一个 `source` 本地的「取列」动作

事实 3 判死了「用数据字典生成」。但 describe 现在只发生在**发起时**
（ADR-0010 §3.1 订正定的顺序：解析形状 → describe → `POST /runs`），
而人需要建表 SQL 的时机是**建任务时、发起之前**——那时没有任何东西跑过 describe。

于是 UI 新增一个 **`source` 本地的「取列」动作**：跑形状预检 + describe，
只拿结果集元数据回来。**它不碰 `sink`、不产生 `run_id`、不建任何东西、不写任何存储。**

**它与 ADR-0010 §3 否掉的「拆成 `precheck` + `open` 两个动作」不是同一件事。**
那条否掉的是**跨 HTTP 的**中间态，理由是会产生「验过了但还没开」而 M1 没有状态存储去持有它。
取列全程在 `source` 进程本地，不产生任何 `sink` 侧状态，失败就是没结果——
**没有中间态可持有，所以那条论证够不着它。协议一字不动。**

**代价认下**：这是 `source` 侧多一个动作，它会**真的连 Oracle 跑一次 prepare + describe**
（describe-only 不可用时按 ADR-0009 §1 的退路 execute 后不 fetch 即关游标）。

**失败面走已有路径，不新增任何报告形态**：形状预检不过 → 就是 ADR-0023 §8 那份
`source` 本地成文的形状预检报告；连不上 Oracle / describe 失败 → 与发起路径上同一类错误同样呈现。

### 3. 不给 ADR-0010 的接口闭集加「不属于任何 run 的元数据查询」

§1 与 §2 定完之后，**建表 SQL 这条驱动力消失了**。这条接口剩下的驱动力只有一条：
让 `target_table` 从填空变成下拉、让人看见目标列。

而这条驱动力已被两处判词围死：

- **ADR-0023 §4「只亮不判」**——非权威元数据不得做门禁；
- **ADR-0009 增补 §3** 明写：「即便 #57 把通道开出来，也不构成『构建器可以拿它做门禁』的授权」。

也就是说，**这条接口开出来，能买到的只有一个下拉框，买不到任何一处拦截**。
而付的账是协议扩面这笔最贵的：要判它在 `/v1/` 下的资源位置、要不要新错误码、
`sink` 要不要为它维护一份不属于任何 run 的连接语义与生命周期。

地图主方向那句的对偶——「不做这件事，闭环能不能成？」——答案是**能**。
**这条路的归宿是 Out of scope，不是 Decisions-so-far**：它越过了本图的终点，
不是路上的一步。ADR-0010 的 12 码闭集与五个端点**一字不动**。

**推论**：ADR-0023 §7 的「`target_table` 人手填、`target_date_col` 预填源端日期列名、可改」
**原样成立，不升级为选择**。#57 第 4 问就此消解——没有目标端列表可选。

### 4. 建表 SQL 的出口只有一个，且常亮

**单出口**：建任务页「取列」之后给，**常亮**，不管目标表存不存在都拿得到。
**预检失败页不重复生成**，只放一个「回到取列拿建表 SQL」的入口。

否掉「预检失败报告里再给一份」，理由是**预检失败的常见形态不是「表不存在」，
是某几列类型不对**。那时把一份全量 `CREATE TABLE` 摆在报告里是**误导**——
人执行它会撞 `ERROR 1050 Table already exists`。要避开就得在 UI 里判
「是不是全部列都缺失 → 才是表不存在」，那是新增一处判定逻辑，
而且它判的是 `sink` 透传回来的报告文本。

**常亮的态度直接继承 [ADR-0026](0026-m2-in-flight-observation.md)**：
取消按钮常亮、点了当场拒，因为**禁用状态本身会说谎**。这里同理——
宁可常亮，也不要一个「看起来知道该不该给你」的按钮。

表名用人已填的 `target_table`；**没填就在 SQL 里留显眼占位符 `<目标表名>`**，不拦着人先看 SQL。

### 5. 生成的 DDL 的内容

```sql
-- db-qbs 生成的目标表建表 SQL，请自行执行；产品不会替你建表。
-- 下面这条索引不是可选项：切换事务的 DELETE 会锁住目标表当日范围，
-- 业务日期列无索引时锁全表（见 ADR-0022 / SWAP_TARGET_BUSY）。
CREATE TABLE `T_POSITION` (
  `N_VA_PRICE` DECIMAL(18,4) NULL,
  `C_NAME`     VARCHAR(50)   NULL,
  `D_BIZ`      DATETIME(0)   NULL,
  KEY `idx_d_biz` (`D_BIZ`)
) DEFAULT CHARSET=utf8mb4;
```

四条规则：

- **全列可空**（`NOT NULL` 被 ADR-0009 §5 全拒，生成带 `NOT NULL` 的表等于生成一张跑不起来的表）。
- **列序取 describe 序**。这一点没有语义后果：ADR-0010 §3.3 订正后切换与写入都用**显式列名**，
  列序已被抽空。取 describe 序只是因为它是手上唯一的序。
- **带一条 `target_date_col` 的普通索引 + 注释写明理由**。这不是替人做索引策略——人的表人自己改；
  但**默认给出会锁全表的 DDL、再靠一个错误码去解释后果，是明知故犯**。
  **不传染暂存表**：ADR-0009 §7 的「全列可空、无索引、无默认值、无主键」是暂存表自己的规则。
- **显式 `DEFAULT CHARSET=utf8mb4`**。不写就吃库默认，库默认若不是 `utf8mb4`
  就直接撞 ADR-0009 §9 的另一条人话 `ERROR 1366`。
  这**不碰**地图 Out of scope 里挂在 [#2](https://github.com/liumingjian/db-qbs/issues/2) 的
  `ZHS16GBK` 中文往返复验——那是「源端读出来对不对」，这里是「目标端存得下什么」，两件事。

**不生成 `ALTER TABLE`。** 「表已存在但某列类型不对」是预检失败的主路径，`ALTER` 看似正好补上它，
但**改一个已有数据的列的类型，安全与否取决于目标表里现有的数据**——
`DECIMAL(38,0)` 改成 `DECIMAL(18,4)` 会不会截断，只有读了那些数据才知道。
产品要给 `ALTER` 就得对这件事表态，而它既没有权限也没有立场。
ADR-0009 §8 的报告已把「`<列名> | 源端 <类型(精度)> | 目标端 <类型(精度)> | 违反：<规则>`」
逐列摆出来了——**写那条 `ALTER` 是 DBA 三十秒的事，判它安不安全才是难的那半，而产品判不了**。

### 6. 回路定形：「重新发起」，不是「重试」

人拿到建表 SQL → 去 MySQL 客户端自己执行 → 回到 UI → **「重新发起」**。

这不是措辞问题。M1 的形态是失败即整 run 失败，ADR-0010 §5 明写重跑 = **一条新 `run_id` 从头**；
ADR-0023 §8 定形状预检每次发起无条件重跑；ADR-0020 定受理即写一条新历史。
于是回路**零新机制**：新 `run_record_id`、新 `run_id`、形状预检重跑、映射预检重跑。

**不存在「重试上一个 run」这个动作**——一个「重试」按钮会让人以为在续上一次，
而 M1 的语义里没有那个东西（续传归 [ADR-0018](0018-delayed-batch-retry-model.md) / M4）。
失败的那条历史记录原样留着，**它是这次改表的凭据**。

### 7. 取列结果是纯瞬态

只活在前端页面状态里，**不进任务定义、不进 SQLite、刷新即丢**。

ADR-0023 §2 已定构建器的选择状态不进任务定义（ADR-0016 四字段格式一字不变），
取列结果是比它更下游的派生物，更没有理由落盘。要建表 SQL 就再点一次，
代价是一次 prepare + describe、不 fetch。

落盘反而要回答「它过期没有」，而**判断源表结构变没变，只有再 describe 一次这一条路**——
缓存买不到任何东西。

### 8. `ERROR 1118 Row size too large` 的承载点：只贴静态提示

ADR-0009 §9 要求 `1118` 翻成人话、不得裸抛，并明写触发点是
「**生成建表 SQL 的人拿去建目标表时**」。

**#57 开票时的假设是错的**：它写「那条人话此前没有 UI 承载点」，暗示 M2 有了 UI 就该有。
**有了 UI 也没有**——执行动作不在产品里，产品从头到尾看不见那个错误。

**取的是**：UI 在展示建表 SQL 时贴一段**静态提示**——
「若执行时报 `ERROR 1118`，含义是列宽合计超出 MySQL 单行上限，需缩窄字符列或拆表」。
零判定、零元数据、零协议，就是把 ADR-0009 §9 已经写好的那句人话搬到人看得见的地方。

**不取**「承认它结构性无承载点、订正掉 §9」——太便宜，白扔掉一句已成文的措辞。
**不取**「让产品替人执行建表 SQL」——直接撞 V1 非目标「自动建目标表」，
且已在地图 Out of scope。

**明确不做的一件事**：**不预先计算行长上限**。ADR-0009 §9 已经论证过——
真实规则要算行格式、off-page 存储、指针开销，自己算出来的近似式算松了照样炸、
算紧了误拒，等于重新实现 MySQL 的行长规则。本 ADR 一个字都不放宽这条。

## 对既有 ADR 的订正

### 订正 ADR-0002 增补：「复用 DDL 生成器」这句话不成立

ADR-0002 增补「结构从哪来」一节写着：

> DDL 生成器是 V1 **本来就要有**的（「只生成建表 SQL 给人执行」），复用它不增加代码。

**这句话把两个不同的生成器当成了同一个**：

| | 暂存表 DDL | 目标表建表 SQL |
|---|---|---|
| 输入 | 目标表 `information_schema` | 源列 **describe** 元数据 |
| 运算 | **复制**（同名、同序、同类型，去掉约束） | **正向推导**（ADR-0009 §2 判定式反用） |
| 位置 | `sink` | **`source`**（本 ADR §1） |
| 何时 | `POST /runs` 内，预检全过之后 | 建任务页「取列」之后，与任何 run 无关 |

两者共享的只有「拼 `CREATE TABLE` 字符串」那点皮。**复用不成立。**

**但 ADR-0002 增补那一节的结论完全不受影响**：暂存表 DDL 仍由映射预检的结果生成、
逐列照目标表类型写、全列可空无索引无默认值无主键、不用 `CREATE TABLE ... LIKE`。
被抽掉的只是三条支撑理由中的一条（「复用不增加代码」）；
另两条——§3 已要求两边列名集合完全相等所以「目标表有映射之外的列」不存在、
DDL 与预检读的是同一份元数据——**原样成立，足以支撑该结论**。

### 订正 ADR-0010 §3.1 的作用域（第二次收窄）

§3.1 的标题「source 一个判断都不做」已在 2026-08-13 被 ADR-0016 §4 收窄为
「**逐列类型判定**一个都不做」。本 ADR 补一条**正交的**边界：

> **§3.1 约束的是「判定」，不是「推导」。**
> `source` 从源列元数据**正向推导**目标表 DDL 不落在 §3.1 的作用域内——
> 它不比对、不接受、不拒绝任何列，也不需要目标端的任何输入。
> §3.1 的全部论证（「一次报全部列」不能降级成「逐端」）针对的是**需要目标端元数据的逐列比对**；
> 推导没有目标端这一边，那段论证够不着它。
>
> **判定权威仍全部在 `sink`，一个字不改。**
> 生成的建表 SQL **不构成任何形式的放行**：人按它建完表，
> 映射预检照样在 `POST /runs` 里从头跑一遍，照样可能拒。
> 这与 ADR-0023 §4「只亮不判」、ADR-0009 增补 §3「拦截层只有预检一处」是同一条线——
> **本 ADR 不增加任何拦截层。**

### ADR-0009 §9 加一条承载点说明

§9 那条 `ERROR 1118` 的人话，其承载点由本 ADR §8 定形为**建表 SQL 旁的静态提示**，
不是运行时捕获——产品结构性地看不见那个错误。§9 的措辞与「不预先计算行长上限」一字不改。

## 后果

**买到的**：

- `CONTEXT.md` V1 范围那句「只生成建表 SQL 给人执行」**第一次有了具体落点**。
- 协议**一字不动**：五个端点、12 码闭集、`POST /runs` 的报文形状全部原样。
  本图至此对 ADR-0010 的改动仍只有 ADR-0022 那一个 `SWAP_TARGET_BUSY`。
- 生成的 DDL 默认避开 `SWAP_TARGET_BUSY` 的成因（§5 那条索引），
  也默认避开 `ERROR 1366` 的成因（`utf8mb4`）。

**付的账（三笔，都记明）**：

1. **判定规则两份实现**（`source` 正向生成器 / `sink` 逐列比对器）。
   兜底是 ADR-0014 的边界测试套件在两端各钉一遍，**不是靠人记得同步改**。
   规则只有三行且无边界推理，这件事做得到——但它**是一笔真账，不是零成本**。
2. **多一次 Oracle 往返**：每点一次「取列」就是一次 prepare + describe。
   不缓存（§7），所以点几次就是几次。
3. **目标端在建任务阶段仍然完全不可见**：人填错 `target_table` 要到发起时才知道。
   这是 §3 的直接代价，明码标价。

**没买到、也不打算买的**：目标表下拉、目标列可见、`ALTER` 建议、行长预算、产品替人建表。

## 重开条件

§3 那条跨端元数据接口，**只在出现「不是为了拦截」的驱动力时重开**——
例如某一票需要 `source` 侧对目标端做**运维性**的操作（而不是给构建器提前判）。
「想要一个下拉框」不构成重开条件；「想提前拦住列集不等」更不构成——
那条已被 ADR-0009 增补 §3 单独封死，且本 ADR 不解封。
重开时须重画本图终点、另起一图。

## 2026-08-16 增补：M3 九行形态下的生成侧与取列面

**来源**：[#101](https://github.com/liumingjian/db-qbs/issues/101)，地图 [#94](https://github.com/liumingjian/db-qbs/issues/94)。
**关联**：[ADR-0030](0030-m3-type-whitelist.md)（九行形态与推导形状）、
[ADR-0031](0031-number-predicate-lower-bound.md) §6（判定侧改下界式，生成侧不动）、
[ADR-0010](0010-http-protocol-contract.md) 2026-08-16 增补（`fsp` 字段）。

**本增补一条既有决策都没推翻。** source 侧生成、单出口常亮、不生成 `ALTER`、
不开跨端元数据接口、取列瞬态不缓存、`ERROR 1118` 只贴静态提示——全部原样成立。
变的只是**作用域从三行扩到九行**，以及三处措辞被 M3 证伪。
这是地图收窄 1「只在新类型要求时做增量扩、不重画」的字面兑现，故落增补而非新 ADR。

### A1. 「事实 1」的措辞订正：需要的是**函数性**，不是**可逆性**

原文写「ADR-0009 §2 的三条判定式**可逆且唯一确定**」，并以此支撑正向推导。
**这个词借强了。** 正向推导只需要「每个源形态唯一确定一个目标形状」——即映射是个**函数**；
它**不需要单射**。M3 之后字面上的可逆性确实更紧张（`DECIMAL(6,6)` 既可能来自
ADR-0030 形态 1 也可能来自形态 2），但那**丝毫不影响生成**：生成的输入永远是源形态，
不存在「从目标形状反推源类型」这个动作。

**可逆性是判定侧才关心的性质**——ADR-0030 §3 的 `DATE` / `TIMESTAMP` 之争正是为它打的，
结论是两边都维持严格、一个目标形状只对一种源类型。那是 ADR-0030 的事，不是本 ADR 的前提。

订正之后，**§1 的整段论证不再随白名单的行数变化**：白名单再扩多少行，
只要每行的推导形状唯一确定，「零目标端输入」就成立。这句订正的全部价值在这里。

### A2. 推导表从三行扩到九行

§「事实 1」那张两列表按 ADR-0030 §1 扩写。**推导形状一律取 ADR-0030 §1 第三列，本增补不新造**：

| 源形态 | 生成的目标列型 |
|---|---|
| `NUMBER(p,s)`，`0 ≤ s ≤ p` | `DECIMAL(p,s)` |
| `NUMBER(p,s)`，`s > p`（纯小数） | `DECIMAL(s,s)` |
| `NUMBER(p,s)`，`s < 0`（负标度） | `DECIMAL(p+\|s\|,0)` |
| 裸 `NUMBER` / 数值表达式列 | 见 A3——**占位符或任务定义配置**，describe 给不出 |
| `VARCHAR2(n)`（`CHAR` / `BYTE` 两种语义） | `VARCHAR(n)` |
| `NVARCHAR2(n)` | `VARCHAR(n)` |
| `CHAR(n)` / `NCHAR(n)` | **`VARCHAR(n)`**——不得照抄源类型名，ADR-0030 §5 的无条件硬约束 |
| `DATE` | `DATETIME(0)` |
| `TIMESTAMP(n)`，`0 ≤ n ≤ 6` | **`DATETIME(6)`**，不随 `n` 走（ADR-0030 §3） |

`VARCHAR2(n BYTE)` 的字节语义按 spike §7.3 已定的「偏松、必然够」原样处理，
`CHAR(n)` / `NCHAR(n)` 同构，**不是新决策**。

**判定侧改用下界式不影响本表**：ADR-0031 §6 已定「判定侧接受一族形状、
生成侧吐这族里的规范代表」，本增补一个字都不为它改。

### A3. 裸 `NUMBER` / 数值表达式列：读任务定义配置，回落占位符，**绝不整份失败**

ADR-0030 §4 放行了这两种形态，但它们的形状来自任务定义里那个可选 `(p,s)` 配置
（ADR-0030 §4.2），describe 结构性地给不出。生成器：

1. **任务定义配了 `(p,s)`** → 吐 `DECIMAL(p,s)`，与其余列无区别；
2. **没配** → 该列吐占位符 `DECIMAL(<p>,<s>)`，并在文件头注释点名是哪几列、
   要去任务定义的哪个字段配。

**不取「整份返回错误」。** §4 已经定死了这件事的态度：表名没填都只留 `<目标表名>` 占位符、
不拦着人先看 SQL；同一份 SQL 里因为一列没配精度就一个字都不给，态度不一致。
实际后果也重——含一列数值表达式的 70 列表会**整份拿不到**，人反而没法先建表再回头配。

### A4. 白名单外的列：**整份不给**，只报「这几列不支持」

拒绝清单（ADR-0030 §2：`BINARY_FLOAT` / `BINARY_DOUBLE`、LOB 族、`TIMESTAMP(n>6)`、
字符表达式列）上的列出现时，**不吐占位符、不吐注释行、整份 `CREATE TABLE` 不给**，
只给一句成文的话：哪几列、什么源类型、需改 SQL 或加 `CAST`。

**判据是「人照着填完之后这张表能不能用」**，A3 与本节因此不矛盾：

- **A3 的列是形状待配**——人在任务定义里配上 `(p,s)`、按这份 SQL 建表，预检就能过；
- **本节的列怎么填都过不了**——建出来要么少一列（撞 ADR-0009 §3 列名集合相等），
  要么多一列 MySQL 建不出的类型。

这正是 §4 拒绝「预检失败页再给一份全量 `CREATE TABLE`」用的同一条理由：
**一份执行了必然白费的 SQL 是误导，不是常亮。常亮的是出口，不是「无论如何都吐点什么」。**

### A5. 前置判定改判**推导形状**，且生成侧与判定侧共用同一个函数

ADR-0030 §6 已把判定侧订正为「先推导形状、再判 `p' > 65 || s' > 30`」。
**生成侧现在判的是源 `(p,s)`**（`crates/source/src/target_ddl.rs`：
`precision <= 65 && (0..=30).contains(&scale) && scale <= precision`），
放行形态 3 之后 `NUMBER(38,-30)` **一条判据都不命中，直接吐出 `DECIMAL(68,0)`**——
一张 MySQL 不让建的表，人执行时撞 `ERROR 1426`。

**订正：前置判定一律判推导形状——先推导、再判 `p' > 65 || s' > 30`**；超限的列按 A4 的粒度处理
（它属于「怎么填都过不了」那一类，ADR-0030 §2 已把它列在拒绝清单上，且 §6 要求单列一条）。

这不是新决策，是 ADR-0030 §6 的连带落点。但必须写在这里——否则它会以
「按产品生成的 SQL 建表却建不出来」的形式在下游爆出来，
**恰恰是 §「付的账」第 1 条那笔「两份实现漂移」的账第一次真的兑现**。

**「两侧共用」的准确含义**：`source` 的生成器与 `sink` 的比对器**不在同一个 crate**，
§1 已明确认下两份实现、并把兜底定成 ADR-0014 套件在两端各钉一遍——
**本增补不推翻它，也没有在跨端消掉两份实现**。共用的是**规格**：
「先推导形状、再判形状」这一条顺序在**每一端各实现一次**，
`source` 侧内部则由生成器与前置判定共用同一个推导函数（同一个 crate 内，这一半是真共用）。
把它读成「抽一个跨 crate 的公共实现」会直接撞 §1 第 2 条——那条已论证过消不掉。

### A6. `target_date_col` 放行 `TIMESTAMP(0..6)`

现行实现硬要求 `target_date_col` 的 describe 类型是 `DATE`，
一张以 `TIMESTAMP` 记业务日期的源表在 M3 之后**整个跑不起来**（不是拿不到 DDL，是发起也过不去）。

**放行 `TIMESTAMP(0..6)`，索引照给，谓词一个字不改**：
ADR-0002 的切换事务删除谓词是**半开区间** `>= :d AND < :d + 1`，
`DATETIME(6)` 上带小数秒的值完整落在区间内。Oracle `DATE` 本来就带时分秒，
这个坑不是 `TIMESTAMP` 引入的，半开区间当初就是为它选的。
索引建在 `DATETIME(6)` 上照样裁剪，ADR-0022 的 `SWAP_TARGET_BUSY` 成因照样避开。

**字符族与 `NUMBER` 族继续拒做业务日期列**，`DATE` / `TIMESTAMP(0..6)` 之外一律拒。

### A7. §2 的「取列」点名**不含值域校核**

ADR-0030 §4.3 把值域校核写进了「预检的固定顺序」第 3.5 步。而 §2 定取列是
「跑**形状预检** + describe」——**「预检」这个词会把 3.5 步顺手拖进来**。

**明确不跑。** 3.5 步是**一次源端全表扫描**（走 dblink 时还过 dblink），
而 §7 定取列结果纯瞬态、不缓存，**点几次按钮就扫几遍**。
取列要买的只有「结果集有哪些列、什么形状」，值域校核对此一个字都不贡献，
代价却与 §2 认下的「一次 prepare + describe」不是一个量级。

**值域校核只在 `POST /runs` 的映射预检里跑。** 直接后果要认下：
**取列成功不构成任何预检承诺**——这与 §「订正 ADR-0010 §3.1 的作用域」
早已写死的「生成的建表 SQL 不构成任何形式的放行」是同一条线，本增补不新增拦截层。

### A8. 订正「后果」：协议**不再**一字不动，但封条不解

原文「买到的」第 2 条写「协议**一字不动**：五个端点、12 码闭集、`POST /runs` 的报文形状全部原样」。
**M3 之后这句失效**：`SourceColumn` 新增一个可选 `fsp` 字段承载 `TIMESTAMP(n)` 的 `n`，
见 [ADR-0010](0010-http-protocol-contract.md) 2026-08-16 增补。

**性质必须分清，否则后人会拿这条当先例去推 §3**：

- 变的是**报文形状加一个可选字段**；
- **没变的**是 §3 判死的那条「不属于任何 run 的元数据查询」端点。
  五个端点不变、错误码闭集不增码、`/v1/` 前缀不动。
  **§3 的封条不解，「重开条件」一节一个字不改。**

加一个可选字段和开一类新端点是两个量级。

### A9. 订正「付的账」第 1 条：漂移面从 3 行扩到 9 行

原文写「规则**只有三行且无边界推理**，这件事是做得到的」。
**这句话的前提在 M3 之后不成立**：九行形态、`NUMBER` 族四种推导式互不相同、
还多了 A5 那条「先推导再判 `p' > 65 || s' > 30`」的前置判定。

**结论仍然成立，但更贵了**——漂移的后果没变（人已付出建表的真实代价、产品却说不行），
面积翻了三倍。承载点不变：**ADR-0014 的边界测试套件对每一行形态在两端各钉一遍，
缺一行就是一条静默漂移路径**。**用例形态归 [#105](https://github.com/liumingjian/db-qbs/issues/105)**，
本增补只记账、不定用例。

**不取**「把生成搬到 sink 消掉两份实现」：§1 第 2 条的理由（搬过去仍是「比对」与「生成」
两段代码，只是同进程，仍会漂移）与 M3 无关，原样成立。

### A10. 明确不变的

- `DEFAULT CHARSET=utf8mb4` **一个字不改**，对 `NCHAR` / `NVARCHAR2` 够：
  `utf8mb4` 是完整 UTF-8，覆盖 AL16UTF16 全部码位；ADR-0030 §7 已定 `n` 是字符数，
  MySQL `VARCHAR(n)` 的 `n` 同样是字符数，两边同构。
  **不加 collation 声明**——那会引入一个 ADR-0009 §6 没有的新判定面。
  行长风险（`utf8mb4` 每字符最多 4 字节）由 §8 的 `ERROR 1118` 静态提示承载，
  **「不预先计算行长上限」一个字不放宽**。
- §5 其余三条 DDL 规则（全列可空、列序取 describe 序、`target_date_col` 普通索引 + 注释）
  在九行形态下原样成立。
- §7 取列结果纯瞬态不受 A3 影响：生成器读的 `(p,s)` 来自**任务定义**，不是取列结果。
- §4 单出口常亮、§6「重新发起不是重试」、§8 `ERROR 1118` 只贴静态提示——全部不动。

## 2026-08-16 增补二：取列卡的三档标记、第四态，与 `TargetDdlError` 订正为复数

**来源**：[#102](https://github.com/liumingjian/db-qbs/issues/102)，地图 [#94](https://github.com/liumingjian/db-qbs/issues/94)。
**关联**：上一份增补 A3（待配精度）/ A4（白名单外列在场）/ A8（加字段不解封条）、
[ADR-0010](0010-http-protocol-contract.md) 2026-08-16 增补二（两处新增字段）、
[ADR-0029](0029-failure-classification.md) §3（方括号类目名「文字不是元素」）、
[ADR-0025](0025-m2-visual-language-and-design-system.md) 2026-08-16 增补。
**产物**：原型 [`docs/prototypes/0102-m3-ui-increments.html`](../prototypes/0102-m3-ui-increments.html) 屏 B / 屏 C。
**本增补只定呈现与结构，不含实现**——实现归 M3 实现票。

### 1. 三档标记：文字，落在「describe 类型」右侧

A3、A4 在取列卡上各要一个可见形态。定**三档、纯文字**：

| `support` | 标记 | 场合 |
| --- | --- | --- |
| `ok` | 无标记 | 常态 |
| `needs_precision` | `[待配精度]` | 裸 `NUMBER` / 表达式列，A3 |
| `unsupported` | `[不支持]` | 白名单外，A4 |

写法与 ADR-0029 §3 的既有落地（`web/src/history.ts:126` 的 `` `[${label}] ${message}` ``）
**逐字同构：纯字符串拼接，不成元素、不给 class、不着色**。
着色会让它逼近 ADR-0025 §3 的形状轴，而它不是错误码、也不是失败态——
它出现在取列这个探索性动作里，染成 crit 红是把「换个写法就行」的提示按失败读。
数据来源是 `SourceColumn.support`（ADR-0010 2026-08-16 增补二 §2）。

### 2. 第四态：**列表照给，只换 DDL 区块**

A4「白名单外的列在场则整份 DDL 不给」在界面上不是失败页。取列**成功了**——
人正需要看着这张列表去改源 SQL 加 `CAST`，把列表一起收走等于把改法的依据也收走。
**上半张列表照给，换掉的只是 DDL 区块**，块内一次列全所有挡路的列。

这与 `shape-failed` 是两回事：那是取列压根没执行（`/api/columns` 在形状预检就 422 了），
本态是 describe 已成、只有生成不给。**两者不得共用一个呈现。**

区块本身是既有 `.row-size-warning` 的 `.is-crit` 变体，只换三个色令牌，
**不是新类**——理由见 ADR-0025 2026-08-16 增补 §1。

### 3. `DdlText`：从「切一个固定字符串」推广成「切一组占位符」

A3 的 DDL 里，待配精度列写成 `DECIMAL(<p>,<s>)`。既有的 `.ddl-placeholder` 本来只服务
`<目标表名>` 一处，现推广成**一组占位符共用一套高亮**，`DdlText` 的切分从单串改成组。
**零新 CSS**，且「这里还没定、等你填」这件事在两处长一个样。

### 4. 订正：`TargetDdlError` 必须是复数

`crates/source/src/target_ddl.rs:6` 现在是单列结构（`column` + `message`），
`/api/columns` 的 422 报文照此形状回（`crates/source/src/server_main.rs:905-911`）。
**这撑不住 A4**：A4 要报的是「哪几列」，单列结构会把体验退化成
「改一列 → 再撞一列 → 再改一列」的循环——正是 [ADR-0009](0009-m1-mapping-precheck-rules.md) §8
「一次报全部列」当初禁掉的形态，而生成侧眼下还在犯。

**订正为复数**：`TargetDdlError` 携带一组挡路列（每项含列名、源类型、不合规原因），
`/api/columns` 的 422 报文同步改成数组。这是本票查出的漏洞，
与 [#101](https://github.com/liumingjian/db-qbs/issues/101) 查出的「生成侧前置判定仍判源 `(p,s)`」
是同一类账：**§8 的口径当初只在预检侧落实，生成侧一直是单列**。
两处一起归 M3 实现票。

### 5. 明确不变的

- **§4 单出口常亮不动**：常亮的是**出口**，不是「无论如何都吐点什么」。
  A4 下一个字都不给，正是 §4 的应有之义。
- **§7 取列结果纯瞬态**不受本增补影响：多的两个字段随结果一起丢。
- **A7 不变**：取列仍不跑值域校核，三档标记不构成任何预检承诺。
- **§5 的四条 DDL 规则、§6、§8 全部原样。**

## 2026-08-18 增补三：§1 第 2 条拒的是**搬移职责**，不是禁止共用**推导**

**来源**：[#125](https://github.com/liumingjian/db-qbs/issues/125)，地图 [#117](https://github.com/liumingjian/db-qbs/issues/117)。
本增补是一次**窄重开**：只订正 A5 括号里那句话的适用范围，**§1 第 2 条的结论一个字不动**。

### 1. 被订正的那句话，与它管不住的东西

A5 末段写着：

> 把它读成「抽一个跨 crate 的公共实现」会直接撞 §1 第 2 条——那条已论证过消不掉。

**§1 第 2 条拒的是「把建表 SQL 的生成搬到 `sink` 去，以此消掉两份实现」**，
理由是搬过去照样是「生成」与「比对」两段代码，只是同进程，仍会漂移。
**那是一条关于职责归属的判词。** A5 那句括号把它读成了「不得有任何跨 crate 的公共实现」，
**范围放大了**：它连「两端各抄一遍**同一个类型性质**」也一并禁掉了，而那不是 §1 论证过的东西。

ADR-0030 §1 的分工是本增补的依据：**「推导形状是什么」与「失效模式是哪一类」是类型的性质**，
「从严具体写成 `s' == s` 还是 `s' >= s`」是判定式。§1 第 2 条守的是**判定式**那一半的归属
（ADR-0010 §3.1：逐列判定集中在 `sink`），性质那一半从来不在它的射程内。

### 2. 订正

**A5 那句括号的适用范围收窄为：不得把判定式抽成跨 crate 的公共实现。**
推导——源形态到目标形状的映射、`DECIMAL(65,30)` 表达能力判定、白名单成员、
业务日期列可用性——**可以且应当只有一份定义**，落在 `db-qbs-shared`
（`crates/shared/src/target_shape.rs`，模块头注释把这条界线钉住了）。

**§1 第 2 条不重开**：建表 SQL 的生成仍在 `source`，逐列比对仍在 `sink`，职责一处不挪。
**ADR-0010 §3.1 不动。**

仓库里早有同类先例，本增补只是把它写明：规范形式的三个纯函数
（`canon_number` / `canon_date` / `canon_timestamp`，ADR-0014 的地盘）一直在
`crates/shared/src/lib.rs`，两端都调。**类型的性质放共享 crate 不是新范式。**

### 3. 界线（这一段是本增补的实质，比结论重要）

| 共用 | 不共用 |
|---|---|
| 源形态 → 目标形状（九行形态，ADR-0030 §1） | `NUMBER` 族的下界式（[#97](https://github.com/liumingjian/db-qbs/issues/97) / [ADR-0031](0031-number-predicate-lower-bound.md)） |
| `DECIMAL(65,30)` 表达能力判定（A5 / ADR-0030 §6） | 日期族的严格相等式（ADR-0030 §3） |
| 白名单成员、拒绝原因的**类型化闭集** | 目标列字符集必须 `utf8mb4`（ADR-0009 §6）、目标列必须可空（§5） |
| 业务日期列可用性（A6） | 两端的**措辞**——`source` 英文进建表卡报错、`sink` 中文进预检报告 |
| 三条出路 → 取列卡三档标记（增补二 §1） | 裸 `NUMBER` 的 `(p,s)` 配置读取与校验（任务定义是 `source` 侧输入） |

**措辞不共用是刻意的**：统一两端文字是用户可见改动，与本增补要买的东西无关，
硬塞进来会把一次纯内部重构变成要跑视觉门禁的改动。

**三档标记仍是展示提示、不是预检裁决**（增补二 §1 / A7 原话）：
共用推导不改变这一点，`sink` 照样自己判、不读那个标记。

### 4. 漂移面缩小了，但 A9 的兜底一条不撤

A9 记的账是「九行形态、四种推导式互不相同、加 A5 那条前置判定，
漂移面从 3 行扩到 9 行，承载点是 ADR-0014 的边界测试套件在两端各钉一遍」。

**本增补把这笔账的一半直接消掉**：推导只有一份定义，**它不可能再漂**。
剩下的一半仍是两份实现——`source` 生成的表，`sink` 的判定式认不认——
**兜底原样保留**：`crates/sink/tests/target_ddl_drift.rs` 那条
「生成的 DDL 解析回目标列、喂给预检必须零告警」的回路。#125 把它补到每形态各一条边界，
更细的用例形态仍归 [#105](https://github.com/liumingjian/db-qbs/issues/105)。

**A9 的「不取『把生成搬到 sink 消掉两份实现』」原样成立。**

### 5. 顺带订正一处宽度不一致（不是缺陷）

形状推导此前在 `source` 侧是 64 位、`sink` 侧被单方面拓到 128 位，算式也写成了两种
（`precision + |scale|` 与 `precision - scale`）。**两端不会算出不同答案**：
Oracle 的 precision 上限 38、scale 范围 −84..127，推导结果最大 122。
合成一份时**统一到 64 位**，上界的来源写进注释。这是抄写后各自演化的痕迹，不是曾经的失效路径。

### 6. 明确不变的

- **§1 第 1 条（建表 SQL 由 `source` 生成）、第 2 条（不搬到 `sink`）——不动。**
- **§3 的封条不解**：不属于任何 run 的元数据查询端点仍然不开，五个端点、错误码闭集不变。
- **A5 的技术结论不动**：前置判定一律判**推导形状**；本增补只订正它括号里那句话的范围。
- **A7 不变**：取列不跑值域校核，取列成功不构成任何预检承诺。
- **§4 / §5 / §6 / §7 / §8 与增补二全部原样。**
