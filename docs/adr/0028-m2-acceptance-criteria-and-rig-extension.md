# ADR-0028: M2 的验收判据落在 `/api` 面，台架扩长驻起停；视觉面另立人工走查

**状态**: 已接受
**日期**: 2026-08-15
**决策票**: [#59](https://github.com/liumingjian/db-qbs/issues/59)（地图 [#47](https://github.com/liumingjian/db-qbs/issues/47)，本图最后一票）

## 背景

M1 的验收判据落在**目标表与七个测量数**上（[#45](https://github.com/liumingjian/db-qbs/issues/45)，
`scripts/run-m1-acceptance.sh`，实跑 9/9 PASS）。那套判据成立，是因为 M1 买的是**搬运能力**——
观察面是数据库，天然可断言。

M2 买的是**可操作性与可观察性**（地图 #47 主方向），观察面变成了 UI 与历史，判据形态整个不一样。
这块雾在 [#58](https://github.com/liumingjian/db-qbs/issues/58) 把屏的清单定形为 **4 屏 + 1 对话框 = 18 态**
之前一直问不准——「测什么」完全取决于交付形态。

同时 ADR-0005 的台架是为**一次性进程**设计的：`up.sh` 起两个库，验收脚本 exec 一次 source 二进制，
退出码 0/1 就是结论。ADR-0019 把 `source` 改成长驻编排进程之后，这套不成立。

本 ADR 定**判据与台架形态**，不写脚本——地图 #47 的终点是规格定稿。

## 1. 断言面画在 `source` 的 `/api/*` 上，不上浏览器自动化

**M2 的自动验收断言 `/api/*` 的响应，不断言 DOM。**

判据的可行性来自 #58 的一条结构事实：**18 个态的判定条件全是 API 响应的函数**——
`run_id` 是否为 `null`、投影在不在、墓碑哪一值、错误码是闭集 12 里的哪一个。
断言 API 就是断言态，且断言的是**规格里写死的东西**。

否掉浏览器自动化（Playwright 之类），理由不是成本：

**它会把设计系统的类名与 DOM 结构变成事实上的契约。** ADR-0025 刚把
`docs/design-system/`（`README.md` + `tokens.css`）定成唯一来源，并明写「要改先改那两个文件」。
DOM 断言让每一次视觉调整都变成验收返工，而买到的增量只有「这个数确实渲染出来了」。

也否掉「M2 全人工走查」：M2 恰恰是**第一次有人能反复操作**的形态，没有回归防护等于把
M1 那 9/9 PASS 的证据链交给运气。

**两条判据互补，不互相替代：**

| 面 | 形态 | 给不给退出码 |
|---|---|---|
| 规格面 | 「某个 `/api` 响应在某情形下是什么」——自动断言 | **给** |
| 渲染面 | 「#58 那 18 态逐一看一眼」——人工走查（§6） | **不给** |

**分界线是一句可判断的话：这条断言失败时，是规格错了，还是渲染错了？** 前者进自动化，后者进人工。

## 2. 台架怎么拉起长驻 `source`

| 子问题 | 决策 | 为什么不是另一种 |
|---|---|---|
| **拉起** | 验收脚本在**宿主机**上后台起进程、记 PID | 不进 `docker compose`：M1 验收里有**杀进程重跑**场景，进了 compose 之后「杀」变成 `docker kill` 与重启策略的博弈；而 source 现在长驻，**杀了之后它自己怎么表现正是被测对象**（#58 的「进程消失」态） |
| **就绪判定** | 轮询 `GET /api/tasks` 拿 200 | **不新开 `/health`**。健康端点是运维需求，地图收窄 2 明令不接运维便利。ADR-0027「协议一字不动」约束的是 `source→sink` 的 5 端点闭集，`source` 自己的 `/api/*` 不受它管——但能不新增就不新增 |
| **收尾** | `SIGTERM` 等优雅退出，超时兜底 `kill -KILL` | 长驻进程持有 SQLite（ADR-0020），收尾语义现在有内容了；`-KILL` 收尾会让「正常收尾」与「进程消失」两个场景不可区分 |

两个数据库容器仍由既有 `up.sh` / `down.sh` 管，本 ADR 不动。

## 3. 场景清单（本 ADR 的主交付物）

按**制造手段**归并，不按屏归并——同一次杀进程能同时验多个态，按屏切会重复起进程。
每条写清「怎么制造 → 断哪个 `/api` 响应的哪些字段 → 期望值」。

### 3.1 台架层自动断言（走 `/api/*`）

| # | 场景 | 制造手段 | 断言 |
|---|---|---|---|
| **A1** | 起停与就绪 | 起进程 → 轮询就绪 → `SIGTERM` | `GET /api/tasks` 200；`SIGTERM` 后进程退出、SQLite 无残留锁、可原地再起一次 |
| **A2** | 建任务 + 取列（正面 + 三条负面） | 合法 `source_sql` 调取列 | 列清单 == Oracle 游标 `describe`；**不产生 `run_id`**；历史 SQLite **零新增行**；`sink` 日志在该窗口内**零 `component=sink` 新行**（§4） |
| **A3** | 取列失败·形状 | 手改 `source_sql` 违反形状预检六条之一 | 六条**一次报全**（通过的也在报告里）；无错误码标签字段——形状预检是 `source` 本地成文，不属 ADR-0010 的 12 码闭集 |
| **A4** | 取列失败·Oracle | 错表名 / 无权限 | 归 Oracle 错误面；仍不产生 `run_id`、不写历史行 |
| **A5** | 正常发起跑完 | 10 万行窄表，正常路径 | 终态 `SWAPPED` 墓碑；**投影六个聚合标量 == 历史行落库值**（§5） |
| **A6** | 形状预检失败态 | 发起时 `source_sql` 形状不过 | `run_record_id` 有、**`run_id` 为 `null`**；`sink` 零请求；历史列表出现该行 |
| **A7** | 映射预检失败态 | 目标表缺列 / 类型不匹配 | `run_id` **有**（已发 precheck）；ADR-0009 §8 逐列报告 + 总计；**不出终态块**（#58 轴二定形） |
| **A8** | 校验失败 | 复用 M1 的 `VERIFY_FAILED` 制造手段 | 终态 `DISCARDED` 墓碑；历史行封口 |
| **A9** | 哨兵逃逸 | 构造命中哨兵的业务值 | `/api` 响应里 `column` / `value` 字段**确实回传**（打码是渲染面的事，见 §6） |
| **A10** | 并发硬拒 | 一个 run 进行中时再发起同 `task_id` + 同业务日期 | 后端**当场硬拒绝**；发起对话框的提示是投影、**只提示不拦截**（ADR-0022），故断言点在 `POST` 的响应而非提示 |
| **A11** | `COMMITTING` 中取消被拒 | **复用 `acceptance/commit-drop-proxy.py`** | `/api` 自己的 409（ADR-0026 §5）；取消按钮常亮是渲染面 |
| **A12** | 进程消失 | `kill -KILL` source 后重起 | 该 run 落「结局不明」族；**不给错误码**（ADR-0026 §4）；投影已丢，走历史回落 |
| **A13** | 服务重启 | `SIGTERM` + 重起 | 同族、情形不同；断言两者在响应上可区分 |
| **A14** | 详情寻址与生命周期 | 对进行中与已终结各取一次 | 一个端点、按 `run_record_id` 寻址、**投影优先历史回落**（ADR-0026 §6）；`live` 字段驱动前端停不停轮询 |

**A12 / A13 必须进自动化**，不得下放人工：它们是 ADR-0026 §6「投影优先历史回落 + 终结即丢」
那条边的**唯一见证**，而杀进程 / 重启在台架上恰恰是最便宜的动作（M1 已有 kill source / kill sink 先例）。

### 3.2 纯函数层（进 CI，零依赖）

| # | 场景 | 断言 |
|---|---|---|
| **F1** | **建表 SQL 生成器 ↔ 映射预检不漂移** | 对 `canon-golden.json` 里每条 `tier = m1` 用例的类型：生成建表 SQL → 把该 DDL 的列定义喂给映射预检判定函数 → **必须过** |
| **F2** | 历史保留期清理 | 输入 = 行时间戳集合 + `now` + 保留期，输出 = 该删哪些（§7） |

### 3.3 台架层手工门禁（挂 ADR-0014 §8 已有机制，不新开一套）

| # | 场景 | 断言 |
|---|---|---|
| **G1** | 不漂移的第二遍 | **真**在 MySQL 上执行生成的 DDL → **真** `describe` 出列元数据 → **真**跑映射预检 |
| **G2** | 规范形式门禁 | 既有 `run-canon-gate.sh`，一字不改 |

## 4. 「取列」的无副作用怎么证

ADR-0027 §2 新增的 `source` 本地取列动作是「只读、无副作用、不碰 `sink`」——这是个**否定命题**，
断言方式必须写死，否则无从证起。四条（A2）：一条正面 + 三条负面。

**`sink` 零请求那条用日志判，不抓包**：断言 `sink` 进程日志在该窗口内无任何
`component = sink` 的新行。ADR-0021 §1 刚把 JSON Lines 定成主载体、并为此新增第六个公共字段
`component`——**这个字段的第一个真实用户就是它**。一条断言护两个 ADR：既证了取列不碰 sink，
也证了 `component` 确实被两端都写了。

## 5. 报告形态：不采性能数，只留一条一致性对照

**M2 报告不采任何性能测量数。** M1 报告记七个数（fetch/push/cursor、commit 及其 `COUNT(*)` 子项、
`purged_rows`、逐批行数、序列化字节分布），是因为 M1 买的是搬运能力；M2 收窄 1 冻结了搬运语义，
重复采一遍只会制造**两个可能打架的数据源**。性能数留在 M1 那份入口里采（§8）。

M2 报告形态 = **场景 × PASS/FAIL + 每条断言的实际值原样贴**，默认写
`docs/spikes/fixtures/local-rig/m2-acceptance-<UTC>.md`。

**唯一新增的记录项是一致性对照**（A5）：run 终结那一刻，投影的六个聚合标量与历史行落库值逐个相等。
它值得单列，因为那是 ADR-0026「投影非权威、终结即丢」与 ADR-0020 §6「终结封口」
**唯一会互相打架的地方**——两条规则各自都对，错法是父进程用不同路径算了两遍。

## 6. 渲染面：另立人工走查清单，照 ADR-0014 §8 的形态

§1 推给人工的第 3 类（API 里根本不存在的东西）落
`docs/spikes/fixtures/local-rig/m2-visual-walkthrough.md`，逐条写
**「打开哪一屏 · 制造什么情形 · 该看见什么」**。触发条件两条：

1. **M2 验收时必跑一次。**
2. **任何改动 `docs/design-system/README.md` 或 `tokens.css` 的变更，合并前必跑一次。**

第二条是关键：它把 §1 拒掉浏览器自动化省下的成本，**如实记成了一笔人工账**，而不是假装没有。
形态照抄 ADR-0014 §8 的台架层手工门禁（带触发条件、跑完贴实际观察不贴「通过」），
不发明第二套机制。

## 7. 保留期计算不得读系统时钟（对实现的约束）

ADR-0020 §9 定保留期按时间、默认 90 天。这条**不可能在台架上等出来**。

于是加一条实现约束：**保留期清理的 `now` 必须是入参，不得直接读系统时钟。**
否则它结构性不可测。理由与 ADR-0014 §11 那条年份域断言同源——成本近乎为零，
买到的是「这段逻辑天天在 CI 里跑」。

## 8. `run-m1-acceptance.sh` 独立保留，M2 另起一个入口

两个入口并列，M2 验收的前置要求是**先跑绿 M1 那份**。

**明确拒掉「把 M1 的 9 类场景改写成经由 UI 发起」**——这是最诱人也最危险的一条：
它让 M1 的回归基线**依赖 M2 的实现**，一旦 `/api` 改了，那条已经 9/9 PASS 的证据链当场失效，
而它本该是**不受 M2 影响的常量**。

也拒掉「M2 入口内部先跑一遍 M1 全套」：把两份编排的失败含义混进一个退出码里。
代价是要跑两条命令，可接受。

## 9. 扩台架的部分算 M2 交付物

与 M1 同规格入库：`scripts/run-m2-acceptance.sh` + `acceptance/` 下的配置与辅助程序，
报告写 `m2-acceptance-<UTC>.md`。

理由是 M1 那份验收编排的真实价值不在「跑过一次」，而在于**它可重复**——#45 之后任何人改了
搬运链路都能一条命令复跑。M2 若把验收留在会话记录里，这个性质就丢了。

**但本票只定形态与判据清单，脚本本身是实现期的事**（地图 #47 终点是规格定稿）。

## 10. ADR-0005 的「上线前必须复验清单」一条都不加

那份 7 条清单的入选标准是**台架结构性答不了的服务端事实**（字符集、11g 小版本、真实列清单、
真实吞吐、`undo_retention`…）。

M2 新增的东西**全都是客户端侧行为**——长驻进程的起停、SQLite 历史、`/api` 响应、投影生命周期，
落在 ADR-0005 那张效力表的第一类「完全可信」里，台架上测得准。

至于「反向代理鉴权在客户环境怎么落」：ADR-0024 已把它定成**部署者的事、产品零感知零校验**。
把它写进复验清单等于让产品重新长出对它的感知，**擦收窄 2 的边**。

## 对既有 ADR 的订正与增补

- **ADR-0005 增补**：台架在长驻形态下的扩展见本 ADR §2；**效力划线（四类可信度）一字不动**，
  §10 说明 M2 不给上线前复验清单加任何条目。
- **ADR-0014 §8 增补**：台架层手工门禁的触发条件加**第四条——M2 验收时必跑一次**（本 ADR §3.3 的 G1/G2）。
- **ADR-0020 §9 增补**：保留期清理的 `now` 必须是入参，见本 ADR §7。
- **ADR-0026 / ADR-0027 正文不动**：§5 那条一致性对照是**验收项**，不是新规则。

## 已知代价

1. **渲染面的回归防护靠人。** §6 那两条触发条件若没人守，设计系统改动可以静默破坏 18 态里的
   任何一态而无人发现。这是 §1 拒掉浏览器自动化明知要付的账，写在明面上。
2. **`/api` 断言看不见「渲染成功」。** 数在响应里正确，不等于屏上看得见——中间那一层
   （React 组件把字段接到组件上）**没有任何自动防线**。
3. **A11 依赖 `commit-drop-proxy.py` 这个台架专用脏手段**，它本身没有测试。M1 已认下这笔账。
4. **F1 的覆盖面止于 `tier = m1` 三种类型**（ADR-0014 §2）。M3 扩类型时，不漂移的证据要跟着扩，
   否则 DDL 生成器与映射预检可以在新类型上悄悄分家。
5. **两个入口意味着两份报告**，「M2 验收通过」这句话从此需要两个文件才能支撑。

## 2026-08-16 增补（[#103](https://github.com/liumingjian/db-qbs/issues/103)）：M3 的三处改写

**来源**：[#103](https://github.com/liumingjian/db-qbs/issues/103)，地图 [#94](https://github.com/liumingjian/db-qbs/issues/94)，
落 [ADR-0032](0032-m3-acceptance-criteria-and-rig-extension.md)。本增补**不推翻本 ADR 的任何裁定**，
只记下 M3 把三处**扩**成了什么样。

| 本 ADR 原文 | M3 的改写 | 落点 |
|---|---|---|
| §1 分界线「失败时是**规格**错了还是**渲染**错了」 | **对 M3 不够用**：M3 买的东西观察面回到 M1 那一侧，要切的是「**值 vs 报告**」。ADR-0032 §1 **并列**新写一句，本条**不替换、继续管规格 vs 渲染那一刀** | ADR-0032 §1 |
| §8「两个入口并列」 | **变三个**：M3 另起 `run-m3-acceptance.sh`，前置是先跑绿 M1 与 M2。拒掉往 M2 那份塞（退出码含义会混），也拒掉往 M1 那份塞（理由与本 ADR §8 拒「M1 改经 UI 发起」同源——M1 基线是常量，不得随白名单漂移） | ADR-0032 §2 |
| §3.2 的 **F1** 覆盖面止于 `tier = m1` 三种类型（**已知代价 4**） | **已兑现**：F1 扩到 ADR-0030 §1 九行形态，并新增 F3（前置判定判推导形状）、F4（`TargetDdlError` 承载多列）。已知代价 4 从「代价」改成「已做」 | ADR-0032 §6 |

**已知代价 5 的「两份报告」随之改为三份**（M1 / M2 / M3 各一份，人工走查另计两份清单）。

**§6 的两条触发条件不动**，且 M3 **没有触发第 2 条**——[#102](https://github.com/liumingjian/db-qbs/issues/102)
判 M3 零设计系统改动，故整份 V1–V25 **不重跑**；M3 另立 `m3-visual-walkthrough.md`（W1–W6），
形态与本 ADR §6 同构。

**§10「ADR-0005 复验清单一条不加」在 M3 上同样成立**，理由与本 ADR §10 逐字同源（见 ADR-0032 §11）。
