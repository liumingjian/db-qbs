# ADR-0023: M2 SQL 构建器的边界——一次性脚手架，只生成不留存；「选条件」订正为「指定日期列」

**状态**: 已接受
**日期**: 2026-08-15
**来源**: [#51](https://github.com/liumingjian/db-qbs/issues/51)（地图 [#47](https://github.com/liumingjian/db-qbs/issues/47)）
**关联**: [ADR-0004](0004-parameterized-business-date.md)（SQL 由人手写、业务日期参数化——本 ADR 不改它，只在它上面加一个可选的生成入口）、
[ADR-0008](0008-business-date-predicate-generation.md)（源端谓词形状与 §5 同名判定；**本 ADR 一个字都不订正**）、
[ADR-0009](0009-m1-mapping-precheck-rules.md)（**§1 那句「`ALL_TAB_COLUMNS` 留给 M2 的 SQL 构建器做列选择」由本 ADR 兑现**）、
[ADR-0010](0010-http-protocol-contract.md)（接口闭集；**本 ADR 不扩它**，§3.1 亦不订正）、
[ADR-0016](0016-task-definition-form.md)（任务定义四字段与 SQL 形状预检；**格式一字不变，§4 第 3 条由本 ADR 重新归类但不搬动**）、
[ADR-0019](0019-m2-source-process-topology.md)（长驻父进程 + Web UI，本 ADR 的宿主）

## 背景

`CONTEXT.md` 的 V1 范围从 M0 起就写着一句话：

> SQL 构建器（**选表 / 选字段 / 选条件** → 生成 SQL，用户可手改）

这句话里的「**选条件**」与 [ADR-0008](0008-business-date-predicate-generation.md) §2 **正面冲突**，
而冲突从写下那天起没人接过。ADR-0008 把源端 WHERE 压到「**除日期谓词外不许有任何其他谓词**」，
且日期谓词的形状被 SQL 形状预检强制成半开区间。
地图 [#22](https://github.com/liumingjian/db-qbs/issues/22) 的 Out of scope 里
「源端 WHERE 里的业务过滤谓词」正是被这条挡在 V1 之外的。

同一句话里的「**用户可手改**」也从没定过边界：手改之后，构建器与 SQL 文本谁是权威、
形状预检站在哪一层，都没有答案。

本 ADR 把这两件事一次定死。**它定的是构建器的形状，不是搬运语义**——
构建器是生成 `source_sql` **文本**的前置工具，生成完之后 M1 那条链路
一个字都不知道它存在过。

## 决策

### 1. 「选条件」坐实收窄，订正为「指定日期列」

**结论：坐实。构建器不许选业务过滤条件。**

M0 写下的「选条件」是**含混**的，它实际盖了两件不同的事：

| 被「选条件」盖住的 | V1 的实际归属 |
|---|---|
| (a) 业务日期条件 | 由系统按 `source_date_col` + 业务日期**生成**（ADR-0008 §1/§3），人只选**哪一列**是日期列 |
| (b) 业务过滤条件（`status = 'X'`） | ADR-0008 §2 **硬拒**，#22 已列进 Out of scope |

于是 `CONTEXT.md` V1 范围那句订正为：

> SQL 构建器（**选表 / 选字段 / 指定日期列** → 生成 SQL，日期谓词由系统按
> [ADR-0008](0008-business-date-predicate-generation.md) §3 的半开区间形状生成；用户可手改）

**为什么不证伪。** 证伪就要重开 ADR-0008 §2，而那一条不是随手加的收窄：
它是 V1 **唯一一处「出事了校验也不会响」**的地方上唯一的防线。
放行 `AND status = 'X'`，生成的清除条件只按日期删，会把目标表里同日但 `status <> 'X'` 的
存量数据一起删掉——**范围不等价，且行数校验结构性抓不到**。
要绕开它，就得同时给出「清除条件如何跟着业务谓词走」的完整方案，
那是一个 M3 议题，不是一张 UI 票能付的账。地图 [#47](https://github.com/liumingjian/db-qbs/issues/47)
的收窄 1（搬运语义冻结）在此正面生效。

### 2. 构建器是**一次性脚手架**，选择状态不进任务定义

三种形态里选第一种：

| | 形态 | 判决 |
|---|---|---|
| **A** | 一次性脚手架：向导 → 吐出 SQL 文本 → 落进 `source_sql`，**选择状态不留存** | **采纳** |
| B | 结构化模型为权威：任务定义存「表 + 列清单 + 日期列」，SQL 每次运行时生成 | 否 |
| C | 双向同步：手改后反解析回结构化模型 | 否 |

**任务定义因此仍是 [ADR-0016](0016-task-definition-form.md) §2 那四个字段，格式一个字不变**，
§6 的未知字段严格拒绝不需要放行任何新字段，老任务文件不会失败。

**否掉 C 的理由**：它要写一个 Oracle SQL 解析器做反向映射，是本图最贵的一块，
而买到的只有「改完还能回到向导」这一条舒适度。

**否掉 B 的理由更重要**：B 看似干净，但「权威在结构化模型」就意味着**人手改的 SQL 是二等公民**，
这与 ADR-0004 认定的现实用法正面冲突——生产那条 70+ 列、带 dblink 的查询**改一改就用**，
**真实的主路径是粘一条现成 SQL**，构建器是给不会写的人用的辅助入口。
把辅助入口做成权威，等于让主路径降级。

推论：**人回头再编辑任务，看到的是 SQL 文本**；要重选就重走一遍向导覆盖它，
构建器不承诺「记得你上次选了什么」。

### 3. dblink 表：一个可选的「数据库链接」输入，不做同义词逐级解析

这一条由一个已经在仓库里的硬事实逼出来（`docs/spikes/fixtures/README.md`）：

> 生产表是 `htbr45.t_r_fr_aststat@FA`，经 dblink 指向更远端的库，
> **「所有字典查询都走 `ALL_TAB_COLUMNS@FA`，本地数据字典里没有这张表」**。

也就是说，「查本地 `ALL_TABLES` 列个表让人点」这件事，**在真正要搬的那张表上一行都查不到**。

**决策**：构建器给一个**可选的「数据库链接」输入**。空则查本地字典；
填了 `FA` 就把该次会话内的所有字典查询加 `@FA` 后缀
（`ALL_TABLES@FA` / `ALL_TAB_COLUMNS@FA`），生成的 SQL 里表名同样带 `@FA`。

**不做的两件事**：

- **不从 `ALL_DB_LINKS` 列出可选 link**：它只列当前用户可见的 link，列表不全反而误导。
- **不做同义词/视图的逐级解析**（`ALL_SYNONYMS@FA` 递归到真表）：那是一条自带失败面的递归，
  而 spike-0001 §5.4 已证 dblink 故障有独立错误签名
  （`ORA-02063: preceding line from <LINK_NAME>`），失败时给人话即可。

> **明知的缺口**：若 `@FA` 后面那个对象本身是**同义词**，构建器在「选表」这一步就列不出它的列，
> 构建器对该表不可用——**人粘 SQL 手写的主路径不受影响**。
> 这不是缺陷，是第 2 节「构建器是辅助入口」的直接后果。

### 4. 构建器读 Oracle 元数据：只亮不判——这是本 ADR 最容易被写反的一条

构建器选表选字段就要列清单，这是 `source` 新增的**第二类**源库访问
（第一类是运行期的 describe + 单游标流式，ADR-0007）。它与「一条 SQL 一个游标」无关：
字典查询发生在**建任务阶段**，不在任何 run 之内，没有 `run_id`。

**决策：类型与精度信息在选字段界面上原样显示（甚至可标注「M1 白名单外，预检大概率会拒」），
但一律不构成门禁——不禁止选中、不做任何拒绝。**

**理由不是「守 ADR-0010 §3.1 的字面」，是两份元数据不是同一份**：

| | 元数据来源 | 出处 |
|---|---|---|
| 构建器 | 数据字典 `ALL_TAB_COLUMNS` | 本 ADR |
| 映射预检 | **游标 describe**（ODPI-C query-info） | ADR-0009 §1（明写字典**不参与**预检） |

视图、dblink、同义词之下两者可以不一致。**拿一份非权威元数据做门禁，制造的是
「构建器放行了、预检却拒」，以及更糟的「构建器拒了、其实能跑」。**
类型判定权威留在 sink（ADR-0010 §3.1 经 ADR-0016 §4 收窄后的原文：
「**逐列类型判定** source 一个都不做」），「一次报全部列」才继续成立。

**元数据不缓存**，每次打开构建器现查——与 ADR-0009 §7「预检不缓存到任务定义上」同一条理由。

### 5. 生成的 SQL 天然过检：六条里五条是冗余断言，第 3 条不然

构建器的输出形态被前四节钉死成：

```sql
SELECT a.C1 AS C1, a.C2 AS C2, a.D_BIZ AS D_BIZ
  FROM <owner>.<table>[@FA] a
 WHERE a.D_BIZ >= TO_DATE(:biz_date,'YYYY-MM-DD')
   AND a.D_BIZ <  TO_DATE(:biz_date,'YYYY-MM-DD') + 1
```

对照 [ADR-0016](0016-task-definition-form.md) §4 那张表的六条形状约束：

| # | 约束 | 生成的 SQL |
|---|---|---|
| 1 | `:biz_date` 恰好两次，构成半开区间，两处同一列 | **结构性必然满足** |
| 2 | WHERE 中不存在其他谓词 | **结构性必然满足**（第 1 节：无处可写） |
| 3 | `upper(target_date_col) == upper(source_date_col)` | **不必然**，见第 6 节 |
| 4 | 相对时间函数扫描（`SYSDATE` / `CURRENT_DATE` / `SYSTIMESTAMP`） | **结构性必然满足**（生成器不产出它们） |
| 5 | 每列必须显式命名 | **结构性必然满足**（只选真列，一律带 `AS`） |
| 6 | 表达式列 / 精度不确定的列一律拒绝 | **结构性必然满足**（只选真列，无表达式） |

**冗余不等于可以省。** SQL 一旦可手改，发起时手上那份文本
**与「它是否由构建器生成过」已经结构性不可区分**，预检必须无条件跑（第 7 节）。

### 6. 第 3 条的重新归类：它不是 SQL 形状问题——只记账，不搬动

五比一的不对称正好指出：**`upper(target_date_col) == upper(source_date_col)`
根本不是 SQL 文本形状判定，它是两个配置字段的一致性判定**，
只是当年（ADR-0016 §4）顺手挂进了同一段预检。

**决策：只记这一笔账，不搬动它。** 它留在同一段、同一时点、同一次报全。
搬动零行为差异，纯粹的重新归类不值得动 M1 链路。

### 7. 目标端两个字段：人手填，`target_date_col` 预填源端日期列名

`source` 结构性看不到目标端元数据——MySQL 连接只在 `sink`（ADR-0016 §5）。

- **`target_table`**：**人手填**。V1 不自动建目标表（只生成建表 SQL 给人执行），
  表是人先建的，人知道名字。
- **`target_date_col`**：**预填成源端选中的那个日期列名，可改**。
  ADR-0008 §5（经 ADR-0016 §2.1 订正）本来就要求两者同名，
  预填即是把那条规则做成默认值；人改了就会被形状预检第 3 条当场拒。

**明确推迟、不在本 ADR 预判的一条路**：新开一条 `source → sink` 的**目标端元数据查询接口**，
让构建器也能列目标表、目标列、甚至直接生成建表 SQL。它要给
[ADR-0010](0010-http-protocol-contract.md) 的接口闭集加一类**不属于任何 run 的元数据查询**，
是真正的协议扩面。**它的归宿是地图 #47 里「目标表 DDL 在 UI 里怎么落地」那张票**，
本 ADR 只写明「这条路存在、被有意推迟」。

> **2026-08-15 结清（[ADR-0027](0027-target-ddl-generation-and-cross-end-metadata.md) §3，
> [#57](https://github.com/liumingjian/db-qbs/issues/57)）：那条路被否掉，归 Out of scope。**
> 建表 SQL 结构性地不需要目标端元数据（源列元数据 → 目标类型是唯一确定的正向推导），
> 于是这条接口剩下的驱动力只有「一个下拉框」，而 §4「只亮不判」与 ADR-0009 增补 §3
> 已围死它买不到任何拦截。**本节两个字段维持人手填 + 预填，不升级为选择。**

### 8. 手改后的形状预检：每次发起无条件重跑，门禁只有一处

**门禁**：`source` 本地、`POST /runs` 之前那一次（ADR-0016 §4 不变），
**每次发起无条件跑，不区分改没改、不区分是否由构建器生成**——
与 ADR-0009 §7 同一条理由：缓存会在「有人半夜改了 SQL 或目标表」时失效，
而那正是预检存在的理由。

**UI 侧的即时反馈不是门禁**：构建器里可以实时跑一遍同一段形状预检做红字提示
（对生成的 SQL 它永远绿，只在人手改后可能变红），但它**不减免**发起时那一次。

**措辞归属**：形状预检的错误是 **`source` 本地成文**的，
**不走 [ADR-0010](0010-http-protocol-contract.md) §7 的透传链路**——
ADR-0017 §6 已记明这是唯一由 source 本地成文的预检错误。
形状预检不过则根本不发 HTTP 请求，`sink` 不知道存在这个 run。

**两段预检的报告在 UI 上分开呈现，不合并**：

| 报告 | 产地 | 措辞来源 |
|---|---|---|
| SQL 形状预检 | source 本地，`POST /runs` 之前 | source 本地成文 |
| 映射预检 | sink，`POST /runs` 之内 | ADR-0010 §7 透传 |

合并等于把两段预检搅成一段，而 ADR-0016 §4 分它们的理由（SQL 文本不跨 HTTP，
sink 结构性判不了）一个字都没变。两段各自「一次报全部」。

### 9. 构建器的输入输出定形

```
输入： 数据库链接（可选，如 FA）
       表（owner.table）
       列勾选
       日期列（从已选列中指定，即 source_date_col）
       target_table      ← 人手填
       target_date_col   ← 预填 = 日期列名，可改

输出： source_sql（一段文本）+ source_date_col + target_table + target_date_col
       ——恰好是 ADR-0016 §2 那四个字段，不多不少
```

**「列勾选允不允许勾成真子集」不由本 ADR 决定。** 它在输入侧占一个位，
其语义后果（映射恒不恒等、未选中的目标列在切换后会被写成什么）由
[#52](https://github.com/liumingjian/db-qbs/issues/52) 裁。#52 若判「不许」，
列勾选退化成「全选 + 只读展示」，**本节的输入输出定形一个字不用改**。

分工：**本 ADR 定形状，#52 定语义。**

> **2026-08-15 已裁（[#52](https://github.com/liumingjian/db-qbs/issues/52)，
> [ADR-0009 增补](0009-m1-mapping-precheck-rules.md)）——判「许」。**
> 列勾选**允许勾成真子集**，且映射依然恒等：ADR-0009 §3 的对齐面是「SQL 结果集 ↔ 目标表」，
> 源表不参与，勾成子集减的是源表的列而非结果集的列。危险的「目标表有列没被选中」由
> ADR-0009 §4 当场硬拒（跑不起来，不是搬错）。落在本节已覆盖的另一半上，
> **本节的输入输出定形一个字未改**。构建器**不得**为提前发现列集不等去查目标端元数据——
> 门禁只有预检一处，理由与 §4「只亮不判」同源；§7 推给 #57 的那条接口也不构成授权。

### 10. 数据预览不做

「点完列跑一次样本查询看看长啥样」——**不做**，进地图 #47 的 Out of scope。

1. 预览要绑 `:biz_date`，等于要人在**建任务**阶段先输一个业务日期，
   把「任务定义不含业务日期，业务日期是运行时参数」（`CONTEXT.md` 术语表）在 UI 上搅浑。
2. 它会被当成校验用——「我预览看过了，数据是对的」。V1 的防线是映射预检，不是肉眼。
3. 它买的是舒适度，不是可操作性闭环。地图主方向那句「不动搬运语义，这件事能不能做成」
   的对偶是「不做这件事，闭环能不能成」——**能**。

## 本 ADR 不订正什么

本票很容易被误读成「碰了搬运语义」。**它没有**：

- **ADR-0008 一个字不动**——§5、预检四条、半开区间形状全部原样。
- **ADR-0010 §3.1 不动**，接口闭集**不扩**（第 7 节那条路被推迟，不是被采纳）。
- **ADR-0016 §2 的四字段、§6 的未知字段严拒不动**；§4 第 3 条**重新归类但不搬动**。
- **ADR-0009 的判定式、拒绝清单、一次报全部不动**——只在 §1 加一条兑现脚注。
- **M1 的搬运链路一个字不知道构建器存在过**：它的全部产物就是一段 `source_sql` 文本。

## 代价

- **构建器在生产主力表上可能直接不可用**（第 3 节的同义词缺口）。主路径是粘 SQL，可接受。
- **构建器会「放行」注定被 sink 拒掉的列**（第 4 节只亮不判）。换来的是判定权威单一、
  不出现两份元数据打架。误拒比误放更贵这条在这里是反的：构建器不是防线，预检才是。
- **重走向导会覆盖手改**（第 2 节不留存选择状态）。UI 须就此明确警告，但不做合并。
- **「选条件」这个词从 V1 范围里消失**，M0 以来对外说过这句话的地方要跟着改口。

## 时效

第 3 节的 dblink 处理架在「生产表经 dblink 且可能是同义词」这条**尚未在生产实测**的推断上
（`docs/spikes/fixtures/README.md` 步骤 6 列的就是这次普查）。
[#2](https://github.com/liumingjian/db-qbs/issues/2) 的生产普查若查明它其实是**真表**，
第 3 节的缺口自动消失、无需改决策；若查明是**多级同义词**，
「构建器要不要做逐级解析」可作为一次独立复审重开。
