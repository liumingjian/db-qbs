# ADR-0014: 规范形式边界值测试套件——文法进规格、分两层测、台架层不进 CI

**状态**: 已接受
**日期**: 2026-08-13
**决策票**: [#31](https://github.com/liumingjian/db-qbs/issues/31)（地图 [#22](https://github.com/liumingjian/db-qbs/issues/22)）

## 背景

ADR-0003 把规范形式定成**全链路正确性的单点**，并在「代价」一节写下：
「规范形式的实现是全链路正确性的单点。必须有专门的、覆盖边界值的测试套件。」
STRATEGY-V1 的风险登记把缓解措施写成「视为一等公民」。

**这个一等公民至今一行规格都没有。** 本 ADR 定它的规格，不写代码。

同时有个必须先摆平的张力：地图 [#22](https://github.com/liumingjian/db-qbs/issues/22)
的主方向是**抓大放小**，而「一等公民」天然往完备的方向长。二者只有一种共存方式——
**套件的分量花在「哪些错会静默」上，不花在「类型有多全」上。**

## 1. 权威在仓库里，不在台架里

**唯一权威 = [`docs/spikes/fixtures/canon-golden.json`](../spikes/fixtures/canon-golden.json)。**

台架 `03-boundary-rows.sql` 里的 `t_canon_expected` 表**不是**权威，理由不是「文件比表方便」：

1. **权威不能有环境依赖。** 读那张表必须起 Oracle 容器，而 `canon_*` 是纯函数，
   它的测试不该需要任何数据库。台架起不来，权威就读不到。
2. **那张表的语义已经不纯。** 它混进了七行 `V1 排除`（`RAW`/`CLOB`/`BINARY_DOUBLE` …），
   服务的是 M0 的「驱动取到了什么」，不是「规范形式对不对」。

先例是 ADR-0011 的 `batch-payload-golden.json`：黄金 fixture 落仓库、两端共用。

## 2. 覆盖全白名单，门禁只认 M1 三种

fixture **收 ADR-0003 白名单的全部七种类型**，每条用例带 `tier`：

| tier | 含义 | 类型 |
|---|---|---|
| `m1` | **门禁必须绿** | `NUMBER(p,s)` / `DATE` / `VARCHAR2` |
| `m3` | 挂起，不跑 | `TIMESTAMP` / `NVARCHAR2` / `CHAR` / `NCHAR` |

为什么全收而不是只写三种：`TIMESTAMP` 的**「固定 6 位补零」**恰好是 `NUMBER`
**「去尾零」**的反例，两条写在一起才看得出这不是自相矛盾。
为什么门禁只认三种：让 M3 的类型进 M1 的门禁，就是地图明令要挡的「顺便也把 X 考虑了」——
问一句「没有 `TIMESTAMP` 用例，链路还能不能从头走到尾」，能。

## 3. 两层，断点画在 **MySQL 之前**

| 层 | 测什么 | 依赖 |
|---|---|---|
| **纯函数层** | `canon_*` 对 fixture 的每条用例给出期望结果 | 无 |
| **台架层** | Oracle 读出 → `canon_*` → 比 fixture | Oracle 容器（`/rexec` 派到 mac） |

**不测 `→ 写 MySQL → 读回` 那一段。** 规范形式的职责终点是**「交给 sink 的那个字符串」**：
MySQL 把 `1.23` 读回成 `1.230000` 不是规范形式错了，是 ADR-0009 预检该拦的事。
把那半段算进来，套件失败时就分不清是谁的锅。

**台架层不可省**，尽管它比纯函数层贵得多。它是**唯一**能证伪
「驱动直接给出规范形式」这个假设的地方——而 ADR-0003 的全部前提都架在这句话上，
目前它只有 M0 spike 一次实测背书。

### 两层之间的不对称：为什么纯函数层测得动 `NUMBER`、却测不全 `DATE`

| 类型 | 规范化是什么操作 | 纯函数层的输入 |
|---|---|---|
| `NUMBER` | **校验**（ADR-0003：驱动输出已是规范形式，恒等变换） | 字符串——可直接手写 |
| `DATE` / `TIMESTAMP` | **格式化**（ADR-0003 明写：驱动给的是时间类型不是字符串） | 结构化时间分量 |
| `VARCHAR2` 等 | **恒等 passthrough** | 字符串 |

fixture 因此给 `DATE` 的 `input` 写成 `{y, mo, d, h, mi, s}` 而不是字符串。
代价写在明面上：**从 Oracle 时间类型到这组分量的那一步，纯函数层测不到，只有台架层测得到**。

## 4. 目标端往返值（[#13](https://github.com/liumingjian/db-qbs/issues/13)）不作断言，只作反向锚点

#13 已跑完，产出的是 **MySQL 行为事实**：`CHAR` 剥尾空格、`DECIMAL(38,0)` 把 `1.23`
静默截成 `1`、38 位整数进 `s>0` 的列报 `ERROR 1264`（`docs/spikes/0001-oracle-driver.md` §7.8）。

这些**不是规范形式的期望值**——规范形式不为 MySQL 读回值负责。fixture 里以 `note`
指向 §7.8，说明这些边界**为什么被选中**（一旦落进标度不足的列会静默变形，故预检必须拦），
但**不把 MySQL 读回值写成断言**。否则这个套件会悄悄变成预检的测试，职责糊掉。

## 5. `NULL` 那组测的是「绕过」，不是「转换」

这组用例被前面几个 ADR 掏空了大半：

- ADR-0011 §2 定 NULL 是 **JSON `null`**，与 string 在语法层就是两种东西 →
  **NULL 根本不进 `canon_*`**，没有值需要规范化。
- 台架 `03-boundary-rows.sql` 第 6 行已实测：**Oracle 把空串存成 NULL**。

于是这组剩下**一条结构性断言**：断言 NULL 走的是**不经过 `canon_*`** 的那条路、最终落成 JSON `null`。
这是整个套件里唯一一条**测「某段代码没被调用」**的用例。它保护的性质是 ADR-0011
花大力气买来的那个：NULL 与空串的区分是**语法层**的。真出错的错法是「图省事让 NULL
也走一遍 `canon_*`、返回空串」——那时 ADR-0011「攻击面在构造上归零」当场作废，
而**行数校验永远发现不了**。一行断言，护住一个 ADR 的全部前提。

**并钉死一句写进规格：M1 的源端不存在空串 `VARCHAR2` 值。任何声称测到它的用例都是假用例。**

## 6. 规格必须明文写出：本套件**不**管什么

按「越容易被误以为管了」排序：

1. **不管长度。** `VARCHAR2` 在 canon 层是恒等 passthrough，`n BYTE` 与 `n CHAR`
   的边界长度归 **ADR-0009 预检**（`VARCHAR2(n)` 下界 `n' >= n`）。
2. **不管精度是否装得下。** `NUMBER` 的 38 位上限**不进文法**——长度是类型的性质，
   不是规范形式的性质，同样归 ADR-0009。
3. **不管目标端装不装得下。** `DATE` 用例含 `0001-01-01`，而 Oracle DATE 域（公元前 4712 起）
   比 MySQL `DATETIME` 的文档域（`1000-01-01` 起）宽。
   **2026-08-13（#35）已收口**：实测公元 1–9999 在 MySQL 侧逐字节原样往返，M1 明文不拦，
   裁定见 [ADR-0009 §10](0009-m1-mapping-precheck-rules.md)。
   本套件由此**多管了一件事**——`canon_date` 的**输入**年份域断言（§11），
   但它判的是「分量合不合法」，仍然不判「目标端装不装得下」。
4. **不管线上表示。** 转义、容器形状、UTF-8 编码归 ADR-0011 与 `batch-payload-golden.json`。

## 7. `NUMBER` 的文法进规格，反例是它的见证

```
^(0|-?[1-9][0-9]*(\.[0-9]*[1-9])?|-?0\.[0-9]*[1-9])$
```

三支分别是「零」「`|x| ≥ 1`」「`|x| < 1`」。`-0` 与 `0.000` 落不进任何一支，故必被拒。

**为什么是文法而不只是反例清单**：只给清单的话，实现者写出的正则只要能拒掉那几条就算过，
而**清单永远不完备**——漏掉的形状被静默放行，正是 ADR-0003 最怕的那种错（在下游远处爆）。
文法进规格，清单就从「验收标准」降级为「读得懂的例子」，两者的关系反过来才对。

反例里有两条不是想象出来的畸形串，是**真实存在的驱动/会话配置能产出的东西**，
它们就是「驱动漂移」四个字的具体含义：

| 反例 | 它从哪来 |
|---|---|
| `1,23` | `NLS_NUMERIC_CHARACTERS` 漂移。台架 `03-boundary-rows.sql` 显式 `ALTER SESSION` 设了 `'.,'`，**生产会话未必** |
| `1E5` / `1.5E+10` | 科学计数法，驱动/会话配置可产出 |
| `.5` | `TO_CHAR` 显示层形态。**在真链路上出现即说明有人绕道 `TO_CHAR` 取值**（ADR-0003 明写不经过 `TO_CHAR`）——报错报得比什么都对 |

`DATE`/`TIMESTAMP` 也有正则，但**角色相反**：`NUMBER` 的正则是**输入的门**，
`DATE` 的正则只是**输出的断言**，真正要测的是闰日 / 世纪边界 / 值域两端这些**语义**边界。

## 8. CI：纯函数层开第一条流水线，台架层明确不进

仓库现在**没有任何 CI**。本 ADR 要么开第一条，要么明写不开——两层的答案不同：

| 层 | 进 CI？ | 为什么 |
|---|---|---|
| 纯函数层 | **是**。开本仓库第一条流水线，就一条 `cargo test` | 零依赖 |
| 台架层 | **否，结构性跑不了** | 要 amd64 模拟的 Oracle XE + arm64 原生 Instant Client，跑在开发者 mac 上（`/rexec`）。ADR-0005 已说清模拟层压在哪一侧 |

台架层改判为**带触发条件的手工门禁**，三条触发条件一并钉死（不能是「以后再说」）：

1. **M1 验收时必跑一次。**
2. **任何改动 `canon_*`、Oracle 驱动版本、或 NLS / 字符集相关配置的变更，合并前必跑一次。**
3. **每次跑完贴实际值进 spike 文档，不是贴「通过」**——照
   [#13](https://github.com/liumingjian/db-qbs/issues/13) 的先例
   （`run-mysql-roundtrip-probe.sh`，可重复，5 秒跑完）。
4. **M2 验收时必跑一次**（2026-08-15 增补，[#59](https://github.com/liumingjian/db-qbs/issues/59) /
   [ADR-0028 §3.3](0028-m2-acceptance-criteria-and-rig-extension.md)）。M2 在这一层多挂一条
   新门禁 **G1**（建表 SQL 生成器 ↔ 映射预检不漂移的台架侧第二遍：真建表、真 `describe`、真跑预检），
   与本节的 `run-canon-gate.sh` 共用这套触发条件，**不新开第二套机制**。

**为什么不硬塞进 CI**：把跑不了的东西写进流水线，等于让它长期红着或长期被跳过，
两种都比诚实地写「这层靠人 + 靠触发条件」更糟。

## 9. 台架侧的落点：新写一个 spike 程序，不动 `spike-odpi`

`t_canon_expected` **留着但降级为 M0 历史产物**，M1 的新程序不碰它、更不由 fixture 反向生成。
理由：它现在还承担着 `spike-odpi` 的判定（`judge` 靠 `note` 里的 `V1 排除` 前缀分流），
删或改等于回头动一个已跑通的 spike——**换不到任何 M1 的收益**。

新断言**另起一个 spike 程序**，不扩 `spike-odpi`：后者的职责是「驱动取到了什么」，
新程序的职责是「取到的东西合不合规范形式」，**两者的失败含义完全不同**，
混在一起会让 M0 那个 `FAIL 0` 的结论失去意义。

## 10. fixture 怎么进测试

`include_str!` 编译期嵌入 + `serde` 反序列化。**不上 `build.rs` 代码生成**——
抓大放小，且嵌入后测试不依赖运行目录。

## 11. `canon_date` 的年份域断言（2026-08-13 增补，[#35](https://github.com/liumingjian/db-qbs/issues/35)）

> **⚠️ 本节「它买不到公元前检测」那部分已由文末「§11 增补（2026-08-16，[#99](https://github.com/liumingjian/db-qbs/issues/99)）」订正**：
> 驱动实测给**负年**，这条断言**就是**纪元丢失的防线。删改它等于重开 #99 的判定。

`canon_date` 除格式化外**多一条输入断言**：`1 <= year <= 9999`，不满足即报错，
**不得静默修正、不得取模、不得钳位**。fixture 里三条 `kind = "format"` 且
`verdict = "reject"` 的用例（`date-reject-year-zero` / `date-reject-year-negative` /
`date-reject-year-overflow`）是它的见证。

**这打破了 §7 那句「`DATE` 的正则只是输出的断言，不是输入的门」吗？不打破，但要说清边界**：
`NUMBER` 的门是**文法**（输入是字符串，形状本身就是被测对象）；`DATE` 的输入是**时间分量**，
形状由类型系统保证，这条断言判的**只有值域**，不判形状。**加一条域断言 ≠ 把 `DATE` 改成校验型。**

**为什么值得加**：它是**纯函数层**的（零环境依赖、进 §8 那条流水线、CI 里天天跑），
成本近乎为零，买到的是「驱动给出带符号的年时，在源端就炸，而不是靠 MySQL 的
`ERROR 1292` 在链路末端炸」——错误发生的位置离原因更近。

**必须同时写明它买不到什么**（否则它会被误当成公元前日期的防线）：
**年份 `4712` 是合法值，断言放行。** 若驱动对公元前日期丢掉纪元，
「公元前 4712-01-01」会变成合法的 `4712-01-01` 一路搬到底，
[ADR-0006](0006-row-count-only-verification.md) 静默清单第七行记的就是它，**防线栏是空的**。
裁定与缺口记在 [ADR-0009 §10](0009-m1-mapping-precheck-rules.md)。

## 已知代价

1. **纯函数层测不到「Oracle 时间类型 → 时间分量」那一步**（§3），它只有台架层覆盖，
   而台架层不在 CI 里——这一段的回归防护**依赖人守住 §8 那三条触发条件**。
2. **反例清单不完备是设计如此**（§7）。清单只是文法的见证；文法错了，清单挡不住。
3. ~~**§11 的年份域断言会被误当成公元前日期的防线**，而它不是（`4712` 是合法年份）。~~
   **已订正（2026-08-16，#99）**：它**就是**那道防线（驱动给负年，实测见 spike §7.12）。
   要防的误读因此反转——从「误以为已解决」变成「误以为这个检查可删」。详见文末 §11 增补。
4. **`m3` 的四种类型有 fixture 但无人跑**，M3 启动时它们可能已经和实现漂移。
5. **`ZHS16GBK` 路径测不到**（ADR-0005 上线前复验第 3 项）。fixture 里的中文用例走的是
   台架的 `AL32UTF8` 路径。

## 对既有 ADR 的影响

- **ADR-0003**：「必须有专门的、覆盖边界值的测试套件」这句由本 ADR 兑现；
  `canon_number` 的 `RE_CANON` 由 §7 给出具体文法。
- **ADR-0009**：本 ADR §6 明确把长度 / 精度 / 值域三件事**推给**预检，不与之重叠。
  §11（#35 增补）是唯一的例外，且不构成重叠：它判的是 `canon_date` 的**输入分量**合不合法，
  预检判的是**列元数据**——预检结构性看不见值，这条断言结构性看不见列。
- **ADR-0005**：§8 是「台架不进 CI」的第一次正式表述，与 ADR-0005 的效力划线同源。

## §11 增补（2026-08-16，[#99](https://github.com/liumingjian/db-qbs/issues/99)）：年份域断言语义升格——它就是纪元丢失的防线

**§11 原文三处写明「这条断言买不到公元前检测」，那三处基于一个未验证前提，现已被实测推翻。**

[#98](https://github.com/liumingjian/db-qbs/issues/98) 走生产同款取数路径实测（spike §7.12）：
**Oracle 驱动对公元前日期给负年**（`-4712` / `-1` / `-44`，`Timestamp::year()` 与 `to_string()`
都带负号），**不是正年**。因此 §11 设想的「公元前 4712 会变成合法的 `4712-01-01` 一路搬到底」
**在这套驱动上根本产不出来**——负年直接撞上 `1 <= year <= 9999`，当场
`Err(CanonError::InvalidDate)`，走 `SourceReadError`（`FailureKind::SOURCE_VALUE`，带列名与原值）
→ 整 run 失败，目标表不动。

### 语义升格：这条断言是**防线**，不是防御性编程

§11 原文把它的收益写成「错误发生的位置离原因更近」——一个**成本近乎为零的锦上添花**。
实测之后它的地位变了：

> **`canon_date` 的 `1 <= year <= 9999` 是 V1 唯一挡住「Oracle 公元前日期搬进 MySQL」的东西。**
> 它上游没有预检（预检看列元数据、看不见值，且 [ADR-0009 §10 增补](0009-m1-mapping-precheck-rules.md)
> 已裁定**不**为它开预检扫描），下游没有兜底（V1 无行 checksum，ADR-0006；
> MySQL 的 `ERROR 1292` 挡的是格式化后仍越界的，挡不住格式化成合法值的）。

**删掉或放宽这条断言 = 重开 [#99](https://github.com/liumingjian/db-qbs/issues/99) 的判定，
不是一次重构自由。** 后来者读 `canon_date` 时若觉得「这个检查多余、类型系统已经保证了」——
类型系统保证的是 `i32`，保证不了纪元。三条 `verdict = "reject"` 的 fixture 用例
（`date-reject-year-zero` / `date-reject-year-negative` / `date-reject-year-overflow`）
是它的见证，**其中 `date-reject-year-negative` 现在有了生产语义**：它见证的不再是
「驱动理论上可能给负数」，而是**公元前日期在生产路径上的实际形态**。

### 订正原文三处

| §11 原文 | 订正 |
|---|---|
| 「**必须同时写明它买不到什么**……年份 `4712` 是合法值，断言放行」 | 前提是「驱动丢纪元给正年」，**实测不成立**。驱动给负年，断言拦住。`4712` 确实合法，但公元前 4712 到不了 `canon_date` 的正年那一支 |
| 「已知代价 3：§11 的年份域断言会被误当成公元前日期的防线，而它不是」 | **反过来了**：它**就是**那道防线。要防的误读从「误以为已解决」变成「误以为可删」 |
| 「留下的尾巴是公元前日期丢纪元这条静默路径（ADR-0006 静默清单第七行，无防线）」 | 第七行已由 [ADR-0006 增补三](0006-count-only-verification-in-v1.md) **撤销**，尾巴收掉 |

### 文案改动（本增补唯一的代码影响）

`CanonError::InvalidDate` 的 `Display` 改为
`invalid DATE components: year must be within 0001..9999 (Oracle BC dates are not supported)`，
理由与它的不精确处见 [ADR-0009 §10 增补](0009-m1-mapping-precheck-rules.md) 第 3 条。
**`CanonError` 的变体不拆**——变体是本套件断言的形状，为一句人话动它不划算。
