# ADR-0012: run 生命周期——权威状态只在 source 且只在内存，sink 只持有资源终态墓碑

**状态**: 已接受
**日期**: 2026-08-13
**关联**: [ADR-0002](0002-staging-table-atomic-swap.md)（封口点、暂存表处置）、
[ADR-0007](0007-single-query-streaming-fetch.md)（批次序号是位置感锚点）、
[ADR-0008](0008-business-date-predicate-generation.md)（半开区间谓词 → 重跑幂等）、
[ADR-0010](0010-http-protocol-contract.md)（协议契约——本 ADR 订正它 §7.1 与 `GET` 两处）、
[#28](https://github.com/liumingjian/db-qbs/issues/28)

## 背景

`CONTEXT.md` 说「运行有唯一 `run_id`、一个钉死的业务日期、和**一份状态**」，
但状态集合与合法迁移从未定义。协议里有「查状态」这个动作，查的是什么答不上来。

ADR-0010 已经把这张图的一半提前定掉了：commit 同步、`retry = 0`、abort 幂等、
`GET` 明写「不是 run 的权威状态」、非常规时序七行响应矩阵。
**本 ADR 只答剩下的四件事**：权威在哪、重启认不认、状态集合多粗、以及 ADR-0010 §时效
点名留给本票的那条——`GET` 的 404 现在同时表示三件事，这个歧义留不留。

## 决策

### 1. 权威 run 状态只有一份，在 source

「source 侧、sink 侧，还是两侧各一份」这个问法本身要拆开：**两侧持有的不是同一种东西**。

- **source 持有 run 状态**：这个 run 走到哪一步了。**它是权威，且是唯一的一份。**
- **sink 持有的是暂存表的资源生命周期**（不存在 / 可写 / 已封口 / 已销毁），
  **不是 run 状态**。它是 source 状态的**投影**，不是副本。

把后者也叫「run 状态」，才会产生「两份状态不一致」这个伪问题。
ADR-0010 `GET` 那句「尽力而为的内存快照，不是 run 的权威状态」由此升格为明文规则：
**任何时候问「这个 run 现在怎么样」，答案的唯一来源是 source 的进程内状态与它的日志。**

于是「source 认为失败、sink 认为还在推」这类不一致**在语义上不存在**——
sink 从来就不「认为」run 处于什么状态，它只知道那张表还在不在、还能不能写。

### 2. 状态纯进程内存，一个字节都不落盘

source 进程一死，run 就**不存在**了；重跑 = 新 `run_id` 从头（`CONTEXT.md` 早已如此定义重跑）。

不落状态文件的理由：M1「失败即整 run 失败」下，落盘状态**唯一的用途是事后取证**，
而这个用途日志已经全额覆盖（`run_id` + 批次序号是 ADR-0007 定的位置感锚点）。
落盘反而要正面回答「重启后看到一个 `STREAMING` 的残留 run 该怎么办」——
**那是续传语义的第一块砖**，而续传在 M2 之后（[#15](https://github.com/liumingjian/db-qbs/issues/15)）。

**代价明写**：source 被 kill 后，目标库可能留一张孤儿暂存表且无人知道它属于哪次运行，
只能靠表名里的 14 位时间戳判年龄——这笔账 ADR-0002 增补已明码标价，本 ADR 不新增。

**这一条直接决定「kill 源端后重跑结果一致」的验收怎么做**：被 kill 的 run **没有状态可查**，
验收判据只能落在目标表上——目标表在 kill 之后**未被触碰**（除非 kill 发生在 `COMMITTING` 中），
重跑一条新 `run_id` 之后目标表当天数据与不 kill 直接跑一次完全一致。

### 3. 状态集合：source 侧五个，按「进程正在做什么」命名

```
PREPARING    describe + 日期谓词检查 + POST /runs（预检 + 建暂存表）
STREAMING    fetch 循环 + POST /batches
COMMITTING   POST /commit 阻塞中
SUCCEEDED    commit 返回 200
FAILED       任何一步失败
```

命名按「进程正在做什么」而不是「数据处于什么阶段」，因为 **commit 同步（ADR-0010 §4）
意味着封口、校验、切换在 source 眼里是同一个 HTTP 请求内不可分的一段**——
source 根本观察不到「已封口待校验」与「校验失败」的区别，它只看到 commit 返回了什么。
给观察不到的东西起名字，是给「状态与实际不符」开门。

**「校验失败」不是状态，是 `FAILED` 的一个 `code`（`VERIFY_FAILED`）。**
ADR-0010 §7 的十码闭集已经把失败原因表达完整了，再让状态集合表达一遍
就是**两套词汇描述同一件事**，早晚漂移。

**`ABORTED` 同样不是状态。** abort 是 `FAILED` 路径上的一个清理动作
（ADR-0010 §6：它「不改变这个 run 已经失败的事实」）。给它状态名等于承认存在
「失败但没清理」与「失败且清理了」两种终态，而这个区别对使用者零价值。

```
        ┌──────────┐  POST /runs 200   ┌───────────┐  POST /commit  ┌────────────┐ 200 ┌───────────┐
  ●────▶│PREPARING │──────────────────▶│ STREAMING │───────────────▶│ COMMITTING │────▶│ SUCCEEDED │
        └────┬─────┘                   └─────┬─────┘                └──────┬─────┘     └───────────┘
             │ 任何失败                       │ 任何失败                    │ 任何失败
             ▼           ┌────────┐          ▼                             ▼
             └──────────▶│ FAILED │◀─────────┘─────────────────────────────┘
                         └────────┘
             建表成功后失败 → 发 abort ┘        发 abort ┘      §6：永不发 abort
```

### 4. 非法迁移：source 侧一律降级为断言，不进协议

ADR-0010 §7.1 那七行覆盖的全是 **sink 侧收到的非法请求**（封口后收批次、已切换后再 commit、
未开任务就推批次……），本 ADR 一条不改、一条不加。

source 侧的非法时序在**单进程线性脚本**里根本构造不出来，因此
**一律降级为 `debug_assert!`，不做运行时处理、不进协议、不占错误码**。
定位与 ADR-0010 §5 对 `seq` 双向断言完全一致：**触发即缺陷，不是故障。**

**本 ADR 不新增任何错误码。**

### 5. 墓碑：消掉 `GET` 的 404 三义

ADR-0010 现状下 404 `RUN_UNKNOWN` 同时表示三件事：sink 重启了 / `run_id` 打错了 /
**切换成功后 sink 主动忘掉了它**（§7.1 第五行）。

要命的场景：**commit 连接在 30 分钟里断了**，source 不知道切换到底成没成，
去 `GET` 一问——得到 404，**答案是「不知道」**。

**决策：sink 为终态 run 保留内存墓碑。** 切换成功 / 校验失败 / 切换失败 / abort 之后，
sink 不再「忘掉」`run_id`，而留一条记录。

**墓碑记的是资源终态，不是 run 状态**（否则第 1 节立刻自相矛盾），两个值：

| `terminal` | 含义 |
| --- | --- |
| `SWAPPED` | 切换事务已提交，暂存表已 DROP。**目标表已是新数据** |
| `DISCARDED` | 暂存表已丢弃，**目标表未被触碰** |

校验失败、切换失败、abort 三条路径**全部归 `DISCARDED`**——
对提问者唯一有价值的区别是**「目标表动没动」**，而这恰好是这两个值的分界。
失败的**原因**归错误码，不归墓碑（同第 3 节的理由）。

```json
← 200 { "run_id": "…", "staging_table": "…", "terminal": "SWAPPED",
        "batches_received": 20, "rows_written": 100000, "sealed": true,
        "purged_rows": 82345, "swapped_rows": 100000 }
```

活着的 run 照旧回 ADR-0010 §GET 的原形状；**`terminal` 字段缺席即代表「还活着」**。

**淘汰纯 FIFO，32 条写死不可配**——与 ADR-0007 的 5000 行、ADR-0010 的超时表同一态度。
被淘汰后回 404，**退化成今天的行为，不是故障**。sink 重启后墓碑全丢，同样回 404，同样不是故障。

#### 5.1 对 ADR-0010 §7.1 的订正

| 情形 | ADR-0010 原文 | 本 ADR |
| --- | --- | --- |
| commit → 已 commit 的 run | 404 `RUN_UNKNOWN` | **409 `RUN_SEALED`，`details` 带墓碑** |
| `GET` → 已终结的 run | 404 `RUN_UNKNOWN` | **200 带 `terminal`** |
| 批次 → 已 abort 的 run | 404 `RUN_UNKNOWN` | **不变**——那条 404 是**故意**的语义等价（「abort 后等价于从不认识」），墓碑不推翻它 |

#### 5.2 被拒的方案：不做墓碑，靠重跑幂等兜住

按 ADR-0008 的半开区间清除条件，重跑同一业务日期对目标表确实幂等，
所以「不知道切换成没成，那就重跑一次」在结果上是安全的。

**拒绝理由：那是碰巧幂等，不该被当成设计依据。** 幂等此前从未作为契约声明过，
一旦有人改动清除条件的形状（M2 的非 DAY 粒度就在门外），这条隐式依赖会无声失效。
把它换成一个 32 条的内存 map，是极便宜的价钱。

### 6. commit 已发出之后，source 永久放弃 abort 权

abort **只在 `PREPARING`（建表成功之后）与 `STREAMING` 的失败路径上发**。
一旦进入 `COMMITTING`，无论结局如何，source **不再发 abort**。

理由是 ADR-0002 的封口点：**commit 发出的那一刻，暂存表的处置权整体移交给 sink**——
成功则 sink 自己 DROP，失败也是 sink 自己 DROP（ADR-0002「✗ 失败 → DROP staging」），
**两条路 sink 都会清理**。此时 source 再发 abort，是拿一个 `DROP TABLE`
去追一个可能正在提交的切换事务，纯制造竞态。

**代价**：sink 在切换途中崩溃这一种情形下，暂存表变成孤儿，手工清——
ADR-0002 增补已明码标价的那笔账，不新增。

### 7. commit 连接断掉之后：自动查一次，只进日志

墓碑使这个动作有了意义。**source 自动发一次 `GET`，但结果只进日志、不改变结局。**

这个 run 无论如何都是 `FAILED`（`retry = 0` 不允许它变成别的）。`GET` 唯一的产出是那行人话：

> 目标端报告该 run 已切换成功（`swapped_rows=100000`），**目标表已是新数据，重跑前请先确认**

对上

> 目标端报告暂存表已丢弃，目标表未被触碰，**可直接重跑**

**这一步失败（连不上、404、已被淘汰）不重试、不升级错误、不改变 `FAILED`**——
它是诊断，不是恢复。查不到就照实说「无法确定目标表是否已被切换」。

## 后果

**买到的**：`CONTEXT.md` 里那句悬空的「一份状态」有了确切所指；
「两端状态不一致」被证明是伪问题而不是被容忍的风险；
commit 超时这个 M1 最难受的窗口从「答案是不知道」变成「有一个确定答案可问」；
「kill 源端后重跑结果一致」的验收判据有了落点（落在目标表上，不落在状态上）。

**付出的**：

- **source 进程一死，run 的一切都没了**（§2）——含孤儿暂存表无人认领。
- **sink 多了一块内存状态**（§5）。虽只有 32 条，但它是 M1「无状态存储」这句话的第一个例外，
  必须写在明处：**它是诊断缓存，不是状态存储**——丢了不影响任何正确性，只影响可诊断性。
- **ADR-0010 §7.1 两行被订正**（§5.1），实现时以本 ADR 为准。
- **sink 崩在切换途中 → 暂存表孤儿**（§6），且此时墓碑也随进程一起没了，
  这是 M1 唯一一处「目标表状态与所有记录都对不上」的窗口，只能靠人查目标表当天行数判断。

## 时效

M1 定稿。最可能触发复审的两条：**续传模型进来时**（#15，M2 之后）——
§2 的「不落盘」是它的第一块绊脚石，届时整节重写；
**非 DAY 粒度进来时**（M2）——§5.2 拒绝的那条隐式幂等依赖会正式失效，
届时要确认墓碑没有被谁当成幂等的替代品用。
