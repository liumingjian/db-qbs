# ADR-0034: 第一版范围由客户实际需求定，通用化留待后续扩展

**状态**: 已接受
**日期**: 2026-08-18

## 背景

[ADR-0005 的 2026-08-16 增补](0005-local-rig-as-v1-verification-baseline.md#台架是通用工具的正当基准不是拿不到客户环境的退路2026-08-16-增补95)
（起因 [#95](https://github.com/liumingjian/db-qbs/issues/95)）把定位钉成：

> db-qbs 是通用离线数据库导入方案；任何具体客户环境都是**一个部署**，不是设计基准。
> 某个部署的数据分布只是**优先级输入**，缺了它不阻塞任何设计决策。

**那次订正解决的是一个真问题**：当时我把「客户生产库类型直方图」当成 M3 扩类型的**必要前置**，
拿不到就停工。用一份拿不到的样本去阻塞一个能自行判定的设计决策，这确实是范畴错误。

**但那句话被推过了头。** 它从「分布不能**阻塞**决策」滑成了「客户需求不能决定**做什么**」——
于是 [#93](https://github.com/liumingjian/db-qbs/issues/93)（数据源管理）判成「排在 M3/M4 之后」、
[#100](https://github.com/liumingjian/db-qbs/issues/100)（列名映射）判成「不做，用 `AS` 别名兜住」，
两条都是**拿通用性论证去否掉客户点名要的能力**。

2026-08-18 用户改判，原话：

> 这个通用的工具它也是基于用户的需求的。那么第一个版本就是要先从用户需求出发，
> 后续如果有其他的，再考虑扩展或者定制。

## 决策

**第一版的范围由客户实际需求定。客户需求可以决定「做什么、先做什么」，不再只是优先级输入。**

客户没有的形态，第一版**允许不做**；客户点名要的能力，**不得以「通用工具不该按一个部署判」为由推迟**。
通用化不是被放弃，是被排到第一版之后：**先按需求闭环，再按类型面外扩。**

### 1. 三条边界——改判不是空白支票

**a. 收窄必须显式落 ADR。** 不能靠「客户没有这种数据」在票正文里悄悄生效。
读代码的人要能从 `docs/adr/` 查到「这一条为什么不做」，而不是从某张已关闭的票的第七段。

**b. 撤掉的防线若挡的是静默改值，撤防线要单独写明失效模式。**
「当场炸」的防线撤了，用户会立刻知道；「静默改值」的防线撤了，数据已经错了、没人知道。
这两者不同价。第一版已知的静默面（撤之前必须逐条点名）：

- [ADR-0030](0030-m3-type-whitelist.md) §1 **形态 1/2**（`NUMBER` 纯小数 / 目标标度写小）——
  MySQL 给 `Note 1265` **不是错误**，`±0.000001` 塌成 `0.0000`，连符号一起丢。
- ADR-0030 §1 **形态 9**（`TIMESTAMP` 小数秒被舍）——一条 Note 都没有。

对照：形态 3（整数位不足，`ERROR 1264`）与字符族超长（`ERROR 1406`）**是当场炸**，
「写不进去自然报错」只对这两类成立，不能推广到全部。

**c. 台架仍是正当验证环境，不是退路。** ADR-0005 2026-08-16 增补的这一条**不撤**（见 §3）。
「按客户需求定范围」管的是**做什么**，不管**拿什么证**——证据面仍是本地台架 + 目标端往返实测。

### 2. 第一版据此生效的范围变更

| 变更 | 推翻了什么 | 承载点 |
|---|---|---|
| 不做自动建表（目标表与索引用户手工预建） | 无（既成事实立成禁令） | [ADR-0033](0033-char-length-byte-semantics.md) §4 |
| 数据源管理（Oracle + MySQL）进第一版 | [#93](https://github.com/liumingjian/db-qbs/issues/93)「排在 M3/M4 之后」 | 第一版地图 |
| 字段映射 / 用户可填筛选条件 / 目标字段选择进第一版 | [#100](https://github.com/liumingjian/db-qbs/issues/100)「不做映射表」 | 第一版地图 |
| 主键与 upsert 进第一版 | 现行「按业务日期区间整段重刷」的幂等前提 | 第一版地图（单独 ADR） |
| 精度判定按最小匹配度，深化留后续 | 无（ADR-0030/0031 判定式暂不动） | 第一版地图 |
| 鉴权**不**进第一版 | 无（V1 非目标，维持） | 本 ADR |

**「10 万行 / 约 100MB 单次导入」是验收目标，不是缺陷票。** 那个痛点来自客户在用的旧系统，
不是 db-qbs 的现存缺陷——db-qbs 的搬运路径本就是流式（`transfer.rs`，逐行取、攒满即推）。
第一版要做的是**证明**它不重蹈覆辙，不是修一个还不存在的 bug。

### 3. 与 ADR-0005 2026-08-16 增补的效力划线

那份增补有四条「后果」，**只有第一条被本 ADR 改**：

- **后果一（类型白名单按类型面判，不按命中分布判）**——**改**。
  「分布是一份样本，不能阻塞决策」这半句**继续成立**；
  「客户需求只是优先级输入、不能决定做什么」这半句**由本 ADR 推翻**。
  注意本 ADR **不动任何已定的判定式**：ADR-0030 的九行形态、ADR-0031 的下界式原样有效。
  改的是**范围怎么定**，不是**已定的东西对不对**。
- **后果二（台架四类可信度表划的是别的线）**——维持。
- **后果三（「已知代价」第 3 条降级为部署风险）**——维持。
- **后果四（上线前清单升格为部署前检查单）**——维持。

增补的标题命题「**台架是通用工具的正当基准，不是拿不到客户环境的退路**」——维持，一字不撤。

## 后果

- **需要跟着订正的正文四处**（本 ADR 落盘时一并改）：`CONTEXT.md` 抬头定位段、
  `docs/STRATEGY-V1.md`「一句话」与「成功标准」抬头、ADR-0005 2026-08-16 增补（加指针，正文不删）、
  M3 地图 [#94](https://github.com/liumingjian/db-qbs/issues/94) 收窄第 4/5 条（以评论订正，正文不改——已关闭的图是历史）。
- **#93 与 #100 的裁定作废**，两条能力重新进第一版范围。原票已 CLOSED，不复活，
  在第一版地图下重新开票，票正文写明「推翻 #93 / #100」。
- **通用化的账没有勾销，只是挪后**：白名单外的类型、多部署形态、鉴权，全部留到第一版之后。
  按需求收窄的每一处，都在本 ADR §2 的表里留着账。

## 时效

**第二版重估。** 触发重估的信号：第一个部署上线后出现第二个部署，
或客户提出与现有需求形状不同的要求——那时「按一个客户的需求定范围」这条就该退役，
换回按类型面与形态面定范围。**退回属正常演进，不是打脸**：本 ADR 只声明第一版怎么定范围，
不声明这是长期形态。
