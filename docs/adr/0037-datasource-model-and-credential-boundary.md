# ADR-0037: 数据源进 source 侧 SQLite，目标端凭据随运行请求过线；静态加密、过线明文

**状态**: 已接受
**日期**: 2026-08-19
**来源**: [#118](https://github.com/liumingjian/db-qbs/issues/118)（地图 [#117](https://github.com/liumingjian/db-qbs/issues/117)）
**关联**: [ADR-0021](0021-m2-log-collection-boundary.md)（**§1 的主机边界由本 ADR §1 改写：凭据成为第二类过线内容**）、
[ADR-0024](0024-m2-unauthenticated-inbound-exposure.md)（**§2 的负面条款由本 ADR §5 判废一半、§6 的重开条件 2/3 由本 ADR §5 触发并显式挂账**）、

[ADR-0036](0036-task-spec-structured.md)（结构化规格是任务定义的唯一真相源；**本 ADR §8 判定数据源绑定不进规格**）、
[ADR-0034](0034-v1-scope-from-customer-needs.md)（§1 要求收窄与丢弃显式记账）、
[ADR-0010](0010-http-protocol-contract.md)（错误码闭集**不增**，见 §9）、
[ADR-0027](0027-target-ddl-generation-and-cross-end-metadata.md)（§3 的封条由本 ADR §9 开一道口子，取列端点归 [#120](https://github.com/liumingjian/db-qbs/issues/120)）

## 背景

客户点名要「在 UI 里管 Oracle + MySQL 两种数据源」。[ADR-0034](0034-v1-scope-from-customer-needs.md) §2
已作废 [#93](https://github.com/liumingjian/db-qbs/issues/93)（数据源管理排到 M3/M4 之后）那条裁定，
地图 #117 的收窄 1 又把它与鉴权**解绑**：只做最小档管理，鉴权整块不进第一版。

于是剩下一个真问题，而且它决定数据模型长什么样：**MySQL 那一侧的凭据放在哪一端？**

现状是**一个数据源一份 config 一个进程**：`source.toml` 一份 Oracle 凭据 + 一个 `sink_base_url`，
`sink.toml` 一份 `mysql_dsn` + `database`。`CONTEXT.md` 明写「`sink` 不感知 Oracle，
`source` 不持有 MySQL 连接」。**Web UI 在 source 端**——要在 UI 里增删改 MySQL 数据源，
这条不对称必然被顶开。

#118 摆了三个选项：(a) source 存两类数据源、MySQL 凭据随运行请求过线；
(b) source 只管 sink 端点、凭据仍留 `sink.toml`；(c) sink 侧存多份连接、source 传 id 引用。

## 决策

### 1. 选 (a)：数据源统一存 source 侧 SQLite，MySQL 凭据随运行请求过线给 sink

> **source 侧的 SQLite 是两类数据源的唯一真相源。** 发起运行时，source 从库里读出目标端
> 连接信息，随 `POST /v1/runs` 的请求体一起交给 sink；**sink 用调用方给的凭据建连接，
> 不再持有自己的那一份**。

**否掉 (b) 的致命处**：它把「换一个 MySQL 库」变成「多部署一个 sink 进程」。客户要的是
在 UI 里管数据源，(b) 兑现的是「在 UI 里管 sink 端点」——名字对上了，能力没对上。
第一版买的是链路闭环，不是把一次配置改动降级成一次运维动作。

**否掉 (c) 的致命处**：sink 今天**连 UI 都没有**。要在界面上增删改 sink 侧的连接，
要么做不到（改对端的 toml），要么得给 sink 新开一整套管理端点——那只是把暴露面搬家，
而且搬到了握着 `DELETE`/`DROP` 的那一端，工作量还最大。

**这条改写 [ADR-0021](0021-m2-log-collection-boundary.md) §1 的主机边界。**
原文只画了一类过线内容（业务数据值——不许出主机），凭据根本不在讨论范围内，
因为当时它压根不流动。现在它流动了：

> **业务数据值仍不出主机**（ADR-0021 §1 不撤销）。**新增第二类过线内容：目标端凭据。**
> 它从 source 主机出发，沿既有的 source → sink 单向 HTTP 通道，只到 sink 主机为止。
> 除此之外**没有第二条流出路径**——`/api/*` 不回读口令（§5），日志不打口令，历史不存口令。

### 2. sink 不再持有目标端凭据：连接按 run 建，`sink.toml` 的两个字段退役

`sink.toml` 的 `mysql_dsn` / `database` **退役**。留着它们就是留两个真相源，
而「以哪份为准」这个问题没有便宜答案。处置：

- 两个字段改成**可选且被忽略**，启动时若仍存在，打一条 `warn` 说明它已退役。
  **不做成硬报错**——现存部署与三份验收台架都还带着它，硬报错换来的只是一次无谓的中断。
- sink 启动**不再连 MySQL**。开连接从「进程启动一次」变成「每个 run 开一次」，
  连不上的失败点从启动挪到 `POST /v1/runs`。
- `database` 从进程级配置变成**每个 run 各自的**，随请求过来。
  暂存表 DDL 里那个库名限定（`build_staging_ddl`）随之改成按 run 取值。

**开连接仪式（`SET NAMES utf8mb4` / `sql_mode` / `max_allowed_packet` 三项回读）
一个字不改**，只是每个 run 各跑一遍。它本来就是每条连接跑一遍的，不是启动跑一遍的。

### 3. 静态存储不再明文：本地密钥文件 + AEAD，威胁模型写死

所有者裁定：**口令不明文落盘。** 具体形态：

> 数据源条目里的口令字段用 **ChaCha20-Poly1305** 加密后存进 SQLite，
> 每次加密取一个随机 96-bit nonce，密文与 nonce 一起以十六进制存在同一字段里。
> 密钥是 32 字节随机数，存在 `data_dir/datasource.key`，权限 `0600`，首次启动时生成。

**这条防的是什么、不防什么，必须写死，否则它会被当成一句「已加密」而被高估：**

- **防**：SQLite 库文件**离开本机**之后的裸读——备份、快照、误发一份 `db-qbs.sqlite3` 出去、
  运维在别处打开它看一眼。这条路径今天是真实存在的（历史 SQLite 已被备份是常见运维动作）。
- **不防**：拿到 `data_dir` 读权限的人。密钥就在**同一个目录**里，同样 0600。
  对这类攻击者，加密只是多一步 `xor`，**不构成防线**。
- **不防**：`listen` 端口本身。ADR-0024 §1 的权限等价一字不变——能连上 source 端口的人
  仍等价于持有全部数据源的权限，因为他能直接发起运行。

**否掉「密钥交由部署者从环境变量/外部 KMS 提供」**：它把「能不能开机」绑到一件部署者
必须先理解的事上，而第一版连鉴权都没有——用一套真密钥管理去守一个端口全开的服务，
是把成本花在防线最厚的地方。**这条留时效**：真要引入鉴权时，密钥来源与它一并重估。

[ADR-0016](0016-task-definition-form.md) §8「凭据明文、靠文件权限兜底」因此**部分退役**：
配置文件里的凭据（`sink_base_url` 之外已无凭据；`source.toml` 的 Oracle 字段见 §10）仍按原样，
但**数据源库里的口令不再明文**。§8 的兜底理由（ADR-0024 §2/§7 改写过的那版：
「端口已等价于凭据权限，加一层不改变暴露面」）**在端口这一侧仍然成立**——
§3 加的这一层守的是**另一条路径**（文件离开本机），两者不互相抵消，也不互相替代。

### 4. 过线是明文 HTTP——这是本裁定最贵的一格，写成部署前提

`sink_base_url` 今天只收 `http`（`HttpSinkClient::new` 硬拒非 http），ureq 编译时连 TLS
特性都没开。于是 §1 的结论展开成一句必须说出口的话：

> **目标端 MySQL 口令以明文穿过 source → sink 的 HTTP 通道。**
> 而 `CONTEXT.md` 明写这两个进程「跨互联网通信」。

**第一版不修，取最便宜的收尾**（地图 #117 主方向）。**代价写成部署前提，与 ADR-0024 §4 同档：**

> **`sink_base_url` 指向的通道必须是可信的**：同主机、可信内网，或部署者自建的 TLS/隧道。
> 把 sink 直接暴露在互联网上并让 source 跨公网连它，在本版**等于把 MySQL 口令发到公网上**。
> 产品对此**零感知、零校验**——它不会检测你有没有隧道，也不会因为你有而放宽任何内部约束。

**为什么不顺手支持 https**：那要给 ureq 开 TLS 特性（rustls 一整条依赖链），
且 sink 侧 `tiny_http` 不终止 TLS，实际仍要部署者在前面放反代——
**真正解决问题的是那个反代，不是客户端的 scheme 检查**。第一版把这条写进部署前提即可，
`scheme` 放开留时效。

### 5. ADR-0024 §6 的重开条件 2 与 3 已经触发——逐条作答，仍不做鉴权，账记在这里

[ADR-0024](0024-m2-unauthenticated-inbound-exposure.md) §6 写了三条可判断的重开条件，
任一成立「**必须真的引入鉴权**」。本 ADR 触发了其中两条，**必须点名，不许滑过去**：

| §6 条件 | 是否触发 | 作答 |
|---|---|---|
| ① source 需被多个不在同一信任域的人访问 | **未触发** | 部署形态未变，仍是回环 + 部署者自理的反代（ADR-0024 §4 一字不改）。 |
| ② 同一进程内出现第二套目标端凭据或第二个租户 | **已触发** | 数据源表按定义可以有 N 套目标端凭据。**但触发的是「第二套凭据」那半句，不是「第二个租户」那半句**：进程内仍只有一个信任域，没有任何按调用方区分权限的诉求。 |
| ③ 任何一票要求 `/api/*` 承载凭据流转 | **已触发** | 数据源的增删改必然经 `/api/datasources` 写入口令。 |

**裁定：两条触发，第一版仍不引入鉴权**（地图 #117 收窄 1，所有者 2026-08-18 裁定）。
这是一次**明知故犯**，账如下：

1. **ADR-0024 §2 的负面条款判废一半。** 原文「`/api/*` 的任何响应不得回传口令，
   UI 不提供连接配置的读写面」：
   - **「不回传口令」保留，且加强成硬规则**——`GET`/`POST`/`PUT` 的**任何**数据源响应
     一律不含口令字段，连密文都不回；界面上只显示「已设置 / 未设置」。
     改口令是**只写**操作：提交空串表示「不改」。
   - **「UI 不提供连接配置的读写面」判废**——它正是本票要做的事。原文那句
     「**没有连接管理页，不是还没画，是不画**」自 2026-08-19 起不再是现行裁定。
2. **暴露面的量级变了，质没变。** ADR-0024 §1 的权限等价原文是「持有该 source 的
   Oracle 凭据与目标端写权限」——**单数**。现在是**全部已配置数据源**的凭据与写权限。
   这是**量的放大**：端口本来就等价于凭据，能连上的人本来就能发起任意运行。
   **但有一处是质变，不许混过去**：口令此前只能「通过本应用作恶」，
   现在虽然仍不回读（第 1 条），**它已经进入了一个能被 UI 写入、能被网络传输的对象**——
   ADR-0024 §2 当年防的正是「口令脱离本服务被直连数据库使用」那一档。
   §3 的静态加密与第 1 条的不回读，是对这一档**唯一**的抵消，且只抵消了一部分。
3. **部署前提的措辞加码**（#118 点名要答的那条）：ADR-0024 §4 的三条规则**一字不改**，
   但启动横幅的措辞升级——source 与 sink 的启动 `warn` 都要说清
   「能连上者等价于持有**全部已配置数据源**的凭据与写权限」，不再是「该 source 的」。
4. **重开条件本身不因本次触发而失效。** ②③ 已触发这件事，从今天起是 `CONTEXT.md`
   缺口清单第 5 条里的**既成事实**，不是待办。真正的重开信号退回到 §6 ①
   （出现互不信任的多人访问）——那一条**一旦成立就没有便宜路可走了**。

### 6. 字段形状：`oracle_client_lib_dir` 留在进程级，理由是驱动层的静默忽略

- **Oracle 数据源**：`connect_string` / `username` / `password`（+ `datasource_id`、`name`）。
- **MySQL 数据源**：`host` / `port` / `username` / `password` / `database`（+ `datasource_id`、`name`）。
  **不存 DSN 串**：口令要单独加密，存整串就得先解析再回填，多一层无谓的转义面；
  mysql crate 的 `OptsBuilder` 本来就收分量。
- **`oracle_client_lib_dir` 不做数据源级字段**，留在 `source.toml` 作进程级配置。

最后一条已在 #118 对着 oracle **0.6.3** 源码查证（`issuecomment-5330212369`）：
`dpiContext` 全进程唯一，`InitParams::init()` 走 `get_or_try_init`，**只有第一次调用**
会把参数传进 `dpiContext_createWithParams`；已初始化后再调返回 `Ok(false)` 且
*"Parameter values in `self` affect nothing"*——**不是报错，是静默忽略**。
两个 Oracle 数据源填不同 lib_dir 时，第二个的值会被无声吞掉、实际用第一个初始化的库。
那正是 [ADR-0034](0034-v1-scope-from-customer-needs.md) §1b 点名的「静默改值」类失效模式，
驱动层连一条告警都不给。**支持多版本 client 库是多进程/多部署问题，不是数据源模型问题。**

`sink_base_url` 同理**留在进程级**：一个 sink 进程能连任意 MySQL（§1），
「哪个 sink」与「哪个库」在第一版没有必须解绑的理由。

### 7. 存储落点：新表 `datasources`；`tasks` 的不兼容形态整表丢弃

新表，不复用 `tasks`：

```sql
CREATE TABLE datasources (
    datasource_id TEXT PRIMARY KEY NOT NULL,
    name          TEXT NOT NULL,
    kind          TEXT NOT NULL,   -- 'oracle' | 'mysql'
    settings      TEXT NOT NULL    -- JSON；口令字段是 §3 的密文
);
```

`settings` 用一列 JSON 承载两种形态，沿用 [ADR-0036](0036-task-spec-structured.md) §4
给 `tasks.spec` 定的先例：**两种 kind 的字段集不同，拆成列就得开一堆恒为 NULL 的列**。

`tasks` 加两列 `source_datasource_id` / `target_datasource_id`（§8）。
**旧行没有可推导的取值**——目标端数据源的凭据在对端的 `sink.toml` 里，
source 拿不到，任何自动填都是编造。故沿用 ADR-0036 §4 的处置：
**列缺失即整表 DROP**，不做就地翻译、不做 legacy 并存。前提与那次相同：第一版尚无真实用户数据。

**删除数据源时若仍有任务引用它，拒绝（409）**，不做级联、不做软删。
悬空引用会把失败推迟到发起运行那一刻才炸，而那时用户手上只有一条「连不上」。

### 8. 任务怎么引用数据源：绑定挂在 `Task` 上，不进 `TaskSpec`

`TaskSpec` 是「搬什么」的完整描述（ADR-0036 §1），它的三个派生面是源端 SQL、
运行参数清单、报文里来自任务定义的字段（§6）。**数据源 id 一个都不参与**——
它是「从哪搬到哪」的**绑定**，不是规格的一部分。

好处不只是概念干净：规格因此**可跨数据源搬运**（同一份规格指到测试库或生产库，
是换绑定不是改规格），而且 `TaskSpec` 的 `deny_unknown_fields` 与既有的
「规格进 SQLite 一列 JSON」不必为了两个 id 而变形。

落地上，两个 id 是 `tasks` 表的**列**，随 `Task` 一起进出 API；
物化给 run 子进程的临时任务 TOML 里，它们已经**解析成了实际凭据**（见 §1 与 §9）。

### 9. 「测试连接」：Oracle 在 source 直连，MySQL 走 sink 新端点，**不增错误码**

- **Oracle**：source 侧按该数据源的凭据开一次连接，`SELECT 1 FROM DUAL`，用完即关。
- **MySQL**：source 侧无法直连（`CONTEXT.md` 的不对称在这一点上**保留**：
  source 仍不建 MySQL 连接）。故 sink 新开一个端点 `POST /v1/target/test-connection`，
  收一份连接信息，跑一遍开连接仪式，回 `{"ok": true}` 或错误信封。

这是 [ADR-0027](0027-target-ddl-generation-and-cross-end-metadata.md) §3
「sink 不开新端点」那道封条的**第一道口子**。#118 与 [#120](https://github.com/liumingjian/db-qbs/issues/120)
是同一个端点面（#117 点名的三处接缝之一）：本 ADR 只开「测试连接」这一个，
**目标端取列端点归 #120**，两票各开各的那一个，封条的完整重述由 #120 一次做完。

**[ADR-0010](0010-http-protocol-contract.md) 的错误码闭集不增。** 连不上目标端复用
`SINK_ENVIRONMENT`（500）——它的本义就是「目标端环境配置错误，不要排查业务数据」，
连不上正是这一类。ADR-0029 的失败分类映射随之不变（`SINK_ENVIRONMENT` → `SINK_ENVIRONMENT`）。

### 10. `source.toml` 的 Oracle 字段退役，但保留一次首启迁移

三个字段 `oracle_connect_string` / `oracle_username` / `oracle_password` **退役**，
改成可选。处置：

> **首次启动时，若 `datasources` 表为空且这三个字段齐备，把它们迁成一条名为「默认」的
> Oracle 数据源写进库。** 迁移只做一次（判据是表为空），迁完打一条 `warn`
> 提示部署者从 `source.toml` 里删掉它们。

**不做硬退役（直接删字段）**的理由：`deny_unknown_fields` 会让现存的每一份 `source.toml`
当场解析失败，而第一版还没有数据源管理界面（那归 [#123](https://github.com/liumingjian/db-qbs/issues/123)）——
硬退役等于在界面就位之前把所有部署打成「一条数据源都没有、也建不出来」。
**`oracle_client_lib_dir` 不退役**，理由见 §6。

## 后果

- **`CONTEXT.md` 三处要改**：部署形态图下方那句「`source` 不持有 MySQL 连接」（改判为
  「不建 MySQL 连接，但持有并转发目标端凭据」）、缺口清单第 1 条（静态加密改写）、
  缺口清单第 5 条（重开条件 ②③ 已触发 + 暴露面放大到全部数据源）。
- **sink 的启动语义变了**：不再启动即连 MySQL。「MySQL 没起」这件事从「sink 起不来」
  变成「每个 run 在 `POST /v1/runs` 失败」。**排障入口跟着变**，验收台架的等待逻辑要跟着改（#122）。
- **三份验收台架的报文形状再次变化**（`OpenRunRequest` 加 `target`），
  与 #121 留下的那笔账合并，一并归 #122。
- **第一版新增一个第三方依赖**（`chacha20poly1305`，纯 Rust，无 C 依赖）。
  仓库此前没有加密依赖，这是第一个。
- **界面只做最小接线**：数据源管理屏归 #123；本票只保证「构建器能选数据源、任务能存住绑定」。
  在 #123 落地之前，建数据源只能走 `/api/datasources`。**这是有意的中间态，不是遗漏。**

## 时效

1. **§4 的过线明文**——出现「source 与 sink 之间确实跨不可信网络」的真实部署时立即重开。
   正解是部署者放 TLS 反代 + 放开 `sink_base_url` 的 scheme 检查，**不是**给客户端塞一条 TLS 依赖链。
2. **§3 的密钥来源**——与鉴权一并重估。引入鉴权那一刻，「密钥和密文放在同一个 0600 目录里」
   就从「防线最薄处之外的合理简化」变成一条真正的短板。
3. **§5 的挂账**——ADR-0024 §6 ① 一旦成立，本 ADR §5 的整段裁定作废，
   必须与 ADR-0016 §8、ADR-0017 §4 / ADR-0021 §2 一并处理。
4. **§6 的 `oracle_client_lib_dir` 进程级**——只有在「一个部署要同时连多个大版本 Oracle」
   出现时才重开，且正解是多进程，不是把字段挪进数据源。
5. **§10 的首启迁移**——它是一次性的兼容垫片。#123 的数据源管理屏落地后，
   下一版可以把 `source.toml` 的三个 Oracle 字段真正删掉，届时本节整段作废。
