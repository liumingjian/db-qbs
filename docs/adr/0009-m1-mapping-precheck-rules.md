## 背景

ADR-0006 把 V1 的校验砍到只比行数之后，**「值有没有被悄悄改掉」不再有任何下游机制兜底**。
#13 的目标端往返实测把这句话坐实成了具体的失效模式：

- `DECIMAL` **标度不足是静默舍入**——`0.5` 写进 `DECIMAL(38,0)` 读回 `1`，
  `STRICT_ALL_TABLES` 下只给一条 `Note 1265`，语句成功提交。行数完全对得上。
- `DATE` 的值写进 `DATETIME(6)` 多出 `.000000`；小数秒写进 `DATETIME(0)` **静默舍掉，一条 Note 都没有**。
- `CHAR(n)` 读回剥掉尾部空格，且**空串与全空格碰撞**，值的可区分性都保不住。

映射预检因此不是「一道方便的校验」，**它就是防线本身**。
本 ADR 把它定死成可直接实现的判定式。

地图 [#22](https://github.com/liumingjian/db-qbs/issues/22) 的主方向是「抓大放小，先把整体流程跑通」，
前提 1 已定：**M1 只支持 `NUMBER(p,s)` / `VARCHAR2` / `DATE` 三种**。
收窄类型**不等于**放松防线——恰恰相反：能过的三种，规则必须严到没有静默失效的缝。

## 决策

### 1. 源列类型的权威来源：游标 describe，不是数据字典

ADR-0007 定了「一条写死的 SQL 单查询流式」，ADR-0004 定了 SQL 由人手写。
于是**源列不一定来自表**：`SELECT a, b*2, NVL(c,'x') FROM t JOIN ...` 里
没有一列在 `ALL_TAB_COLUMNS` 上有条目。

**预检的源端输入一律取驱动 describe 这条 SQL 得到的结果集元数据**
（ODPI-C query-info：每列的 type num / precision / scale / 列名），
拿到的就是这条查询**实际会吐出来的列**。`ALL_TAB_COLUMNS` 不参与预检，
它留给 M2 的 SQL 构建器做列选择。

> **2026-08-15 兑现（[ADR-0023](0023-m2-sql-builder-boundary.md) §4，
> [#51](https://github.com/liumingjian/db-qbs/issues/51)）——构建器读字典，但「只亮不判」。**
> M2 的构建器确实按本条去查 `ALL_TAB_COLUMNS`（dblink 表走 `ALL_TAB_COLUMNS@<link>`），
> 并把类型与精度**显示**给人看，但**一律不构成门禁**：不禁止选中、不做任何拒绝。
> 理由正是本条划下的这道界——**构建器手上那份是数据字典，预检手上那份是游标 describe，
> 两者在视图 / dblink / 同义词之下可以不一致**。拿非权威元数据做门禁，
> 制造的是「构建器放行了、预检却拒」，以及更糟的「构建器拒了、其实能跑」。
> 逐列类型判定权威仍全部在 `sink`（ADR-0010 §3.1 经 ADR-0016 §4 收窄后的作用域），
> §8「一次报全部列」由此继续成立。

副作用是刻意要的：表达式列的 precision/scale 往往是 0 或不确定，
这类列会直接落进拒绝清单，**逼着任务定义把 SQL 写成明确的列**，
与 ADR-0003「宁可停机也不要猜」一致。

> **实现前须在台架确认**：ODPI-C 的 describe-only 执行模式可用（prepare + describe，不 fetch）。
> 若不可用，退路是 `execute` 后立刻读 query-info、不 fetch 就关游标——
> **同样拿得到元数据，本 ADR 的规则一个字都不用改**。这是实现细节，不是决策分叉。

### 2. 判定式随失效模式分级——这是本 ADR 的中心思想

> **2026-08-16：本节的 `NUMBER` 判定式已由 [ADR-0031](0031-number-predicate-lower-bound.md) 取代
> （[#97](https://github.com/liumingjian/db-qbs/issues/97)）。** 逐位相等 `p' == p && s' == s`
> **退役**，改为下界式 `s' >= s && p'-s' >= p-s`，对 [ADR-0030](0030-m3-type-whitelist.md) §1 的
> **推导形状**判。**当前 `NUMBER` 判定式是什么，只看 ADR-0031 §1。**
> 下文那段「M1 的目标是最窄链路，宽容度不值钱」是 M1 语境下的原始论证，**保留不删**——
> ADR-0031 摘的正是这条经济理由，而非正确性理由。
> **本节的分级思想本身、`VARCHAR2` 的 `n' >= n`、`DATE` 的 `fsp == 0` 全部原样成立**
> （日期族为什么不跟着放宽，见 ADR-0031 §7）。

**严格程度跟着失效模式走，不追求形式上的一致：**

| 失效模式 | 判定式 | 为什么 |
|---|---|---|
| **静默改值**（无人兜底） | **从严** | 预检是唯一防线，漏了就永远发现不了 |
| **当场炸**（硬 ERROR） | **从宽** | MySQL 自己会拦，预检再严一遍只是徒增误拒 |

三种类型的具体判定式：

```
NUMBER(p,s) → DECIMAL(p',s')     逐位相等：p' == p  &&  s' == s
VARCHAR2(n) → VARCHAR(n')        下界：    n' >= n
DATE        → DATETIME(fsp)      严格：    fsp == 0
```

**`NUMBER` 取逐位相等**，不取「标度下界 + 整数位下界」。
后者同样保值（#13 组 2 已证），但逐位相等**判定式最短、没有边界推理、
错误信息能直接把两边写出来**。M1 的目标是最窄链路，宽容度不值钱。
下界式不在 M1 范围内；[#19](https://github.com/liumingjian/db-qbs/issues/19) 已把现行三种
`NUMBER` 目标形状都定为精确匹配。M3 若要改用下界式，必须复审
[ADR-0003](0003-numeric-as-string.md) 的精确匹配决策。无论是否放宽，V2 checksum 都必须
承担目标端重规范化那笔债（§7.8 组 2 第 3 条）。

**`VARCHAR2` 取下界**，与 `NUMBER` 不一致是**故意的**：
目标列窄了 MySQL 给硬 `ERROR 1406 Data too long`，**当场炸，不会静默截**。
`n CHAR` 与 `n BYTE` 两种语义都按 `n` 的数值直接比，不做字符/字节换算——
UTF-8 下 `n` 字节至多 `n` 个字符，故 `VARCHAR(n)` 必然够（偏松，不会截断）。

**`DATE` 要求严格 `fsp == 0`**，理由不是保字节（V1 不比 checksum，`.000000` 只是字节变了、值没变），
是**保规则的单一性**：一旦允许 `DATETIME(6)`，M3 引入 `TIMESTAMP(n)` 时
同一个目标列型会对应两种源类型，映射不再可逆。M1 一列一型，不留歧义。

### 3. 列的对齐方式：按名字，不按位置

两边列名集合**必须完全相等**（不多不少，比较时统一大写），**顺序无关**。

按位置对齐有一类**静默搬错**：有人调了 `SELECT` 里两列的先后，两列碰巧都是 `VARCHAR2(50)`，
预检全过，数据整整齐齐灌进错的列——V1 只比行数，一样发现不了。
这与标度静默舍入是同一类病。

代价：**写死的 SQL 必须每列显式命名**（表达式列必须写别名），否则列名是 `B*2` 这种东西对不上。
这与第 1 条「表达式列精度不明本来就要拒绝」指向同一个要求。

### 4. 拒绝清单

M1 白名单只有三种类型。以下**一律拒绝，不猜、不降级、不静默搬运**：

| 拒绝项 | 判据 | 归属 |
|---|---|---|
| 白名单外的一切 Oracle 类型 | `TIMESTAMP`、`CHAR`/`NCHAR`、`CLOB`/`BLOB`/`RAW`、`BINARY_FLOAT`/`BINARY_DOUBLE`、`XMLType`… | M3 或 V1 永不支持（见 ADR-0003） |
| 裸 `NUMBER`（p/s 皆 NULL） | describe 给不出精度 | M3（[#20](https://github.com/liumingjian/db-qbs/issues/20)） |
| `NUMBER(p,s)` 且 `s > p`（纯小数） | 需 `DECIMAL(s,s)` 换算 | M3 |
| `NUMBER(p,s)` 且 `s < 0`（负标度） | 需 `DECIMAL(p+\|s\|,0)` 换算 | M3 |
| `NUMBER(p,s)` 且 `s > 30 \|\| p > 65` | **MySQL `DECIMAL` 无法表达** | 前置判定，见下 |
| 表达式列 / 精度不确定的列 | describe 给出的 precision/scale 不可用 | 改 SQL |
| 两边列名集合不相等 | 第 3 条 | 改 SQL 或改目标表 |
| 精度/长度/fsp 不满足第 2 条判定式 | — | 改目标表 |
| 目标列 `NOT NULL` | 第 5 条 | 改目标表 |
| 目标列字符集不是 `utf8mb4` | 第 6 条 | 改目标表 |

**`s > 30 || p > 65` 必须单列一条前置判定**，报「MySQL `DECIMAL` 无法表达该源类型」。
否则逐位相等规则会把 `NUMBER(38,35)` 报成「目标列精度不匹配」，
让人对着一张**根本建不出来的表**改半天。

`CHAR`/`NCHAR` 在 M1 **拒绝**，尽管 `CHAR(n)` → `VARCHAR(n)` 是已知正确的映射（#13 已坐实）。
放行等于把白名单从 3 撑到 5，换来的只是少一类拒绝——**没有 `CHAR`，链路照样从头走到尾**。
§7.4 第 5 条的硬约束保留在文档里不动，它是实测结论，只是 M1 用不上。

### 5. 可空性：目标列一律必须可空

ADR-0003 要求 NULL 与空串可区分，#13 组 4 已证目标端 `VARCHAR` 上四者两两可区分。
预检**不得自动加 `NOT NULL`**——这说的是「我们不主动加」。反过来：

**目标表上已有 `NOT NULL` 的列，预检直接拒绝。**

不取「跟着源端可空性走」的聪明规则：它多一个分支、多依赖一份元数据通道，
换来的只是「接受一种我们自己生成的建表 SQL 根本不会产出的目标表」。

**暂存表 `<target>__stg_<run_id>` 不受这条约束**——它由我们自己建，一律建成全列可空（见第 7 条）。

### 6. 字符集判 `utf8mb4`，排序规则不判

**逐列判 `CHARACTER_SET_NAME = 'utf8mb4'`，不是就拒绝。**
`latin1` 列灌中文在严格模式下会炸（`ERROR 1366`），那还算好的；
更糟的是连接层字符集配错时会**双重编码进库**——#13 第一轮就真踩到过，
这一类不炸、悄悄改字节。

**这只是同一个失效模式的一半（2026-08-13 补，见 [ADR-0011](0011-batch-payload-wire-format.md) §5）**：
逐列判的是**目标列**的字符集，**列对了、连接层错了照样双重编码**。另一半是 sink 的
MySQL 连接显式配 `utf8mb4` + 开连接后断言三个 `character_set_*` 变量，
它跟列无关、发生时点早于预检，**不进本 ADR §8 的逐列报告**。两半缺一个都挡不住 #13 那一类。

**排序规则 M1 不判。** NO PAD 语义只在「比较字符串」时才有意义，
而 V1 只比行数，没有任何地方比较字符串值。它是 V2 checksum 的前提，不是 M1 的门禁。

### 7. 预检时点、元数据来源与暂存表 DDL

**每个 run 开跑前无条件跑一次，是硬门禁。** 不缓存到任务定义上——
缓存会在「有人半夜改了目标表」时失效，而这正是预检存在的理由；
两次元数据查询相对一次 10 万行搬运可以忽略。

固定顺序：

```
1. describe 源端 SQL          → 每列 type/precision/scale/列名
   （同一次解析里由 ADR-0008 强制日期谓词形状）
2. 查目标端 information_schema.COLUMNS
   → DATA_TYPE / NUMERIC_PRECISION / NUMERIC_SCALE
     / CHARACTER_MAXIMUM_LENGTH / DATETIME_PRECISION
     / IS_NULLABLE / CHARACTER_SET_NAME
3. 按名字对齐，逐列比对（第 2~6 条）
4. 全部通过 → 才建暂存表；任一列不过 → 整 run 失败，什么都不建
```

**暂存表 DDL 由预检结果生成**，不用 `CREATE TABLE ... LIKE`：
`LIKE` 会把目标表的 `NOT NULL` 继承回来（违反第 5 条），还会带上索引——
暂存表是纯写入中转，索引只有拖慢批量插入这一个作用。
生成的 DDL：**逐列照目标表的类型写，全列可空、无索引、无默认值、无主键**。
切换时 `INSERT INTO <target> SELECT ... FROM stg` 由目标表自己的约束把关。

附带好处：预检刚把每列的目标类型逐列读过一遍，DDL 是**同一份数据的直接产物**，
不会出现「预检看的是一张表、实际建的是另一张」的偏差。

### 8. 错误信息形态：一次报全部

**把所有列都跑完，一次报出全部不合规的列**，每条固定形态：

```
<列名> | 源端 <类型(精度)> | 目标端 <类型(精度)> | 违反：<规则>
```

末尾一行总计。预检是开跑前的一次性门禁，人拿到报告是去改目标表 DDL 的——
一次报一条会让「改表 → 重跑 → 又炸一条」循环七八轮，
而生产表 70 列的场景下这个循环的代价是实打实的。预检只读元数据，不存在继续检查引发副作用的顾虑。

### 9. 两条必须翻成人话的错误码

对齐 ADR-0007 对 `ORA-01555` 的处理，本 ADR 钉进两条（**不得裸抛错误码**）：

- **`ERROR 1118 Row size too large`**（**生成建表 SQL 的人拿去建目标表时**）→
  「建表失败：列宽合计超出 MySQL 单行上限，需缩窄字符列或拆表」。
  **不是建暂存表时**——[ADR-0002 增补](0002-staging-table-atomic-swap.md#增补2026-08-13暂存表的命名建表失败与孤儿回收)
  已订正：暂存表逐列照目标表的类型建，行长与**已经建得出来的**目标表相同，这类失败在暂存阶段不可能发生。
- **`ERROR 1366 Incorrect string value`**（写入时，第 6 条的漏网）→
  指出是字符集问题，不是数据问题。

**预检不预先计算行长上限。** §7.4 第 6 条提过 `VARCHAR(n)` 在 `utf8mb4` 下按 `4n` 计、
单行 65535 字节——但真实规则要算行格式、off-page 存储、指针开销，
自己算出来的近似式算松了照样炸、算紧了误拒，**等于重新实现 MySQL 的行长规则**，没有价值。
建表失败即整 run 失败，靠上面这条人话把关。

> **2026-08-15 增补（[ADR-0027](0027-target-ddl-generation-and-cross-end-metadata.md) §8，
> [#57](https://github.com/liumingjian/db-qbs/issues/57)）——`ERROR 1118` 那条人话的承载点。**
> 它**不是运行时捕获**：执行建表 SQL 的动作在产品之外（V1 不自动建目标表），
> **产品结构性地看不见那个错误**，M2 有了 UI 也一样看不见。
> 承载点定形为**建表 SQL 旁的一段静态提示**——零判定、零元数据、零协议，
> 只是把本节这句已成文的措辞搬到人看得见的地方。
> 本节的措辞与「**预检不预先计算行长上限**」一字不改。

### 10. 明文缺口：`DATE` 的**值域**不判，转 M3（[#35](https://github.com/liumingjian/db-qbs/issues/35)）

第 2 条的 `DATE` 判定式只有 `fsp == 0`。**值域不在里面，这是有意识留下的缺口，不是遗漏。**

Oracle `DATE` 的域从公元前 4712 起，MySQL `DATETIME` 的**文档域**从 `1000-01-01` 起。
值域与本 ADR 其他规则**不同类**：`DATE → DATETIME` 这个映射本身合法，越界的是**值**——
而预检看的是**列元数据**，结构性看不见值。唯一看得见值的位置是运行期 `canon_date` 之后，
在那里判等于把「预检拦住」降级为「跑到一半炸」，与第 8 条「一次报全部列」的形状冲突。

**裁定 M3，理由不是「不阻塞 M1」，是「防线已经存在」**（实测见 spike §7.9，MySQL 8.0.46）：

- 公元 **1–9999 全域**写进 `DATETIME` 是**逐字节原样往返、零 warning**，
  **不是静默改值**——ADR-0006 的静默清单上没有这一行，没有东西需要预检去补。
- 格式化后**仍越界**的形态（负年份、五位年）在 `STRICT_ALL_TABLES` 下是硬 **`ERROR 1292`**，
  当场炸、整 run 失败、目标表不动——落在既有形状里。这道闸是
  [ADR-0015](0015-staging-table-write-path.md) 开连接仪式那条 `sql_mode` 断言买来的：
  非严格模式下同样的输入**静默塌成 `0000-00-00`**。
- 因此 M1 对公元 1000 年以前的日期（脏数据、`0001-01-01` 这类哨兵值）的行为是**明文规定的**：
  **原样搬过去，不拦、不改、不警告**。

**两条必须跟着这个缺口一起记住的**：

1. **这依赖的是实测，不是文档保证。** MySQL 文档写的 `DATETIME` 域是 `1000-01-01` 起，
   更早的值属于「可能能用但不保证」。上面这条规定架在 **MySQL 8.0.46 的实测行为**上
   （spike §7.9，探针 `probes/mysql-datetime-domain.sql` 在仓库里，可重跑）。
   **换 MySQL 大版本时这条要重测**，不能默认还成立。
2. **有一条静默路径本条挡不住，且没有别的东西挡得住**：`canon_date` 若对公元前日期
   丢掉纪元，会产出一个合法的公元日期（公元前 4712 → `4712-01-01`），MySQL 全盘接受。
   已记进 [ADR-0006](0006-row-count-only-verification.md) 静默清单第七行，**防线栏是空的**。
   查清它要起 Oracle 台架 + 另写 ODPI spike 程序，M1 不付这笔钱。
   M3 若要收口，顺序是：先测驱动对公元前日期给正年还是负年，再谈预检还是运行期判。

M1 侧唯一动的是 [ADR-0014 §11](0014-canonical-form-boundary-test-suite.md) 给 `canon_date`
加的年份域断言（`1 <= year <= 9999`，纯函数层，零环境依赖）——它买到的是
「负年份在源端就炸，不靠 MySQL 报错」，**买不到公元前检测**。

## 后果

**买到的**：三种类型上**没有静默失效的缝**——#13 暴露的三条静默改值路径
（标度舍入、小数秒截断、`CHAR` 剥空格）在 M1 全部被预检挡在开跑之前。
判定式短到可以逐条读代码核对。

**付出的**：

- **误拒面很宽**。合法但不逐位相等的 `NUMBER` 目标列、`DATETIME(6)`、`NOT NULL` 列、
  非 `utf8mb4` 列，统统跑不起来。这是 #11 白名单制刻意选的代价：
  **不完整不会变成「搬错」，只会变成「跑不起来」。**
- **对写死的 SQL 追加两条形状约束**（每列显式命名 + 表达式列须精度确定），
  与 ADR-0008 的日期谓词形状约束叠加。三条一起构成「M1 能接受的 SQL 长什么样」。
- **`Note 1265` 成了哨兵**：预检拦住之后它不该再出现。运行期一旦出现，
  等于预检漏了列，**属于 P0 缺陷而非运行故障**。

**对其他 ADR 的影响**：ADR-0003 白名单不变，本 ADR 是它在 M1 的**收窄子集**，
被排除的类型转 M3 而非否决。ADR-0006、ADR-0007、ADR-0008 不受影响。

## 时效

**M1 只支持三种类型是本图的前提，不在本 ADR 的复审范围内**——要改得重画地图。
最可能触发本 ADR 复审的是 [#2](https://github.com/liumingjian/db-qbs/issues/2)
的生产类型普查：若扫出白名单外类型大面积命中，M3 的类型扩展会连带重审第 2 条的判定式分级。

## 增补（2026-08-15，[#52](https://github.com/liumingjian/db-qbs/issues/52)）：M2 的列选择进来之后，§3 一字不改

§1 原文把 `ALL_TAB_COLUMNS` 「留给 M2 的 SQL 构建器做列选择」。M2 地图
[#47](https://github.com/liumingjian/db-qbs/issues/47) 的
[#52](https://github.com/liumingjian/db-qbs/issues/52) 来兑现这句话时，
带着一个疑虑：列选择一旦进来，§3「两边列名集合完全相等」这条前提会不会被顶开，
以及 [ADR-0002](0002-staging-table-atomic-swap.md) 的 `DELETE` + `INSERT`
会不会把「没被选中的目标列」静默清成 `NULL`。

**结论：本 ADR 一个字都不改。** 下面四条是正面回答，不是新规则——
它们全部是既有规则在新场景下的原样成立。本增补存在的唯一理由，
是把这四条**写下来**，以免后人再对着同一个疑虑重开一次。

### 1. 「勾成真子集」不产生非恒等映射——因为源表根本不参与 §3

疑虑的措辞把两件事绑在了一起，而它们是脱钩的。

**§3 的对齐面是「SQL 结果集的列 ↔ 目标表的列」，源表不在里面。**
这由 §1 定死：预检的源端输入一律取**驱动 describe 这条 SQL** 得到的结果集元数据，
`ALL_TAB_COLUMNS` 不参与预检。构建器上「勾成真子集」减掉的是**源表**的列，
减完之后结果集就是被勾中的那些——**一列不多、一列不少**。
源表 70 列只勾 10 列，结果集 10 列、目标表 10 列，集合相等，**映射恒等**。

因此 M2 的列选择**允许勾成真子集**。反过来禁止它，等于要求「源表全列必须全搬」，
在生产主力表 70 列的场景下是个荒谬的约束，而且它**挡不住任何东西**——
危险面在目标端，不在源端。

### 2. 真正危险的是「目标表有列没被选中」，而它是 §4 明写的一条硬拒

危险的从来不是「源表有 70 列我只勾 10 列」，是「**目标表有 12 列，我只喂进去 10 列**」。
这时结果集与目标表的列名集合不等——**§4 拒绝清单里「两边列名集合不相等」正是这一条**，
归属栏写的是「改 SQL 或改目标表」。

于是 §7 的固定顺序接管：`任一列不过 → 整 run 失败，什么都不建`。

**「未选中的目标列在切换后会被写成什么」这个问题没有答案，因为不存在这种切换。**
它要求暂存表先建出来，而预检在建暂存表**之前**就拒了。
ADR-0002 的 `DELETE` + `INSERT` 那条静默清 `NULL` 的路径**走不到**——
这不是靠某条新规则挡住的，是 M1 现成的硬门禁本来就挡住的。

这正落在本 ADR「后果」里那句代价上：**不完整不会变成「搬错」，只会变成「跑不起来」。**

### 3. 拦截层只有一处：预检。构建器不查目标端、不做提前拦截

构建器**不得**为了提前发现「列集不等」去查目标端 `information_schema`。理由与
[ADR-0023](0023-m2-sql-builder-boundary.md) §4「只亮不判」完全同源，且更强：

- §4 挡的是「拿**数据字典**这份非权威元数据做门禁」，制造「构建器放行了、预检却拒」
  与更糟的「构建器拒了、其实能跑」；
- 这里要拿的是**跨端**元数据——`source → sink` 那条查询目标端元数据的接口
  在 ADR-0023 §7 已被指名**推给 [#57](https://github.com/liumingjian/db-qbs/issues/57)**，
  通道都还不存在。本增补**不预判 #57**：即便 #57 把通道开出来，
  也不构成「构建器可以拿它做门禁」的授权。

构建器侧允许做的只有一件：在 UI 上钉一句**静态约束文案**（「目标表必须恰好是这 N 个同名列」）。
它是说明，不是判定，不读任何目标端元数据。「按当前勾选生成建表 SQL」这个出口**归 #57**。

> **2026-08-15 兑现（[ADR-0027](0027-target-ddl-generation-and-cross-end-metadata.md)，
> [#57](https://github.com/liumingjian/db-qbs/issues/57)）：那个出口有了，而本节一个字不用改。**
> 建表 SQL 由 `source` 从**取列**（形状预检 + describe，只读无副作用）拿到的元数据正向推导，
> **不查目标端、不构成放行**——人按它建完表，映射预检照样从头跑一遍、照样可能拒。
> 本节预判的那句「即便 #57 把通道开出来，也不构成授权」更进一步兑现为：
> **通道压根没开**（ADR-0027 §3 判它 Out of scope）。**拦截层仍然只有预检一处。**

**门禁只有一处**——与 ADR-0023 §8 已定的态度一致。

### 4. 目标列 `NOT NULL`：问题消解在 §5 一条更宽的规则里

疑虑问的是「若选列产生『目标表有非空列未被选中』，挡在哪一层」。

**§5 是全拒的**：目标表上已有 `NOT NULL` 的列，预检直接拒绝——**不分选没选中**。
带 `NOT NULL` 列的目标表在 M1 从来就跑不起来，M2 的列选择不制造任何新情形。
这里不需要新裁定，也不需要新的拦截层。

### 5. 「改名」不支持——但 `AS` 别名不是改名

M2 **不引入「作为任务定义概念的字段映射」**。
[ADR-0016](0016-task-definition-form.md) §2 的四字段清单、§2.1 对
[ADR-0008](0008-business-date-predicate-generation.md) §5 的字符串判定订正
（`upper(target_date_col) == upper(source_date_col)`）、`CONTEXT.md` 术语表
「不含字段映射」那条，**全部继续成立，一字不动**。ADR-0016「后果」里那笔预留的账
（判定改回查映射表 + 任务定义加字段 + §6 严格拒绝让老文件当场失败）**M2 不付**。

**必须写明的一条区分**：SQL 文本里的 `AS` 别名**不是**字段映射。
§3 本来就要求「写死的 SQL 必须每列显式命名，表达式列必须写别名」——
改列名这个能力**在 M1 就已经存在**，它在 `SELECT a.c_name AS WHATEVER` 里，
而且用它写出来的仍然是**恒等映射**（别名即目标列名）。
构建器要不要在界面上给一个重命名输入框，是纯 UI 便利问题，**语义上零后果**，
归后续 UI 票；无论给不给，任务定义都还是那四个字段。

### 本增补不订正什么

- **§1～§10 全部原文**——本增补不改判定式、不改拒绝清单、不改预检时点与顺序、不改错误信息形态。
- **ADR-0002**——`DELETE` + `INSERT` 的切换语义一字不动；第 2 条说明的是这条路径**到不了**，
  不是它有问题。
- **ADR-0008 §5 / ADR-0016 §2 / §2.1 / §6 / `CONTEXT.md` 术语表**——见第 5 条，全部继续成立。
- **ADR-0023 §9** 的输入输出定形——它已写「#52 若判不许，列勾选退化成全选 + 只读展示，
  本节的输入输出定形一个字不用改」。本增补判「许」，落在它覆盖的另一半上，
  **同样一个字不用改**。

## 增补（2026-08-16，[#100](https://github.com/liumingjian/db-qbs/issues/100)）：§3 的 M3 复审已做，判**维持**

`STRATEGY-V1.md` 的 M3 第二项写着「列名映射策略：Oracle 大写带引号 → MySQL 小写，
允许用户覆盖」。M3 地图 [#94](https://github.com/liumingjian/db-qbs/issues/94) 把它单开成
[#100](https://github.com/liumingjian/db-qbs/issues/100) 复审，因为它同时顶开 §3、
[ADR-0016](0016-task-definition-form.md) §2 §6 与 [ADR-0008](0008-business-date-predicate-generation.md) §5。

**结论：不引入字段映射表。§1～§10 与 2026-08-15 增补全部原样成立，本 ADR 无一处判定式改动。**
下面三条是复审回执，不是新规则。

### 1. §3 维持「集合相等」，不换成「查表」

换成查表就是把 §3 的防线形状改掉：§3 消灭的失效面是「列对错位」，
而映射表恰好把「映射表写错」这个新失效面装回来——ADR-0016 §2 已经把这笔账算过一遍。
在 [ADR-0006](0006-count-only-verification-in-v1.md) 只比行数的前提下，预检是唯一防线，
不拿它换便利。

**而便利早有替代品**：2026-08-15 增补第 5 条已定，SQL 文本里的 `AS` 别名**不是**字段映射——
§3 本就要求每列显式命名，改列名的能力 M1 就存在（`SELECT a.c_name AS WHATEVER`），
写出来仍是**恒等映射**（别名即目标列名）。[ADR-0023](0023-m2-sql-builder-boundary.md)
已定 SQL 文本可手改且文本是权威，手改后每次发起无条件重跑形状预检（§8），
于是「改列名」这件事既有入口也有门禁，不需要新概念。

### 2. 「大写→小写」这层策略：比较层已经做完，DDL 层判不做

- **比较层**：§3 原文「比较时统一大写」是实现事实（`crates/sink/src/precheck.rs`
  的列名比较全走 `to_uppercase()`）。**源列全大写、目标表列全小写的组合今天就能过预检**，
  无需任何新策略。MySQL 的列名本身也大小写不敏感，语义上无可折叠之物。
- **DDL 层**：[ADR-0027](0027-target-ddl-generation-and-cross-end-metadata.md) 生成的建表 SQL
  把 describe 拿到的列名原样输出（通常全大写），**维持不折**。折小写的收益是纯外观，
  代价是引入唯一一处「展示的名字 ≠ 源端的名字」，让人误以为存在映射——在 V1 只比行数的前提下
  这是负资产。任务定义、预检报告、建表 DDL 三处列名字面一致，恒等映射肉眼可验。
- **表名一律不折**：`target_table` 走同一个 `quote_identifier`，而 Linux 上 MySQL 默认
  `lower_case_table_names=0`，**表名是大小写敏感的**。任何「统一折小写」的规则若不排除表名，
  会让 sink 按用户填的 `T_POSITION` 找不到建议建成 `t_position` 的表。

### 3. 三处受影响面的逐条回执

| 受审处 | 裁定 |
|---|---|
| 本 ADR §3（集合相等、按名字对齐） | **维持**，见第 1 条。§3 的「M3 复审」自此了结 |
| ADR-0016 §2（四字段）、§6（未知字段严格拒绝） | **不受影响**。任务定义仍是四字段，不加映射字段；§6 不会让老任务文件失败。ADR-0016「后果」里那笔预留的账 **M3 也不付** |
| ADR-0008 §5 / ADR-0016 §2.1（日期列名字符串判定） | **不受影响**。`upper(target_date_col) == upper(source_date_col)` 原样保留，不改成查映射表 |

### 本增补不订正什么

- **§1～§10 与 2026-08-15 增补全部原文**——不改判定式、不改拒绝清单、不改预检时点与顺序、
  不改错误信息形态。
- **ADR-0023 §9** 的输入输出定形——构建器**不加**列级重命名输入框（要改名在 SQL 文本框里敲 `AS`），

- **`CONTEXT.md` 术语表**「不含字段映射」那条——继续成立。
