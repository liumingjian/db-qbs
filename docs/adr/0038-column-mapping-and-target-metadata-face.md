## 背景

客户点名的五条需求里有两条落在本票：**「目标端选主键与目标字段」**、
**「默认同名映射、不同名可手选」**。

ADR-0034 §2 已作废 #100「第一版不做字段映射」那条裁定。剩下的问题不是做不做，
而是**做成什么**——以及一笔更重的账：**目标端的列清单从哪来**。
`CONTEXT.md` 明写「`source` 不持有 MySQL 连接」，而 ADR-0027 §3 给跨端元数据接口下了封条，
#101 两次援引它不解。要在 UI 上「勾目标字段」，这条封条绕不过去。

### 三条改变问法的事实（本票查证）

**事实 1——`sink` 早就在读目标端元数据，只是没有暴露成端点。**
`crates/sink/src/mysql_destination.rs:88` 的 `target_columns()` 已在查
`information_schema.COLUMNS`，返回的 `TargetColumn` 带列名 / 类型 / 精度 / 长度 / 可空 /
字符集 / 序号；`:139` 的 `target_keys()` 已在查 `information_schema.STATISTICS`
拿 `PRIMARY KEY` / `UNIQUE`（ADR-0035 §2 的主键预检要用）。
**ADR-0027 §3 挡的从来不是「能不能查」，只是「要不要把它接出来」——查询逻辑一行不用新写。**

**事实 2——封条已经开过一道口子。**
#118 落地时 sink 上多了 `POST /v1/target/test-connection`（`crates/sink/src/http.rs:73`），
凭据随请求体过线、不产生 `run_id`、不写任何状态。**「不属于任何 run 的端点」这个范畴已经破了**，
ADR-0037 §9 明写取列端点归本票一次做完。本票要判的不是「破不破例」，是「这一面长什么样」。

**事实 3——`AS` 别名机制不在 `sql_builder.rs` 了。**
ADR-0036 把 SQL 生成整段搬进 `task_spec.rs`，`sql_builder.rs` 现在只剩查数据字典。
#120 正文里「`sql_builder.rs:47` 投影写死 `a.{column} AS {column}`」**已过期**——
投影现在由 `TaskSpec.columns: Vec<String>` 现算。加映射是 `TaskSpec` 的**形状变更**，
不是加个输入框。

### 所有者 2026-08-18 的两条裁定（本 ADR 的输入，不重开）

七条裁定（#117 评论）里有两条归本票：

1. **主键必选且 `NOT NULL`** → ADR-0009 §5 改成「主键列 `NOT NULL`、非主键列可空」，
   解开它与 ADR-0035 §2 的死锁。
2. **字段映射默认同名自动 + 手动调整；允许只搬选中列**；ADR-0009 §3 的恒等防线撤除，
   按 ADR-0034 §1b 写失效模式。

## 决策

### 1. 映射走 `AS` 别名，不引入映射表

> 用户选的「目标字段」**就是投影的别名**。`SELECT a.C_NAME AS CUST_NAME` 写出来的
> 仍是恒等映射（ADR-0009 增补第 5 条：别名即目标列名），**搬运语义一个字节不变**。

**否掉真映射表**（过线报文带一份 source→target 对照、sink 按它对齐）的理由不是便宜，是**结构**：
目标列名本来就是 `SELECT` 投影的别名，映射表是在协议层重新表达一件 SQL 已经能表达的事。
代价是判定规则要在两端各有一份实现，漂移了报出来的就是「列对不上」这种最难排的错
（同 ADR-0027 §1 的反方论据）。

**别名对用户零感知，这是正确的。** 界面上只有「源字段 → 目标字段」两栏；
`AS` 是把右边那栏写进 SQL 的手段，不是一个功能。用户无从判断该不该加它——
所有者 2026-08-19 就此定下一条通则：**这类零感知的技术选择不上会，按最佳实践直接落地。**

**因此不受影响、一笔不付的**：ADR-0010 协议面（报文里仍只有一份列名——目标名）、
ADR-0016 §2/§6（已由 ADR-0036 §4 退役，本 ADR 不再涉及）、
两端判定式仍各自只有一份（sink 侧比对、source 侧正向生成，规则未增）。

### 2. `TaskSpec.columns` 的新形状：零迁移

```rust
pub struct ColumnMapping {
    pub source: String,   // 源列名（来自 ALL_TAB_COLUMNS，构建器选中）
    pub target: String,   // 目标列名（默认预填 = source，可改）
}
pub struct TaskSpec {
    // ...
    pub columns: Vec<ColumnMapping>,   // 原 Vec<String>
    pub primary_key: Vec<String>,      // 存**目标列名**，见 §6
    // ...
}
```

**「默认同名自动映射」就是 `target` 预填成 `source`**——这不是将就的默认值，
它就是恒等映射的正确表达，与老任务的语义完全一致。

**零迁移**：ADR-0036 §4 已判「已有的任务定义直接丢弃」（含 2026-08-19 增补的运行历史整表 DROP），
前提是第一版尚无真实用户数据。`TaskSpec` 本身是本图新落的结构，本次形状变更落在同一段窗口内，
**不需要任何兼容层，也不需要 serde 容错**。按 ADR-0034 §1 的规矩，这件事在此显式记账。

**派生面不变**（ADR-0036 §6 三样）：源端 SQL 的投影段改用 `AS <target>`；
运行参数清单不受影响；报文里的列名一律取 `target`。

### 3. `sink` 开出目标端元数据面——ADR-0027 §3 的封条完整解除

> **新增两个端点，与 #118 的 `test-connection` 同属「不属于任何 run 的元数据面」：**
>
> - `POST /v1/target/tables` —— 请求体 `TargetConnection`；查
>   `information_schema.TABLES WHERE TABLE_SCHEMA = <database>`，返回表名列表。
> - `POST /v1/target/columns` —— 请求体 `TargetConnection` + `target_table`；
>   调用已有的 `target_columns()` 与 `target_keys()`，返回列清单（含 `COLUMN_DEFAULT` / `EXTRA`，
>   见 §5）与 PK/UNIQUE 约束。
>
> 两者**不产生 `run_id`、不进 run 注册表、不留 tombstone、不写任何存储**，
> 连接按请求建、用完即弃——形状照抄 `handle_test_connection`（`sink/src/http.rs:196`）。
> `source` 侧各配一个代理函数，照抄 `test_target_connection`（`source/src/server_main.rs:970`）。

**ADR-0027 §3 那句论证保留并重述，而不是抹掉**：「这条接口开出来，能买到的只有一个下拉框，
买不到任何一处拦截」——**这句话今天依然字字成立，但它已不是拒绝理由**。ADR-0034 改判前提之后，
**那个下拉框本身就是客户点名的需求**。§3 当年权衡的是「便利 vs 协议扩面」，
现在权衡的是「需求 vs 协议扩面」，同一份论证得出相反结论，这是前提变了，不是论证错了。

**目标表名从人手填升级为下拉**，ADR-0023 §7 的「不升级为选择」随之退役。三条理由：

1. **不对称本身是缺陷**——同一个建任务页，源端选表（`/api/builder/tables` 查 `ALL_TABLES`）、
   目标端打字，用户会理所当然地问「为什么这边不能选」。
2. **所有者给的实际场景**：用户往往只记得表名的一两个关键字，手打比选更难。
   因此**下拉必须支持关键字过滤**，不是纯滚动列表（落点归 [#123](https://github.com/liumingjian/db-qbs/issues/123)）。
3. **打错表名的失败模式被结构性消除**——`T_POSTION` 这种笔误此前要一路走到映射预检才拒；
   下拉产不出这个错，同 ADR-0036 §5「生成器结构性产不出坏形状」的论证。

**不做库清单端点，理由是硬的**：ADR-0037 §6 已把 `database` 定成 **MySQL 数据源自己的字段**。
用户建任务时先选数据源，库随之定死；**再给一个库下拉等于让任务推翻数据源的定义**，那是两个真相源。
目标端的层级因此是 `数据源(含库) → 表 → 列`，比源端的 `OWNER → 表 → 列` 少一级——
这是对的，不是缺一块。

**拦截层仍然只有映射预检一处。** ADR-0009 增补 §3 那句
「即便通道开出来，也不构成『构建器可以拿它做门禁』的授权」**一字不改**：
新端点喂的是选择面，不是判定面。构建器仍**只亮不判**（ADR-0023 §4）。
理由与当年同源且未削弱——`information_schema` 与运行时刻的目标表可以不一致，
拿它拦人就会制造「构建器放行了、预检却拒」与更糟的「构建器拒了、其实能跑」。

### 4. ADR-0009 §3 撤除：列名集合「完全相等」改成「子集」

> **原文**：两边列名集合必须完全相等（不多不少，比较统一大写，顺序无关）。
> **新规**：**投影出的目标列名集合必须是目标表列名集合的子集**（仍统一大写、仍顺序无关）。
> 反向多出来的——映射到目标表不存在的列——**照旧拒**。

这是所有者裁定 2 的兑现：「允许只搬选中列」。**只能全选就不叫『选目标字段』。**

**按 ADR-0034 §1b 点名失效模式——撤掉的这半防线原本挡的是什么：**

§3 当年防的是**按位置对齐的静默搬错**（调了 `SELECT` 里两列的先后，两列碰巧同类型，
预检全过，数据整齐灌进错的列）。**那条防线由「按名字对齐」提供，本次撤除不碰它**——
撤的只是「不多不少」里的**「不多」**那半句：目标表可以有投影里没有的列。

**「不多」这半句原本兜的是一个真实场景**：人少选了一列却没察觉，那一列在目标表里
从此恒为 `NULL`（或默认值），而 V1 只比行数（ADR-0006），**发现不了**。
**这条失效模式现在没有产品侧防线**，取而代之的是两件事：

1. **它不再是「静默」的**——列选择是用户在构建器里逐列勾的显式动作，
   映射面上「哪些目标列没被映射」是当场可见的（§3 的端点使之可见）。
   静默改值与「用户自己少勾了一列」是两类事，前者产品必须挡，后者产品挡不了也不该挡。
2. **§5 的新规则兜住其中真正会炸的那一档**（未映射列写不进去）。

**留时效**：若日后出现「少勾一列」的真实事故，正解是在映射面上加一条**提示**
（「目标表有 N 列未被映射」），**仍不是门禁**——门禁只有预检一处这条不因此松动。

### 5. ADR-0009 §5 重划：主键列 `NOT NULL`、非主键列可空，未映射列放默认值一条口子

> **原文**：目标表上已有 `NOT NULL` 的列，预检直接拒绝（不分选没选中）。
> **新规，三条：**
>
> 1. **被映射到的主键列：必须 `NOT NULL`。** 可空的主键列会让 `UNIQUE` 的多 `NULL` 语义
>    把 upsert 静默退化成纯 INSERT（ADR-0035 §2 已论证）。
> 2. **被映射到的非主键列：必须可空。** 原 §5 的理由一字不变——防的是源端 `NULL` 写不进去。
> 3. **未被映射的列**：若 `NOT NULL` **且无 `COLUMN_DEFAULT` 且非 `auto_increment`** → **拒**，
>    人话写「目标表的 `X` 列未被映射且不允许留空，请映射它或给它默认值」。
>    **`NOT NULL` 但有默认值 / `auto_increment` → 放行。**

第 1、2 条是所有者裁定 1 的兑现，**正式解开 ADR-0035 §2 与 ADR-0009 §5 的死锁**——
ADR-0035 §69–75 行当年只写了「本 §2 让路」，本 ADR 把它落成 §5 的正式条文。

第 3 条是本 ADR 自行判的，**代价与收益都要写清**：

- **收益**：`create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`、
  `is_deleted TINYINT NOT NULL DEFAULT 0` 这类审计列**根本不需要映射，靠数据库默认值自己填，
  实际完全跑得通**。严格按「非主键列可空」判会把它们全拒掉，提示是「请把 `create_time` 改成可空」——
  **那是让用户去改一张本来没问题的表**，而 db-qbs 不建表（ADR-0033 §4），改表的代价全在用户那边。
- **代价**：§5 从「一条规则、零例外」变成三分支。判断依据是**免费**的——
  `target_columns()` 那条 `information_schema.COLUMNS` 查询多取 `COLUMN_DEFAULT` 与 `EXTRA`
  两个字段即可，不增加任何来回。
- **失效模式已挡死**：未映射的非空无默认列会撞 `ERROR 1364 Field doesn't have a default value`，
  **第 3 条把它从运行中途提前到预检**。这是本 ADR 唯一新增的一条拒绝规则，
  它是 §4 放宽的配套，不是独立收紧。

**报告形态不变**（ADR-0009 §8）：一次报全部，逐列摆「列名 | 源端类型 | 目标端类型 | 违反规则」。
第 3 条的条目源列一栏写「（未映射）」。

### 6. 主键的勾选面：从已选列里勾，存目标列名

- 用户在构建器里**从已选中的列里勾主键**（ADR-0035 已定主键必选，勾中项存
  `TaskSpec.primary_key`，`task_spec.rs:138` 该字段已存在）。
- **存的是目标列名**（即映射后的名字），与 `TaskSpec.columns[].target` 同名空间，
  也与过线报文、sink 侧比对同名空间。
- **不做「读目标表 PK 自动带出、用户不用选」**：目标表可能有多条 `UNIQUE`，
  按哪一条去重是**业务判断**不是元数据事实；而且自动带出会让人以为产品替他确认过，
  这正是 ADR-0026「禁用状态本身会说谎」那条态度的同款。§3 的端点**可以把目标表的
  PK/UNIQUE 亮在旁边供参考**（只亮不判），但勾选是用户的动作。
- **真实约束的存在性由 sink 预检兜**（ADR-0035 §2 三条，一条不改）：勾的列在目标表上
  没有 `PRIMARY KEY`/`UNIQUE` 覆盖就拒跑。**构建器不拿新端点做这个判定**（§3 末段）。

### 7. 建表 SQL 的生成随映射走

ADR-0027 §4/§5 的建表 SQL 出口（单出口、常亮、`target_ddl.rs:43`）**形态不变**，
但**生成的列名改用 `ColumnMapping.target`**，否则生成的表与投影对不上，
人按它建完表预检照样拒——那正是 ADR-0027 §1 反方论据最怕的那一类错。

`target_date_col` 的预填相应改成**取业务日期源列的目标名**。
（ADR-0008 已由 ADR-0035 整体退役，此处只剩建表 SQL 那条索引的列名，见 ADR-0027 §5。）

### 8. 取表 / 取列结果纯瞬态

**ADR-0027 §7 原样推广到两个新端点**：结果只活在前端页面状态里，
**不进任务定义、不进 SQLite、刷新即丢**。理由与 §7 当年一字不差——
落盘就要回答「它过期没有」，而判断目标表结构变没变只有再查一次这一条路，缓存买不到任何东西。

**划清一条线**：**映射关系本身必须存**——`TaskSpec.columns` 里那对
「源列名 → 目标列名」是任务定义的一部分，进 SQLite；**目标表结构快照不存**。
这与 ADR-0036 §6「瞬态的取列结果不得粘进持久的任务定义」是同一条线的两侧。

### 9. 错误码闭集不增

照抄 #118 对 `test-connection` 的处置（`sink/src/http.rs:207`）：

- **连不上目标端** → `SINK_ENVIRONMENT` + `details.kind = "OTHER"`。
- **表不存在** → **返回空列表，不是错误**。这是有意的：表不存在与表存在但无列
  在 `information_schema` 里长得一样，硬要区分得多查一次 `TABLES`，
  而 UI 上「这张表取不到列」这一句话已经够用。

**ADR-0010 的 15 码闭集与端点语义一字不动**——新增的是三个「不属于任何 run」的端点，
它们不在 `/v1/runs` 的生命周期里，不参与 ADR-0012 的状态机。

### 10. 两套 `length` 同屏：界面标注单位，口径差写进时效

§3 的端点开出来之后，源列长度与目标列长度会**真的并排显示**：

- 源端 `BuilderColumn.length`（`sql_builder.rs:20`，走 `ALL_TAB_COLUMNS.CHAR_LENGTH`）——**字符**；
- 目标端 `target_columns()` 取的是 `CHARACTER_MAXIMUM_LENGTH`（`mysql_destination.rs:94`）——**字符**。

**两栏单位其实一致**，界面上都标「（字符）」即可（落点归 #123）。

**真正不一致的是预检**：它按 `SourceColumn.length`（驱动给的**字节**）判（ADR-0033）。
于是会出现——**界面显示的数与预检判的不是同一个数**，`utf8mb4` 下的中文列上尤其明显：
界面看着源列 10 目标列 10 刚好够，预检却说不够（源端 30 字节 > 目标端 10）。

**第一版不修**（ADR-0033 已定，地图 #117 收窄 3 明列「`length` 两套单位的统一」在 Out of scope）。
**但这句话必须写进时效段，不许只标个单位就算完**——否则现场第一个中文列就会撞上，
而没人知道为什么。UI 上贴一句静态说明（同 ADR-0027 §8 处理 `ERROR 1118` 的手法：零判定、零元数据）。

## 代价与时效

1. **ADR-0009 §3 的「不多」半句撤了，且没有替代防线**——见 §4 的失效模式点名。
   若出现真实事故，正解是加提示不是加门禁。
2. **§5 从一条规则变三分支**，这是第一版里第二次动 ADR-0009 §5
   （第一次是 ADR-0035 为主键破例）。**累积在此点名**：M1 立的「目标列一律可空」
   这条最简规则已经不复存在，后续任何再动它的提议都要先读本节。
3. **sink 的非 run 端点从 1 个变 3 个**，暴露面随之扩大。ADR-0037 §5 的记账
   （明知故犯不做鉴权、端口等价于全部数据源凭据）**原样适用，不因本 ADR 加码也不减轻**——
   新端点只读元数据、不写任何东西，而能连上 source 端口的人本来就能发起运行。
   **口令仍随请求过线明文**，ADR-0037 §4 的通道可信部署前提一字不改地覆盖这两个新端点。
4. **表 / 列下拉的加载时机**：每次点开都真连一次 MySQL（§8 不缓存）。
   表很多时首屏会慢——**无现象前不优化**，需要时的正解是前端做过滤而不是后端加缓存。
5. **`length` 口径差**：见 §10，留第一版之后。
