# ADR-0008: 业务日期谓词——源端收窄形状 + 目标端生成，等价性靠结构不靠人

**状态**: 已接受
**日期**: 2026-08-13
**关联**: [ADR-0002](0002-staging-table-atomic-swap.md)（关键约束一节由本 ADR 兑现）、
[ADR-0004](0004-parameterized-business-date.md)（业务日期参数化）、
[#24](https://github.com/liumingjian/db-qbs/issues/24)

## 背景

ADR-0002 结尾留了一条没有规则的关键约束：**清除条件必须与源端 WHERE 圈定同一批数据**。
这是 V1 **唯一一处「出事了校验也不会响」**的地方——行数校验只比对「源端读了多少行」与
「暂存表落了多少行」，两边都对，而清除条件多删或少删了一天的数据，目标表已经错了，
没有任何机制会发现。

ADR-0004 只说了「两者都由同一个业务日期推导」，没说这两个条件长什么样、由谁写。
而 ADR-0004 定的形状是**用户手写整条 SQL**（生产那条 70+ 列、带 dblink 的查询改一改就用），
与「消灭不等价的最强手段是两侧都由系统生成」正面冲突。本 ADR 在这条断层上做选择。

## 决策

### 1. 表达形式：源端收窄形状 + 目标端生成

任务定义提供三个字段，**不提供任何目标端 SQL 片段**：

```
source_date_col   源端日期列名
target_date_col   目标端日期列名
粒度              DAY（V1 唯一取值，不可配）
```

- **源端**：SQL 仍由人手写（ADR-0004 不变），但日期谓词的**形状被收窄**，
  必须**恰好出现一次** `:biz_date`，且构成半开区间（见 3）。预检解析并强制。
- **目标端**：**不写 SQL**。清除条件由系统按 `target_date_col` + 同一个业务日期生成。

两段可能不等价的 SQL 由此压成「一段被约束的 SQL + 一个不可能写错的生成条件」。

### 2. 等价性靠什么：靠生成 + 靠预检，不靠人

**这是对「V1 到底靠什么保证等价」的正面回答。** 不靠文档、不靠人工确认。
目标端条件是生成的，从结构上不可能与源端的日期范围错位。

**代价：源端 WHERE 里除日期谓词外不许有任何其他谓词。** 若允许
`d_aststat >= :biz_date AND d_aststat < :biz_date + 1 AND status = 'X'`，
生成的清除条件只按日期删，会把目标表里同日但 `status <> 'X'` 的存量数据一起删掉——
范围不等价，且校验依然抓不到。**预检硬拒**这种 SQL。

> **本决策放过了哪一类错误**：只剩一类——「按业务日期整天替换」这个搬运语义
> 本身不适用于该表（例如目标表里同一天的数据来自多个源）。这类错误预检看不见，
> 因为它不在 SQL 里，在业务假设里。V1 明确只支持「按业务日期整天替换」，
> 其他搬运语义不是被防住的，是**不被支持**的。

### 3. 边界语义：统一半开区间，不用等值

```sql
-- 源端（人手写，预检强制此形状）
WHERE a.d_aststat >= TO_DATE(:biz_date,'YYYY-MM-DD')
  AND a.d_aststat <  TO_DATE(:biz_date,'YYYY-MM-DD') + 1

-- 目标端（系统生成，人看不到也改不了）
DELETE FROM <target> WHERE <target_date_col> >= ? AND <target_date_col> < ?
```

**不用 `= TRUNC(D)` 形态。** 等值要求源端日期列零点对齐；一旦列里带时分秒，
等值会**静默漏数据**：源端读 0 行 → 暂存表 0 行 → 行数校验通过 → 目标表当天数据被删光。
这正是校验抓不到的同一类事故。半开区间对「纯日期列」与「带时分秒的列」**都正确**，
用户不需要判断自己的列是哪种，也就不存在判断错。

也不用 `TRUNC(<col>) = :biz_date`——语义对，但会废掉 `<col>` 上的索引。

### 4. `:biz_date` 的线上表示与时区

**业务日期是无时区的日历日**，线上表示为 `YYYY-MM-DD` 字符串，全程只此一份：

- **源端 Oracle**：`TO_DATE(:biz_date,'YYYY-MM-DD')` 显式给格式串绑定。
  已实测能穿 dblink 且远端仍是绑定变量（spike §5.3）。
  **不依赖 `NLS_DATE_FORMAT` 默认值**——会话 NLS 变了就换语义。
- **目标端 MySQL**：同一个字符串作为参数绑定给 `DATETIME` 列比较。
- **两端都不做任何时区换算，都不读会话时区。**

### 5. 目标日期列的约束

**目标表必须存在一个由 `source_date_col` 直接映射过来的列，`target_date_col` 只能是它。**
~~映射预检检查：该列在字段映射里，且其源列就是 `source_date_col`。~~不满足即拒绝运行。

> **2026-08-13 订正（[ADR-0016](0016-task-definition-form.md) §2.1，
> [#34](https://github.com/liumingjian/db-qbs/issues/34)）：M1 没有字段映射可查。**
> ADR-0009 §3 要求两边列名集合完全相等（统一大写、顺序无关），映射恒等，
> 于是任务定义里根本不存在一张映射表。本条**退化为一条纯字符串判定**：
> `upper(target_date_col) == upper(source_date_col)`。语义一个字没变——恒等映射下
> 「由 `source_date_col` 直接映射过来的列」就是同名列——只是判据从查一张不存在的表
> 变成了比两个字符串。M2 引入非恒等映射时本条改回原文。

「目标日期列由别的列推导/换算」不在 V1。

## 预检必须实现的四条（硬门禁，接在 ADR-0006 的映射预检上）

1. 源端 SQL 中 `:biz_date` **恰好出现两次**，构成 `<col> >= :biz_date AND <col> < :biz_date + 1`
   的半开区间，两处引用**同一列** `source_date_col`。
2. 源端 WHERE 中**不存在其他谓词**。
3. `target_date_col` ~~在字段映射中存在，且源列为 `source_date_col`~~ —— 见 §5 订正，
   M1 实为 `upper(target_date_col) == upper(source_date_col)`（[ADR-0016](0016-task-definition-form.md) §2.1）。
4. ADR-0004 的相对时间函数扫描（`SYSDATE` / `CURRENT_DATE` / `SYSTIMESTAMP`）继续生效。

> **2026-08-13 增补（[ADR-0016](0016-task-definition-form.md) §4，#34）——这四条在哪一端跑：**
> 第 1、2、4 条都要读 SQL 文本，而 **SQL 文本不跨 HTTP**（ADR-0010 报文定稿里没有它），
> 所以它们**结构性地只能在 source 本地跑，且发生在 `POST /runs` 之前**，
> 与 ADR-0009 §4 的「每列显式命名 / 表达式列精度不确定」合成一段独立的
> **「SQL 形状预检」**，一次报全部形状问题；不过则根本不发 HTTP 请求。
> 第 3 条只比两个配置字段，同段。ADR-0010 §3.1 那句「source 一个判断都不做」
> 的作用域随之收窄为「**逐列类型判定**一个都不做」。

## 代价

- 源端 WHERE 的表达力被压到「一天，全表」。带业务过滤条件的搬运任务在 V1 跑不起来
  （**跑不起来**，不是搬错——与 ADR-0003 类型白名单同一种代价选择）。
- 半开区间形状比 `= TRUNC(D)` 啰嗦，且用户原来那条生产 SQL 需要再改一次写法。
- 粒度只有 DAY。按月/按小时替换不支持。

## 2026-08-18 退役（ADR-0035）

**本 ADR 整条退役。** 它解决的问题是「源端 WHERE 与目标端清除条件必须圈定同一批数据」，
而 [ADR-0035](0035-upsert-write-model.md) §1 把写入模型换成主键 upsert 后**没有目标端清除条件**，
这个不等价面连同「V1 唯一一处出事了校验也不会响」的风险一起消失。
源端谓词的形状收窄（恰好一次 `:biz_date` + 半开区间）随之作废，改由
[#121](https://github.com/liumingjian/db-qbs/issues/121) 的条件形状校验接手。
**不是风险归零而是风险换位**：新的静默面是「目标表没有主键约束 → upsert 退化成纯 INSERT」，
由 ADR-0035 §2 的预检挡住。正文不删，作为历史保留。
