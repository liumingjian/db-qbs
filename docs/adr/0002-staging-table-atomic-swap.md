# ADR-0002: 暂存表 + 原子切换，校验作为强制门禁

**状态**: 已接受
**日期**: 2026-08-13

## 背景

三个诉求同时成立：重试语义是「清掉重来」、要保证源端与目标端最终一致、要有数据校验能力。
朴素做法（目标端先 DELETE 再逐批 INSERT）在任何中途失败时都会把目标表留在残缺状态——
旧数据已删、新数据没齐。对 POC 环境不可接受。

## 决策

数据先落**暂存表**，校验通过后**原子切换**进目标表。

```
1. 源端开任务，声明 run_id / 目标表 / 清除条件 / 业务日期
   └─▶ 目标端建 <target>__stg_<run_id>（结构复制自目标表）

2. 源端流式分页读 Oracle，每 5000 行一批推送
   ├─ 边读边累计行数与 checksum
   └─▶ 目标端批量 INSERT 进暂存表；批次带序号，断线可重推

3. 源端 commit，附上总行数（**封口点**：此后拒绝该 run_id 的任何批次写入）
   └─▶ 目标端校验暂存表实际行数
       ✓ 通过 → 单事务：DELETE target WHERE <清除条件>
                        INSERT target SELECT * FROM staging
                        DROP staging
       ✗ 失败 → DROP staging，返回错误，目标表未被触碰
```

**校验不是可选功能，是切换的前置条件。** 校验不过就不切换。

**V1 的校验内容只有行数**，行 checksum 推迟到 V2——防线前移到映射预检，
见 [ADR-0006](0006-count-only-verification-in-v1.md)。**映射预检因此是硬门禁**：
预检不过不许发起运行。

**commit 是暂存表的封口点。** 源端 commit 之后，sink 拒绝该 `run_id` 的任何批次写入，
拒绝是硬错误。否则一个迟到的重推批次落在「校验通过」与「切换」之间，
切换进目标表的就不是被校验过的那份数据——校验门禁在那一刻是空的。
封口点**之前**批次怎么重推、怎么幂等，是重试模型的事
（[#15](https://github.com/liumingjian/db-qbs/issues/15)）；封口点**之后一律拒绝**，是本 ADR 的事。

## 结论

- **清掉重来**：DELETE + INSERT 同事务，目标表无中间态。
- **重试安全**：任何一步失败，扔掉暂存表即可，目标表纹丝不动。重跑 = 换个新 `run_id` 重来一遍。
- **校验内建**：不需要额外做一套对账，校验就在关键路径上。行数不符即丢弃暂存表。
- **断点续传**：暂存表按批次序号幂等接收，断线后从未确认的批次续推，不用从头来。

## 代价

- 目标端峰值占用约两倍空间（暂存表 + 目标表）。100MB 量级可以忽略。
- 切换事务里 `INSERT ... SELECT` 10 万行会持有较长时间的锁。需实测；
  若成为问题，可退化为「暂存表 RENAME 成目标表分区」之类的方案，但 V1 不预先优化。
- 遗留暂存表需要清理机制（进程崩溃时 DROP 不会执行）——按 `run_id` 前缀定期回收。

## 关键约束

**清除条件必须与源端 WHERE 圈定同一批数据。** 两者范围不一致会直接造成目标表数据重复或丢失，
而校验只校验暂存表内容、校验不出这个错。见 ADR-0004——两者都由同一个业务日期推导，是唯一的防线。

## 增补（2026-08-13）：暂存表的命名、建表失败与孤儿回收

原文只说「建 `<target>__stg_<run_id>`，结构复制自目标表」，三件事没说：
结构怎么来、`run_id` 长什么样、建不出来怎么办。
[#32](https://github.com/liumingjian/db-qbs/issues/32) 补齐。

### 结构从哪来：见 ADR-0009 §7，本 ADR 不另立规则

暂存表 DDL **由映射预检的结果生成**，逐列照目标表的类型写，
**全列可空、无索引、无默认值、无主键**——不是 `CREATE TABLE ... LIKE`。
完整理由在 [ADR-0009](0009-m1-mapping-precheck-rules.md) §7，此处只记结论与两条推论。

> #32 讨论中一度倾向 `LIKE`（一条 SQL、与本 ADR 的 `INSERT ... SELECT` 切换语句天然对齐）。
> 作废，因为 ADR-0009 的三条前提把它的好处抽空了：§3 已要求**两边列名集合完全相等**，
> 「目标表有映射之外的列」这个分歧点不存在；DDL 生成器是 V1 **本来就要有**的
> （「只生成建表 SQL 给人执行」），复用它不增加代码；而 DDL 与预检读到的是**同一份元数据**，
> 不会出现「预检看的是一张表、实际建的是另一张」。

两条推论：

- **暂存表不带索引与唯一约束**，重复键不会在暂存阶段暴露，会留到切换事务里的
  `INSERT ... SELECT` 才炸。整 run 失败、目标表不动，代价可接受。
- **原文「结构复制自目标表」按此理解**：复制的是**列名、列序与列类型**，不是表的全部属性。

### `run_id` 的形态

**`<UTC 时间戳 14 位>_<6 位随机 hex>`**，如 `20260813091530_a3f19c`，21 字符。

**全链路只有这一个形态**——协议里、日志里、暂存表名里是同一个字符串，
不做「长 `run_id` + 短表名后缀」的二次派生：两个标识符对不上就是排障噩梦。

选它而不是 UUID，是因为表名要塞进 MySQL 标识符的 64 字符上限：

| `run_id` 形态 | 长度 | 留给目标表名 |
| --- | --- | --- |
| UUID（32 位 hex 无横杠） | 32 | 26 字符 |
| **`<14 位时间戳>_<6 位 hex>`** | **21** | **37 字符** |

时间戳段还白送一个能力：**孤儿暂存表的年龄可以直接从表名读出来**。
M1 没有状态存储，回收机制手上除了表名什么都没有。随机段兜住同秒并发。

**目标表名超过 37 字符时，映射预检拒绝该任务定义**——不在运行时截断表名。
这是 ADR-0009 §4 拒绝清单之外、由本 ADR 推给预检的一条。

### 建表失败：四类一律硬失败

**整 run 失败，目标表纹丝不动**（与「失败即整 run 失败」一致），
差别只在错误信息要分类到人能直接行动的粒度。

| 失败 | 处置 |
| --- | --- |
| **表已存在** | 硬失败。**绝不自动 `DROP` 重建**——那可能是另一个正在跑的 run 的活数据，删掉不可逆。报错须提示「可能是遗留暂存表，表名里的时间是 …」 |
| **权限不足** | 硬失败，报错须点名缺的是 `CREATE` 还是 `DROP`。不做预检期的 create/drop 探针：建表本就是预检通过后的第一个动作，失败得已经够早 |
| **`Row size too large`** | **不为它写处理代码——这类失败在本方案下不可能发生。** 暂存表逐列照目标表的类型建，行长与**已经建得出来的**目标表相同。修正 ADR-0009 §9：那条人话属于「建表 SQL 生成」（V1 只生成不执行，人拿去建目标表时才可能撞上），不属于建暂存表 |
| **其他**（磁盘满、连接断） | 归目标端故障，硬失败 |

### 孤儿回收：M1 不做

原文「代价」里的「按 `run_id` 前缀定期回收」**不在 M1**。
自问「没有回收，链路能不能从头走到尾」——能：遗留表只占空间，不挡任何新 run
（新 run 的表名必然不同）。M1 只交付两件让回收变廉价的东西：`__stg_` 中缀（可判别）
与 14 位时间戳（可判年龄），于是手工回收就是一句 `information_schema` 查询拼 `DROP`。

**代价说清楚**：崩溃遗留的暂存表会一直占着目标库空间，直到有人手工清。POC 环境接受。
