# ADR-0035: 写入模型改为主键 upsert，业务日期降级为普通过滤条件

**状态**: 已接受
**日期**: 2026-08-18

## 背景

起因是第一版闭环地图 [#117](https://github.com/liumingjian/db-qbs/issues/117) 的票
[#119](https://github.com/liumingjian/db-qbs/issues/119)。客户原话：

> 主键主要是用来去重使用的，方便进行 upsert。

以及在收口 grilling 中对「业务日期」的改判：

> 你说的业务日期是否有点局限了？WHERE 条件里面可以有业务日期，也可以有其他字段。
> 我们这里面不需要刻意去设置这个东西，它就是一个普通的 where 条件。

**现行模型**（`crates/sink/src/mysql_destination.rs:156-225`）：一个事务里
`SELECT COUNT(*)` 校暂存表行数 → `DELETE FROM 目标表 WHERE 业务日期 >= ? AND < ?` →
`INSERT ... SELECT` 从暂存表灌回。**全程不用主键**，幂等靠「同一业务日期的整段数据被完整替换」。
[ADR-0002](0002-staging-table-atomic-swap.md) 结尾把「清除条件与源端 WHERE 必须由**同一业务日期**推导」
立成硬约束，因为两者不等价会造成**静默数据重复/丢失**。

业务日期在现行系统里不是一条 WHERE 条件，是**一个参数化的 WHERE**：任务定义里选定
`source_date_col` / `target_date_col`（建任务时填），每次发起运行传 `biz_date`（运行时填），
并兼任并发互斥键（[ADR-0022](0022-concurrent-run-mutual-exclusion.md)）与历史筛选维度
（[ADR-0020](0020-m2-run-history-store.md)）。**本 ADR 换掉的是前提本身，不是补一段**，故单独立册。

本 ADR 是 [ADR-0034](0034-v1-scope-from-customer-needs.md) §2 表中「主键与 upsert 进第一版」
那一行的承载点，也是地图 #117 收窄 5 允许顶开搬运骨架的**唯一**一处。

## 决策

### 1. 写入模型换成纯 upsert，不再 DELETE

切换段改为 `INSERT ... SELECT ... ON DUPLICATE KEY UPDATE`，**去掉 DELETE**。
幂等不再靠「按业务日期区间整段重刷」，改由**目标表的主键 / 唯一约束**保证。

裁定的是 #119 三选一里的 **(a) 纯替换**，不是 (b) 并存。并存能保住三份已绿的台架不返工，
更便宜；但两种模式并存等于把「该选哪个」的解释成本推给用户，且第一版没有任何需求要「删除传播」。

**`ON DUPLICATE KEY UPDATE` 的更新列 = 全部选中列，排除主键列本身。**
语义是「同一主键的行，以本次源端数据为准」。不做部分更新——没有对应需求，且会引入
「这列这次没更新是有意还是漏了」的排查成本。

**代价，明写在此**：源端删掉的行**不会**在目标端消失（旧模型会，因为它先删整段）。
这是本次改判丢掉的唯一语义，第一版**不补兜底**（先 DELETE 再 upsert 的两段式同时继承两边的前提，最贵）。
需要删除传播的用户在第一版没有出路，见「时效」。

### 2. 主键由用户在构建器里选，由预检核对目标端事实

- **来源**：用户建任务、选表时从源列里勾主键列（恒等映射下源列名即目标列名——
  `sql_builder.rs:47` 的 `a.{column} AS {column}`，见 [ADR-0009](0009-m1-mapping-precheck-rules.md) 增补第 5 条）。
- **校验**：预检必须去目标表的 `INFORMATION_SCHEMA` 核对，**三条一并判，任一不满足即拒跑**：
  1. 勾选的主键列在目标表上确有 `PRIMARY KEY` 或 `UNIQUE` 约束覆盖；
  2. 主键列必须落在本次选中的列里；
  3. 主键列必须 `NOT NULL`。
- **为什么必须校验**（[ADR-0034](0034-v1-scope-from-customer-needs.md) §1b 要求点名失效模式）：
  目标表上没有对应约束时，`ON DUPLICATE KEY UPDATE` **静默退化成纯 INSERT**——不报错、写得进去、
  重跑就重复行。MySQL 的 `UNIQUE` 允许多个 `NULL`，主键列可空会造成同样的静默退化。
  db-qbs **不建表**（[ADR-0033](0033-char-length-byte-semantics.md) §4），那个约束是否存在产品说了不算，
  所以这条预检是撤掉 DELETE 防线后**唯一**挡住静默重复的东西。
- **不增错误码**：失败复用 `PRECHECK_FAILED`（422），`details` 里多一类 issue。
  [ADR-0010](0010-http-protocol-contract.md) 的 15 码闭集不动——增码要连带改 source 侧分类映射与 M3 诊断表，
  而这里本就是「开跑前的结构性拒绝」，语义完全落在 `PRECHECK_FAILED` 里。

### 3. 业务日期不再是一等公民，降级为普通过滤条件

**「业务日期」这个专有概念退役。** 它承载的两件事分开处理：

- **过滤**：变成构建器里的普通条件——「字段 + 比较符（`>` `<` `=`）+ 值」，可有若干条。
  第一版只做这一种最简形态，不做 `IN` / `BETWEEN` / `LIKE` / 表达式。控件与 SQL 生成归
  [#121](https://github.com/liumingjian/db-qbs/issues/121)，**本 ADR 只定语义**。
- **运行期传参**：每条条件的值来源二选一——**常量**（建任务时写死）或**运行时填**
  （发起运行时逐条填）。现行的 `biz_date` 退化成这个机制的一个普通实例，不再有专属地位。
  不支持 `sysdate-1` 这类相对表达式。**保留传参能力是必须的**：全部写死会让「每天导昨天的」
  变成每天改一次任务定义，那不叫闭环。

**四处硬编的日期逻辑一律降级，不留兼容双轨**（双轨会让每处判断都要问「这任务是老式还是新式」）：

| 位置 | 现状 | 改成 |
|---|---|---|
| `crates/sink/src/precheck.rs:132` | `target_date_col` 必须对应同名 Oracle DATE/TIMESTAMP 源列 | **删除**——upsert 后目标端根本不用日期 |
| `web/src/shape.ts:20` | 自定义 SQL 的 WHERE **强制**写业务日期半开区间 | 降级为「有条件就校验条件形状」；**允许无 WHERE 的整表取数** |
| `crates/source/src/server_main.rs:656` | 并发互斥键 = `task_id + biz_date`（ADR-0022） | 互斥键 = `task_id + 本次运行参数集`；无参数时退化成**同任务不许并跑** |
| 历史库 + 两处 UI（ADR-0020） | 按 `biz_date` 筛选与展示 | 改成「运行参数」列，值原样展示 |

**[ADR-0004](0004-parameterized-business-date.md) 与 [ADR-0008](0008-business-date-predicate-generation.md) 的处置**：

- **ADR-0004 的禁令维持**：SQL 里仍然禁止 `SYSDATE` / `CURRENT_DATE` / `SYSTIMESTAMP`
  这类相对时间表达式，理由（不可重放）一字不改。它的「业务日期提升为运行的显式参数」
  被**泛化**成本 ADR 的「条件值可标记为运行时填」——业务日期不再是那个参数的唯一形态。
  ADR-0004 的「UI 默认填昨天、可改，补数由此免费获得」在新形态下由「运行时填」继续兑现。
- **ADR-0008 整条退役**。它解决的问题是「源端 WHERE 与目标端清除条件必须圈定同一批数据」——
  新模型**没有目标端清除条件**，这个不等价面连同它的「V1 唯一一处出事了校验也不会响」的风险一起消失。
  它对源端谓词形状的收窄（必须恰好出现一次 `:biz_date`、必须构成半开区间）随之作废，
  改由 #121 的条件形状校验接手。**注意这不是风险归零而是风险换位**：
  旧模型的静默面是「清除条件多删少删一天」，新模型的静默面是「目标表没有主键约束 → upsert 退化成纯 INSERT」，
  后者由 §2 的预检挡住。

`sql_builder.rs:56` 写死的日期半开区间随之退役，源 SQL 的 WHERE 由用户条件生成；一条条件都没有时
**允许整表取数**。整表取数的量级风险由 [#122](https://github.com/liumingjian/db-qbs/issues/122)
的 10 万行 / 100MB 验收目标去证，不在这里挡。

**排序（字段 + 正序/倒序）对写入模型与幂等没有任何影响**（upsert 与行顺序无关），
它与过滤条件是同一个构建器控件面，一并归 #121；其性能代价（Oracle 端 `ORDER BY` 与
[ADR-0007](0007-single-query-streaming-fetch.md) 单查询流式叠加，可能拖长首行返回）归 #122 证。

### 4. 门禁断言与指标口径

- **切换段的行数断言改成区间**。现行断言 `swapped_rows == staged_rows`（`mysql_destination.rs:213`），
  而 MySQL 在 `ON DUPLICATE KEY UPDATE` 下 `affected_rows` **插入记 1、更新记 2**——
  这条等式会把**成功的任务全判成失败**。改为
  `staged_rows ≤ affected_rows ≤ 2 × staged_rows`，`sink_reported_rows` 仍报 `staged_rows`。
  区间断言仍能抓住「灌回时少写了行」这类真故障。
  **被否掉的另一条路**：切换后再 `SELECT COUNT(*)` 目标表——目标表本来就有别的批次数据，
  count 推不出任何等式，是死路。[ADR-0013](0013-verification-gate-row-counting.md) 的门禁四数口径按此补一句。
- **`purged_rows` 恒为 0**，字段保留。这句话是**真的**（确实没删任何行），不是拿 0 糊弄。
  [ADR-0010](0010-http-protocol-contract.md) §9 那条「推了 0 行、删了 8 万行」的便宜保险
  **随 DELETE 一起退役**——它报的警在新模型里没有对应的破坏动作。
  改名成 `updated_rows`（用 `affected_rows − staged_rows` 算命中更新的行数）是更好看的指标，
  但那是四份 ADR（0010/0013/0017/0020）+ 历史库 + UI 的账，没有需求推着，见「时效」。

### 5. 受影响断言清单（交给 #122 照单扩台架）

M1（9/9）、M2、M3（B1–B6 + canon 36/0）三份台架的绿**全部是在 DELETE 模型上取得的**，必须重跑。
已知必然要改的面：

- 任何断言「重刷后目标表行数」「重跑同一业务日期不出现重复行」的用例——保证方从 DELETE 换成主键约束，
  台架的目标表 DDL **必须显式带 PK/UNIQUE**，否则新预检会直接拒跑（这本身值一条负向用例）。
- 断言 `purged_rows > 0` 的用例——新模型恒 0。
- 任务定义里带 `target_date_col` / `biz_date` 的 fixture——降级后按普通条件重写。
- 新增负向用例三条，对应 §2 的三条预检：目标表无约束、主键列不在选中列里、主键列可空。

`STRATEGY-V1.md` 成功标准第 5 条「重跑同一业务日期，目标表不出现重复行」**保持不变**，
但保证方换成目标表的主键约束 + §2 的预检。

## 后果

- **[ADR-0002](0002-staging-table-atomic-swap.md) 结尾那条硬约束**（清除条件与源端 WHERE
  必须由同一业务日期推导）**整条退役**——不是修订，是新模型里根本没有清除条件。
  ADR-0002 的其余部分（暂存表、绝不 DROP 重建、事务内切换）**一字不动**。
  [ADR-0015](0015-staging-table-write-path.md) 的事务边界同样不动：切换仍是一个事务。
- **[ADR-0008](0008-business-date-predicate-generation.md) 整条退役**，
  **[ADR-0004](0004-parameterized-business-date.md) 的相对时间禁令维持**（§3）。
- **ADR-0022 的互斥结论不变**，只加一句键的退化说明（§3 表）。
- **ADR-0010 的错误码闭集不变**（15 码），§9 的 `purged_rows` 保险条目标注退役。
- **ADR-0013 门禁四数**：`sink_reported_rows` 的取值口径补一句（§4）。
- **改动面超出了「换写入模型」**：§3 连带重做了构建器的条件模型、互斥键与历史维度。
  这仍在 #117 范围内（#121 本就要做条件），但 **#119 与 #121 的边界重划为：
  #119 定语义，#121 定控件与 SQL 生成**。
- 三份台架必须重跑，期望值按 §5 改。**在跑之前，任何报告不许写「通过」**。

## 时效

**第二版重估。** 四条挂账，触发信号各自不同：

1. **删除传播**（源端删行不在目标端消失）——出现「源端会物理删行且目标端必须跟着删」的部署时重估，
   届时的正解大概率是把 (b) 并存或 (c) 两段式补回来。
2. **过滤条件的表达力**——只要出现 `IN` / `BETWEEN` / 多值 / 相对时间（`sysdate-1`）的真实诉求就重估。
3. **`purged_rows` → `updated_rows`**——下次已经要动 ADR-0010/0017/0020 时顺手做，不单独开。
4. **业务日期的运行期传参**——第一版是「常量 or 运行时填」二选一的最小形态；
   若出现「按调度自动推算日期」的需求（定时调度本身是 V1 非目标），这条要连带重做。
