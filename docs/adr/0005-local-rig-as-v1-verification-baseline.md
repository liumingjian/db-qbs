# ADR-0005: 以本地 Docker 台架为 V1 的验证基准，客户环境复验推迟到上线前

**状态**: 已接受
**日期**: 2026-08-13

## 背景

M0 的原始设计（#1、#2）假定 spike 能拿到客户生产环境：导出 `htbr45.t_r_fr_aststat@FA`
的真实列元数据与样本数据，在真实链路上验驱动。整个 M0 的依赖图都挂在这个假定上——
#2 阻塞 #5，#5 阻塞 #8，#8 决定 V1 用什么语言写。

**这个假定不成立：客户环境要不到。** 不是"暂时排不上"，是拿不到。

继续按原图走的后果是闸门永远关不掉，M1–M4 永远不启动。

## 决策

**V1 的验证基准改为本地 Docker 台架**（`docs/spikes/fixtures/local-rig/`）：
arm64 原生 Instant Client 19.32 → amd64 模拟的 Oracle XE 11.2.0.2 + arm64 原生 MySQL 8.0。

**客户环境的复验不取消，改为上线前的门禁**，见下面的「上线前必须复验的清单」。

### 判据的重新划线

台架能验什么、不能验什么，取决于**模拟层压在哪一侧**：客户端（Instant Client + 我们的代码）
跑在 arm64 原生上，服务端（Oracle）跑在 Rosetta 上。因此：

| 类别 | 台架上的效力 | 例子 |
|---|---|---|
| **客户端侧行为** | **完全可信** | 内存形状、每行处理开销、驱动类型保真度、错误特征 |
| **逻辑量** | **可信** | 网络往返次数、远端 SQL 的文本、执行计划形状、传输字节数 |
| **服务端绝对性能** | **不可信** | 10 万行要几秒、RTT |
| **服务端配置事实** | **不适用** | `NLS_CHARACTERSET`、11g 小版本、`@FA` 指向什么对象 |

**闸门判据只准建立在前两类上。** 后两类一律降级为「上线前复验」，不得作为闸门的通过条件——
否则闸门就是在拿一个测不出的东西卡自己。

### `NLS_CHARACTERSET` 这条为什么不能靠"再搭一个台架"绕开

台架是 `AL32UTF8`，XE 建库时定死，`ALTER DATABASE CHARACTER SET` 只允许向超集转，
`AL32UTF8 → ZHS16GBK` 是收窄，不放行。要 `ZHS16GBK` 的 11.2.0.4 只能拿 EE 介质自己 build，
需要 Oracle 账号与许可。**这条明确不做**，GBK 往返列入上线前复验。

## 上线前必须复验的清单

这些是**已知未验**，不是已通过。M4 收尾前必须在真实源端跑一遍：

| # | 复验项 | 为什么台架答不了 | 一旦不符会怎样 |
|---|---|---|---|
| 1 | `t_r_fr_aststat` 的真实列清单与类型 | 台架覆盖的是"类型面"不是"列清单" | 命中 ADR-0003 白名单外的类型 → 映射预检拒绝，需回炉扩白名单 |
| 2 | 真实单行字节 | 台架表 4 个窄列，生产 70+ 列 | 批次上限判据是「批次 × 单行字节」，行宽远超 3 kB 则批次要下调 |
| 3 | `ZHS16GBK` 中文往返 | 台架字符集改不了 | 中文乱码或长度截断 |
| 4 | 10 万行的真实吞吐 | 服务端在模拟层上 | 单次运行远超"几十秒"→ ADR-0001 的同步 IO 假设需复审 |
| 5 | 11g 小版本是否 ≥ 11.2.0.4 | 服务端配置事实 | < 11.2.0.4 则 19c Instant Client 不在认证范围，客户端版本要往下退 |
| 6 | `@FA` 指向的是表、视图还是同义词 | 服务端配置事实 | 非表则列投影下推行为可能不同，需按 #6 的办法复验 |
| 7 | 真实 run 时长与源库 `undo_retention` | 台架没有并发写入压力，也没有真实链路撑出的游标寿命 | run 时长逼近或超过保留时间时，`ORA-01555` 可能成为常态；DBA 保证需升为 M4 硬前置 |

采集脚本已备好：`docs/spikes/fixtures/`（`01-env-facts.sql` … `04-gen-boundary-samples.sql`），
拿到访问权当天就能跑，不需要重新设计。

## 已知代价

1. **闸门的把握度下降。** M0 原本要回答"Rust + ODPI-C 在真实生产链路上能不能用"，
   现在只能回答"在结构等价的台架上能不能用"。**类型保真、内存形状、投影下推这三条的
   证据强度没有下降**（都是客户端侧或逻辑量），下降的是吞吐与真实数据分布这两条。
2. **上线前复验若失败，代价比 M0 阶段失败大得多。** 清单里第 1、3 项若命中，
   是 M1/M3 的返工；第 4 项若命中，是 ADR-0001 的复审——那正是 M0 当初想在第 0 天挡住的。
   **这个风险是本决策买来的，必须写在明面上**，不能等出事了才说没测过。
3. **样本数据的真实分布缺失。** 台架的边界值是我们按 ADR-0003 构造的，
   覆盖的是"我们想到的边界"，不是"生产数据里真实存在的边界"。

## 备选方案

- **等客户环境**：闸门无限期挂起，M1–M4 全停。已否决——要不到就是要不到。
- **改用 EE 介质自建 ZHS16GBK 的 11.2.0.4 镜像**：能补掉清单第 3、5 项，
  但需要 Oracle 账号与许可，且 ARM 上仍要模拟，吞吐照样测不了。**成本不匹配收益，不做。**
- **直接回退 Java**：以"驱动风险验不透"为由回退。已否决——台架已经证实
  ODPI-C 的类型保真（#3，FAIL 0）与流式读（#5，内存与行数无关），
  **回退 ADR-0001 的触发条件一条都没触到**，拿"没验"当"验不过"用是错的。

## 影响

- ADR-0001 的「Oracle 驱动待 M0 spike 确认」由 #8 按台架证据收口，不再等客户环境。
- #2 从阻塞式事实采集改为上线前复验清单的载体，不再阻塞任何票。
- #1 的闸门判据 3「吞吐与内存可接受」拆为 3a 内存形状（台架可验，已过）、
  3b 客户端每行处理开销（台架可验，待做）、3c 服务端吞吐绝对值（台架不可验，转清单第 4 项）。

## 长驻形态下的台架扩展（2026-08-15 增补，[#59](https://github.com/liumingjian/db-qbs/issues/59)）

ADR-0019 把 `source` 从一次性进程改成长驻编排进程之后，本 ADR 假定的驱动方式
（exec 一次二进制、退出码 0/1 即结论）不再成立。扩展形态见
[ADR-0028 §2](0028-m2-acceptance-criteria-and-rig-extension.md)：宿主机后台起进程（**不进 compose**）、
轮询 `GET /api/tasks` 判就绪（**不新开健康端点**）、`SIGTERM` 优雅收尾。

**本 ADR 的效力划线（上面那张四类可信度表）一字不动。** M2 新增的被测面
——长驻进程起停、SQLite 历史、`/api` 响应、投影生命周期——全部落在第一类「客户端侧行为，完全可信」里。

**「上线前必须复验的清单」因此一条都不加**（ADR-0028 §10）：那份清单的入选标准是
**台架结构性答不了的服务端事实**，M2 没有新增任何这类事实。

## 台架是通用工具的正当基准，不是拿不到客户环境的退路（2026-08-16 增补，[#95](https://github.com/liumingjian/db-qbs/issues/95)）

> **2026-08-18 部分订正**：本增补的标题命题（台架是正当基准，不是退路）与「后果二/三/四」
> **全部维持**。**只有「后果一」被 [ADR-0034](0034-v1-scope-from-customer-needs.md) 改了一半**：
> 「单个部署的分布是一份样本、不能阻塞决策」继续成立；
> 「客户需求只是优先级输入、不能决定做什么」**已被推翻**——第一版的范围由客户实际需求定。
> 下文「客户环境是第一个部署，不是设计基准」这类措辞，读作**证据面的划线**，
> 不再读作**范围的划线**。已定的判定式（ADR-0030 / ADR-0031）不受影响。


本 ADR 的「背景」把台架写成**因为客户环境要不到才退而求其次**。这个叙述带偏了后续决策：
[#95](https://github.com/liumingjian/db-qbs/issues/95) 在判 M3 扩哪几种类型时，
把「客户生产库类型直方图」当成了扩类型的**必要前提**，拿不到就自称走「退路」。

**这是范畴错误，本增补订正它。**

`CONTEXT.md` 第一句写的是「数据查询导入服务」——db-qbs 是**通用的离线数据库导入方案**，
面向「任意两个网络隔离的 Oracle / MySQL 之间搬数据」，不是对某一个客户 schema 的定制开发。
客户环境是**第一个部署**，不是设计基准。

### 后果一：类型白名单按类型面判，不按命中分布判

**单个生产库的直方图是一份样本。** 它能回答「先做哪种类型收益大」，
**永远不能回答「一个通用工具必须支持哪些类型」**——后者由 Oracle 的类型系统与
MySQL 的可表达范围共同定义，与任何一个部署的实际用法无关。

因此：**扩类型的正确性判据是类型面覆盖 + 目标端往返实测，不是命中列数。**
分布数据只是**优先级输入**，缺了它不构成任何阻塞。#95 里那份「证据强度分档」
不是退路，**它就是判据本身**。

### 后果二：ADR-0005 正文的四类可信度表一字不动，但它划的是别的线

正文那张表回答的是「**台架能证什么**」（客户端侧行为可信 / 服务端绝对性能不可信），
与「**为什么用台架**」无关。本增补只改后者的叙述，不动前者的效力划线。

类型保真度、规范形式往返、映射预检行为、错误特征——**全部落在第一类「客户端侧行为，完全可信」**。
这正是台架能独立支撑类型决策的原因。

### 后果三：「已知代价」第 3 条降级

原文第 3 条「样本数据的真实分布缺失：台架的边界值覆盖的是我们想到的边界，
不是生产数据里真实存在的边界」——对通用工具，「生产数据里真实存在的边界」**本来就不可穷举**，
因为部署是开放集合。边界值只能、也应该**按类型的值域定义构造**
（[ADR-0003](0003-numeric-as-string.md) / [ADR-0014](0014-canonical-form-boundary-tests.md) 已经是这么做的）。

它仍是**某个具体部署的风险**（这份数据里有没有我们没想到的形态），
**不是设计的缺口**。降级为部署风险，不再作为「台架买来的代价」记账。

### 后果四：「上线前必须复验的清单」不撤，改性质

那七项的入选标准是「**台架结构性答不了的服务端事实**」——`NLS_CHARACTERSET`、11g 小版本、
`@FA` 指向什么对象、服务端吞吐、`undo_retention`。这些**每一个部署都要复验一遍**，
不是某个客户特有的。

因此清单**从「某客户的上线前门禁」升格为「部署前检查单」的雏形**，
条目一条不减，措辞里的「客户」应读作「该次部署的源端」。
清单第 1 项「`t_r_fr_aststat` 的真实列清单与类型」是唯一带客户色彩的一条，
它的通用形式是：**该部署要搬的表命中了白名单外的类型时，预检必须拒绝并点名到列**——
这已由 [ADR-0009](0009-m1-mapping-precheck-rules.md) §8 兑现，属现货能力，不是待复验项。
