# ADR-0011: 批次载荷的线上表示——按序数组、值只有 string 或 null、全程 UTF-8

**状态**: 已接受
**日期**: 2026-08-13
**关联**: [ADR-0003](0003-numeric-as-string.md)（规范形式——**落库规则**，本 ADR 定的是**线上表示**）、
[ADR-0007](0007-single-query-streaming-fetch.md)（批次是纯推送切分单位——本 ADR 给它加第二个切分条件）、
[ADR-0009](0009-m1-mapping-precheck-rules.md)（§6 字符集判 `utf8mb4`——本 ADR 补上另一半）、
[ADR-0010](0010-http-protocol-contract.md)（§3.3 列序基准、§10 传输参数——本 ADR 订正其中两处）、
[#27](https://github.com/liumingjian/db-qbs/issues/27)、
spike-0001 §4.6（批次 × 单行字节）、[#13](https://github.com/liumingjian/db-qbs/issues/13)（双重编码实测）

## 背景

ADR-0003 定下的规范形式是**落库规则**——同一个值写进 MySQL 时的唯一确定字符串表示。
但它同时被当成了**上线格式**在用：source 把值取成规范形式，经 HTTP 送到 sink，sink 写进 MySQL。
**中间这一段的表示从来没定过。**

「NULL 有专门标记，与空字符串区分」在内存里好说，**在 JSON 的字节里怎么表示是另一回事**——
而搞错的后果是静默把 NULL 变成空串，V1 只比行数（ADR-0006），**没有任何机制会发现**。

**本 ADR 与 ADR-0003 的分工**：ADR-0003 定**值长什么样**，本 ADR 定**这些值怎么装进报文**
（容器形状、NULL、类型的线上形态、字符编码、切分）。两者会被独立复审——换传输格式不该动落库规则，
反之亦然。

## 决策

### 1. 行的容器：按序数组，锚是 `source_columns`

```json
{ "seq": 1, "rows": [ ["1.23", "张三", null], ["0.5", "", "2026-08-13 09:15:30"] ] }
```

不用按名字的对象。70 列 × 5000 行要把列名重复 5000 遍，是纯冗余；更要紧的是
ADR-0010 §3.3 已经把 `POST /runs` 的 `source_columns` 顺序定为列序基准，
换成按名字等于让那条约定作废、并给「sink 必然要做的那次列序重排」多开一种走法。

**代价与它的对冲**：抓包看到的是一串裸值，「哪一列」要数到第 n 个。
换来一条**更强的检查**——**sink 收到 `row.len() != source_columns.len()` 即 `BAD_REQUEST` 硬失败**。
列名在报文里其实挡不住错位（重复列名、别名重名照样对得上），行长断言把列错位从静默变成当场炸。

### 2. NULL 用 JSON `null`，且线上只有两种形态

**每个值只能是 JSON string 或 JSON `null`，没有第三种。** 于是 `null` 唯一地表示 SQL NULL。

不用带内标记（形如 `"<NULL>"` 的哨兵串）。带内标记的死穴是**没有任何字符串在值域之外**——
`VARCHAR2` 能装下任意字节序列，标记选什么，就存在一个「值本身正好是那个标记」的输入
把 NULL 伪造出来。**攻击面在构造上归零，不是「难伪造」而是「不可表示」**：
JSON `null` 与 JSON string 在语法层就是两种东西。

Rust 侧类型直接落成 `Vec<Vec<Option<String>>>`，serde 天然不会把 `null` 与 `""` 混起来。

**规格条款**：解析器**不得**开启任何「`null` 视作空串」「空串视作 `null`」的宽容选项。
这条不留给实现判断。

### 3. 三种类型的线上形态：全部是 JSON string

| 类型 | 线上形态 | 由谁产生 |
|---|---|---|
| `NUMBER` | JSON string，内容是 ADR-0003 的规范形式串，**原样透传** | 驱动直出，source 只按文法校验（ADR-0003 的恒等校验） |
| `DATE` | JSON string `"YYYY-MM-DD HH:MM:SS"` | source 格式化（驱动给的是时间类型，这里是真的格式化） |
| `VARCHAR2` | JSON string，原样 UTF-8 | 驱动直出 |

**`NUMBER` 不得以 JSON number 传输。** 这是硬条款，不是偏好：接收端按 `f64` 解就是 15–17 位
有效数字，**ADR-0003 的全部前提当场毁掉，且毁得静默**——金额少几分钱，行数照样相等，
V1 的任何机制都发现不了。`serde_json` 的 `arbitrary_precision` 能保住，但那是一个
「默认关掉就丢精度」的雷，不能把全链路正确性押在一个 feature flag 上。

**转义完全交给 JSON 自己**（`"`、`\`、控制字符走 `\u00XX`），**不发明任何自定义分隔或转义**。
理由与第 2 节同源：一有自定义转义，就又冒出一个「值伪装成分隔符」的面。

### 4. 全程 UTF-8，唯一的转换点在源端驱动内部

生产库是 `ZHS16GBK`，链路后面全是 UTF-8。**转换发生在源端 ODPI-C 内部**——
连接的客户端字符集固定为 UTF-8，Rust 手里拿到的 `String` 已经是 UTF-8，
此后 JSON、HTTP、MySQL 全程不再转。

**规格条款**：ODPI-C 的客户端字符集**必须显式设置，不许依赖默认**。依赖默认正是
#13 踩过的那种坑（默认值在不同环境里不一样，且错了不炸只改字节）。

`Content-Type: application/json` **不带 charset 参数**——JSON 按 RFC 8259 就是 UTF-8，
带上 charset 参数反而开了「有人填 GBK」的口子。

**这一节的实测缺口照旧存在**：台架是 `AL32UTF8` 且改不了（ADR-0005），
`ZHS16GBK` 往返仍挂在 [#2](https://github.com/liumingjian/db-qbs/issues/2) 的上线前复验清单第 3 项。
本 ADR 定的是**在哪一层转**，不是「已经验过了」。

### 5. sink 侧连接层字符集：显式 `utf8mb4` + 开连接断言

ADR-0009 §6 判的是**目标列**的字符集。**列对了、连接层错了照样双重编码**——
#13 第一轮就是这么作废一整组结论的（`mysql` 客户端默认落 `latin1`）。这是同一个失效模式的两半。

**sink 的 MySQL 连接显式配 `utf8mb4`，并在开连接后断言**
`character_set_client` / `character_set_connection` / `character_set_results` 三个变量
全部为 `utf8mb4`，任一不符即失败并翻成人话。

**这条不进预检的逐列报告**：它跟列无关，且一失败就是整个 sink 不可用，
发生时点早于预检。态度与 ADR-0003 对驱动漂移一致——**正确性单点上宁可停机不要猜**。

> **2026-08-13 增补（[ADR-0015](0015-staging-table-write-path.md) §5，
> [#33](https://github.com/liumingjian/db-qbs/issues/33)）：本节并入「开连接仪式」，权威改在那边。**
> 字符集断言不是孤立的一条——同一条新连接在可用之前还要 `SET SESSION sql_mode = 'STRICT_ALL_TABLES'`
> 并回读断言、断言 `@@max_allowed_packet >= 64 MiB`。三件事是**同一个动作**，
> 分两处成文的唯一结果是将来有人加第四条时只改一处。
> ADR-0015 §4 同时回答了本节隐含却没问的问题：**sink 不 pin 连接，用连接池，
> 仪式挂在连接池的连接创建钩子上**——挂在业务代码开头的话，池子里第 2 条连接就是裸的。

### 6. 批次切分加字节预算：5000 行或 16 MiB，先到先切

M0 spike §4.6 已经写过一句话，本 ADR 兑现它：

> **真正的上限是「批次 × 单行字节」，不是批次行数。** 若 #2 拿回来的真实行宽远超 3 kB，
> 批次要按字节反算下调。

而 #2 拿不回来。按 §4.6 的 3 kB/行估，JSON 化后每值多两个引号一个逗号
（70 列 ≈ +210 B/行），**典型批次约 15 MB**——不是 ADR-0010 §10 写的「几 MB」，
差一个数量级，而且离 64 MiB 只剩 4 倍。真实行宽若是 15 kB（70 列里几个宽 `VARCHAR2` 装中文就够），
一批 75 MB，**撞 413 就是整 run 失败且无补救**：批次大小不可配，人除了改 SQL 少选几列
什么都做不了，还是跑到一半才炸。

**攒批时同时数已序列化的字节数，行数满 5000 或字节满 16 MiB，先到先切。**

- 这不动 ADR-0007 的定性：批次仍是**纯粹的推送切分单位**，按字节切只让 `seq` 多涨几个数，
  协议一个字不改。
- 它把「行宽超预期」从**跑到一半整 run 失败**降级成**批次变多、链路照常走完**——
  正是 M1「没有 X，链路还能不能从头走到尾」的取舍。
- 代价：批次不再恒为 5000 行，日志里 `seq` 与行数不能心算对上。ADR-0007 早已把序号
  定成诊断锚点而非幂等键，不受影响。

16 MiB 与 64 MiB 之间的 4 倍余量，是留给「单行本身就畸大」的呼吸空间。

### 7. 64 MiB 保留，但它是断路器不是上限

有了第 6 节的预算，ADR-0010 §10 的 64 MiB 退回它本该有的角色：**纯防御**。
M1 里触发 413 等同于「批次预算逻辑出了 bug」——**缺陷，不是故障**，
与 `INTERNAL_PRECHECK_ESCAPE`（ADR-0010 §7）是同一类东西。
`PAYLOAD_TOO_LARGE` 的 message 要按这个方向措辞，别让运维以为是数据问题。

### 8. 不压缩，`Content-Encoding` 的口子明确关闭

ADR-0010 §10 把「要不要开压缩」挂在本票上。**答案是不开，连口子都不留。**

理由不是「带宽够」，是 ADR-0010 §10 自己给的那条排障价值——不压缩时抓包能直接读出
是哪一列的什么值。M1 唯一的正确性防线是预检，出问题时**看得见报文**比省带宽值钱得多。
留一个「协商上可选」的口子等于允许两端就压缩与否分歧，而两个二进制永远同版本部署，
协商本身就是多余的。要压是 M2 的事，届时连同重试模型一起改。

### 9. 黄金 fixture：样例落成文件，不只落在文档里

规范形式的实现是**全链路正确性的单点**（ADR-0003 原话），文档挡不住实现漂移。

**`docs/spikes/fixtures/batch-payload-golden.json`** 是两端序列化 / 反序列化测试的共同输入。
除了本票要求的 NULL / 中文 / 38 位数值 / 日期四列，另加两列，因为它们**就是本 ADR 的攻击面**：

- 一列值恰好是**空字符串** `""` —— 钉死它与 `null` 在报文里长得不一样（第 2 节）；
- 一列 `VARCHAR2` 含**双引号、反斜杠与控制字符** —— 钉死转义走 JSON 自己那套（第 3 节）。

ADR-0003 的 NUMBER 边界值（`0.5` / `0.000` / `-0` / `007` / `1.2300000000`）
以多行样本进 NUMBER 那列。

## 报文定稿

`POST /v1/runs/{run_id}/batches` 的 `rows` 元素形状（ADR-0010 留给本 ADR 的那处）：

```json
{ "seq": 1,
  "rows": [
    ["12345678901234567890123456789012345678", "张三", "he said \"hi\" \\ done", "", "2026-08-13 09:15:30", null],
    ["0.5", null, "", "", "2026-01-01 00:00:00", "7"]
  ] }
```

列序 = `POST /runs` 的 `source_columns` 序（ADR-0010 §3.3）。
每个元素是 string 或 `null`，长度必须等于 `source_columns.len()`。

## 后果

**买到的**：

- **NULL 与空串在线上的区分是语法层的，不是约定层的**——不存在能伪装成 NULL 的值。
- `NUMBER` 的 38 位精度在协议上被正面保住，而不是靠「大家都记得别用 number」。
- 「批次 × 单行字节」这个 M0 就写下、一直没人接的上限，落到了实现能执行的形式。

**付出的**：

- **抓包时列名不在报文里**，定位靠数第 n 个值 + 行长断言。
- **批次行数不再恒定**，日志与监控不能假设 `rows == 5000`。
- **`ZHS16GBK` 往返仍未实测**（第 4 节）——本 ADR 只定了转换点在哪，
  真值等 #2 的客户环境复验。命中就是 M1 返工，这一条没有被本 ADR 消掉。
- **不压缩 = 内网跑约 300 MB / 10 万行**。M1 接受。

**对其他 ADR 的影响**：

- **ADR-0003** 只加一行指针（线上表示见本 ADR），内容不搬——同一个决策只住一个地方。
- **ADR-0007** 增补：批次切分加第二个条件（第 6 节），原文「批次大小只按行数，不设字节上限」由此订正。
- **ADR-0009 §6** 增补一行指针：字符集是两半，另一半（连接层）见本 ADR 第 5 节。
- **ADR-0010 §10** 增补：「几 MB/批」订正为约 15 MB；64 MiB 改判为断路器；
  `Content-Encoding` 的复审线由本 ADR 关闭。
- ADR-0002、ADR-0004、ADR-0005、ADR-0006、ADR-0008 不受影响。

## 时效

最可能触发复审的三条：#2 拿回的**真实行宽**（→ 16 MiB 预算与 5000 行的配比）、
#2 复验的 **`ZHS16GBK` 往返**（→ 第 4 节的转换点是否成立）、
M2 引入重试与压缩（→ 第 8 节）。
