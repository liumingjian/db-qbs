# ADR-0019: M2 的 source 进程形态——长驻编排 + 每 run 一个短命子进程，任务定义进 source 侧存储

**状态**: 已接受
**日期**: 2026-08-15
**来源**: [#48](https://github.com/liumingjian/db-qbs/issues/48)（地图 [#47](https://github.com/liumingjian/db-qbs/issues/47)）
**关联**: [ADR-0016](0016-task-definition-form.md)（**§3、§5、§7、§8、§9 由本 ADR 订正**）、
[ADR-0012](0012-run-lifecycle-and-state-authority.md)（状态权威与五态；本 ADR **不订正**它，只扩作用域）、
[ADR-0017](0017-run-log-format-and-contract.md)（日志契约，本 ADR 让 §5 从「承诺」变成「被依赖的接口」）、
[ADR-0010](0010-http-protocol-contract.md)（协议契约，一字不改）、
[ADR-0002](0002-staging-table-atomic-swap.md)（封口点与暂存表处置）

## 背景

ADR-0016 §时效原文：**「第 3 节的 one-shot 形态在 M2 引入 Web UI 与 SQL 构建器时整体重开：
届时 source 变长驻，ADR-0012 那五个状态会第一次真的有外部查询者，任务定义也会从文件挪进某种存储。」**

本 ADR 就是那次重开。M1 的 source 是一次性进程：`--config` / `--task` / `--biz-date` 三个启动参数、
跑完即退、退出码只有 0/1、没有入站接口。Web UI 要发起运行，这个形态在结构上不成立。

本 ADR 是 M2 地图的地基之一：鉴权定价、并发互斥、实时观察、验收判据四票的问题形状都压在它上面。

**M2 地图的主方向是本 ADR 的最强约束**：*让 M1 那条链路第一次有人能用地跑起来*——
M1 的搬运链路只被**包装**，不被**重写**。下面每一条决策都以此为判据。

## 决策

### 1. 拓扑：长驻编排进程 + 每 run 一个短命子进程

```
              ┌────────────────────────────────────────────────┐
              │ db-qbs-source（长驻，单进程单端口）                │
浏览器 ──HTTP─▶│  /      内嵌的 React 产物（静态资源）             │
              │  /api/* JSON API                               │
              │  ├─ 任务定义存储（SQLite，本进程是唯一写者）        │
              │  └─ run 登记（内存中的**投影**，非权威）           │
              └───────────┬────────────────────────────────────┘
                          │ fork + 读 stdout（JSON Lines，单向）
                          ▼
              ┌────────────────────────────────────────────────┐
              │ db-qbs-source-run（短命，= M1 那个一次性进程）     │
              │  ├─ 持有 Oracle 连接                            │
              │  ├─ 持有**权威 run 状态**（进程内存，ADR-0012 §1）  │
              │  └─ 按 ADR-0010 与 sink 通信，跑完即退（0/1）      │
              └───────────┬────────────────────────────────────┘
                          │ HTTPS（ADR-0010，一字不改）
                          ▼
                        sink
```

**谁长驻**：编排进程。**谁短命**：run 执行体，一个 run 一个。
**谁持有 Oracle 连接**：只有子进程。**谁持有权威 run 状态**：只有子进程，且只在内存。

被否掉的两条：

- **单进程（run = 长驻进程里的一个线程/任务）**：会让 ADR-0012 §2「进程一死 run 即不存在」
  第一次面对**进程活着但 run 没了**（线程 panic、run 被取消），那条推理要整个重新论证；
  且验收里「kill 源端」从 kill 一个进程变成语义模糊的动作，`run-m1-acceptance.sh` 的抓手全部失效。
- **UI 与编排分两层部署**：凭空多一套内部协议。收窄 2（不做鉴权、不做调度）撑不起这一层。

**选定形态的致命处也明写**：父进程要管子进程生命周期（回收、信号），
且父进程看到的 run 状态是**投影**（见 §4）——多了一个可能与权威不一致的读者。
这笔账用 §4 的明文降级偿付。

### 2. ADR-0012 §2 在新形态下**逐字仍然成立**

这是选 §1 的**首要理由**，不是副产品：

| ADR-0012 §2 的原文推理 | 在 M2 新形态下 |
|---|---|
| 状态纯进程内存，一字节不落盘 | 成立——权威状态仍只在子进程内存 |
| 进程一死 run 就不存在，重跑 = 新 `run_id` 从头 | 成立——死的仍是那个一次性进程 |
| kill 源端后的验收判据只能落在目标表上 | 成立——`run-m1-acceptance.sh` 的判据一条不改 |
| 落盘状态唯一的用途是事后取证，日志已全额覆盖 | 成立——日志契约反而被更严肃地依赖（§4） |

**父进程重启会让所有在跑的 run 一起消失**，这不是新缺口，正是同一条规则的直接推论。
「重启前跑过的 run 在 UI 上还看不看得见」是**历史**问题，归
[#49](https://github.com/liumingjian/db-qbs/issues/49)，本 ADR 不抢答。

### 3. 五个状态原样暴露，UI 文案不是状态

ADR-0012 §3 的 `PREPARING` / `STREAMING` / `COMMITTING` / `SUCCEEDED` / `FAILED`
**原样对外暴露**，不重命名、不新增。UI 上的中文（准备中／传输中／提交中／成功／失败）
是**展示层翻译，不是状态**；失败原因仍走 ADR-0010 §7 的十码闭集。

另起一套面向人的词汇会立刻造出 ADR-0012 §3 亲手拒绝的东西——**两套词汇描述同一件事，早晚漂移**。
而「按进程正在做什么命名」这个命名法在本形态下**比 M1 更准**：确实有一个进程与之一一对应。

两种 M1 不存在的边缘情形，**都不占状态名**：

- **已受理、子进程尚未进入 `PREPARING`**：父进程登记里的一个瞬时标记（「已受理」），不进五态。
- **子进程消失且无终态日志**（被 SIGKILL、段错误）：父进程记 `FAILED`，
  并标注**「进程消失，无终态日志」**。这是「进程一死 run 即不存在」在**有了登记者之后**
  唯一的新增语义：过去无人观察，现在必须能如实说出「它没了，我不知道它死在哪」。

### 4. 父子通道：单向读子进程 stdout 的 JSON Lines，父进程持有的是**投影**

父进程解析 ADR-0017 已定的 JSON Lines（`event` 闭集 + 逐事件必带字段）更新登记。
**不新增回调协议、不新增内部 HTTP、子进程零改动。**

否掉「子进程回调父进程本地 HTTP」的致命处：无论怎么设计，它都是 ADR-0017 §6 那套
`event` 词汇的**第二次表达**——ADR-0012 §3 拒绝过一次的同一种病；且子进程要改（多一个回调地址参数）、
要新增一套「回调失败怎么办」的错误处理，而 §1 的全部价值恰恰建立在子进程一行不改上。

**明文降级（照 ADR-0010 `GET` 那句的措辞）**：

> **父进程登记里的 run 状态是尽力而为的日志投影，不是 run 的权威状态。**
> 任何时候问「这个 run 现在怎么样」，权威答案的唯一来源仍是子进程的进程内状态与它的日志。

**代价明写**：ADR-0017 §5 的日志契约由此从「承诺」变成**被依赖的接口**——
父进程是它的第一个程序化消费者。**本 ADR 只声明「已被依赖」这个事实，
不定演进规则的收紧措辞**：收多紧取决于 [#49](https://github.com/liumingjian/db-qbs/issues/49)
选「引入历史存储」还是「消费日志」，那条措辞归它。

### 5. 任务定义进 source 侧存储；两个连接配置仍是文件

- **任务定义**从 `task-<name>.toml` 挪进 **source 侧本地 SQLite**（单文件），
  **长驻父进程是唯一写者**。
- **`source.toml` / `sink.toml` 原样保留为文件**——它们属**部署**，不属业务。

这让 ADR-0016 §5 那条论证在新形态下继续成立：ADR-0010 §8 不让 source 指定往哪个库写，
sink 的 `database` 依然不出现在 source 侧任何业务数据里。

**字段清单仍是 ADR-0016 §2 那四个**（`source_sql` / `source_date_col` / `target_table` /
`target_date_col`）。列选择进来后要不要加字段，归
[#52](https://github.com/liumingjian/db-qbs/issues/52)。

### 6. 任务身份：系统生成的 `task_id`，文件路径退场

ADR-0016 §7「任务的身份就是文件路径」的论证原文是「M1 **没有任务注册表、没有按 name 查找的使用者**」。
**Web UI 就是那个使用者**，前提消失。

- 任务身份 = **系统生成的稳定 `task_id`**，人给的名字是可改的展示字段，**不是身份**。
- ADR-0016 §6「未知字段严格拒绝」的**目的**（拼错字段静默生效）在表单 + 存储列约束下
  结构性不存在；TOML 层面的 `deny_unknown_fields` 对**任务定义**随文件一起退场，
  对两个连接配置**继续有效**。

### 7. 子进程的启动契约：父进程把定义物化成临时 TOML，M1 二进制一行不改

```
父进程：读 SQLite → 写临时 task TOML（0600）→ fork 子进程
子进程：db-qbs-source-run --config source.toml --task <临时路径> --biz-date <UI 传入>
```

命令行契约**一个字不改**。被否掉的两条：

- **子进程改收 `--task-id` 自己读 SQLite**：存储立刻有第二个读者，且子进程从此依赖存储，
  ADR-0016 §5「消费者只有一个」的同型论证破功。
- **通过 stdin 喂定义**：与 `--task <path>` 相比零收益，且让手工敲命令复现一次运行变难。

**临时文件的生命周期与权限一并定死**：`0600`；写在 source 数据目录下的固定子目录里，
文件名带 `run_id`；**子进程退出即删**；父进程启动时清扫该目录下的残留
（残留必然属于已经不存在的 run——§2）。

**退出码 `0`/`1` 保留不变，但作用域订正为「**子进程**的退出契约」**：
长驻父进程作为服务本身没有这个契约。ADR-0017 §1.1「`run_id` 由 JSON 行承载」继续有效。
`run-m1-acceptance.sh` 因此可以继续直接驱动子进程二进制，不经过 UI。

### 8. 取消运行：定义它，`COMMITTING` 中明确拒绝

UI 让起跑变廉价，也让「点一下就停」变成默认期待；而**这个动作在 §1 拓扑下已经存在**——
父进程本来就握着子进程句柄，人一定会去杀它。不定义它，行为就退化成「运维怎么杀的算怎么的」，
而 `COMMITTING` 中被杀恰是 ADR-0002 增补里代价最高的那条路径。

| run 处于 | 取消的行为 |
|---|---|
| `PREPARING` / `STREAMING` | 父进程发 `SIGTERM`，子进程走**已有的失败路径**（发 abort、清暂存表），终态 `FAILED` |
| `COMMITTING` | **拒绝取消**，如实告诉人「已过封口点，停不了」——ADR-0012 §7 第一次成为用户可见的规则 |

**不新增状态**：人取消的与跑挂的都是 `FAILED`，区别由 ADR-0010 十码里的既有失败码与
日志 `event` 表达。

### 9. 前端：React + TypeScript，外部构建，产物内嵌进二进制；UI 与 API 同进程同端口

**订正一条被写宽的前提**：CONTEXT.md 的「离线／离线带入」只约束**数据库主机**。
**source 与 sink 的服务机都可以出网**，彼此也能通过互联网通信。因此
「源端装不了 node」这个理由**不成立**，本节的选择另有理由。

- **技术栈**：React + TypeScript。
- **构建**：在开发机 / CI 构建，**源端不参与前端构建**。
- **交付**：产物 `dist/` **内嵌进 source 二进制**（`rust-embed` 一类）。
  理由是**交付物仍只有「一个二进制 + 两个 TOML」**，不引入第二个需要版本对齐的部署件——
  旁挂 `dist/` 目录与二进制版本错配是一个新失效面。
- **产物不进 git**，仓库只留构建脚本，产物随 release 走。
- **UI 与 API 同一个进程、同一个监听端口**：`/` 出静态资源，`/api/*` 出 JSON。
  另起端口只在要放不同鉴权 / 网关时才有意义，而收窄 2 明说不做鉴权。
- 与 [#55](https://github.com/liumingjian/db-qbs/issues/55) 的衔接：#55 产出 design system
  与 HTML 原型，本 ADR 只定「原型怎么变成被内嵌的 `dist/`」这条通道，不定组件库等细节。

### 10. sink 一行不改

sink 面对的仍然是「一个短命 source 进程按 ADR-0010 跑完一轮」。协议、墓碑、暂存表、
`GET` 语义全部原样。本 ADR **不新增错误码、不改任何报文**。

## 后果

- **ADR-0016 被订正的节**：
  - **§3**（one-shot 形态）——由 §1 整体取代，但其三条推论**全部继续成立**（见 §2）。
  - **§5**（三个配置文件分立）——任务定义那一份进存储，两个连接配置仍是文件，论证不变。
  - **§6**（未知字段严格拒绝）——对任务定义随 TOML 一起退场，对连接配置仍有效。
  - **§7**（身份即文件路径）——由 §6 的 `task_id` 取代。
  - **§8**（`--task` 显式必填 / 凭据明文）——`--task` 对**子进程**仍必填；
    「凭据明文靠 0600 兜底」的前提（机器在隔离内网）**已被 §9 的事实修正**，
    重新定价归 [#54](https://github.com/liumingjian/db-qbs/issues/54)。
  - **§9**（退出契约）——作用域缩到子进程，两个码不变。
  - **仍然有效、一字不改的**：§1（TOML 作为落地形式，对连接配置）、§2（四字段清单）、
    §2.1（`target_date_col == source_date_col` 字符串判定）、§4（SQL 形状预检在 source，
    发生在 `POST /runs` 之前）。
- **ADR-0012 一条不订正**，其 §2 的作用域从「M1 的一次性进程」平移到「M2 的 run 子进程」，
  推理逐字成立；§1 的「权威只有一份」新增一个**明文非权威**的读者（父进程投影）。
- **ADR-0017 §5 的地位变了**：它有了第一个程序化消费者，契约从「承诺」变成「被依赖的接口」。
  收紧措辞归 #49。
- **ADR-0010 与 sink 侧全部实现零改动**，M1 搬运链路被包装、未被重写——地图主方向兑现。
- **新增的失效面只有一个**：父进程与子进程之间的投影可能落后或缺失，
  由 §3 的「进程消失，无终态日志」与 §4 的明文降级共同兜住。

## 时效

- §1 的父子拓扑在 **M4 引入延迟批次重推**（ADR-0018）时重开：`INCOMPLETE` 是**跨进程**
  的可恢复状态，届时「run 状态只在子进程内存」第一次真的不成立。
- §5 的 SQLite 边界在 [#49](https://github.com/liumingjian/db-qbs/issues/49) 决定运行历史落法时
  **一并定形**（同一个存储还是两个）。
- §9 的「凭据明文」相关部分**已经在重开中**，见 #54。
