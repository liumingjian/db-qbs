# ADR-0003: 数值全程按字符串搬运，定义规范形式

**状态**: 已接受
**日期**: 2026-08-13

## 背景

生产查询里有大量 `N_*` 字段是金额与价格（`N_VA_PRICE`、`N_ORIG_MV`、`N_PORT_IV` 等，
单表 70+ 列中占多数）。Oracle `NUMBER` 是任意精度十进制，最高 38 位有效数字。

- 映射成浮点（`f64` / `DOUBLE`）会静默丢精度——金融数据不可接受。
- 映射成 Rust `rust_decimal` 只有 28–29 位有效数字，**覆盖不了 Oracle NUMBER 的完整值域**。

同时，落库必须对「同一个值」有唯一确定的字符串表示。

## 决策

**V1 不对数值做任何类型转换。** Oracle 侧读成字符串，规范化格式后原样写进 MySQL `DECIMAL`。

规范形式（V1 用于落库；V2 的行 checksum 复用同一套）：

| 类型 | 规范形式 |
|---|---|
| NUMBER | 十进制字符串；去除整数部分的前导零和小数尾零；**`\|x\| < 1` 时保留小数点前的 `0`**（`0.5`，不是 `.5`）；整数不带小数点；负号前置；零一律为 `0` |
| DATE | `YYYY-MM-DD HH:MM:SS` |
| `TIMESTAMP(n)`，`0 ≤ n ≤ 6` | `YYYY-MM-DD HH:MM:SS.ffffff`（固定 6 位，不足补零） |
| VARCHAR2 / NVARCHAR2 / CHAR | 原样 UTF-8；`CHAR` 保留尾部空格 |
| NULL | 专用标记，与空字符串区分（**线上表示见 [ADR-0011](0011-batch-payload-wire-format.md) §2：JSON `null`**） |

**本表是落库规则——同一个值写进 MySQL 时的表示。它怎么装进 HTTP 报文（容器形状、NULL、字符编码）是另一件事，见 [ADR-0011](0011-batch-payload-wire-format.md)。**

~~行 checksum = 各列规范形式按固定分隔符拼接后取 hash；整批做顺序无关聚合（XOR / 求和）。~~
**2026-08-13 修订**：V1 不做行 checksum，校验只比行数，见
[ADR-0006](0006-count-only-verification-in-v1.md)。**规范形式本身不变**——它是落库规则，
不只服务 checksum。变的是它的守护者：原本靠 checksum 事后发现违规，现在靠**映射预检**
在运行开始前拦住。

### NUMBER 的边界澄清（2026-08-13 补，见 [#10](https://github.com/liumingjian/db-qbs/issues/10)）

「去除前导零」只作用于**整数部分**，不吃掉小数点前那个表示「小于 1」的 `0`：

| 源值 | 规范形式 |
|---|---|
| `0.5` | `0.5` |
| `-0.01` | `-0.01` |
| `0.000` | `0` |
| `1.2300000000` | `1.23` |
| `-0` | `0` |
| `007` | `7` |

依据是实测而非口味：#3 用 `oracle` crate（ODPI-C）取值，**驱动直接给出的字符串就是上表右列**。
`sqlplus` / `TO_CHAR` 输出的 `.5` 是显示层行为，真正的搬运链路不经过 `TO_CHAR`，
不能拿它当规范形式的依据。

### NUMBER 的规范化定位：校验，不是重写

既然驱动输出已经是规范形式，`NUMBER` 上的规范化就是**恒等变换**，实现定位相应地定成**校验**：
按规范形式的文法校验驱动给出的字符串，合规原样放行，**不合规立即报错，不静默修正**。

`RE_CANON` 的具体文法见 [ADR-0014](0014-canonical-form-boundary-test-suite.md) §7。

```rust
fn canon_number(s: &str) -> Result<&str> {
    if !RE_CANON.is_match(s) {
        bail!("driver emitted non-canonical NUMBER: {s:?}");
    }
    Ok(s)   // 恒等
}
```

理由：静默重写会把「驱动换版本 / 换驱动 / NLS 设置漂移」这类行为变化兜住，让它以
「checksum 对不上」的形式在下游远处爆出来；报错则当场定位到源头。代价是驱动一旦漂移就跑不动，
这是想要的——全链路正确性的单点上，宁可停机也不要猜。

注意这条只覆盖 `NUMBER`。`DATE` / `TIMESTAMP` 仍是真正的格式化（驱动给的是时间类型不是字符串），
不适用「校验即可」。

### `DECIMAL` 精度与标度：目标形状精确匹配（2026-08-14 补，见 [#19](https://github.com/liumingjian/db-qbs/issues/19)）

> **2026-08-16：本节的判定式已由 [ADR-0031](0031-number-predicate-lower-bound.md) 取代
> （[#97](https://github.com/liumingjian/db-qbs/issues/97)）。** 精确匹配（`p' == p && s' == s`）
> **退役**，改为下界式 `s' >= s && p'-s' >= p-s`，对**推导形状**判。
> **当前 `NUMBER` 判定式是什么，只看 ADR-0031 §1。**
> 本节其余内容原样成立：推导仍然唯一、超出 `DECIMAL(65,30)` 仍直接拒、不要求人维护源端精度配置。
> 唯一被削掉的是「源列声明变化后目标列必须同步调整」那句运维成本——见 ADR-0031 §4.1。

**选择源目标精度/标度精确匹配，不用目标端重规范化代替映射门禁。**

这里的「精确匹配」不是把 Oracle 原始 `(p,s)` 无条件照抄，而是先按源类型推导唯一的
MySQL 目标形状，再要求目标列的 `(p',s')` 与该形状逐位相等：

| Oracle 源类型 | 唯一目标形状 | 预检判定 | 生效阶段 |
|---|---|---|---|
| `NUMBER(p,s)`，`0 ≤ s ≤ p` | `DECIMAL(p,s)` | `p' == p && s' == s` | M1 |
| `NUMBER(p,s)`，`s > p`（纯小数） | `DECIMAL(s,s)` | `p' == s && s' == s` | M3 |
| `NUMBER(p,s)`，`s < 0`（负标度） | `DECIMAL(p+\|s\|,0)` | `p' == p+\|s\| && s' == 0` | M3 |

后两条换算与精确匹配规则已经确定，但尚未进入 M1 白名单，等 M3 才生效。推导出的形状若超过 MySQL
`DECIMAL(65,30)` 的表达能力，预检直接拒绝，不截断。M1 的具体判定式和拒绝顺序见
[ADR-0009](0009-m1-mapping-precheck-rules.md) §2、§4。

选择精确匹配不是因为更宽的目标列必然改值。目标标度不小于源标度、整数位也不少于源端时同样保值，
但精确匹配的判定式最短，错误报告可以直接列出期望与实际形状，也不会为 V1 引入边界推理。
代价是合法的宽目标列也会被拒绝；这是「宁可停机也不要猜」在数值映射上的具体落点。

生产表 70+ 列不要求人再维护一份源端精度配置：源 `(p,s)` 每次运行都由游标 describe 取得，
人只需让目标表 DDL 与报告中的期望形状一致。预检会检查完全部列后一次性报告所有不匹配，
因此一次源表变更最多形成一轮 DDL 修正，不会变成逐列「改一处、重跑一次」的循环。
源列声明变化后目标列必须同步调整是本策略有意接受的运维成本。M3 若要放宽成「够大即可」，
必须另行复审本节的精确匹配决策。

目标端重规范化解决的是另一件事：MySQL `DECIMAL` 读回字符串会补齐到声明标度，
即使 `(p,s)` 精确匹配，`0.5` 从 `DECIMAL(38,2)` 读回仍是 `0.50`。因此精确匹配只保证
**数值不因映射被静默舍入**，不保证读回字节等于去尾零的规范形式。V1 不做行 checksum，
没有目标端重规范化的执行点；V2 若计算目标端 checksum，仍必须先按本 ADR 的 NUMBER 文法去尾零。
重规范化不能挽回已经在较小标度列上发生的舍入，故也不能取代本节的写入前门禁。

### 无精度声明的 `NUMBER`：人工定形，全量验值（2026-08-14 补，见 [#20](https://github.com/liumingjian/db-qbs/issues/20)）

**任务定义必须显式给出目标 `DECIMAL(p,s)`；预检不猜形状、不采样，也不把
`DECIMAL(65,30)` 当默认值。** MySQL 没有一个同时最大化整数位和小数位的 `DECIMAL`：
`(65,30)` 只剩 35 个整数位，既装不下 Oracle `NUMBER` 可表示的 38 位整数，也装不下标度超过
30 的小数。当前数据的最小形状同样不能代表列的业务域或未来写入，因此不能自动固化成目标 DDL。

M3 放行这类列时，映射预检按以下顺序执行。下文 `p` / `s` 均指任务定义中配置的值：

1. 配置必须满足 MySQL 约束 `1 <= p <= 65`、`0 <= s <= 30`、`s <= p`；目标列必须恰好是
   配置的 `DECIMAL(p,s)`，否则拒绝。这是上一节「目标形状精确匹配」在源端没有声明形状时的
   退化规则：精确匹配的是**人工配置与目标列**，不是不存在的源 `(p,s)`。
   **2026-08-16 订正（[ADR-0031](0031-number-predicate-lower-bound.md) §3）**：
   「目标列必须**恰好**是配置的 `DECIMAL(p,s)`」放宽为同一条下界式
   `s' >= s && p'-s' >= p-s`，比较对象仍是**配置**。
   **第 2 条全量值域校核的基准不变，仍是配置而非目标列**——目标列是容器，配置是人声明的域。
2. 在与本次取数查询相同的 `FROM` / `WHERE` 和绑定参数范围内，对结果集做**全量**值域校核。
   候选值 `x` 可无损写入 `DECIMAL(p,s)` 当且仅当 `x = TRUNC(x,s)` 且
   `ABS(x) < POWER(10,p-s)`。预检以数值运算统计
   所有不满足条件的非 `NULL` 值；`invalid_rows > 0` 即拒绝，不截断、不舍入。

```sql
SELECT NVL(SUM(CASE
         WHEN n_bare IS NOT NULL
          AND (n_bare <> TRUNC(n_bare, :scale)
               OR ABS(n_bare) >= POWER(10, :precision - :scale))
         THEN 1 ELSE 0
       END), 0) AS invalid_rows
  FROM <与取数查询相同的来源>
 WHERE <与取数查询相同的业务谓词>;
```

同一结果集有多列裸 `NUMBER` 时，在一条聚合查询里为每列各算一个 `SUM(CASE ...)`，只扫一遍。
这个检查对命中的结果集是 `O(行数 × 裸 NUMBER 列数)`；通常必须读取全部候选行，会增加一次源端
扫描和逐值数值运算。业务日期谓词、分区裁剪和既有索引仍可缩小结果集，但不能用抽样换掉全量检查。
若源库承受不了这次扫描，该列保持拒绝，不提供「带风险放行」开关。

`MAX(LENGTH(TO_CHAR(...)))` 不是判据：长度混入负号与小数点，受格式/NLS 影响，长结果还可能使用
科学计数法；更重要的是，在样本上算任何精确指标都不能证明未抽中的值可表示。上述两个数值谓词
分别直接证明「没有超过 `s` 的有效小数位」和「整数位不超过 `p-s`」。

全量预检仍与后续取数是两条语句，源表并发写入可能在两者之间引入新极值。因此搬运时每个
`NUMBER` 规范字符串在进入批次前必须再按同一 `(p,s)` 做有界的位数校核：去掉符号后，小数位数
不得超过 `s`；整数部分为 `0` 时按 0 个整数位计，否则不得超过 `p-s`。失败即中止整个 run，
不得把该值交给 MySQL。已写入的批次仍只在暂存表中；source 在 commit 前进入既有的 abort
清理路径。即使 abort 失败而留下孤儿暂存表，目标表也不会被触碰，source 也不会发出
[ADR-0002](0002-staging-table-atomic-swap.md) 的 commit 封口请求。这样「预检后出现极端值」最多造成
显式整 run 失败，不会变成静默舍入；采样漏值不作为可接受风险存在。

### V1 类型白名单：表上没有的，预检直接拒绝（2026-08-13 补，见 [#11](https://github.com/liumingjian/db-qbs/issues/11)）

上面的规范形式表从「已知类型的清单」升格为**白名单**：**只有表中列出的类型允许进入搬运链路**。

| V1 白名单 | 规范形式 |
|---|---|
| `NUMBER` / `DATE` / `TIMESTAMP(n)`（`0 ≤ n ≤ 6`）/ `VARCHAR2` / `NVARCHAR2` / `CHAR` / `NCHAR` / `NULL` | 见上表 |

白名单之外的一切类型，**映射预检阶段报错拒绝，不静默按某种默认形式搬过去**。#3 在台架上
实测读得出、但 V1 明确不支持的有：

| 排除的类型 | 为什么不是「补一行规范形式」就能收的 |
|---|---|
| `BINARY_FLOAT` / `BINARY_DOUBLE` | 二进制浮点不是十进制精确值，**「一律走字符串」对它不构成无损往返的保证**。#3 实测 `1.7976931348623157E+308` 取成字符串是 **309 位十进制展开**；这个值落进 MySQL `DECIMAL` 必然溢出，正确的目标类型是 `DOUBLE`，而 `DOUBLE` 上的 checksum 又不能按字符串比。要支持就得引入 shortest-roundtrip 十进制表示或 IEEE-754 位模式，那是**另一条搬运通道**，不是本 ADR 补一行的事 |
| `RAW` / `LONG RAW` / `BLOB` | 字节本身无损，但表示法（十六进制大小写 / Base64）必须钉死一种两端才可比；且 `BLOB` 是流式大对象，与「行 checksum = 各列规范形式拼接」的内存模型冲突 |
| `CLOB` / `NCLOB` / `LONG` | 文本规则可与 `VARCHAR2` 同，但超长值同样打破行拼接的 checksum 模型，且目标端要 `TEXT`/`LONGTEXT`，「预检比对 `DECIMAL(p,s)` 精度」那套规则在这里不适用 |

### TIMESTAMP 的标度上限：超过 6 位即拒绝（2026-08-14 补，见 [#12](https://github.com/liumingjian/db-qbs/issues/12)）

Oracle `TIMESTAMP(n)` 允许 `0 ≤ n ≤ 9`，但本 ADR 的规范形式和 MySQL `DATETIME(6)` 都只能
保留 6 位小数秒。因此白名单里的 `TIMESTAMP` **只指 `0 ≤ n ≤ 6`**；未显式声明标度的
`TIMESTAMP` 默认 `n = 6`，也在此范围内。

**决定：映射预检读取游标 describe 返回的 `OracleType::Timestamp(n)` 小数秒精度，`n > 6` 时
在取数前报错拒绝。**
当前 M1 已按 [ADR-0009](0009-m1-mapping-precheck-rules.md) 拒绝全部 `TIMESTAMP`；本条约束的是
M3 放行 `TIMESTAMP` 时必须增加的分支，不能因 M1 暂时用不到而省略。

三种方案的代价不对称：

- **预检拒绝（采用）**：代价是该列跑不起来，但失败在开跑前可见，源值与目标表都不受影响。
- **允许并截断（排除）**：第 7–9 位非零时会静默丢精度，V1 的行数校验仍会通过。先扫值域再决定
  是否放行，会把结构性门禁变成依赖数据的额外全表扫描，且仍接受了目标类型表达不了的源声明。
- **规范形式改为 9 位（排除）**：MySQL `DATETIME` 最高只有 6 位，改成 9 位仍存不下；改存字符串
  又会失去日期类型的比较、日期函数与索引语义，不是本 ADR 的日期搬运通道。

这里宁可承担「跑不起来」的显性代价，也不接受「搬错了且行数仍相等」的静默代价；与白名单制
及 `NUMBER` 漂移时拒绝而非重写是同一条原则。

### `TIMESTAMP` 的规范形式定长 6 位，与列声明的 `n` 无关（2026-08-16 补，见 [#105](https://github.com/liumingjian/db-qbs/issues/105)）

上表 `TIMESTAMP(n)` 那一行写的是「`YYYY-MM-DD HH:MM:SS.ffffff`（固定 6 位，不足补零）」。
**M3 放行 `TIMESTAMP` 时，这句话被追问过一次**：`TIMESTAMP(0)` 列上的
`2026-08-13 14:35:09`，规范形式到底是 `...09` 还是 `...09.000000`？

**裁定：`...09.000000`。定长 6 位补零，`canon_timestamp` 的签名里没有 `n`。**

| 源列声明 | 值 | 规范形式 |
|---|---|---|
| `TIMESTAMP(0)` | `2026-08-13 14:35:09` | `2026-08-13 14:35:09.000000` |
| `TIMESTAMP(3)` | `2026-08-13 14:35:09.120` | `2026-08-13 14:35:09.120000` |
| `TIMESTAMP(6)` | `2026-08-13 14:35:09.120000` | `2026-08-13 14:35:09.120000` |

**理由不是「本表已经这么写」，是一条更硬的分层**：

> **规范形式是值的性质，不是列声明的性质。**

`n` 是列元数据。[ADR-0014](0014-canonical-form-boundary-test-suite.md) §6 已经把「长度装不装得下」
「精度装不装得下」整类推给映射预检，理由正是它们是**类型的性质**；`n` 与它们同类。
让 `canon_timestamp` 读 `n`，等于把列元数据引进 ADR-0014 §3 那个**零环境依赖**的纯函数层——
那一层的输入至今只有「驱动给出的字符串」与「结构化时间分量」两种，两种都是值。

**顺带订正 [#105](https://github.com/liumingjian/db-qbs/issues/105) 票正文一处**：
票里写「钉错会把 `DATE` 与 `TIMESTAMP(0)` 的可逆性一起带塌」。**直接塌的不是可逆性**——
即便规范形式随 `n` 走，推导形状仍是 `DATE → DATETIME(0)`、`TIMESTAMP(n) → DATETIME(6)`，
一列一型（[ADR-0030](0030-m3-type-whitelist.md) §3）。真正的危险是**滑坡的第一步**：
一旦承认「规范形式随 `n` 走」，「推导形状为什么不随 `n` 走」就有了论据，
而 ADR-0030 §3 已经算清那一步的终点是 `TIMESTAMP(0) → DATETIME(0)` 与 `DATE` **正面相撞**。
**定长 6 位切断的是这条滑坡，不是相撞本身。**

**并订正票正文第二处**：票里写「定长 6 位从没有断言钉过」。实际上
`docs/spikes/fixtures/canon-golden.json` 的 `_grammar.TIMESTAMP_OUTPUT`
（`^[0-9]{4}-[0-9]{2}-[0-9]{2} [0-9]{2}:[0-9]{2}:[0-9]{2}\.[0-9]{6}$`）已是机器可读的定长断言，
`ts-zero-frac` 用例也已钉死「小数秒为零 → `.000000`」。**缺的只有「`n=0` 的列声明也走同一条」这一维**，
而按上面那条分层，这一维根本不存在于纯函数的输入里——**它由本节这句话钉死，不由新增用例钉死**。

`canon_timestamp` 这个纯函数本身的规格（签名、三条输入断言、错误变体、边界用例清单）
见 [ADR-0014 §12](0014-canonical-form-boundary-test-suite.md)。

### 为什么现在就排除，而不是等真实类型清单

本条的先决输入本来是 [#2](https://github.com/liumingjian/db-qbs/issues/2) 的生产表真实类型清单——
清单里没有的类型不必定规范形式。但客户环境短期不可达，#2 推不动。

选择**先排除**而不是先定义，理由是**两种错法的代价不对称**：

- 排错了（清单里真有 `CLOB`）→ 预检**当场报错**，映射跑不起来，缺口立刻暴露，回来补 ADR。
- 定错了（为一个未必存在的类型编了规范形式）→ 无人验证的规范形式成为全链路正确性单点的一部分，
  以「checksum 对不上」的形式在下游远处爆出来。

这与本 ADR 对 `NUMBER` 规范化取「校验而非静默重写」是同一条原则：**正确性的单点上，宁可停机也不要猜。**

因此 #2 的类型清单从**阻塞项降级为验收项**：拿到客户环境后跑
`docs/spikes/fixtures/03-type-census.sql` 的「11g 遗留类型点名检查」一段——
返回空则本决策成立；有命中则按命中的类型逐一回炉，重开 #11。

## 理由

绕开所有 decimal 库的精度上限，链路上不存在任何可能丢精度的环节。
更重要的是**可验证性**：「不做转换」比「正确地做转换」容易验证一个数量级——
测试只需断言字符串进出一致，而不是穷举精度边界。

## 代价

- 字符串比二进制数值占带宽多。100MB 量级可接受。
- MySQL 目标列若 `DECIMAL(p,s)` 的标度小于源值，插入时会**静默舍入**。
  **V1 去掉行 checksum 后，这个错没有下游机制会发现**（行数照样相等），
  因此「映射预检提前比对精度」从建议升为**硬门禁**，见
  [ADR-0006](0006-count-only-verification-in-v1.md) 与
  [#19](https://github.com/liumingjian/db-qbs/issues/19)。
- 规范形式的实现是全链路正确性的单点。必须有专门的、覆盖边界值的测试套件。
  **2026-08-13：该套件的规格已由 [ADR-0014](0014-canonical-form-boundary-test-suite.md) 定下**
  （黄金 fixture `docs/spikes/fixtures/canon-golden.json`，`RE_CANON` 的具体文法见其 §7）。
- 白名单把「未支持的类型」变成**跑不起来**而不是**搬错**。若生产表真的含 `CLOB` 之类，
  V1 在预检阶段就停住，需要回炉补 ADR 再跑——这是刻意选的代价，见上文「两种错法不对称」。
