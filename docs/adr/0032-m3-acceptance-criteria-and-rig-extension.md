# ADR-0032: M3 的验收判据分两面落，台架另起第三个入口；边界值矩阵写死进规格

**状态**: 已接受
**日期**: 2026-08-16
**决策票**: [#103](https://github.com/liumingjian/db-qbs/issues/103)（地图 [#94](https://github.com/liumingjian/db-qbs/issues/94)）

## 背景

`STRATEGY-V1.md` 给 M3 写的验收是「目标表少一列 / 标度不足 / 类型不兼容三种情况，
预检都能在跑之前拦下并说清楚」。**这三条 M1 就已经过了**
（[ADR-0009](0009-m1-mapping-precheck-rules.md) §4 的拒绝清单 + M1 验收 9/9）。
M3 的验收必须重写，且要覆盖本图真正买到的东西：
**每一种新放行的形态都端到端搬对了，每一条新拒绝规则都真的拦得住。**

同时票正文里有一处与现状的错位，先摆正，它决定本 ADR 的整个骨架：

> [ADR-0028](0028-m2-acceptance-criteria-and-rig-extension.md) §1 把判据面画在 `/api/*` 上，
> 分界线是「这条断言失败时，是**规格**错了还是**渲染**错了」。**这条线对 M3 不够用**——
> M3 买的东西观察面回到了 M1 那一侧：「每种新类型搬对了」的断言对象是
> **MySQL 目标表里的值**，不是 `/api` 响应。M3 要切的不是「规格 vs 渲染」，是「**值 vs 报告**」。

本 ADR 定**判据、矩阵与台架形态**，不写脚本——地图 #94 的终点是规格定稿。

## 1. 断言面两面并存，新写一句分界线

**M3 的自动断言落在两个面上**，与 ADR-0028 §1 那句**并列，不替换**：

> **这条断言的对象是「一个值搬得对不对」，还是「一份报告说得对不对」——
> 前者落目标表，后者落 `/api`。**

| 断言对象 | 落点 | 归属 |
|---|---|---|
| 一个值搬得对不对 | **MySQL 目标表逐值** | M1 那套 DB 面 |
| 一份报告说得对不对 | **`source` 的 `/api/*` 响应** | M2 那套 API 面 |

两面都不做的**否定命题**（「不该发生的事没发生」）走**日志判**，先例是 ADR-0028 §4
的「`sink` 零请求用日志判，不抓包」，本 ADR §5 复用它，不发明第二套机制。

**为什么不能压成一面**：把往返保真挤进 `/api`，会逼出一个「读回目标表」的新端点——
擦 [ADR-0027](0027-target-ddl-generation-and-cross-end-metadata.md) §3「协议一字不动」封条的边，
而买到的只是一次断言的形式统一；把报告断言挤进 DB 面则**根本无处可断**，
预检报告不落库（run 失败时暂存表一张都不建）。

**浏览器自动化继续拒，理由一字不变**（ADR-0028 §1）。

## 2. 新开第三个入口 `run-m3-acceptance.sh`

三个入口并列，M3 验收的前置要求是**先跑绿 M1 与 M2 那两份**。

**拒掉「往 `run-m2-acceptance.sh` 里塞 A15…」**：那份入口的失败含义是「可操作性坏了」，
混进「`NUMBER(4,35)` 没搬对」会让退出码不可读。

**拒掉「往 `run-m1-acceptance.sh` 里塞」**，尽管它已经是 DB 面、看起来最顺手：
理由与 ADR-0028 §8 拒掉「把 M1 改写成经 UI 发起」同源——**M1 那 9/9 是不受后续里程碑影响的常量**，
往里加新类型等于让这条基线随白名单漂移，白名单一改基线就失效，而它本该是常量。

**已知代价**：「M3 验收通过」这句话从此需要**三个文件**才能支撑
（ADR-0028 已知代价 5 的那个「两份」由本 ADR 改成三份）。

| 层 | 前缀 | 内容 | 进 CI |
|---|---|---|---|
| 台架层自动断言 | **`B1`–`B6`**（新前缀） | §4 | **否** |
| 纯函数层 | **续 F 系列**（`F3` / `F4`） | §6 | **是** |

## 4. B 系列：台架层自动断言（本 ADR 的主交付物之一）

按**制造手段**归并，不按形态归并——九行形态一次搬完，按形态切会重复起 run。

| # | 场景 | 制造手段 | 断言面 | 断言 |
|---|---|---|---|---|
| **B1** | 九行形态正面往返 | 一张宽表、一次搬完 | **目标表逐值** | §4.1 矩阵逐格 |
| **B2** | 拒绝面一次报全 | 一张「全违规表」 | `/api` 预检报告 | §4.2 逐列一条 + 总计对得上 + **暂存表一张不建** |
| **B3** | `TIMESTAMP(n>6)` | 单拎一列 | `/api` + `sink` | 拒绝点在 sink（ADR-0027 §3.1 + 协议 `fsp` 字段），不是预检 |
| **B4** | 裸 `NUMBER` 值域校核·正面 | 表中含超域值 | `/api` 报告 **+** 目标端 | 该列一条不合规记录（`invalid_rows`）**且暂存表一张不建**；附记录项见 §9 |
| **B5** | 值域校核·否定命题 | 全常规形态任务 | **`source` 日志** | 该窗口内**零值域校核 SQL** |
| **B6** | 公元前日期 | BC `DATE` 行 | 整 run 失败 | `SourceReadError` / `FailureKind::SOURCE_VALUE`，**带列名与原值**；目标表不动 |

**B5 不可省**。它证的是一个否定命题：**不含裸 `NUMBER` / 数值表达式列的任务不得触发那次源端全表扫描**。
不验的话，[ADR-0030](0030-m3-type-whitelist.md) §4.3 认下的那笔扫描代价会以
**「预检怎么突然这么慢」的性能事故**形式在客户现场爆出来，而不是在台架上。

**B3 必须与 B2 分开**。`TIMESTAMP(n>6)` 的拒绝发生在 **sink**，混进 B2 那张全违规表会让
「一次报全部列」的断言**横跨两个进程**，失败时分不清是谁没报。

### 4.1 B1 的边界值矩阵——值本身就是规格

**矩阵写死在本 ADR 里，不只写选值规则。** ADR-0014 §7 那套「清单不完备 → 文法进规格」的论证
在这一层**反过来**：台架层没有「文法」这种东西可写，**逐值比对的值本身就是规格**。
不写死，实现者会挑好造的值（`1.23`、`ABCD`），而危险面恰恰在难造的那些。

**选值依据两类，分工写死**：**域端点**买「链路没截断」，**已实测的静默变形点**买「防线真的在」。
后者**每一条都必须能指回一个 spike 小节号，指不回去的用例不许进**——这是 ADR-0014 §4
「目标端往返值只作反向锚点」在台架侧的同款约束，防止用例退化成臆想出来的畸形值。

| 形态 | 源列 | 目标列 | 边界值 | 出处 |
|---|---|---|---|---|
| **1** 常规 `NUMBER(p,s)` | `NUMBER(38,2)` | `DECIMAL(38,2)` | `0` / `1.23` / `-0.01` / 36 整数位撑满 / NULL | §7.8 组 2 |
| **2** 纯小数 `s > p` | `NUMBER(4,6)` | `DECIMAL(6,6)` | `0.000001` / `-0.000001` / `0.009999` / `-0.009999` / `0` / NULL | §7.11 组 1（原样取值） |
| **3** 负标度 `s < 0` | `NUMBER(8,-2)` | `DECIMAL(10,0)` | `9999999900` / `-9999999900` / `12300` / `12400` / `0` / NULL | §7.11 组 2（原样取值） |
| **4** 裸 `NUMBER` **+ 表达式列** | 裸 `NUMBER` 列 + 一个 `a*b` 数值表达式列 | 配置 `DECIMAL(20,4)` | `0` / `1.2345` / `-99999999999999.9999`（撑满配置）/ NULL | ADR-0030 §4 |
| **5** `VARCHAR2(n)` | `VARCHAR2(10 CHAR)` | `VARCHAR(40)` | `ABCD` / `AB`+8 空格 / 10 空格 / `甲乙`+8 空格 / NULL | §7.8 组 1、组 4 |
| **6** `NVARCHAR2(n)` | `NVARCHAR2(10)` | `VARCHAR(10)` | `甲乙`+尾空格 / `ABCD` / NULL | §2.2 + §7.8 组 1（**首次端到端**） |
| **7** `CHAR(n)` / `NCHAR(n)` | `CHAR(10 CHAR)` + `NCHAR(10)` | `VARCHAR(40)` + `VARCHAR(10)` | `AB`（驱动给 `"AB        "`）/ 全空格 / `甲乙` / NULL | §2.2 + §7.8 组 1、组 4 |
| **8** `DATE` | `DATE` | `DATETIME(0)` | `0001-01-01 00:00:00` / **`0044-01-01`** / **`0999-12-31`** / `9999-12-31 23:59:59` / `2026-08-13 14:35:09` / NULL | §7.9 + §7.12 |
| **9** `TIMESTAMP(n)`，`0 ≤ n ≤ 6` | `TIMESTAMP(0)` / `(3)` / `(6)` 三列 | `DATETIME(6)` ×3 | `...09`（n=0）/ `...09.120`（n=3）/ `...09.120000` / `...09.999999` / NULL | §7.8 组 3（**n=0 / n=3 首次**） |

出处小节号全部指 [`docs/spikes/0001-oracle-driver.md`](../spikes/0001-oracle-driver.md)。

> **形态 5/7 的目标列宽 2026-08-18 由 [ADR-0033](0033-char-length-byte-semantics.md) 订正**：
> `VARCHAR2` / `CHAR` 的 describe 长度是驱动给的**字节数**（AL32UTF8 下 `10 CHAR` → 40），
> 而下界式 `n' >= n` 按字符比，故目标列建 `VARCHAR(40)`；N 族拿到的是字符数，形态 6 仍是 `VARCHAR(10)`。
> **边界值与 §4.3 的期望值一格不动**——加宽目标列不改变存进去的字节。

三条读法必须跟着矩阵一起写进规格，否则矩阵会被误用：

1. **形态 4 的表达式列进 B1 正面，不另开场景。** 裸 `NUMBER` 与数值表达式列的判定式**逐字相同**
   （ADR-0030 §4 花了整章说它们是一回事），拆开验等于在台架上承认它们是两回事。
2. **每行都带一个 NULL 值，不单列一条 NULL 场景。** ADR-0011 的「NULL 是 JSON `null`、
   不进 `canon_*`」是**语法层**性质，逐形态验才能证它没被某个新分支绕过；
   单列一条只能证「某一种类型上 NULL 没坏」。成本是每行多一个值，近乎为零。
3. **形态 8 的公元 1–999 那两值（`0044` / `0999`）不许省。** [#99](https://github.com/liumingjian/db-qbs/issues/99)
   判「公元 1–999 原样搬不改」，这是那四条裁定里**唯一一条会被后来者当成疏漏改掉的**——
   没有台架用例钉着，看见 `0001` 能过就以为覆盖了，而**三位数年份的补零是独立的一段**（§7.12 实测）。
4. **形态 9 的「边界值」一列写的是源值，不是期望值**（2026-08-16 补，
   [#105](https://github.com/liumingjian/db-qbs/issues/105) 裁定后加）。`TIMESTAMP(0)` 列上写进去的
   确实是无小数秒的 `...09`——把这一格改成 `...09.000000` 反而会让人以为源端能写出六位零。
   **它的规范形式与 `DATETIME(6)` 读回值均为 `...09.000000`**（[ADR-0003](0003-numeric-as-string.md)
   「`TIMESTAMP` 的规范形式定长 6 位」），**§4.3 的逐字节比对比的是后者，不是这一列**。

### 4.2 B2 的全违规表

一张表、一次预检、一份报告、**逐列一条、总计对得上、暂存表一张不建**。

| 违规列 | 期望报出 | 出处 |
|---|---|---|
| `BINARY_FLOAT` / `BINARY_DOUBLE` | 白名单外 | ADR-0030 §2 |
| `CLOB` | 白名单外 | ADR-0030 §2 |
| `col1 \|\| col2` 字符表达式列 | 白名单外 | ADR-0030 §2 |
| 字符列，但目标建成 `CHAR(10)` | 目标 `DATA_TYPE` 必须 `varchar` | ADR-0030 §1、§5 |
| `NUMBER(38,-30)` → 推导 `DECIMAL(68,0)` | `p' > 65` 前置判定 | **ADR-0030 §6，F3 的台架侧见证** |
| `NUMBER(4,35)` → 推导 `DECIMAL(35,35)` | `s' > 30` 前置判定 | ADR-0030 §6 |
| 目标表少一列 / 类型不兼容 | M1 老三样回归 | ADR-0009 §8 |

**归并成一张表的收益不只是省 run**：它**顺手兑现 ADR-0009 §8「一次报全部列」**——
那条规则至今只有 M2 的 A3 在**形状**预检那半边验过，**映射**预检这半边没有任何见证。

`NUMBER(38,-30)` 那一行是本图最贵的一条：[#101](https://github.com/liumingjian/db-qbs/issues/101)
查出「生成侧前置判定仍判源 `(p,s)`」这个会真炸的漏洞（吐出 `DECIMAL(68,0)` → `ERROR 1426`），
台架侧的见证只有它。

### 4.3 期望值口径：默认逐字节，`DECIMAL` 族必须例外

| 形态 | 判定 |
|---|---|
| 5 / 6 / 7 / 8 / 9（字符族与日期族） | **`HEX()` 逐字节相等**（照 §7.8 先例，排除排序规则与 PAD 语义的干扰） |
| 1 / 2 / 3 / 4（`DECIMAL` 族） | **读回值 == 「按目标列标度补零后的规范形式」**，不是 == 规范形式本身 |

**`DECIMAL` 那条例外不是宽容，是必须。** §7.8 组 2 第 3 条与 §7.11 组 1 结论 3 已量死：
**逐位相等保值不保字节**——`0.5` 写进 `DECIMAL(38,2)` 读回 `0.50`，因为规范形式**去尾零**
而 `DECIMAL` **总补齐到声明标度**。不单列这条口径，九行里的 `NUMBER` 四行会**全部假 FAIL**，
然后被人用「那就改成语义相等吧」一把削掉，**连带把真正的静默舍入一起放过**。

**形态 9 的 `TIMESTAMP(0)` 规范形式已由 [#105](https://github.com/liumingjian/db-qbs/issues/105)
裁定：`...09.000000`，定长 6 位，`canon_timestamp` 的签名里没有 `n`**——见
[ADR-0003](0003-numeric-as-string.md)「`TIMESTAMP` 的规范形式定长 6 位」与
[ADR-0014 §12](0014-canonical-form-boundary-test-suite.md)。**B 系列用例引用它、不自定**
（两票各定一遍必然漂移，而 ADR-0030 §3 把「推导形状恒为 `DATETIME(6)` 不随 `n` 走」架在那句上）。
因此形态 9 三列的期望值分别是 `...09.000000` / `...09.120000` / `...09.120000`——
**三个 `n` 的期望值形状完全一样，这正是「规范形式是值的性质、不是列声明的性质」在台架上的样子**。

### 4.4 不开新 `task` 票补实测缺口

`TIMESTAMP` 只在 `n=6` 实测过、`NVARCHAR2` 的源端与目标端是分开量的——这两个缺口**不先取证**。

理由：**往返保真的期望值是先验的**（逐字节相等 / 按标度补零后相等，§4.3 已定），
不需要先跑一遍才知道该期望什么。**M3 验收台架跑起来，那一跑就是取证本身。**
先开 `task` 票等于把同一次实测跑两遍，第二遍还叫「验收」。

## 5. 纯函数层与台架层的分界线

**分界写死：判定式与推导形状全部归纯函数层（进 CI）；台架层只买「真 MySQL 认这张 DDL，且值真的搬对了」。**

灰区三块按这条线各归各位：

| 灰区 | 归属 | 为什么 |
|---|---|---|
| ADR-0030 §6 的前置判定改判**推导形状** | **纯函数层 F3**（+ 台架 G1 作独立见证） | 判定式是纯函数，零环境依赖 |
| #101 查出的**生成侧**前置判定漏洞 | **纯函数层 F3**（同一条断言两侧各判一次） | 同上 |
| #102 定的 `TargetDdlError` **复数化** | **纯函数层 F4** | 结构形状，与数据库无关 |

**#105 的边界同时生效**：`canon_*` 与它的边界断言归 #105（纯函数层），
**往返保真归本票（台架层）**。两票不重叠、也不留空——分界点就是「交给 sink 的那个字符串」
（ADR-0014 §3 已画过同一条线）。

## 6. F 系列扩两条，并兑现 ADR-0028 已知代价 4

| # | 场景 | 断言 |
|---|---|---|
| **F1**（**扩**） | 建表 SQL 生成器 ↔ 映射预检不漂移 | 覆盖面从 `tier = m1` 三种类型**扩到 ADR-0030 §1 的九行形态** |
| **F2** | 历史保留期清理 | 不动 |
| **F3**（新） | 前置判定判的是**推导形状**不是源 `(p,s)` | `NUMBER(38,-30)` → `DECIMAL(68,0)` 与 `NUMBER(4,35)` → `DECIMAL(35,35)` 双向判死；**判定侧与生成侧各判一次** |
| **F4**（新） | `TargetDdlError` 承载**多列** | 多个白名单外的列，错误结构里逐列都在（#102 查出的单列结构撑不住 ADR-0027 A4） |

**F1 的扩就是 ADR-0028 已知代价 4 的兑现**：那条代价原文写「M3 扩类型时，不漂移的证据要跟着扩，
否则 DDL 生成器与映射预检可以在新类型上悄悄分家」。本节把它从「已知代价」改成「已做」。

**F3 不能只有纯函数层。** 纯函数层里判定函数自己判自己不构成证据——生成器与预检可以
**同时错**（#101 查出的正是这种同时错）。独立见证在 §7 的 G1。

## 7. 台架层手工门禁：G1 就地扩，不新增字母

| # | 场景 | M3 的改动 |
|---|---|---|
| **G1** | 真在 MySQL 上执行生成的 DDL → 真 `describe` → 真跑映射预检 | **覆盖面扩到九行形态**；`NUMBER(38,-30)` 那一列的期望是**生成侧就拒**，不是吐出 `DECIMAL(68,0)` 让 MySQL 报 `ERROR 1426` |
| **G2** | `run-canon-gate.sh` 规范形式门禁 | 一字不改（新增用例由 #105 加进 fixture，门禁机制不动） |

**ADR-0014 §8 的触发条件加第五条：M3 验收时必跑一次。** 与第 4 条（M2 验收）同构，
**不新开第二套机制**——这是 ADR-0014 §8 与 ADR-0028 §3.3 已经用过两次的形态。

## 8. 渲染面：另立 `m3-visual-walkthrough.md`，不重跑整份 V1–V25

[#102](https://github.com/liumingjian/db-qbs/issues/102) 已判 **M3 零设计系统改动**
（`docs/design-system/README.md` 与 `tokens.css` 一字未动），故 ADR-0028 §6 的**第 2 条触发条件不成立**，
**整份 V1–V25 不重跑**。

但确有五处新信息位 + 一处 `web/src/app.css` 的失败态改动，#102 把用例甩给了本票。
落 `docs/spikes/fixtures/local-rig/m3-visual-walkthrough.md`，**W1–W6 六条**，
触发条件两条、形态与 M2 那份同构。

**不并进 `m2-visual-walkthrough.md`**：并进去之后「跑过 M2 走查」这句话的含义会随 M3 漂移，
理由与 §2 的三入口分立完全同源。

## 9. 报告形态：不采通用性能数，唯一新增记录项是值域校核的代价

**沿用 ADR-0028 §5：M3 不采任何通用性能数**，M1 那七个数继续留在 M1 那份入口里采。

**唯一新增的记录项**（挂在 B4 上）：**裸 `NUMBER` 预检的值域校核耗时 + 扫描行数，原样贴进报告。**

它值得单列，理由是 ADR-0030 §4.3 自己写死的那句——**这笔代价不许以
「预检怎么突然这么慢」的形式在下游爆出来**，而**台架是它唯一的暴露面**。
形态照抄 ADR-0028 §5「唯一新增的记录项是一致性对照」那个先例。

报告落 `docs/spikes/fixtures/local-rig/m3-acceptance-<UTC>.md`，
**场景 × PASS/FAIL + 每条断言的实际值原样贴**，
**不许写「通过」**（ADR-0014 §8 第 3 条）。

## 10. CI 口径一字不改

| 层 | 进 CI |
|---|---|
| 纯函数层 F1–F4 | **是**（全部零依赖） |
| 台架层三个入口（M1 / M2 / M3） | **否** |
| `run-canon-gate.sh` | **否** |
| 人工走查（V 系列 / W 系列） | **否**，不给退出码 |

理由与 ADR-0014 §8 一字不变：把结构性跑不了的东西写进流水线，等于让它长期红着或长期被跳过。

## 11. ADR-0005 的「上线前必须复验清单」一条都不加

那份清单的入选标准是**台架结构性答不了的服务端事实**。M3 新增的东西**全都是台架测得准的**——
类型往返、预检拒绝、值域校核、DDL 生成，落在 ADR-0005 效力表的第一类。

[#99](https://github.com/liumingjian/db-qbs/issues/99) 那条候选「换 MySQL 大版本要重测 `DATETIME` 值域」
已判**承载点是台架断言**，本 ADR 把落点钉死：**B1 形态 8 的六个域端点用例**
（`0001` / `0044` / `0999` / `9999-12-31 23:59:59` / 常规值 / NULL）。
换 MySQL 大版本时重跑 `run-m3-acceptance.sh` 即是重测，**不需要清单上多一行提醒人去做**。

## 对既有 ADR 的订正与增补

- **ADR-0014 §8 增补**：台架层手工门禁的触发条件加**第五条——M3 验收时必跑一次**（本 ADR §7）。
- **ADR-0028 增补**：§1 的分界线在 M3 上**不够用**，本 ADR §1 并列新写一句「值 vs 报告」；
  §8 的「两个入口」在 M3 变三个（§2）；**已知代价 4 由本 ADR §6 兑现**，已知代价 5 的「两份报告」改「三份」。
- **ADR-0005 不动**：§11 说明 M3 不给上线前复验清单加任何条目，**效力划线一字不动**。
- **ADR-0030 / ADR-0031 / ADR-0027 正文不动**：本 ADR 只为它们造见证，不改规则。
- **`docs/STRATEGY-V1.md`**：M3 的「验收」一句按 §12 重写。

## 12. `STRATEGY-V1.md` M3 验收一节的新措辞

> **验收**：(1) [ADR-0030](0030-m3-type-whitelist.md) §1 **九行形态每行**的边界值端到端搬对——
> 字符族与日期族逐字节相等，`DECIMAL` 族按目标标度补零后逐格相等；
> (2) ADR-0030 §2 **每条**拒绝规则都真的拦得住，且映射预检**一次报全部列**；
> (3) 裸 `NUMBER` 的全量值域校核**正反两面都验**——超域当场拒且暂存表一张不建，
> 不含裸 `NUMBER` 的任务**零扫描**。
> **前置**：先跑绿 `run-m1-acceptance.sh` 与 `run-m2-acceptance.sh` 两份。

原措辞（「目标表少一列 / 标度不足 / 类型不兼容三种情况」）**M1 就已经全过了**，作废。

## 已知代价

1. **三个入口意味着三份报告**，「M3 验收通过」需要三个文件才能支撑（§2）。
2. **B1 那张宽表会很宽**：九行形态 × 3–6 个边界值，一张表几十列。这是「按制造手段归并」
   换来的——分开搬则要起十几个 run，且每个 run 都要走一遍预检与切换。
3. **矩阵写死进 ADR 意味着扩白名单要改 ADR**（§4.1）。这是刻意的：白名单是单向门
   （ADR-0031），台架矩阵跟着它一起变成单向门才对得上。
4. **`DECIMAL` 族的期望值口径是两条规则里的第二条**（§4.3），比逐字节复杂。
   写错的后果是**假 PASS**——按标度补零补错了方向会把真正的静默舍入判成通过。
   这一条本身没有元测试。
5. **W 系列六条仍然靠人守**（§8），与 ADR-0028 已知代价 1 同源，M3 没有改善它。
6. **B5 的日志判依赖 `source` 真的把值域校核 SQL 写进日志**。若实现期没写，这条断言会**恒真**
   ——一条永远绿的断言比没有断言更糟。实现时必须把「校核 SQL 已发出」当成一条显式日志行。
