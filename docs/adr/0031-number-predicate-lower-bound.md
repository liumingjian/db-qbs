## 背景

ADR-0009 §2 要求 `NUMBER(p,s) → DECIMAL(p',s')` **逐位相等**（`p' == p && s' == s`），
ADR-0003 的「目标形状精确匹配」一节是它的上游。两处都在文本里挂着同一个复审钩子：

> **M3 若要放宽成「够大即可」，必须另行复审本节的精确匹配决策。**（ADR-0003）
>
> **M3 若要改用下界式，必须复审 ADR-0003 的精确匹配决策。**（ADR-0009 §2）

M3 到了。[ADR-0030](0030-m3-type-whitelist.md) 把白名单撑到九行形态，`NUMBER` 一族占四行，
生产表 70 列——逐位相等意味着目标表每一列的 `DECIMAL(p,s)` 都得跟推导形状一模一样，
人手建表错一位就整 run 拒。**本 ADR 摘这个钩子。**

摘钩子的依据是三条既有事实，不是新的偏好：

1. **下界式不削弱保值防线。** 唯一的静默失效面是**标度写小**（`Note 1265`；形态 2 上
   `±0.000001` 塌成 `0.0000` 连符号一起丢），而 `s' >= s` 恰好就守在那里。
   ADR-0009 §2 自己写着下界式「同样保值（#13 组 2 已证）」——当初取逐位相等给的理由是
   「判定式最短、没有边界推理、M1 的目标是最窄链路，**宽容度不值钱**」，
   **那是经济理由，不是正确性理由**。M3 的主方向是「买能搬的东西变多」，宽容度开始值钱，
   同一笔账算出来的结果就变了。
2. **V2 checksum 那笔债与本判定无关。** ADR-0003 自己写着「即使 `(p,s)` 精确匹配，
   `0.5` 从 `DECIMAL(38,2)` 读回仍是 `0.50`」，ADR-0009 §2 也写着「**无论是否放宽**，
   V2 checksum 都必须承担目标端重规范化那笔债」。所以「放宽会把重规范化的债坐实」这句顾虑
   **站不住**——债的存在与判定式宽严无关，见 §4.2。
3. **逐位相等的价钱已经被量出来了。** [#104](https://github.com/liumingjian/db-qbs/issues/104)
   实测 `DECIMAL(38,6)` 与 `DECIMAL(6,6)` 读回**逐格相同**：`p' == s` 那半条买的是**形状整齐**，
   不是正确性。保值的是标度，不是整数位。

## 决策

### 1. 统一下界式，对**推导形状**判

```
s' >= s  &&  p' - s' >= p - s
```

其中 `(p,s)` 是 **ADR-0030 §1 推导出的目标形状**，不是源端 `(p,s)`。
这一条承 ADR-0030 §6 的订正——放行形态 2/3 之后，「判源」与「判形状」不再重合。

落到 `NUMBER` 四行形态上（`MySQL` 恒有 `0 <= s' <= p'`，故括号里的半条恒真、实现上可省）：

| 形态 | 推导形状 | 判定式 | 退化后实际判什么 |
|---|---|---|---|
| 1 `NUMBER(p,s)`，`0 ≤ s ≤ p` | `DECIMAL(p,s)` | `s' >= s && p'-s' >= p-s` | 两半都判 |
| 2 `NUMBER(p,s)`，`s > p`（纯小数） | `DECIMAL(s,s)` | `s' >= s &&` (`p'-s' >= 0`) | **只判 `s' >= s`** |
| 3 `NUMBER(p,s)`，`s < 0`（负标度） | `DECIMAL(p+\|s\|,0)` | (`s' >= 0`) `&& p'-s' >= p+\|s\|` | **只判整数位** |
| 4 裸 `NUMBER` / 数值表达式列 | 人工配置的 `DECIMAL(p,s)` | `s' >= s && p'-s' >= p-s` | 两半都判，比较对象是**配置**，见 §3 |

形态 2 与形态 3 各自只剩半条，**恰好各自守住自己那个危险面**：形态 2 的危险面是标度写小
（静默改值 → 从严），形态 3 的危险面是整数位写小（`ERROR 1264` 当场炸 → 从宽），
而形态 3 的目标标度恒为 0，**它根本没有「标度不足」这个危险面**（#104 结论）。
判定式退化的形状与 ADR-0030 的失效模式归类**逐行对上**——这是本 ADR 对分级思想的兑现，
不是巧合。

**`p' > 65 || s' > 30` 的前置判定不受影响**：它判的是推导形状**本身建不建得出来**，
与目标列怎么比是两件事（ADR-0030 §6）。顺序仍是「先推导形状 → 前置判定 → 再与目标列比」。

**字符族与日期族的判定式本 ADR 不动**：`VARCHAR2` / `NVARCHAR2` / `CHAR` / `NCHAR` 的
`n' >= n` 与「目标 `DATA_TYPE` 必须 `varchar`」照 ADR-0009 §2 / ADR-0030 §1 原样；
日期族的严格式见 §7。

### 2. `p' - s' >= p - s` 这半条**留着判**，尽管失效模式是「当场炸」

按 ADR-0009 §2 的分级，整数位不足是 `ERROR 1264 Out of range value`——**当场炸 → 从宽**，
而从宽的极限是**不判**。本 ADR 仍然判，理由有两条，都不是保值：

- **早拒 vs 晚炸**。不判的话它会在搬到第几百万行时炸，整 run 失败还要走暂存表回滚，
  而预检的全部意义就是「开跑前一次性拦住」（ADR-0009 §8）。
- **与 `VARCHAR2` 同构**。`VARCHAR2(n)` 的失效模式同样是当场炸（`ERROR 1406`），
  ADR-0009 §2 仍然保留了 `n' >= n`。**「从宽」的含义是「取下界而不取相等」，
  不是「不判」**——这一条在此明确写死，免得后人拿分级表把任何「当场炸」的规则都删掉。

### 3. 形态 4（裸 `NUMBER` / 数值表达式列）同步放宽，但**配置仍是全量验值的基准**

ADR-0003「无精度声明的 `NUMBER`」增补第 1 条要求「目标列必须**恰好**是配置的 `DECIMAL(p,s)`」。
ADR-0030 §4 没有替它裁定，[#96](https://github.com/liumingjian/db-qbs/issues/96) 明写归本票。

**判：跟着放宽**，同一条下界式，只是比较对象从「推导形状」换成「人工配置的 `(p,s)`」。
配置写小了，全量值域校核 `x <> TRUNC(x,s)` / `ABS(x) >= POWER(10,p-s)` 当场命中、
`invalid_rows > 0` 即拒；目标列比配置宽，值一样装得下——**保值成立，没有新的静默失效面**。

**不取「让目标列充当验值基准、删掉配置字段」这条路。** 目标列可能被建得过宽
（下界式之后这正是常态），拿它当基准等于放弃业务域声明、退回「当前数据的最小形状」那类判据，
而 ADR-0003 增补已经明写拒过：「当前数据的最小形状不能代表列的业务域或未来写入」。
**配置是人声明的域，目标列是容器；容器可以更大，域不能由容器定义。**

ADR-0016 §2 那个可选字段（ADR-0030 §4.2）**形状与去留一字不改**。

### 4. ADR-0003 的「目标形状精确匹配」退役

#### 4.1 退役范围

ADR-0003 §「`DECIMAL` 精度与标度」那一节的**判定式一栏**（`p' == p && s' == s` 及两条 M3 换算的
精确匹配式）由本 ADR §1 取代。**该节的其余内容原样成立**：

- 「先按源类型推导唯一的 MySQL 目标形状」——**推导仍然唯一**，本 ADR 放宽的是「怎么比」，
  不是「推导成什么」（ADR-0030 「时效」已预写这句）。
- 「推导出的形状若超过 MySQL `DECIMAL(65,30)` 的表达能力，预检直接拒绝，不截断」——不动。
- 「生产表 70+ 列不要求人再维护一份源端精度配置」——不动，且**本 ADR 使它更成立**。
- 「源列声明变化后目标列必须同步调整是本策略有意接受的运维成本」——**这句被本 ADR 削掉大半**：
  源列声明变宽后，只要目标列仍满足下界式就不必动 DDL。源列变**窄**同样不必动。
  真正还要动 DDL 的只剩「源列变宽到超出目标列」这一种。

#### 4.2 V2 checksum 那笔债：明写「与本判定无关」

ADR-0009 §2 与 ADR-0003 都提过「目标端重规范化」这笔债，容易被读成「放宽会把债坐实」。
**在此钉死：不是。**

MySQL `DECIMAL` 读回字符串会补齐到**声明标度**，与源标度是否相等无关——
ADR-0003 自己举的例子就是「即使 `(p,s)` 精确匹配，`0.5` 从 `DECIMAL(38,2)` 读回仍是 `0.50`」。
**债由「MySQL 按声明标度补零」这个行为产生，不由判定式产生**；V2 若计算目标端 checksum，
无论本 ADR 放不放宽，都必须先按 ADR-0003 的 `NUMBER` 文法去尾零。
本 ADR **一分钱新债都不欠**，它只是让本来就要还的债在更多形状上显形。

### 5. 报告措辞：判定用下界式，建议值用推导形状

逐位相等唯一真正的好处是「错误信息能直接把期望与实际两边写出来」。下界式的「期望」是一族形状，
不能直接打印——**解法是报告同时给出唯一推导形状作为建议值，并点名越界的是哪一半**：

```
N_AMT | 源端 NUMBER(10,2) | 目标端 DECIMAL(12,1) | 违反：目标标度 1 < 源标度 2（建议建成 DECIMAL(10,2)）
```

**ADR-0009 §8 的四段固定形态（`<列名> | 源端 <类型(精度)> | 目标端 <类型(精度)> | 违反：<规则>`）
与「一次报全部列」一字不改**——建议值写在「违反」那一段里，不新增段。
信息量**不降反升**：原来只说「不匹配」，现在说清「哪一半不够」加「照哪个建最省事」。
逐位相等的这条好处因此不构成保留它的理由。

**ADR-0009 §9 的两条人话不动，也不加第三条。** §9 管的是「预检结构性看不见、
只能在运行期或产品之外炸出来」的错；本 ADR 没有往那个集合里加东西——
`ERROR 1264` 仍被 §2 那半条挡在预检门外，形态 4 的并发新极值有 ADR-0003 增补第 3 条的逐值兜底。

### 6. 生成侧不动

[ADR-0027](0027-target-ddl-generation-and-cross-end-metadata.md) 的建表 SQL **一个字不改**，
仍吐**唯一推导形状**。判定侧接受一族形状、生成侧吐这族里的规范代表，两者不矛盾。

[#97](https://github.com/liumingjian/db-qbs/issues/97) 票正文给过第三条出路——「让建表 SQL 保证
按它建的表必然逐位相等，把问题挪到生成侧」——**本 ADR 不取，且它已无必要**：
放宽之后误拒面自己就没了，人手建的宽表照样过。**问题不需要挪。**

连带钉死一句给 [#101](https://github.com/liumingjian/db-qbs/issues/101)：
**#101 不需要为本 ADR 改任何推导式**，它要扩的是新形态在生成侧的行数，不是判定侧的宽严。

### 7. 本判定**不外溢到日期族**——两条判据轴不同

把本 ADR 的原则套到 ADR-0030 §1 的日期两行上，会看见这个：

- **形态 9 `TIMESTAMP(n) → DATETIME(6)` 的「严格」本来就是下界式的退化。**
  保值要求 `fsp' >= 6`，而 MySQL 的 `fsp` 上限就是 6，故 `fsp' >= 6` ≡ `fsp' == 6`。
  它**不是真严格**，本 ADR 的原则套上去一个字都不用改。
- **形态 8 `DATE → DATETIME(0)` 的 `fsp' == 0` 是真严格**，且 ADR-0009 §2 自己写着
  「理由不是保字节（`.000000` 只是字节变了、值没变）」。按保值算，它只要求 `fsp' >= 0`，
  等于不判。**它是九行形态里第二处「买整齐不买正确」的判定式。**

**尽管如此，本 ADR 不改它。** 两处严格的**判据轴不同**：

| | `NUMBER` 的逐位相等 | `DATE` 的 `fsp' == 0` |
|---|---|---|
| 原始理由 | **经济性**：判定式最短、M1 宽容度不值钱（ADR-0009 §2） | **可逆性**：一列一型，`DATETIME(0)` 与 `DATETIME(6)` 各自只对应一种源类型（ADR-0009 §2、ADR-0030 §3） |
| M3 里理由还成不成立 | **不成立**——宽容度在 70 列 × 九形态下开始值钱 | 未受本 ADR 触动 |
| 谁裁的 | #19 / M1，本 ADR 复审 | ADR-0030 §3，2026-08-16 刚裁，`TIMESTAMP` 引入后伏笔自解 |

**预先写好答复**，免得后人拿本 ADR 来打 ADR-0030 §3：

> 本 ADR 放宽的依据是「判定式随**失效模式**分级」（ADR-0009 §2 的中心思想）——
> 标度写小是静默改值故守住、整数位写小是当场炸故取下界。
> `DATE` 的 `fsp' == 0` 不在这条轴上：它守的不是失效模式，是**规则的单一性**。
> 拿失效模式轴上的结论去推可逆性轴上的规则，是**换了判据**，不是延伸。
>
> 可逆性这条辩护词本身有多硬，是另一个问题——`NUMBER` 早就有碰撞
> （`NUMBER(4,6)` 与 `NUMBER(6,6)` 在逐位相等下也都推 `DECIMAL(6,6)`），没人受害，
> 因为规范形式是字符串、映射不需要从目标 DDL 反推。**这一点本 ADR 记录在案但不裁**：
> 它要动的是 ADR-0030 §3，而 ADR-0030 §3 三天前刚裁过，重开需要新的实测结论或新的失效模式，
> **本 ADR 两样都没有提供**。

## 后果

**买到的**：

- **误拒面大幅收窄**。合法但不逐位相等的 `NUMBER` 目标列不再被拒——
  ADR-0009「后果」里「误拒面很宽」那条列举的第一项**就此消失**。
- **运维成本削掉大半**（§4.1）：源列声明变宽或变窄都不必跟着改目标表 DDL，
  只有「源列变宽到超出目标列」还要动。
- **分级思想第一次贯彻到底**。放宽之后，白名单上**除日期族外全是下界式**，
  而日期族的严格由另一条轴（可逆性）撑着，两条轴各自自洽，见 §7。

**付出的**：

- **判定式引入边界推理**。`p' - s' >= p - s` 比 `p' == p` 难读，负标度形态上尤其
  （`p' - s' >= p + |s|`）。代价用报告的建议值抵掉（§5），但**代码与测试上是实打实的多一层**。
- **目标端存下的字节可以与源端不同**（`0.5` 存进 `DECIMAL(38,6)` 读回 `0.500000`）。
  V1 只比行数，这不构成问题；V2 的重规范化按 §4.2 **本来就要做**。
- **「期望形状」从一个值变成一族**。任何下游想反推「这列源端是什么」的做法都不再成立——
  但没有任何现存机制这么做（生成侧是正向的，见 §6）。

## 时效

- **本判定的复审不由客户类型分布触发**（[#95](https://github.com/liumingjian/db-qbs/issues/95) /
  [ADR-0005 增补](0005-local-rig-as-v1-verification-baseline.md)）。触发复审的是**新的目标端往返实测结论**，
  或 MySQL / Oracle 驱动的行为变化——比如某个 MySQL 版本上「宽标度列写窄标度值」不再是无损补零。
  本 ADR 的实测底座是 **MySQL 8.0.46**（spike §7.8 组 2 / §7.11），**换大版本要重测**。
- **放宽是单向门。** 退回逐位相等属**破坏性变更**：本来能过预检的目标表会开始被拒，
  已经在跑的任务会成批失败。这与 ADR-0010 错误码闭集「只增不删」同性质——
  **要退必须当一个新决策重走**，不能作为「订正」处理。
- **日期族那处「买整齐不买正确」记录在案未裁**，见 §7。重开它要么拿出新实测，
  要么拿出可逆性被真正需要的场景；两样都没有之前，ADR-0030 §3 成立。
