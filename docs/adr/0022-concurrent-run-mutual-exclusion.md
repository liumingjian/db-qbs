# ADR-0022: 同任务同业务日期的并发 run 互斥——硬拒绝、进程内、体验问题不是完整性问题

**状态**: 已接受
**日期**: 2026-08-15
**来源**: [#53](https://github.com/liumingjian/db-qbs/issues/53)（地图 [#47](https://github.com/liumingjian/db-qbs/issues/47)）
**关联**: [ADR-0002](0002-staging-table-atomic-swap.md)（暂存表与切换事务）、
[ADR-0012](0012-run-lifecycle-and-state-authority.md)（状态权威；本 ADR **不订正**它）、
[ADR-0019](0019-m2-source-process-topology.md)（长驻编排 + 每 run 短命子进程，本 ADR 的前提）、
[ADR-0010](0010-http-protocol-contract.md)（错误码闭集 11 → 12，见 §4）

## 背景

[#22](https://github.com/liumingjian/db-qbs/issues/22)（M1 地图）曾把「同任务 + 同业务日期的并发 run 互斥」
判为 Out of scope，三条理由：`run_id` 随机段保证暂存表不撞名、两次切换是 last-writer-wins
且终态等于后提交者的完整当日快照、**「且 M1 手动触发、source 一次性进程，并发起跑靠人控」**。

Web UI 把第三条理由拿掉了：点两下按钮就能并发起跑。本 ADR 重判前两条。

## 1. 终态推理成立，但成立的理由要换一条

切换事务的实际语句（`crates/sink/src/mysql_destination.rs::atomic_swap`，`TxOpts::default()`
→ 服务器默认隔离级，InnoDB 为 REPEATABLE READ）：

```
BEGIN
  SELECT COUNT(*) FROM <target>__stg_<run_id>      -- 每 run 一张，永不相撞
  DELETE FROM <target> WHERE <date_col> >= ? AND <date_col> < ?
  INSERT INTO <target> (cols) SELECT cols FROM <target>__stg_<run_id>
COMMIT
```

**终态确实等于某一个 run 的完整当日快照，不会出现两个 run 混合。** 但成立的理由不是 #22 写的
那三条，而是一条 InnoDB 事实：**`DELETE` 是当前读（current read），不走事务快照**。
后提交的那个事务，它的 `DELETE` 必然看见并删掉前一个 run 刚 `INSERT` 的行，
随后插入自己的完整快照。RR 的快照读根本不参与切换路径——
**「两个 run 不会真正同时进入切换事务」不是前提，也不需要是前提。**

因此 **ADR-0002 的「重跑一致」契约在并发下不受影响**，`CONTEXT.md`「导入任务」词条那句
「同样的任务定义 + 同样的业务日期，重跑后目标表状态应当完全一致」**一个字不改**：
终态是某一个 run 的完整快照，而同任务同日期两个 run 的快照本就相同。

## 2. UI 让并发变廉价之后真正付的账：两个可操作性代价

数据是对的，人看到的东西是错的：

1. **锁等待**。两个 run 的 `DELETE` 争同一段范围锁，后到的阻塞到前一个 `COMMIT`。
   而这个事务里坐着 10 万行的 `COUNT(*)` 与 `INSERT ... SELECT`，持锁时间秒级往上；
   `innodb_lock_wait_timeout` 默认 50s，超时即 run 失败。
2. **死锁**。当天范围内没有既有行时（首次跑该日期，或范围本就空），两个 `DELETE` 只拿间隙锁，
   **间隙锁彼此兼容**，两个事务都能过 `DELETE`；随后两个 `INSERT` 各自去插对方持有的间隙，
   插入意向锁冲突 → InnoDB 判死锁杀掉一个。

两种情况下，输的那个 run 报的是 `Lock wait timeout` / `Deadlock found` 这类 MySQL 原生错，
**而不是「有人在跑同一份数据」**——一条从第一行就指错方向的报错。

**定性：本 ADR 要买的是可操作性，不是数据完整性。** 这条定性是 §3 允许「尽力而为的锁」的全部依据。

## 3. 决策：防，硬拒绝，进程内，粒度 = 任务 + 业务日期

- **防**。#22 那条 Out of scope **被本 ADR 推翻**，不是改写理由。
- **粒度：`task_id` + 业务日期**。
- **硬拒绝，不排队**。同任务同日期的第二个 run 跑完的结果与第一个逐字相同，
  排队只是多烧一遍 Oracle 全量读。「跑到一半改了定义想让新的接上」不是排队，
  是取消 + 重发，走 ADR-0012 的取消路径。
- **锁在哪：长驻编排进程内存**。ADR-0019 定死 source 是「单进程单端口、SQLite 唯一写者」，
  单实例部署是既定形态，进程内锁就够。**不引入跨进程锁**——按 §2 的定性，
  这是体验问题，不值一笔分布式锁的账。若将来 source 要多实例部署，本条须重开。
- **锁的生命周期**：父进程 fork 子进程前取，子进程回收（正常退出 / 被 kill / 崩溃）时释放。
  父进程自己死了锁随之消失——与 ADR-0012 §2「进程一死 run 即不存在」同构，不新增语义。

### 3.1 被否掉的两个粒度

- **按目标表互斥**：挡得更干净，但把「同一张目标表的不同业务日期并行导入」这个完全合法的
  用法一起封死。为一个低概率场景付这个代价，性价比不对。
- **预检要求目标表业务日期列有索引**：给搬运链路加新门禁，M2 地图「收窄 1」当场挡掉；
  且它解决的是一个尚未被观测到的问题。

**但要明写一条实查出来的事实**：全仓找不到任何一处要求**目标表业务日期列有索引**
（ADR-0009 §7 只管暂存表，且明写无索引）。没有索引时 `DELETE ... WHERE d >= ? AND d < ?`
是全表扫描，RR 下锁住目标表每一行——**§2 的两个代价因此不止发生在同任务同日期，
同一张目标表的不同业务日期之间同样会互相阻塞**。§3 选的粒度挡不住这一段，§4 是它的兜底。

### 3.2 顺带结清 ADR-0012 §时效点的那条警告

ADR-0012 §时效写过：「非 DAY 粒度进来时（M2）——§5.2 拒绝的那条隐式幂等依赖会正式失效，
届时要确认墓碑没有被谁当成幂等的替代品用。」非 DAY 粒度被 M2 地图「收窄 1」挡在图外，
但「幂等是碰巧的、不该被当成设计依据」这条警告在 UI 让并发变廉价之后同样适用。

**结清**：本 ADR 的互斥**不依赖墓碑，也不依赖任何幂等性质**——它是父进程内存里的一把锁，
在 fork 前取、子进程回收时放。墓碑（sink 侧、内存、可被淘汰）在本 ADR 里不承担任何角色。
§1 的终态推理靠的是 InnoDB 的当前读语义，不是「重跑碰巧幂等」。警告不成立，条目可以关掉。

## 4. 兜底：sink 把锁等待与死锁翻成人话，`SWAP_TARGET_BUSY`，闭集 11 → 12

§3 的粒度认下的那部分阻塞（同表不同日期），恰恰会以 §2 那两条 MySQL 原生错的形态暴露。
故 **sink 侧在切换事务中捕获锁等待超时（`ER_LOCK_WAIT_TIMEOUT`, 1205）与
死锁（`ER_LOCK_DEADLOCK`, 1213）两类错误，映射为新错误码 `SWAP_TARGET_BUSY`（HTTP 409）**，
不与 `SWAP_FAILED` 混用：

| `code` | HTTP | 说明 |
|---|---|---|
| `SWAP_TARGET_BUSY` | 409 | 目标表当前被另一个切换事务占用；`details` 带 `target_table` 与底层 errno |

message 明写「目标表当前被另一个切换事务占用，通常是同一张表上有另一个 run 正在切换；
这不是数据错误，重跑即可」。**不自动重试**——重试是 ADR-0018 的地盘，本 ADR 只管分类。

这样拿到的是「按目标表互斥」的收益，付的是「按任务+日期互斥」的代价：
不同日期仍允许并行，真撞上了给的是一句人话。改的是 sink 的**错误分类**，不是搬运语义，
过得了「收窄 1」。ADR-0010 §7 的闭集表须同步增码（增码只增不删）。

## 5. UI：后端硬拒绝是唯一真相，UI 只提示、不拦截

ADR-0019 明写父进程的 run 登记是**投影、非权威**（权威在子进程内存）。
拿非权威视图去禁用按钮，等于让 UI 对一件它无权知道的事下判断，迟早出现
「UI 说能点、后端拒绝」或更糟的「UI 禁着、其实早已没在跑」。

- UI **显示**「该任务该业务日期有一个 run 进行中」——信息来自投影，**允许滞后**。
- 发起按钮**照常可点**，拒绝由后端给（§3 的进程内锁）。
- 投影滞后的后果因此只是**多一次被拒的点击**，而不是一个能卡死人的假禁用。

提示所依赖的「进行中 run」视图，形态归 [#49](https://github.com/liumingjian/db-qbs/issues/49)（运行历史）
与实时观察那块雾，本 ADR 只钉死「它是提示、不是门禁」这一条。

## 后果

- `CONTEXT.md` 不动；ADR-0002 的重跑一致契约不动；ADR-0012 五态不动。
- ADR-0010 错误码闭集 11 → 12（`SWAP_TARGET_BUSY`）——**这是 M2 第一次动协议层**，
  但只增一个分类码，不改任何报文形状与时序。
- #22 那条 Out of scope 作废，理由不是「靠人控」失效，而是**结论本身被推翻**。
- 遗留：source 若要多实例部署，§3 的进程内锁须重开。
