# ADR-0016: 任务定义在 M1 的落地形式——三个 TOML 文件、source 是一次性进程、SQL 形状预检在源端

**状态**: 已接受
**日期**: 2026-08-13
**来源**: [#34](https://github.com/liumingjian/db-qbs/issues/34)
**关联**: [ADR-0004](0004-parameterized-business-date.md)（SQL 由人手写）、
[ADR-0008](0008-business-date-predicate-generation.md)（三字段与预检四条，§5 由本 ADR 订正）、
[ADR-0009](0009-m1-mapping-precheck-rules.md)（按名字对齐、预检时点）、
[ADR-0010](0010-http-protocol-contract.md)（§3.1 与 §8 由本 ADR 订正/落实）、
[ADR-0012](0012-run-lifecycle-and-state-authority.md)（状态只在 source 进程内存）、
[ADR-0017](0017-run-log-format-and-contract.md)（日志形态；**§9 由它订正**）

## 背景

STRATEGY-V1 给 M1 定的是「SQL 先写死、不做 UI」。「写死」这个词回避了一个必须回答的问题：
**任务定义这个东西在 M1 到底以什么形式存在**——配置文件、命令行参数，还是编译期常量。

它已经不是一块空地，三个 ADR 从三个方向把它收窄到只剩形式问题：

- **ADR-0008 §1** 钉死它必须承载的三个字段：`source_date_col` / `target_date_col` / 粒度。
- **ADR-0010 §8 与报文定稿** 从另一头收窄：跨过 HTTP 的只有 `target_table` / `target_date_col` /
  `biz_date` / describe 出的源列元数据；`source_date_col` 与粒度是源端自己的事；
  database 归 sink 连接配置、不进任务定义。
- **ADR-0012** 定下 run 状态不落盘，于是**任务定义是 M1 里唯一可能存在的持久化输入**。

同时，「SQL 形状的三条约束由谁在什么时候检查」一直散在两个 ADR 里没人合并，
而合并的动作会直接顶上 ADR-0010 §3.1 那句「source 一个判断都不做」。

## 决策

### 1. 形式：配置文件（TOML），一任务一文件；命令行只传路径与业务日期

```
db-qbs-source --config source.toml --task task-t_position.toml --biz-date 2026-08-13
db-qbs-sink   --config sink.toml
```

两条判据都指向同一侧：

- **「改一次任务要不要重新编译」**：编译期常量是分钟级重编 Rust。而 ADR-0015 §1 给验收
  追加了**窄表**必测形状，M1 验收至少要两份任务定义（宽表 70 列 / 窄表 3 列），
  常量方案要改代码重编两次。
- **「验收脚本怎么跑 10 万行」**：命令行方案要把那条 70+ 列、带 dblink、多行的生产 SQL
  塞进 `argv`，撞上 shell 的引号与换行转义。这是 ADR-0011 §2「不发明第二套转义」的
  同一种病，只是换了一层。

**SQL 文本内联**进 TOML 的 `'''` 多行字面量字符串（literal string，TOML 对它不做任何转义处理），
不旁挂 `.sql` 文件——旁挂要引入相对路径解析规则，而任务定义只有一个消费者（source），
单文件自足。代价：编辑器里那条 SQL 没有语法高亮。

### 2. 字段清单定稿：四个，且有两样被证明不该存在

| 字段 | 来源 | 说明 |
|---|---|---|
| `source_sql` | ADR-0004 / ADR-0007 | 人手写、写死，形状被第 4 节的预检收窄 |
| `source_date_col` | ADR-0008 §1 | 源端自己的事，**不跨 HTTP**（ADR-0010 报文定稿） |
| `target_table` | ADR-0010 §8 | **裸表名，不带 database** |
| `target_date_col` | ADR-0008 §1 | ADR-0008 三字段里唯一跨得过那道墙的 |

```toml
# task-t_position.toml
source_sql = '''
SELECT a.n_va_price AS N_VA_PRICE, a.c_name AS C_NAME, a.d_biz AS D_BIZ
  FROM t_position a
 WHERE a.d_biz >= TO_DATE(:biz_date,'YYYY-MM-DD')
   AND a.d_biz <  TO_DATE(:biz_date,'YYYY-MM-DD') + 1
'''
source_date_col = "D_BIZ"
target_table    = "T_POSITION"
target_date_col = "D_BIZ"
```

**不在清单里的，逐条给理由**：

- **粒度**：ADR-0008 §1 的原文是「DAY，V1 唯一取值，**不可配**」。既然不可配，它就不该在
  文件里出现——出现即是给了一个改了会静默错的口子。它是代码里的常量。
- **字段映射**：**M1 没有字段映射可配。** ADR-0009 §3 要求两边列名集合完全相等
  （统一大写比较、顺序无关），于是映射恒等，配置它反而制造出「映射表写错」这个失效面，
  而那正是 ADR-0009 §3 要消灭的东西。`CONTEXT.md` 术语表里任务定义那条「字段映射」
  由本 ADR 订正。
- **清除条件**：ADR-0008 §1 由系统生成，人看不到也改不了。
- **database**：ADR-0010 §8 归 sink 连接配置。
- **业务日期**：`CONTEXT.md` 已定它是运行时参数，形式上就是 `--biz-date`，不进任务文件。

#### 2.1 订正 ADR-0008 §5

ADR-0008 §5 与它预检四条里的第 3 条都写作「`target_date_col` 在**字段映射**中存在，
且其源列就是 `source_date_col`」。字段映射在 M1 不存在，该规则**退化为一条纯字符串判定**：

```
upper(target_date_col) == upper(source_date_col)
```

语义一个字没变（恒等映射下「由 source_date_col 直接映射过来的列」就是同名列），
只是判据从查一张不存在的表变成了比两个字符串。

### 3. source 是一次性进程，sink 是长驻服务——这条不对称是故意的

第 1 节把任务与业务日期做成了**进程启动参数**，而启动参数是 one-shot 进程的形状：
长驻服务的任务是从请求里来的。M1 的 source 跑完一个 run 即退出。

`CONTEXT.md` 部署形态图里 source 的 **Web UI 与 SQL 构建器属 M2**，M1 的 source 没有入站接口。

三条推论一并认掉：

1. **ADR-0012 那五个状态在 M1 没有外部查询者。** 没有 UI，也没有「source 侧的 `GET`」。
   `PREPARING`/`STREAMING`/`COMMITTING`/`SUCCEEDED`/`FAILED` 退化成进程内的一个执行阶段变量，
   作用只剩两个：日志里打阶段名，以及守住 ADR-0012 §7 那条
   「进入 `COMMITTING` 后永久放弃 abort 权」。**这不是削弱 ADR-0012，是它「状态只在进程内存」
   的最强形态**——连进程外的读者都不存在。
2. **「source 进程一死 run 即不存在」从风险变成必然。** 验收里「kill 源端后重跑」就是
   kill 掉这个一次性进程，重跑 = 再敲一次命令、拿到一个新 `run_id`，
   与 ADR-0012 §2 钉的判据（判目标表，不去查上次那个 run）严丝合缝。
3. sink 必须长驻（它得接 HTTP），source 不必。两个二进制形态不同，规格里写明是故意的。

### 4. SQL 形状预检在 source，且发生在 `POST /runs` 之前——订正 ADR-0010 §3.1

三条形状约束此前散在两个 ADR 里：

| 约束 | 出处 |
|---|---|
| 日期谓词恰好一处 `:biz_date` 的半开区间，两处引用同一列 | ADR-0008 预检四条之 1 |
| WHERE 中不存在其他谓词 | ADR-0008 预检四条之 2 |
| 相对时间函数扫描（`SYSDATE` / `CURRENT_DATE` / `SYSTIMESTAMP`） | ADR-0004 / ADR-0008 预检四条之 4 |
| 每列必须显式命名（表达式列必须写别名） | ADR-0009 §3 |
| 表达式列 / 精度不确定的列一律拒绝 | ADR-0009 §4 |

**ADR-0010 §3.1 说「source 一个判断都不做，全部判定集中在 sink」，但 SQL 文本根本不跨 HTTP**
（报文定稿里没有它），sink 结构性地判不了这些。§3.1 那句话的作用域被写宽了：
它的论证（「一次报全部列」不能降级成「逐端」）只对**需要目标端元数据的逐列类型比对**成立；
SQL 形状问题在 sink 侧不可表示，不存在「本可以合并却分了两端报」这回事。

**预检因此明确分两段，各自「一次报全部」**：

```
1. SQL 形状预检   source 本地，POST /runs 之前   ← 本 ADR
2. 映射预检       sink，POST /runs 之内          ← ADR-0010 §3 不变
```

顺序钉死为 **解析形状 → describe 拿列元数据 → `POST /runs`**：形状不合法时 describe 出的
列表不可信（没写别名的表达式列，列名是 `B*2` 这种东西）。

**形状预检不过则根本不发 HTTP 请求**：sink 不知道存在这个 run，无暂存表、无 `run_id` 泄漏、
无需 abort。ADR-0010 §3.1 的措辞订正为「**逐列类型判定**一个都不做」。

### 5. 三个配置文件，不合并

| 文件 | 读它的进程 | 内容 |
|---|---|---|
| `source.toml` | source | Oracle 连接串与凭据、Instant Client 相关、sink base URL |
| `sink.toml` | sink | MySQL DSN 与凭据、**database**、监听地址 |
| `task-<name>.toml` | source | 第 2 节那四个字段 |

**sink 全程不读任何任务定义**，它对任务定义的存在一无所知。

分开不是为了整洁，是**为了让 ADR-0010 §8 的论证在文件层同样成立**：那条「不让 source 指定
往哪个库写」，如果被一份「source 读的任务文件里写着 sink 的 database」抵消掉，
等于把权限又挪回 source 手上，只是从报文挪到了文件。生命周期也不同——
连接配置属部署，任务定义属业务。

### 6. 未知字段严格拒绝

任务文件与两个连接配置文件中**出现未知字段即启动失败，并点名那个字段**
（serde `deny_unknown_fields`）。

这与 ADR-0015 §5 把 `sql_mode` 写死成完整字符串、不做追加是同一种态度：被忽略的拼错字段
= 你以为配了、实际用的是别的值 = 静默。任务定义只有四个字段，没有任何前向兼容负担要照顾。

### 7. 任务的身份就是文件路径，不加 `name` 字段

出错时人要能说清「是哪个任务跑挂了」，而 `run_id` 的形态被 ADR-0002 增补钉死
（`<UTC 14 位>_<6 位 hex>`，全链路单一形态、不做二次派生），任务身份塞不进去。

**不加 `name`/`id` 字段**：source 启动时把 `--task` 解析成的**绝对路径**打进日志第一行。
加 `name` 会凭空造出「`name` 与文件名不一致」这个新失效面，而 M1 没有任务注册表、
没有「按 name 查找」的使用者——它一分钱都买不到。

### 8. 配置文件显式指定；凭据明文，靠文件权限

- **`--config <path>` 与 `--task <path>` 均显式必填，没有默认搜索路径、没有环境变量覆盖。**
  隐式搜索会让「这次跑的到底是哪份配置」变成需要推理的事，而验收要在台架上反复切
  宽表 / 窄表两份任务定义。
- **数据库凭据明文写在 TOML 里，靠文件权限（0600）兜底。** 不做环境变量、不做加密：
  V1 明确不做鉴权（`CONTEXT.md` V1 范围），在一个没有鉴权的系统里单给凭据加一层是零收益，
  且会让「配置的真值」分散到两个地方。
  **代价明写：配置文件不进 git，仓库里只放 `.example`。**

### 9. 退出契约：0 / 1 两个码，`run_id` 单独打一行到 stdout

- **退出码只有 `0`（`SUCCEEDED`）与 `1`（`FAILED`），不按 ADR-0010 的十码闭集分配。**
  分配等于多一张必须两处同步的表，而错误分类的权威表示已经在 `message` 与日志里；
  验收脚本要判「哪种失败」本来就得读日志。
- **`POST /runs` 成功后立刻把 `run_id` 打到 stdout**，让验收脚本能抓到它，
  拿去 sink 那边查暂存表与墓碑（ADR-0012 §5）。
  **（由 [ADR-0017](0017-run-log-format-and-contract.md) §1.1 订正：原文是「单独打一行」「无解析地抓到」；
  stdout 全量 JSON Lines 之后那会是流上唯一的非 JSON 行，改由 JSON 行的 `run_id` 字段承载，
  抓取方式变成一次 `jq`。退出码仍只有 0 / 1，不变。）**

## 后果

- **M1 的持久化输入定型为三个 TOML 文件**，且其中只有一个（任务定义）属于业务、会被频繁改。
  ADR-0012 的「状态不落盘」由此有了一个干净的边界：**落盘的只有输入，没有任何状态**。
- **预检从「一段」变成明确的「两段」**，规格里第一次写清 source 侧也有硬门禁。
  好处是形状问题在不接触 sink 的情况下就被拦下；代价是「一次报全部」这条承诺
  现在有两个各自成立的作用域，文档里必须一直说清是哪一段。
- **字段映射在 M1 被证明不存在**，`CONTEXT.md` 术语表与 ADR-0008 §5 两处随之订正。
  代价：M2 引入非恒等映射时，ADR-0008 §5 那条规则要从字符串判定改回查映射表，
  且任务定义要加字段——那是一次真正的格式变更，第 6 节的严格拒绝会让老文件当场失败，
  这是要的行为。
- **凭据明文**是一个明知的缺口，随 V1「不做鉴权」一起被接受；引入鉴权时两者一并重开。

## 时效

- 第 3 节的 one-shot 形态在 **M2 引入 Web UI 与 SQL 构建器时整体重开**：届时 source 变长驻，
  ADR-0012 那五个状态会第一次真的有外部查询者，任务定义也会从文件挪进某种存储。
- 第 2 节的字段清单在**引入非恒等字段映射**时失效（见「后果」）。
- 第 8 节的凭据处理绑在「V1 不做鉴权」上，鉴权一旦进来即重开。
