# ADR-0020: M2 运行历史——父进程消费子进程日志，落 source 侧同一个 SQLite

**状态**: 已接受
**日期**: 2026-08-15
**来源**: [#49](https://github.com/liumingjian/db-qbs/issues/49)（地图 [#47](https://github.com/liumingjian/db-qbs/issues/47)）
**关联**: [ADR-0012](0012-run-lifecycle-and-state-authority.md)（状态权威与墓碑；本 ADR **不订正**它，见 §11）、
[ADR-0017](0017-run-log-format-and-contract.md)（**§5 的演进规则由本 ADR 收紧，§6.2 增一条消费者脚注，§7 C1 由本 ADR 关闭**）、
[ADR-0019](0019-m2-source-process-topology.md)（父子拓扑与 SQLite；**§7 的临时文件命名由本 ADR 订正**）、
[ADR-0010](0010-http-protocol-contract.md)（协议契约，一字不改）、
[#36](https://github.com/liumingjian/db-qbs/issues/36)（UI 观察面清单，C1 的出处）

## 背景

ADR-0017 §时效原文：**「第 7 节 C1 在 M2 起图时第一件重开：选历史存储还是选消费日志，
选后者则第 5 节的契约从『承诺』变成『被依赖的接口』，演进规则要相应收紧。」**

C1 是 #36 三张线框撞出的四条冲突之首：**历史运行列表、按任务/日期查**。M1 对它照实认零
（ADR-0012 §2 状态不落盘，墓碑只有 32 条且明写「是诊断缓存，不是状态存储」）。M2 的 UI 要给出
运行历史，这个零必须被填上。

**但 ADR-0019 已经把「A 引入存储 / B 消费日志」这个二分吃掉了一半**：§5 已经在 source 侧放了
一个 SQLite（任务定义，长驻父进程是唯一写者），§4 已经让父进程成为 ADR-0017 日志的
**第一个程序化消费者**（解析 JSON Lines 更新内存投影）。两件东西都已经在场了。
真正待决的，是那份**已经在被解析的投影落不落盘**。

## 决策

### 1. 一条路，不是两条：日志是采集通道，SQLite 是留存位置

> **父进程解析子进程 stdout 的 JSON Lines，把每次发起聚合成一条历史行，写进 source 侧存储。**

采集侧用 B 的机制（**子进程一行不改、不新增任何埋点**），留存侧是 A 的结论。

**被否掉的是纯 B——不落盘，查询时现场读日志文件重建。它的致命处不是性能：**

- **ADR-0017 §6.1 原文**：「程序自身不创建日志文件、不轮转、不外采；**是否把 stdout 重定向到
  文件由部署者决定**」。纯 B 让「UI 上有没有历史」取决于当初有没有人写那个 `> run.jsonl`、
  有没有人给它配轮转。一个产品级功能挂在**产品之外的部署动作**上，且**失效时不报错**——
  历史只是悄悄缺一段，而缺的那一段恰好是没人配轮转的那台机器上的全部。
- **ADR-0019 §3 的「子进程消失、无终态日志」**（SIGKILL、段错误）情形下，日志里**根本没有那一行**。
  这一条历史只能由父进程自己封口写出——**这已经证明历史行的作者是父进程，不是日志**。
  纯 B 在这里结构性地写不出任何东西。

同时也不取「A 的极端读法」：**不为历史新增任何埋点**。历史行的每一个字段都来自
ADR-0017 §6.2 的既有事件（见 §7）。

### 2. ADR-0017 §5 的演进规则收紧

日志契约由 ADR-0019 §4 起「有了第一个程序化消费者」，由本 ADR 起**成为运行历史这个用户可见
功能的唯一数据来源**。§5 的演进规则相应收紧：

| ADR-0017 §5 原文 | 本 ADR 之后 |
|---|---|
| 字段只增不删、不改义。删字段或改字段含义是破坏性变更，**须与 M2 的消费者一并处理** | **删除字段与改变字段含义一律禁止**，不存在「一并处理」这个出口 |
| `event` 取值进契约 | 不变；**从闭集中删除 `event` 同样禁止** |
| `message` 文字随时可改、字段顺序与空白不保证 | 不变 |

**新增仍然自由**（新 `event`、既有 `event` 的新字段），这是收紧之后仍然留着的唯一演进方向。
理由是不对称的：新增字段对既有消费者无害，而删除或改义会让**已经落盘的历史行与新日志行
语义不同**——那不是一次可以「一并处理」的迁移，是一段无法回溯校正的历史数据。

### 3. 历史行的身份：主键是 `run_record_id`，`run_id` 是可空字段

**`run_id` 当不了主键。** ADR-0017 §2 明写 SQL 形状预检失败时它是 `null`（run 根本没发起，
sink 不知道存在这个 run），而实现上它由**子进程**在预检通过之后才生成
（`crates/source/src/main.rs`，紧跟 `sql_shape_precheck_passed`）。「点了发起、预检就挂了」
恰恰是 UI 上最需要留痕的一类失败。

- **主键 `run_record_id`**：父进程在**受理发起的那一刻**生成，标识「父进程受理的一次发起」。
- **`run_id`**：历史行上的一个**可空字段**，父进程从子进程日志中学到（第一条带 `run_id` 的行起）
  并回填。它标识的仍然是「**sink 认识的那个 run**」。

**被否掉的两条**：

- **父进程预生成 `run_id`，新增 `--run-id` 传给子进程**：破 ADR-0019 §7「命令行契约一字不改」，
  但更要命的是它改了 `run_id` 的**语义**——这个 id 进暂存表名（ADR-0002）、进 HTTP 路径
  （ADR-0010 §1）。预检失败时它不存在是**语义正确**，不是缺陷；提前生成等于把一个
  目标端资源标识降格成 UI 记录号，并让 ADR-0017 §2 那条「显式 `null` 让『这个 run 还不存在』
  成为可断言的事实」当场失效。
- **只给有 `run_id` 的 run 建历史行**：预检失败结构性进不了历史，UI 上「点了发起什么都没发生」。

**两个标识符的代价认下并明写。** ADR-0002 拒绝过「长 `run_id` + 短表名后缀」的二次派生，
理由是「两个标识符对不上就是排障噩梦」——但那拒的是**同一个东西的两个名字**。这里
`run_record_id` 与 `run_id` 的**外延不同**：预检失败时前者存在、后者不存在。挡住排障噩梦的
规则只有一条，必须进规格：

> **UI 与历史行一律同时显示两者；`run_id` 为 `null` 时 UI 明说「未发起，目标端不知道这次运行」。**

**订正 ADR-0019 §7**：临时 task TOML 的文件名带 **`run_record_id`**，不带 `run_id`——
父进程 fork 时还没有 `run_id`，原文在实现上不成立。§7 其余（`0600`、固定子目录、
子进程退出即删、父进程启动清扫残留）一字不变。

### 4. 任务身份不进日志，由父进程侧关联

ADR-0017 §2 的公共字段 `task` 是**任务定义的绝对路径**，而 ADR-0019 §7 让父进程把定义
物化成一个临时 TOML、子进程退出即删。**M2 一落地，日志里的 `task` 就是一个转瞬即逝的
临时路径，不再是任务身份**——#36 清单第 17 项「按任务聚合」正好断在这里。

**决策：`task_id` 不进日志，由父进程在写历史行时补上。**

理由是所有权：`task_id` 是**父进程的知识**，子进程连它都不知道（ADR-0019 §7 只给它
`--task <临时路径>`）。让子进程打一个它不拥有的字段，等于把存储的知识塞回给它——
而 ADR-0019 §7 刚刚为此否掉过 `--task-id` 方案。

被否掉的另两条：**新增公共字段 `task_id`**（合规但在闭集里留一个明知无用的 `task`），
**改 `task` 的含义去承载 `task_id`**（直接违反 §2 刚收紧的规则，且「唯一消费者是自己人、
改了没人受害」这个借口恰恰最危险——它会成为规则的第一个例外）。

**订正 ADR-0017 §2 中 `task` 的说明**：它是**子进程收到的任务定义路径**；M1 下是任务身份，
M2 下是临时物化路径，**不再是身份**。字段本身与值域不变，只订正说明文字。

### 5. 历史落在**同一个** SQLite

ADR-0019 §5 时效点名本票一并定形：**同一个库文件，不另起第二个。**

- 写者是同一个（父进程，ADR-0019 §5 已定唯一写者）。
- 历史行要按 `task_id` 关联任务名展示，同库一次查询就够。

第二个文件唯一站得住的理由是「历史会长大、想整体轮转或删掉」，而 §9 走的是行级清理，
这个理由不成立。**代价**：SQLite 的单写者锁被任务定义写入与历史写入共用——按 §6 的写入频率
（每次发起 ≤7 次写）量级不构成理由，口径同 ADR-0017 §3。

### 6. 写时机：受理即写、原地更新、终结封口

```
父进程受理发起 → INSERT 一行（run_record_id，状态「已受理」）
              → fork 子进程
每读到 stage_changed → UPDATE 该行
读到 run_finished    → UPDATE 封口（终态与全部度量）
子进程消失且无终态行 → UPDATE 封口为失败，标注「进程消失，无终态日志」
```

**否掉「只在 run 终结时写一条」的致命处**：父进程重启会让所有在跑的 run **连痕迹都不剩**。
ADR-0019 §2 说它们「消失」是对**权威状态**说的，而 UI 上一次运行凭空蒸发是最糟的
可观察性缺口——人只会认为自己没点到那个按钮。

这条同时给 ADR-0019 §3 那个「子进程消失、无终态日志」一个落点：

> **父进程启动时扫描库里所有非终态历史行，就地封口为失败并标注「服务重启，结局未知」。**

与 ADR-0019 §7 已定的「父进程启动时清扫临时 TOML 残留」是**同一次启动清扫**，不新增机制——
两者的前提也是同一条：残留必然属于已经不存在的 run（ADR-0019 §2）。

**两条边界一并钉死**：

- **不逐批写。** 只在 `stage_changed` 与终结时写（每次发起 ≤7 次）。批次级进度留在
  ADR-0019 §4 的内存投影里，归 C2（进行中的实时观察），**不让历史存储变成进度存储**。
- **中间态的行仍是投影，不是权威。** 沿用 ADR-0019 §4 的明文降级：任何时候问
  「这个 run 现在怎么样」，权威答案的唯一来源仍是子进程的进程内状态与它的日志。

### 7. 历史行的字段与来源：日志**够用**，不缺字段

票里「§6 的 `event` 闭集与必带字段是否足以重建 UI 要的历史行」这一问的正面答案：
**除任务身份（§4 已解）外，不缺任何字段。** `run_finished` 那一行几乎就是一整条历史行。

| 历史行字段 | 来源 |
|---|---|
| `run_record_id` | 父进程受理时生成（§3） |
| `task_id` | 父进程知识（§4） |
| `run_id`（可空） | 公共字段，第一条带它的日志行 |
| `biz_date` | `source_started.biz_date`（同 `run_id` 跨行关联） |
| `staging_table` | `run_opened.staging_table`（同上） |
| 起 / 止时刻 | `source_started.ts` / `run_finished.ts` |
| `outcome` / `stage` | `run_finished.terminal` / `.stage`（见 §8） |
| `target_table_effect` | `commit_diagnosed.terminal` 与终态推断（见 §8） |
| 门禁四数与诊断数 | `run_finished.source_rows` / `staged_rows` / `sink_reported_rows` / `purged_rows` / `source_batches` / `received_batches` |
| 分段耗时 | `run_finished.fetch_ms` / `push_ms` / `commit_ms` / `count_ms` / `cursor_ms` |
| 失败定位 | `run_finished.source_code` / `sink_code` / `column` / `value` / `message` |

**父进程必须做 run 级聚合，不是逐行映射**——`biz_date` 与 `staging_table` 在别的事件上，
按 `run_id` 关联。这不是缺口，是 §1 那句「历史行的作者是父进程」的具体形态。

### 8. `terminal` 一名两义：消费侧分成两列，日志侧一字不改

**查实的事实**：同一条日志流上 `terminal` 有两个不相交的值域——
`run_finished.terminal` ∈ `{SUCCEEDED, FAILED}`（`RunStage`），
`commit_diagnosed.terminal` ∈ `{SWAPPED, DISCARDED, null}`（ADR-0012 §5 的 sink 墓碑 `Terminal`）。
父进程刚被任命为它的程序化消费者，这是个真陷阱。

日志侧**改名 = 改义 = 被 §2 刚收紧的规则禁止**，所以只能在消费侧分开：

| 历史行列 | 值域 | 取值规则 |
|---|---|---|
| `outcome` | `SUCCEEDED` / `FAILED` | 抄 `run_finished.terminal` |
| `target_table_effect` | `SWAPPED` / `DISCARDED` / `UNKNOWN` | 成功路径记 `SWAPPED`；失败发生在进入 `COMMITTING` **之前**记 `DISCARDED`（目标表未被触碰是确定的）；commit 断连且 ADR-0012 §7 那唯一一次 `GET` 也没问出来，才记 `UNKNOWN`，其余抄 `commit_diagnosed.terminal` |

`UNKNOWN` 不是设计瑕疵，是 §10 的诚实呈现：**抄不到就是抄不到**。

**ADR-0017 §6.2 增一条消费者脚注**（新增，不改任何既有字段——§2 下唯一合规的补法）：

> 两个 `event` 的 `terminal` 值域不相交：`run_finished.terminal` 是 run 终态
> （`SUCCEEDED` / `FAILED`），`commit_diagnosed.terminal` 是 sink 墓碑的资源终态
> （`SWAPPED` / `DISCARDED` / `null`）。**程序化消费者必须按 `event` 分派**，不得按字段名合并。

### 9. 保留期：只设时间维度，默认 90 天，惰性清理

- **只有时间一个维度，不设条数上限。**
- **默认 90 天**，配置项进 `source.toml`。
- **父进程在启动时清一次、每次写入历史行后顺带清一次；零定时器。**

**条数上限被否掉的理由**，正是本票点名要避免的那个病：它把「能查多久」变成
**「跑了多少次的函数」**——高频任务的历史几小时就被冲光，而人实际问的是
「上个月末那次跑了吗」。sink 那 32 条 FIFO 之所以可以按条数，是因为它服务于
**一次断连后立刻发生的追问**（ADR-0012 §7），时间尺度是分钟；运行历史服务于人的回溯，
时间尺度是月。**同一种上限用在两种时间尺度上，是第二个「32 条」的来源。**

量级：90 天 × 每天几十次发起 = 几千行，SQLite 单表毫无压力。

**放 `source.toml` 而非任务定义**，因为保留期是**部署属性不是业务属性**——沿用 ADR-0019 §5
「两个连接配置仍是文件，因为它们属部署」的同一条分法。**惰性清理而非定时器**，是为了不去擦
地图收窄 2「不做调度」的边：本 ADR 不引入任何周期性触发器。

### 10. sink 的 32 条墓碑分立，一条不改

ADR-0012 §5 的墓碑**不被吸收**，本 ADR 对 sink **零改动**（与 ADR-0019 §10 一致）。

两者记的不是同一种东西：历史记的是 **run**（source 视角，跨全程），墓碑记的是
**目标端资源终态**（sink 视角）。更硬的理由是墓碑的**唯一用途**——commit 连接断掉时
source 去 `GET` 问一次「目标表到底动没动」（ADR-0012 §7）：

> **这个问句的提问者是 source、回答者必须是 sink。** source 侧的历史里恰恰不可能有这个答案，
> 因为它正是在断连。历史行里的 `target_table_effect` 只是把 `commit_diagnosed` 的结果**抄**下来。

吸收 = 把一个**跨机器的诊断问答**误当成一份可以本地化的数据。

### 11. ADR-0012 §2 的作用域：**不订正**

与 ADR-0019 §2 同一个判定：**ADR-0012 一条不订正。**

§2 说的是**权威 run 状态**不落盘——权威状态仍然只在子进程内存里，进程一死 run 仍然不存在，
重跑仍然是新 `run_id` 从头，`run-m1-acceptance.sh` 的判据仍然一条不改。本 ADR 落盘的是
**父进程的非权威投影**（ADR-0019 §4 已明文降级），不是权威状态。历史行里有一条
`SUCCEEDED` 的记录，**不代表可以拿它当状态查**——它记的是「那次发起最后被观察到的样子」。

有一条推理要记在明处：ADR-0012 §2 论证不落盘时说「落盘状态**唯一的用途是事后取证**，
而这个用途日志已全额覆盖」。**这半句在 M2 被部分反驳**——日志只在被部署者重定向到文件时
才留存（ADR-0017 §6.1），这正是 §1 否掉纯 B 的第一条理由。但它**不推翻 §2 的结论**：
被反驳的是「日志足以充当留存」，不是「权威状态该落盘」。本 ADR 落的是取证面，不是状态。

**M1「无状态存储」这句话由此有了第二个例外**（第一个是 sink 墓碑，ADR-0012 后果里已明写），
同样必须写在明处：**它是历史留存，不是状态存储**——丢了不影响任何正确性，只影响可回溯性。

## 后果

- **ADR-0017 §7 的 C1 关闭。** M2 的运行历史有了确切落点，#36 面 2「结束后能查到什么」
  从「一行都拿不到」变成一条 SQLite 行；「按任务/日期查」由 `task_id` + `biz_date` 兑现。
- **ADR-0017 §5 从「承诺」正式变成被依赖的接口**（§2），删字段与改义**禁止**。
  代价：M1 日志的字段集合从此是一个**只能生长的**接口。
- **ADR-0017 被订正的处**：§2 中 `task` 的说明（§4）、§6.2 增一条消费者脚注（§8）、
  §7 表中 C1 那一行（关闭）。**字段与 `event` 闭集本身一个不改。**
- **ADR-0019 §7 被订正一处**：临时 task TOML 文件名带 `run_record_id`（§3）。§5 的
  「同一个还是两个存储」定形为**同一个**（§5）。
- **ADR-0012 一条不订正**（§11），但它「M1 无状态存储」的第二个例外由本 ADR 产生。
- **sink、ADR-0010、ADR-0002 零改动**；子进程二进制**一行不改、零新增埋点**——
  地图主方向「M1 链路只被包装、不被重写」兑现。
- **新增两个概念进 CONTEXT.md**：运行历史、`run_record_id`。
- **新增的失效面**：父进程漏读或误解一行日志，历史就与实际不符。由 §6 的「投影不是权威」
  与 §8 的按 `event` 分派共同兜住；根治手段只有契约测试——ADR-0017 §6.2 的闭集测试
  从此**同时是历史存储的测试**。

## 时效

- **§9 的 90 天在有人抱怨查不到、或库文件真的变大时复审**，两者都还没发生过。
- **§5 的「同一个 SQLite」在引入鉴权（[#54](https://github.com/liumingjian/db-qbs/issues/54)）
  时复审**：历史行含失败列与值（ADR-0017 §4 的业务数据），届时「谁能看历史」会第一次成为问题，
  而现在它与任务定义同库同权限。
- **§1 的采集边界归 [#50](https://github.com/liumingjian/db-qbs/issues/50)。** 本 ADR 只用了
  「父进程读自己 fork 的子进程 stdout」这一段——同机、同进程组、不出网。#50 要判的是
  这条线之外还采不采、采到哪，以及 ADR-0017 §4「值可打」的兜底承诺怎么换。
  **本 ADR 让 #50 的第 5 问有了确定前提：历史选了存储，采集侧不再背负重建历史的职责。**
- **§6 的父子写入模型在 M4 引入延迟批次重推**（ADR-0018）**时重开**：`INCOMPLETE` 是跨进程的
  **可恢复**状态，届时「启动时把非终态行一律封口为失败」会第一次错——那时它必须先分辨
  哪些行是可恢复的。
