# ADR-0030: M3 类型白名单——从三种扩到八种形态，失效模式逐种归类

**状态**: 已接受
**日期**: 2026-08-16
**关联**: [ADR-0003](0003-numeric-as-string.md)（规范形式与 V1 白名单，本 ADR 是它在 M3 的启用子集）、

[#95](https://github.com/liumingjian/db-qbs/issues/95)（证据强度分档）、
[#104](https://github.com/liumingjian/db-qbs/issues/104)（`NUMBER` 两形态往返实测）、

## 背景

ADR-0009 把 M1 的类型白名单收窄到 `NUMBER(p,s)`（常规形态 `0 ≤ s ≤ p`）/ `VARCHAR2` / `DATE`
三种，并在 §4 的拒绝清单上把一串项标着「归属 M3」。M3 地图
[#94](https://github.com/liumingjian/db-qbs/issues/94) 的主方向是「**买能搬的东西变多**」，
本 ADR 把那份清单一次定形。

**判据不是客户分布，是类型面 + 目标端往返实测**（[#95](https://github.com/liumingjian/db-qbs/issues/95) /
[ADR-0005 增补](0005-local-rig-as-v1-verification-baseline.md)）：db-qbs 是通用离线导入方案，
任何具体部署都是一个样本，答得了「先做哪种收益大」，答不了「必须支持哪些」。

**ADR-0006 的前提一个字没变**：V1 只比行数，没有行 checksum，预检仍是「值没有被悄悄改掉」的
**唯一防线**。放宽类型不得以「V2 的 checksum 会兜住」为论据。因此本 ADR 的中心不是「多收几种」，
而是 **ADR-0009 §2 的分级思想逐种兑现**：静默改值 → 从严；当场炸 → 从宽。
每一行都必须写出**危险面**与**失效模式**，以及**实测出处**——推理不构成放行依据。

## 决策

### 1. 白名单：八种源形态

「形态」而非「类型」：`NUMBER` 的四种形态判定式各不相同，按类型数会数不清。

| # | 源形态 | 推导目标形状 | 危险面 | 失效模式 | 分级 | 实测出处 |
|---|---|---|---|---|---|---|
| 1 | `NUMBER(p,s)`，`0 ≤ s ≤ p` | `DECIMAL(p,s)` | 标度写小 | **静默改值**（`Note 1265`） | **从严** | §7.8 组 2 |
| 2 | `NUMBER(p,s)`，`s > p`（纯小数） | `DECIMAL(s,s)` | 标度写小 | **静默改值**（`Note 1265`，`±0.000001` 塌成 `0.0000`，**符号一起丢**） | **从严** | §7.11 组 1 |
| 3 | `NUMBER(p,s)`，`s < 0`（负标度） | `DECIMAL(p+\|s\|,0)` | 整数位写小 | **当场炸**（`ERROR 1264`，行不落库） | **从宽** | §7.11 组 2 |
| 4 | 裸 `NUMBER`（p/s 皆 NULL）与**表达式列** | 人工配置的 `DECIMAL(p,s)` | 配置写小 / 预检后出现新极值 | 由全量值域校核 + 逐值兜底转成**当场拒**，见 §4 | 专章 | ADR-0003 增补 |
| 5 | `VARCHAR2(n)`（`CHAR` / `BYTE` 两种语义） | `VARCHAR(n)` | 目标列窄 | **当场炸**（`ERROR 1406`） | **从宽** | §7.8 组 1 |
| 6 | `NVARCHAR2(n)` | `VARCHAR(n)` | 同上 | **当场炸** | **从宽** | §2.2 源端 / §7.8 组 1 目标端 |
| 7 | `CHAR(n)` / `NCHAR(n)` | `VARCHAR(n)` | **目标建成 `CHAR`** | **静默改值**（剥尾空格；空串与全空格**碰撞**） | **从严** | §7.8 组 1、组 4 |
| 8 | `DATE` | `DATETIME(0)` | 目标 `fsp > 0` 只是补 `.000000`（不改值）；**反向**（`TIMESTAMP` 落 `fsp=0`）才危险 | 见 §3 | **严格** | §7.8 组 3 |
| 9 | `TIMESTAMP(n)`，`0 ≤ n ≤ 6` | `DATETIME(6)` | 目标 `fsp < 6` | **静默改值**（小数秒舍掉，**一条 Note 都没有**） | **严格** | §7.8 组 3 |

> 形态 8/9 合起来占一个「日期面」，故编号到 9 而形态数记八种（`NUMBER` 四 + 字符三 + 日期二 = 九行，
> 其中形态 5/6 判定式逐字相同，实现上是一个分支）。数字不重要，**每行有没有实测出处才重要**。

**判定式（目标列 `(p',s')` / `n'` / `fsp'` 怎么跟推导形状比）不在本 ADR。**
本 ADR 只定「推导形状是什么」与「失效模式是哪一类」——这两样是**类型的性质**。
「从严具体写成 `s' == s` 还是 `s' >= s`」是一条横跨全部 `NUMBER` 形态的统一决策，
归 [#97](https://github.com/liumingjian/db-qbs/issues/97)，本 ADR 定稿后由它续写。
`VARCHAR2` / `CHAR` 族的下界式 `n' >= n` 与日期族的严格式 ADR-0009 §2 已定，本 ADR 原样沿用。

**目标端 `DATA_TYPE` 逐列判**（现行实现已有，本 ADR 只是把它对新形态点名）：
`NUMBER` 族必须 `decimal`、字符族必须 **`varchar`**、日期族必须 `datetime`。
形态 7 的全部危险面**就消解在「必须 `varchar`」这一条上**——见 §5。

### 2. 拒绝清单（M3 版）

| 拒绝项 | 判据 | 归属 |
|---|---|---|
| `BINARY_FLOAT` / `BINARY_DOUBLE` | 二进制浮点不是十进制精确值，「一律走字符串」不构成无损保证。§2.4 实测 `1.7976931348623157E+308` 取成 **309 位十进制展开**，落进 `DECIMAL` 必然溢出；正确目标类型是 `DOUBLE`，而 `DOUBLE` 上的校验不能按字符串比——**那是另一条搬运通道** | **V1 不支持**（证据反向支持继续拒） |
| `CLOB` / `NCLOB` / `LONG` / `BLOB` / `RAW` / `LONG RAW` / `XMLType` / 对象类型 / 嵌套表 | 顶开 ADR-0007 单查询流式与 ADR-0011 批次载荷格式，是 V2 的量级 | **V1 不支持**（地图 #94 Out of scope） |
| `TIMESTAMP(n)`，`n > 6` | 规范形式与 `DATETIME(6)` 都只保 6 位，放行等于静默丢 3 位 | **拒绝**（ADR-0003「TIMESTAMP 标度上限」已定，取数前读 describe 判，不截断、不扫值域） |
| `TIMESTAMP WITH TIME ZONE` / `INTERVAL` | 白名单外；时区转换会在正确性单点上引入环境依赖变量（同 §7.4 第 3 条拒 MySQL `TIMESTAMP` 的理由） | **V1 不支持** |
| 推导形状超出 MySQL `DECIMAL` 表达能力 | 见 §6 —— **判据已订正** | 前置判定，单列一条 |
| **字符表达式列**（`SUBSTR(c,1,3)` 等，describe 给不出 `length`） | `n' >= n` 下界式失去比较基准 | **拒绝**，改 SQL 写明确的列或加 `CAST` |
| 两边列名集合不相等 / 目标列 `NOT NULL` / 目标列字符集不是 `utf8mb4` | ADR-0009 §3 / §5 / §6 | **原样保留，本 ADR 不动** |

### 3. `DATE` 与 `TIMESTAMP` 都维持严格——ADR-0009 §2 那条伏笔兑现方式是「两边都不放宽」

ADR-0009 §2 把 `DATE` 判成严格 `fsp == 0`，理由原文是「一旦允许 `DATETIME(6)`，
M3 引入 `TIMESTAMP(n)` 时同一个目标列型会对应两种源类型，映射不再可逆」。M3 真的引入了，
**伏笔自解**：`DATE → DATETIME(0)` 严格、`TIMESTAMP(n) → DATETIME(6)` 严格，
两条都严格，`DATETIME(0)` 与 `DATETIME(6)` 各自只对应一种源类型，**一列一型，可逆性从未被威胁**。

**真正会捅破它的是放宽任何一边**，故两边都维持。

**`TIMESTAMP(n)` 的推导形状恒为 `DATETIME(6)`，不随 `n` 走。** ADR-0003 的规范形式表写死
「固定 6 位，不足补零」，`TIMESTAMP(2)` 产出的仍是 `...09.120000`。若推导成 `DATETIME(n)`，
`TIMESTAMP(0)` 就会推出 `DATETIME(0)`，跟 `DATE` 正面相撞，**恰恰把 §2 担心的事做实**。

### 4. 裸 `NUMBER` 与表达式列：人工定形 + 全量值域校核，两者走同一条规则

ADR-0003「无精度声明的 `NUMBER`」增补的三段式规则（任务定义显式给 `DECIMAL(p,s)`、
预检对与取数同一结果集做**全量**值域校核 `x = TRUNC(x,s)` 且 `ABS(x) < POWER(10,p-s)`、
搬运时每个规范字符串进批次前再按 `(p,s)` 逐值校核兜住并发）**原样启用，一个字不改**。

#### 4.1 表达式列一并放行，ADR-0009 §1 那句「刻意要的」**改写**

现行实现里裸 `NUMBER` 与表达式列共用同一条拒绝分支（`precision`/`scale` 为 `None`），
而两者在技术上没有区别：`SELECT n_qty * n_price AS N_AMT FROM t` 的 describe 同样给不出精度，
而全量值域校核用的是「与取数查询相同的 `FROM`/`WHERE` 和绑定参数」——**表达式照样扫得动，判据一字不差**。

ADR-0009 §1 原文把「表达式列精度不明本来就要拒绝」称为**刻意要的**副作用，
用来逼着任务定义把 SQL 写成明确的列。**该理由的实质是「精度不明就别搬」，
而人工定形 + 全量验值恰恰是把精度补明确的机制——理由被自己的解药消掉了。**
本 ADR 明确订正它：**数值表达式列与日期表达式列放行**（日期族判的是目标 `fsp`，
源端本就不需要精度），**字符表达式列继续拒**（见 §2）。

**ADR-0009 §3「每列显式命名，表达式列必须写别名」原样保留**——放行的是**精度不明**，
不是**列名不明**。列名不明会撞上 §3 的按名字对齐，那是另一条防线。

#### 4.2 `(p,s)` 配置进任务定义：可选字段，且它**不是** #100 判掉的那张映射表

任务定义（ADR-0016 §2 四字段）新增**一个可选字段**，形如列名 → `(p,s)` 的表。
不含裸 `NUMBER` / 数值表达式列的任务文件不写它；ADR-0016 §6 的「未知字段严格拒绝」
管的是**未知字段**、不管**缺省的可选字段**，**老任务文件一个都不会失败**——
ADR-0016「后果」里那笔预留的账 **M3 也不付**。

**必须写明的一条区分**（否则后人会拿 [#100](https://github.com/liumingjian/db-qbs/issues/100) 来打这条）：
这张表跟 #100 判掉的「字段映射表」形状同构——都是按列名索引的旁路配置——但**失效面性质相反**：

- **映射表写错没有任何东西会发现**：列对错位，行数照样相等，V1 无下游机制。这正是 #100 的判据。
- **`(p,s)` 写错被全量值域校核兜住**：写小了，`x <> TRUNC(x,s)` 或 `ABS(x) >= POWER(10,p-s)`
  当场命中，`invalid_rows > 0` 即拒；写大了，目标列必须与配置逐位相等，值全装得下，保值成立。
  **配置错误不构成新的静默失效面。**

不取「把定形推回源端、要求人写 `CAST(n_amt AS NUMBER(38,10))`」这条路：
`source_sql` 是 ADR-0023 定的权威且随时可手改，配置会跟着漂，
且预检拿不到「人想要的形状」、只拿得到 `CAST` 之后的形状，全量验值失去比较基准。

#### 4.3 预检形状：从「只读元数据」变成「只读、不写」

ADR-0009 §7 的固定顺序**加一步**：

```
1. describe 源端 SQL
2. 查目标端 information_schema.COLUMNS
3. 按名字对齐，逐列比对
3.5 若存在裸 NUMBER / 数值表达式列 → 跑一条聚合值域校核（每列一个 SUM(CASE ...)，只扫一遍）
4. 全部通过 → 才建暂存表；任一列不过 → 整 run 失败，什么都不建
```

**§8「一次报全部列」原样成立**：值域校核是一条聚合 SQL、一次算完全部相关列，
产出形态与其余逐列规则完全一样（一列一条不合规记录），进同一张报告。

**§7 末尾那句「预检只读元数据，不存在继续检查引发副作用的顾虑」订正为「预检只读、不写，
不产生副作用」**，并且必须连**代价**一起写下，别让它以「预检怎么突然这么慢」的形式在下游爆出来：

> **含裸 `NUMBER` / 数值表达式列时，预检不再是常数时间的元数据查询，
> 而是多一次源端全表扫描**；走 dblink 时这一扫同样过 dblink。
> 业务日期谓词、分区裁剪与既有索引仍可缩小结果集，但**不能用抽样换掉全量检查**；
> 源库承受不了这次扫描，该列**保持拒绝**，不提供「带风险放行」开关。

**`invalid_rows > 0` 复用既有的预检失败分类，不增码。** 它就是预检拒绝，
只是判据从元数据变成了值。ADR-0010 的错误码闭集与 ADR-0029 §2 对照表**本 ADR 不动**——
增码是「只增不删」的单向门，不为一个已有归属的失败开门。

### 5. 形态 7 的碰撞已消解，不需要新规则

#13（§7.8 组 1、组 4）坐实：`CHAR(n)` 目标端读回**剥尾空格**，且**空串与全空格碰撞**
（两者读回都是空，`PAD_CHAR_TO_FULL_LENGTH` 不但救不回还会凭空补出源端没有的空格，
且在 8.0.46 上已 deprecated）。

**碰撞只发生在目标列是 `CHAR` 的时候**，而 §1 的 `DATA_TYPE` 判定要求字符族目标必须是 `varchar`，
目标建成 `CHAR` 直接拒。源端那头 §2.2 实测驱动给出 `"AB        "`，尾空格完整；
§7.8 组 4 实测 `VARCHAR` 上 NULL / 空串 / 全空格 / 字面量 `NULL` **四者两两可区分**。
**全链路没有一处碰撞点。**

连带一条点名：[ADR-0027](0027-target-ddl-generation-and-cross-end-metadata.md) 生成建表 SQL 时，
`CHAR(n)` / `NCHAR(n)` 源列必须吐 `VARCHAR(n)`，**不得照抄源类型名**
（§7.4 第 5 条「生成建表 SQL 时目标端不得出现 `CHAR`」是无条件硬约束）。

### 6. 订正：`s > 30 || p > 65` 前置判定改成判**推导形状**

ADR-0009 §4 把这条前置判定写成对**源** `(p,s)` 判 `s > 30 || p > 65`，
报「MySQL `DECIMAL` 无法表达该源类型」。M1 只有常规形态，推导形状就是 `(p,s)` 本身，
判源等于判形状，**两者重合**。放行形态 2/3 之后**不再重合**：

- `NUMBER(38,-30)` → `DECIMAL(68,0)`。源侧 `p=38 ≤ 65`、`s=-30`，**现行判据一条都不命中，直接放过**；
  而 `DECIMAL(68,0)` 建不出来。
- `NUMBER(4,35)` → `DECIMAL(35,35)`。源侧 `s=35 > 30` 命中，**是碰巧**——
  判据算的是源标度，跟目标标度只是恰好相等。

**订正为：先推导形状，再判 `p' > 65 || s' > 30`。**
ADR-0003「`DECIMAL` 精度与标度」增补的原则（「推导出的形状若超过 MySQL `DECIMAL(65,30)`
的表达能力，预检直接拒绝，不截断」）本就如此，缺的是 ADR-0009 §4 那条具体判据没跟着改——
**它是 M1 三类型下的一个特例式，被当成通式写下来了**。

**「单列一条前置判定」的地位与人话措辞原样保留**，且理由更强了：不单列的话，
`NUMBER(38,-30)` 的报告会写成「期望 `DECIMAL(68,0)`」，而那张表 MySQL 根本不让建，
人会对着一张建不出来的表改半天。

### 7. `NVARCHAR2` 收编，并订正 spike §7.3 的一处笔误

`NVARCHAR2(n)` 进白名单，**判定式与 `VARCHAR2` 逐字相同**（`VARCHAR(n)`、`n' >= n`、
目标 `utf8mb4`、越界当场炸 `ERROR 1406`）。它与 `VARCHAR2` 的差别只在源端字节/字符语义，
而 §7.3 已定「`n` 已是字符数，直接对齐」——**目标端往返面完全同构，不引入任何新失效模式**。

**spike §7.3 把 `NVARCHAR2(n)` 那一格标成「M1 生效」是笔误**：ADR-0009 §4 的三类型白名单是权威，
M1 的实现（`describe_column` 只认 `Number` / `Varchar2` / `Date`）也确实拒它。已就地订正。

### 8. 对其他 ADR 的订正落点

| ADR | 订正 |
|---|---|
| **ADR-0009** | §2 的三行类型清单与 §4 的拒绝清单**被本 ADR 部分取代**；§1 关于表达式列「刻意要的」那句由 §4.1 改写；§4 的前置判定由 §6 订正；§7 顺序加 3.5 步、末句措辞由 §4.3 订正。**§2 的分级思想本身、§3 按名字对齐、§5 可空性、§6 字符集、§8 报告形态、§9 两条人话——全部原样成立** |
| **ADR-0003** | **不改**。本 ADR 的白名单是 ADR-0003 白名单（`NUMBER`/`DATE`/`TIMESTAMP(0..6)`/`VARCHAR2`/`NVARCHAR2`/`CHAR`/`NCHAR`/`NULL`）的**启用子集**，一种都没超出；「无精度声明的 `NUMBER`」与「TIMESTAMP 标度上限」两条增补由本 ADR **启用**，不修改 |
| **ADR-0011** | **只加行**：§3 那张「三种类型的线上形态」表补上新形态，全部仍是 **JSON string**（`CHAR`/`NCHAR`/`NVARCHAR2` 同 `VARCHAR2` 原样 UTF-8，尾空格是值的一部分；`TIMESTAMP(n)` 是 source 格式化出的 `"YYYY-MM-DD HH:MM:SS.ffffff"`；三种 `NUMBER` 新形态仍走规范形式串原样透传）。**§1/§2/§4~§9 一字不动**——唯一会顶开线格式的是 `BINARY_FLOAT`/`BINARY_DOUBLE`，而它已判继续拒。特别点名 §2「解析器不得开启『`null` 视作空串』『空串视作 `null`』宽容选项」那条规格条款：`CHAR` 进来之后「空串」第一次成为高频形态（全空格列、定长补位），该禁令从原则变成**有具体输入会踩** |
| **ADR-0016** | §2 加**一个可选字段**（裸 `NUMBER` / 数值表达式列的 `(p,s)` 配置），见 §4.2。§6 未知字段严格拒绝不受影响，老任务文件不失败 |
| **ADR-0027** | `CHAR`/`NCHAR` 源列的建表 SQL 必须吐 `VARCHAR(n)`，见 §5 |
| **ADR-0014** | 每种新形态的 `canon_*` 纯函数与边界断言要扩，**本 ADR 不定**——已毕业成独立票 |
| **ADR-0010 / ADR-0029** | **不动**，不增码，见 §4.3 |

## 后果

**买到的**：白名单从 3 种撑到 9 行形态，`ADR-0009` §4 上标着「归属 M3」的项**一次清空**。
每一行都带实测出处，没有一条是推理放行的。

**付出的**：

- **预检不再是常数时间**。含裸 `NUMBER` / 数值表达式列时多一次源端全表扫描，见 §4.3。
  这是本 ADR 最大的一笔代价，也是 [#96](https://github.com/liumingjian/db-qbs/issues/96)
  讨论里唯一一处「买的东西超出了类型面」的地方。
- **判定式分支从 3 条变成 9 行**，其中 `NUMBER` 族 4 种形态的推导式互不相同。
  ADR-0009 §8 的「一次报全部列」因此在 70 列生产表上会更密——**呈现问题归
  [#102](https://github.com/liumingjian/db-qbs/issues/102)，规则本身不受影响**。
- **任务定义多一个字段**，ADR-0016 §2 从四字段变成四 + 一可选。
- **误拒面收窄但没有消失**：`BINARY_FLOAT`/`BINARY_DOUBLE`、LOB 族、`n > 6` 的 `TIMESTAMP`、
  字符表达式列仍然跑不起来。ADR-0009「后果」那句代价原样成立：
  **不完整不会变成「搬错」，只会变成「跑不起来」。**

## 时效

- **判定式的宽容度由 [#97](https://github.com/liumingjian/db-qbs/issues/97) 续写**——
  本 ADR 定稿时它仍开着。#97 若判改用下界式，改的是「怎么比」，不改本 ADR 的推导形状与失效模式归类。
- **`DATETIME` 值域那条实测依赖 MySQL 8.0.46**（ADR-0009 §10 第 1 条），
  **换 MySQL 大版本要重测**；本 ADR 新增的形态同样架在 8.0.46 的实测上。
- **ADR-0009 §10 第 2 条那条静默路径（`canon_date` 对公元前日期丢纪元）本 ADR 不收口**，
  归 [#98](https://github.com/liumingjian/db-qbs/issues/98) / [#99](https://github.com/liumingjian/db-qbs/issues/99)。
- **本 ADR 不由「客户生产环境的类型直方图」触发复审**（[#95](https://github.com/liumingjian/db-qbs/issues/95) /
  ADR-0005 增补）：分布是优先级输入，不是判定式的依据。触发复审的是**新的目标端往返实测结论**，
  或 MySQL / Oracle 驱动的行为变化。
