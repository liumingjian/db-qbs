## 背景

地图 [#47](https://github.com/liumingjian/db-qbs/issues/47) 写死了一条硬要求：
**UI/UX 不是完工后补的皮**，且**设计系统一旦定调，后续所有原型必须复用、不得另起一套**。
本 ADR 是那次定调。

定调必须早：晚定的话，本图后面每一张高保真原型都要返工。
定调的材料来自 [#36](https://github.com/liumingjian/db-qbs/issues/36) 的低保真线框
（`docs/prototypes/0036-m2-ui-observability-wireframes.md`），只用其中**数据来源确定**的部分——
面 3（run 失败时）与面 2（run 结束后）里 ADR-0017 §6 `event` 闭集能提供的字段。

**这是 HITL 决策**：四个方向的高保真变体由 agent 产出，**选型由人做**。
本 ADR 记录的是人选定之后的结论，不是 agent 的推荐。

## 决策

### 1. 选定方向 D「调度台」——DolphinScheduler 中后台范式

> **左侧固定导航 + 顶栏面包屑 + 灰底内容区 + 白卡片包表格。**

**理由是受众，不是审美**：db-qbs 的用户是**运维与开发**，他们每天已经在 DolphinScheduler
这类调度台范式里工作。界面不该要求他们重新学一套。

落选的三个方向及其被放弃的东西，记在原型页里（A 值班台 = 极高密度但要人认得 `SEQ_MISMATCH`；
B 卷宗 = 可转发的报告感但一屏放不下几行；C 双轴仪表 = 形状语言最讲究但网格噪声高）。
**它们不是备选项，是已关闭的分支**——要回头得重开本 ADR。

**「像个能做调度的软件」指的是视觉形态，不是功能。** 收窄 2（不做鉴权调度）一字不动：
`定时调度` / `告警` 只在左导航**占位、置灰、不可点**并标 `M3+`。
任何把调度画成 M2 已有功能的产物**退回**。

### 2. 三条取舍写死

1. **蓝色 `#2C8AF0` 只标「可点」**（主按钮、选中导航、操作链接），**不参与状态语义**；
   状态色只出现在圆点、标签、告警框上。
2. **灰底衬白卡是唯一的分层手法**：不叠阴影、不做渐变、不用胶囊圆角。
3. **表格与数字是主体**：行高 44px、数字右对齐等宽、不做仪表盘卡片与装饰性图标。
   这是搬数据的工具，不是营销页。

具体令牌值以 [`docs/design-system/tokens.css`](../design-system/tokens.css) 为准，
**该文件是唯一来源**；本 ADR 不复制数值，避免两处漂移。

### 3. 状态与错误分三条互不重用的形状轴

这是本 ADR 最该被后续票引用的一条。「红黄绿三色」不够——同屏并列时必须一眼分清
**跑到哪了 / 目标表动没动 / 为什么失败**：

| 轴 | 语义来源 | 形状 |
|---|---|---|
| 轴一 **进程阶段** | ADR-0012 五态的进行中部分 | **圆点**串（当前 `--info` 带光晕，已过 `--ok`，未到 `--mute`），**只在进行中出现** |
| 轴二 **资源终态** | ADR-0012 墓碑两值 | **块**：`SWAPPED` 实心 / `DISCARDED` 描边中性；回答「目标表动没动」，与「为什么」无关 |
| 轴三 **错误码** | ADR-0010 闭集 **12 码** | **标签**（等宽码名 + 小号 HTTP 码），**4xx 虚线边框 = 你能改，5xx 实线边框 = 找人** |

**硬规则**：

- 三轴形状**不得互换、不得复用**。新状态先判它属于哪条轴；不属于任何一条，
  先回 ADR 定语义再画——**不在原型里就地发明状态**。
- **错误码是闭集**：UI 不得自造码、不得只显示 HTTP 码而吞掉码名；未知码按 `INTERNAL_*` 那档呈现并原样回显。
- 码名右边永远跟一句**中文人话结论**（ADR-0013 §6 的两类分法：校验数不符 / 校验没跑成）。
  人话在前、码在后：码是给能查文档的人的锚点，不是解释。
- 进行中不用轴二，终态不用轴一；两轴并列允许，三轴同现不允许。
- **4xx/5xx 用边框形态而非仅用色区分**，是为了色觉障碍与黑白打印下不丢信息。

### 4. 业务值只有一个容器，且默认打码

失败详情里的 `column` / `value`（ADR-0017 §4）装进**独立告警框**，与普通字段视觉上完全分开，
**默认打码**，点「显示」才出，框上写明**「显示即把源库真实值送进这台浏览器」**。

**这是设计上的落点，不是安全机制。** 暴露面定价归 ADR-0024（端口即凭据），本 ADR 不重开。
ADR-0024 §2 的负面条款在设计系统里复述一遍，防止原型忘掉：
**没有连接配置管理页，不是还没画，是不画。**

### 5. 中文优先排版：系统字体栈是唯一诚实解

离线与 CSP 约束下**中文 webfont 无法内联**——不假装能发字体。

- 正文栈 `PingFang SC → HarmonyOS Sans SC → Source Han Sans SC → Noto Sans CJK SC → Microsoft YaHei → Hiragino Sans GB → sans-serif`。
- **数字与标识符走独立等宽栈** + `font-variant-numeric: tabular-nums`：
  `run_id`、行数、字节数、耗时、错误码、列名、SQL 一律等宽定宽，**列对齐才成立**。
- 行高：界面正文 1.55，成段中文 1.7。
- **强调字重 600，不用 700**——中文在 13–14px 下 700 会糊。
- **不用斜体**：中文没有真斜体，合成伪斜体是坏字形。

### 6. 暗色主题：**不发**

V1 **只发浅色**，不提供暗色主题，也不留主题切换开关。三条理由：
受众在办公环境且该范式本身是浅色；两套主题是**持续维护成本**（每张新原型双份检查）；
M2 买的是可操作性不是外观选项。

**这是 #55 第 5 问的正面回答，不留给实现期默认。**
变体原型里那套暗色 token 只是当时的对照材料，**不进** `tokens.css`。
要发暗色需重开一票并改设计系统 §6。

### 7. 本 ADR 的效力：设计系统是单一来源

> **本图之后所有 UI 产物（原型与生产前端）一律复用 `docs/design-system/`，不得另起一套。**
> 要改先改那两个文件，**不在单张票里就地发明**。

一致性靠单一来源保证，不靠每张票各自把握。

## 不在本 ADR

- **不定信息架构与流程**（有哪些屏、屏上的先后）——归 [#48](https://github.com/liumingjian/db-qbs/issues/48) /
  [#49](https://github.com/liumingjian/db-qbs/issues/49) / [#51](https://github.com/liumingjian/db-qbs/issues/51) /
  [#56](https://github.com/liumingjian/db-qbs/issues/56)。本 ADR 只定「长什么样」。
  设计系统 §7 给历史列表、实时进度、SQL 构建器**预留了位置**，那是「用哪些既有组件」，不是信息架构。
- **不定前端技术栈**——ADR-0019 §9 已定 React+TS 内嵌二进制。
- **不写生产前端代码。**
- **不重开暴露面定价**（ADR-0024）与**搬运语义**（收窄 1）。

## 代价（选 D 时一并接受）

- **范式眼熟 = 不容易出彩**。换来的是零学习成本；本图的目标是可操作性，接受这笔交换。
- **密度中等偏松**：一屏比极高密度方案少放约 40% 的行，看长历史要多滚。
- **单主题**：暗色环境下的用户没有选项。有实际反馈时按 §6 重开。

## 重开条件

1. 出现「受众不是运维与开发」的实际部署（§1 的唯一支柱失效）；
2. 有暗色需求的实际反馈（§6）；
3. 三轴形状在某块屏上不够用——**此时改的是本 ADR §3，不是那块屏就地加第四种形状**。

## 2026-08-16 增补（[#102](https://github.com/liumingjian/db-qbs/issues/102)）：M3 的界面增量**零设计系统改动**，一条布局裁定落在 `app.css`

**来源**：[#102](https://github.com/liumingjian/db-qbs/issues/102)，地图 [#94](https://github.com/liumingjian/db-qbs/issues/94)。
**产物**：原型 [`docs/prototypes/0102-m3-ui-increments.html`](../prototypes/0102-m3-ui-increments.html)（三屏，令牌逐字内联）。

### 1. 结论：`docs/design-system/README.md` 与 `tokens.css` **一个字不改**

M3 把类型面从三行扩到九行，界面上多了五处新信息位（预检报告的「建议」列、
取列卡三档标记、DDL 占位符、整份 DDL 不给、值域校核条目）。**五处全部由既有元素承载**：

- 五列表 = 既有 `DiagnosticTable`（吃 `columns: string[]`，加一列零 CSS）；
- 三档标记 = 纯文字（ADR-0029 §3 的写法），**不成元素**；
- `DECIMAL(<p>,<s>)` = 既有 `.ddl-placeholder`；
- 「整份 DDL 不给」= 既有 `.row-size-warning` 的 `.is-crit` 变体。

故**不触发** `docs/spikes/fixtures/local-rig/m2-visual-walkthrough.md` 的整份 V1–V25 走查。
§7「设计系统是单一来源」原样成立：本票没有就地发明，也没有回头改那两个文件。

### 2. 裁定一：三档标记**不着色**，不上形状轴

`[待配精度]` / `[不支持]` 曾在原型里分别上过 `--warn` / `--crit`。**撤掉。**
§3 的三条形状轴各有其归属（运行态、墓碑、错误码），这两个标记哪条都不是：
它们出现在**取列**这个探索性动作里，不是失败态。着色会让读的人按 §3 轴三
（错误码 = 标签）去理解它，而它没有错误码。**与 ADR-0029 §3 逐字同构：纯拼接、零颜色。**

### 3. 裁定二：映射预检失败时，两栏并置退化成整宽堆叠

`.precheck-reports`（`web/src/app.css:241`）是固定两列网格。M1 三类型时两侧行数相当，
M3 满载后失衡：左栏「SQL 形状预检」恒为 6 行，右栏一次可报 17 条五列记录。
1024 视口实测（原型屏 A）：**第五列「建议」整列被切到框外，要横滚才看得见**，
同时左栏大片留白，读起来像漏渲染。

**裁定：映射预检失败态下两栏改为整宽堆叠**（容器加 `is-map-failed`，其下 `section`
取 `grid-column: 1 / -1`）。两栏并置的目的是让两道预检**对照**；一边 17 行一边 6 行时，
对照价值已经没有了，而把最该读的一列藏进横滚是明知故犯。

**边界**：`shape-failed`（映射预检显示为 `is-skipped`）**不套用**——那时右栏只有一句话，
两栏并置照旧合适。

**这条动的是 `web/src/app.css`，不是 `docs/design-system/`**，故不触发整份走查；
但**必须在 [#103](https://github.com/liumingjian/db-qbs/issues/103) 的 M3 验收走查里加这一屏用例**
（1024 与 1440 各一次，看五列是否全在框内）。落地归 M3 实现票，本票不写生产代码。

### 4. §3 三轴、§6 单主题、§7 单一来源全部不动

本增补不新增形状、不新增颜色语义、不重开暗色。「重开条件」第 3 条未被触发——
本票没有出现「三轴形状不够用」的情形，出现的是**布局失衡**，那不在 §3 的管辖内。

## 2026-08-16 增补三：轴二的「实心」那半边补齐，§8 的黑白承诺从定性改成可量

来源：[#89](https://github.com/liumingjian/db-qbs/issues/89)（走查 V5 记的账，
`m2-visual-walkthrough-20260816T103300Z.md`）。**本增补动 `docs/design-system/`，
故按 `CLAUDE.md` 的门禁重跑整份 V1–V25 走查。**

### 1. 事实：承诺的两半只兑现了一半

§3 轴二把 `SWAPPED` 定为**实心**、`DISCARDED` 定为**描边**，§8 据此承诺
「黑白打印下三轴仍可分（实心块 vs 描边块 ...）」。走查 V5 整页 `filter: grayscale(1)`
后实测块内中位亮度：**`SWAPPED` 247、`DISCARDED` 255，差 8/255 = 3.1%**，
同列纯文字格也是 255。

**「描边」那半边一直是对的**（#58 定形时就写死了 `DISCARDED` 不给底色，理由记在
`app.css` 的注释里）；失守的是**「实心」那半边**——`--ok-bg` 是个几乎白的柔和底，
灰度下根本没画出「填充」这件事。承诺是两边各守一半，缺一边就不成立。

### 2. 根因：一个 token 承担了两个方向相反的要求

`--ok-bg` 同时供着两个角色：

- **大面积柔和底**（`.success-conclusion` 的成功结论条、告警框）——要**淡到不抢**；
- **轴二实心块的填充**——要**深到在灰度下与白底可分**。

**这两个要求方向相反，同一个 token 承载不了。** 3.1% 就是折中的结果：
对结论条来说刚好，对实心块来说等于没画。

**裁定：给轴二实心块单开 `--ok-fill`，`--ok-bg` 一字不改**，两个角色各自持有一个 token。
不取「直接把 `--ok-bg` 加深」这条路——那会把成功结论条一起压深，
而结论条是一整条横幅，加深它是另一个方向的视觉改动，与本票要解决的问题无关。

配套新增 `--ok-ink`：**填充加深必须让文字跟着加深**，否则买到的灰度可分是拿文字可读换的。
`--ok`（`#19BE6B`）落在 `--ok-fill` 上只有 **1.91:1**，`--ok-ink`（`#0B6637`）是 **5.55:1**，
过 WCAG AA 正文档。**这不是顺手改的观感，是本裁定的必要配套**——只改填充就是一次退化。

| token | 值 | 灰度中位亮度 | 角色 |
|---|---|---|---|
| `--ok-bg` | `#F0FAF4` | 246 | 大面积柔和底（**不动**） |
| `--ok-fill` | `#CDEBD9` | **227**（实测） | 轴二实心块填充，与白底 255 差 **28（11.0%）** |
| `--ok-ink` | `#0B6637` | 70 | `--ok-fill` 上的文字，对比 5.55:1 |

表里 `--ok-bg` / `--ok-ink` 两格是按 ITU-601 离线算的；`--ok-fill` 那格给的是走查实测——
浏览器 `filter: grayscale(1)` 按 Rec.709 折算，同一个 `#CDEBD9` 离线估 224、屏幕上量到 227。
**判据以实测为准**，差 3 不改结论（28 ≥ 25）。

`--ok-bd` 落在 `--ok-fill` 上亮度几乎相同（221 vs 224），**边框因此看不见了——这是对的**：
实心块本来就不该靠边框立住，靠边框立住的那个叫描边块。已写进 §3 轴二一行，
免得下一轮走查把它当缺陷报回来。

### 3. §8 那条承诺从定性改成可量：**差 ≥ 25/255（≈10%）**

**这是本增补比改颜色更值钱的一半。** 3.1% 的状态被走查看过**两轮**都判「部分符合」而非 FAIL，
原因不是走查的人不认真，是**判据本身挡不住这类退化**：

> 定性判据问的是「分不分得开」，而承诺说的是「**靠实心 vs 描边**分得开」。
> 「靠形状仍分得开」这句话在 3.1% 时**也为真**（边框和文字在，块当然分得开），
> 于是每一轮都能诚实地写下「部分符合」，然后过去。

故 §8 改写为可量的判据：轴二两个块整页灰度后**块内中位亮度差须 ≥ 25/255（≈10%）**，
走查该条**必须贴实测数字，不接受「目视可分」**。`m2-visual-walkthrough.md` V5 一行同步。

取样口径沿用走查记录里已经用过的那套（整页灰度截图 → 块内取样片中位亮度），
**不新造工具**——它已经产出过 247/255 这组数，是本裁定的事实来源。

### 4. 认下的代价

- **原型不跟改**：`docs/prototypes/0058-*.html` / `0102-*.html` 内联的 token 块停在改动前的值。
  原型是按票号编号的**决策快照**，回改等于重写记录；且生产前端的样式来源只有
  `docs/design-system/tokens.css` + `web/src/app.css`（§7 单一来源），原型不是可引用的样式源。
  0102 只复制了 token 块、不渲染终态块，这份陈旧值**是惰性的**。
- **新增两个 token**，语义四色那一组不再是整齐的「色 / 底 / 边」三件套。
  换来的是两个相反要求各自有处安放；合并回去就是把 3.1% 那个折中请回来。

### 5. §3 三轴、§6 单主题、§7 单一来源不动

不新增形状、不新增颜色语义、不重开暗色。「重开条件」第 3 条未被触发——
本票不是「三轴形状不够用」，是**其中一轴的形状没画出来**。
