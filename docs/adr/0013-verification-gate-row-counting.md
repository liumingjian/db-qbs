# ADR-0013: 校验门禁的两个数怎么数——source 累加器 vs 暂存表 `COUNT(*)`，在切换事务内比

**状态**: 已接受
**日期**: 2026-08-13
**决策票**: [#29](https://github.com/liumingjian/db-qbs/issues/29)（地图 [#22](https://github.com/liumingjian/db-qbs/issues/22)）

## 背景

ADR-0006 定了「V1 校验只比行数」，`CONTEXT.md` 写成「比对源端读出的行数与暂存表实际落盘的行数」。
ADR-0010 §4 把「封口 → 数 → 比 → 切换」收进一个同步 commit 请求，报文里留了
`source_rows` / `staged_rows` 两个字段，并明写「怎么数、不一致怎么报归 #29」。

问题在于**两个数各有三种数法**，且三种数的都是不同的东西。选错一种，门禁要么恒真（自比自），
要么恒假（跨读一致性视图）——两种都等于没有门禁。

## 0. 先承认这道门禁的真实跨度

commit 报文里的 `source_rows` 是 **source 自己报的数，sink 无从核对**。

所以这道门禁比的不是「源库里有多少行」和「暂存表里有多少行」，而是：

> **「source 自称读出了多少行」** vs **「暂存表实际落了多少行」**

它覆盖的区间是 **source 报文出口 → 暂存表落盘**，**不覆盖 源库 → source 累加器**。
这句话不是免责声明，它决定了下面每一条的形状（尤其 §1 为什么不选 `COUNT(*)`、§7 第 2 条）。

## 1. 源端行数 = fetch 循环累加计数

三种数法与各自数的东西：

| 数法 | 它数的是什么 | 判决 |
|---|---|---|
| **fetch 循环累加器** | 我从游标里取出来多少行 | **选它** |
| 另跑 `SELECT COUNT(*)` | **另一个时间点**的源表有多少行 | 拒绝 |
| 累加 sink 返回的 `rows_written` | sink 说它写了多少 | 拒绝 |

- **`COUNT(*)` 是第二次查询、第二个读一致性视图。** ADR-0007 已定单查询流式：一条 SQL 一个游标。
  再发一条 `COUNT(*)` 就落在另一个 SCN 上，源表在跑时两个数**必然**不同——
  用它当门禁不是更严格，是**制造假警报**，且假警报会训练人去无视门禁。
- **累加 `rows_written` 是拿 sink 的数和 sink 的数比**，门禁自比自恒等，形同虚设。

累加器是三者中唯一**独立于 sink** 的数，这是它当门禁一边的资格。

## 2. 暂存表行数 = 封口后 `SELECT COUNT(*) FROM stg`

| 数法 | 它信任谁 | 判决 |
|---|---|---|
| **`SELECT COUNT(*) FROM stg`** | 数据库 | **选它** |
| 累加每批 `rows_written` | sink 的 `INSERT` 返回值 + sink 自己的加法 | 拒绝（转岗，见 §3） |

**校验的意义在于不信任中间环节。** `rows_written` 之和信的正是最该被怀疑的那一段；
`COUNT(*)` 问的是数据库本身。两者不等本身就是一类要抓的错——affected rows 语义、
连接层重连、静默回滚，都长这个样子。

代价：100k 行、无索引的暂存表全表 count 一次。**只在 commit 里发生一次**，可接受。

## 3. `rows_written` 转岗：source 侧逐批硬断言，不进门禁

ADR-0010 说 `rows_written` 的价值是「推了 5000 只落 4999 **当场定位到第 n 批**」——
但这个价值只在 source **收到响应就断言**时才兑现。

**规则**：每批响应回来，source 立刻比 `rows_written == 本批行数`，不等则**当场整 run 失败**，
错误消息带 `seq`。它**不参与** commit 的门禁算式。

于是两道防线各防各的，不重复也不互相顶包：

- **逐批断言**：抓「某批没写全」，能指名道姓到批次号。
- **commit 门禁**：抓「每批都自称写对了、总数却不对」，是纯粹的兜底。

## 4. 在 sink 侧比，且在切换事务之内

**比的一侧**：sink，在 commit 请求里。ADR-0010 §4 已把封口/校验/切换收进一个同步请求；
改成 source 比，就得先把暂存表数目回给 source、等它说「可以切」再切——
**多一个来回、多一个可断连的窗口**，且违背 ADR-0012「处置权随封口点移交 sink」。

**比的位置**：**切换事务之内**，同一连接同一事务：

```
BEGIN
  SELECT COUNT(*) FROM stg            -- 门禁的一边
  -- 不等 → ROLLBACK，回 409 VERIFY_FAILED
  DELETE FROM <target> WHERE <target_date_col> >= :d AND < :d+1
  INSERT INTO <target> SELECT * FROM stg
COMMIT
DROP TABLE stg
```

封口之后协议层已经拒绝该 `run_id` 的写入，所以从协议角度事务内外等价。选事务内的理由是
**代价为零**（事务本来就要开，count 只是多一条语句），换来的是
**「被数的那份」和「被切换的那份」在数据库层面就是同一个快照**——
不必再论证「封口之后没人能动暂存表」这句话对不对。ADR-0006 那条
「校验与切换之间要封口」的动机，在事务里是免费兑现的。

## 5. `total_batches` 与行数同级，一起当门禁

commit 报文已有 `total_batches`（source 自报推了几批），sink 自己数了收到几批。
这个比对**几乎免费，且抓的错和行数不同**：

- **整批丢失**在行数上表现为「差 5000 行」——看着像数据问题。
- 同一件事在批数上表现为「差 1 批」——**一眼是传输问题**。

两个数一起报，人不用猜是哪一类。不一致同样走 `VERIFY_FAILED`。

## 6. 失败报文：四个门禁数 + 一个诊断数

```json
← 409 { "code": "VERIFY_FAILED",
        "source_rows": 100000, "staged_rows": 99995,      // 门禁
        "source_batches": 20,  "received_batches": 20,    // 门禁
        "sink_reported_rows": 100000,                     // 诊断：sink 逐批 rows_written 之和
        "message": "…" }
```

第五个数把失败**自动分成两类**，人不必翻日志：

| 判据 | 含义 |
|---|---|
| `sink_reported_rows == source_rows` 且 `staged_rows <` 它 | **写进去了又没落**（数据库侧：affected rows 语义、静默回滚） |
| `sink_reported_rows < source_rows`（含批数不符） | **批次没到齐**（协议侧） |

### 6.1 明确不承诺「差在哪一批」

§3 的逐批断言已经把「某批没写全」在 source 侧当场炸掉了。所以**能走到 commit 才发现的不一致，
按定义是「每一批都自称写对了、总数却不对」**——逐批明细里全是「对的」，指不出任何一批。

因此 **sink 不保留 `seq → rows_written` 明细，规格也不承诺定位到批次**。
它在这条失败路径上**结构性地不可能有用**，留着只会让人以为报告里该有个批次号。
**这一条必须写进规格**，否则实现者一定会去建那个列表。

批次级定位由 §3 提供；那条路径上批次号是准的。

## 7. 人话定稿

与 ADR-0012 §7 的措辞对齐，都以「目标表未被触碰，可直接重跑」收尾：

- **写进去了又没落**：
  > 校验未通过：源端读出 100000 行，sink 逐批报告已写入 100000 行，但暂存表实际只有 99995 行
  > ——数据在写入 MySQL 的过程中丢失。目标表未被触碰，可直接重跑；重跑仍失败请报 issue。
- **批次没到齐**：
  > 校验未通过：源端读出 100000 行 / 20 批，sink 只收到 99995 行 / 19 批——有批次未送达。
  > 目标表未被触碰，可直接重跑。

## 8. 失败后的处置：立即 `DROP` 暂存表，不留现场

保留暂存表有真实的诊断价值（拿它和源表对一遍就知道丢了什么）。**仍然丢弃。**

理由：M1 的前提是「失败即整 run 失败、丢弃暂存表」。为校验失败开例外，等于引入一类
**由失败产生、无人回收**的孤儿表（回收已由 [#32](https://github.com/liumingjian/db-qbs/issues/32)
判出 M1，见 [#30](https://github.com/liumingjian/db-qbs/issues/30)）——而且它恰恰产生在
「出了怪事」的时候，也就是最可能反复发生、最容易堆积的时候。

终态记 `DISCARDED` 墓碑（ADR-0012），目标表未动。想事后查的人重跑一次即可复现（源库没变的话）。

**明面上的代价：M1 放弃校验失败后的现场取证。**

## 9. 规格必须明文写出：校验**不**保证什么

按「越容易被误以为保证了」排序：

1. **不保证值是对的。** 行数相等而值被静默改掉的六条路径，全部由**映射预检**挡（ADR-0006 的表）。
   **校验过了 ≠ 数据对了。**
2. **不保证源端那个数是对的。** `source_rows` 是 source 自报，sink 无从核对（§0）。
   游标少读了行、SQL 写错了，这道门禁**一律放行**。
3. **不保证目标表当天数据与源库当天数据一致。** 清除条件与源端 `WHERE` 的等价性由
   **ADR-0008 的结构**保证，不由校验保证；`purged_rows` 只是给人看的（ADR-0010 §9），不是门禁。

## 对既有 ADR 的影响

- **ADR-0010**：`VERIFY_FAILED` 报文由「两个数」扩到「五个数」（§6）；
  `rows_written` 的用途由「让人当场定位」明确为「source 侧逐批硬断言」（§3）；
  `total_batches` 从纯记录升为门禁的一边（§5）。
- **ADR-0006**：「校验是切换的前置门禁」不变，本 ADR 只填口径。§9 是 ADR-0006
  「行数相等但内容不同 V1 抓不到」那句的规格化表述。
- **ADR-0002**：切换事务多一条 `SELECT COUNT(*)` 前置语句（§4）。
- **ADR-0012**：校验失败的终态是 `DISCARDED` 墓碑，`VERIFY_FAILED` 是失败**原因码**不是状态——不变。

## 留给台架验收的

- **`SELECT COUNT(*) FROM stg` 在 10 万行无索引表上的实际耗时**——它现在坐在切换事务的最前面，
  直接加在 ADR-0010 那 30 分钟读超时的账上。并进 ADR-0010 已要求的「commit 实际耗时」一起测。
- **必测场景**：人为丢掉一个批次（或截断一批的行），确认 §6 的五个数确实把两类失败分开了，
  且 §7 的人话确实打出来了。
