# ADR-0015: sink 写暂存表——多值 `INSERT` 显式列名、每批一事务、开连接仪式

**状态**: 已接受
**日期**: 2026-08-13
**来源**: [#33](https://github.com/liumingjian/db-qbs/issues/33)

## 背景

[ADR-0011](0011-batch-payload-wire-format.md) 把批次载荷的形状定死了（按序数组、每值只能是
JSON string 或 `null`、列序 = `source_columns` 序），但 **sink 拿到这堆值之后怎么落进暂存表，
一行规格都没有**。而 [ADR-0010](0010-http-protocol-contract.md) §3.3 在这块埋了一个明写的陷阱：
批次行值按 `source_columns` 序、暂存表列序照目标表 `ORDINAL_POSITION`，两个序混用会造成
[ADR-0009](0009-m1-mapping-precheck-rules.md) §3 警告的那类**静默搬错**——预检全过、
数据整整齐齐灌进错的列，而 V1 只比行数（[ADR-0006](0006-count-only-verification-in-v1.md)），
发现不了。

讨论中挖出一条票面上没有、但直接改写问题形状的硬事实：

> **MySQL 预编译语句的占位符上限是 65535 个**（协议里参数个数是 2 字节）。
> ADR-0011 的批次是 5000 行，生产表 70 列 → 350,000 个占位符，**一条 `INSERT` 装不下**。

于是「一批 = 一条 `INSERT`」这个所有人默认的前提，在 M1 的真实规模下根本不成立。
它往下游污染了事务边界与 `rows_written` 的口径，本 ADR 一并处理。

## 决策

### 1. 写入手法：多值 `INSERT` 参数绑定，一批切成若干条子语句

```sql
INSERT INTO <stg> (`c1`, `c2`, ...) VALUES (?,?,...),(?,?,...), ...
```

`chunk = min(floor(65535 / 列数), 批次行数)` 行为一条子语句，**在建 run 时算一次**
（列数整个 run 不变），不每批算。

**否掉 `LOAD DATA LOCAL INFILE` 的理由是决定性的，且与 ADR-0011 §2 同源**：
它要把值序列化成文本再让服务端解析，**等于在 ADR-0011 刚把转义收敛到 JSON 一处之后，
第二次打开转义面**——分隔符、`ESCAPED BY`、以及表示 NULL 的 `\N`。
而 `\N` 正是 ADR-0011 §2 拒绝带内 NULL 标记时论证过的东西：
**没有任何字符串在 `VARCHAR2` 的值域之外**，标记选什么都存在一个「值本身正好是那个标记」的输入。
那一节把 NULL 与空串的区分从约定层提到了语法层，这里不能再降回去。
`local_infile` 需要服务端与客户端同时打开，只是次要理由。

**否掉「预编译语句逐行 `exec` 循环」的理由是它对不上 ADR-0007 的串行模型**：
逐行执行把 10 万行变成 10 万个来回，而多值 `INSERT` 把它压到约 110 条语句。
[ADR-0007](0007-single-query-streaming-fetch.md) 已定 fetch 与推送**串行不做流水线**，
耗时全摊在关键路径上，这里不该再送一个数量级。

**子语句切分是纯粹的协议层限制的产物，不得被赋予任何语义**：
不是事务单位、不是重试单位、不进任何报文、不进日志的位置感。
否则它会悄悄变成第二种「批次」，与 ADR-0007 那条「批次 = 纯粹的推送切分单位」打架。
`chunk` 夹一个 `批次行数` 的上界，是为了让**窄表与宽表走同一条代码路径**——
不夹的话窄表永远「一批一条语句」、宽表永远「一批多条语句」，两条路径在测试里不会同时被覆盖到。

### 2. 列序：`INSERT` 显式列出列名，把置换交给 MySQL——不在代码里重排

**这一节订正 ADR-0010 §3.3。** 那里写的是「sink 写暂存表时**必然**要做一次列序重排，
这不是可以省掉的一步」。**可以省掉**，而且省掉之后正确性更强。

`INSERT` 的列名清单**按 `source_columns` 序**列出，行值**原样绑定、不动位置**：

```sql
INSERT INTO <stg> (`c_src1`, `c_src2`, ..., `c_srcN`) VALUES ...
```

列名清单**由映射预检的结果生成**——与暂存表 DDL 同一份元数据（ADR-0009 §7 那条
「DDL 是同一份数据的直接产物，不会出现『预检看的是一张表、实际建的是另一张』」在此复用）。

于是票面问的「重排的映射表在哪儿算、算一次还是每批算」这个问题**消失了**：没有映射表。
而票面要的「一条**当场炸**的断言」不是断言，是**构造性消除**——两个序混用在这个形状下
**不可表示**：

| 出错方式 | 后果 |
|---|---|
| 列名写错 / 拼错 | `ERROR 1054 Unknown column` 当场炸 |
| 列数对不上 | ADR-0011 §1 的 `row.len() != source_columns.len()` 断言当场炸 |
| 「按 `source_columns` 序绑值、按 `ORDINAL_POSITION` 序解释」 | **不存在这种可能**——列名把每个值钉到了具体的列上 |

这与 ADR-0011 §2 用 JSON `null` 消灭 NULL 哨兵、[ADR-0002 增补](0002-staging-table-atomic-swap.md)
用表名长度预检消灭运行时截断是**同一种手法**：不靠实现小心，靠形状。

**连带把切换语句也改成显式列名**：

```sql
INSERT INTO <target> (`c1`, ..., `cN`) SELECT `c1`, ..., `cN` FROM <stg>
```

代价为零，换掉 ADR-0002 那条对 `SELECT *` 列序的隐式依赖。
（暂存表列序仍照目标表 `ORDINAL_POSITION` 建，ADR-0009 §7 不变;
本条只是让切换语句不再**依赖**这件事。）

### 3. NULL：`Option<String>` 全程不落地成 `String`

JSON `null` → `Option<String>::None` → 绑定为驱动的 `NULL` 值。**中间不得出现任何字符串形态**，
也不得使用任何 `NULL` 字面量拼接路径（那是第 1 节三条之外的第四条路，等于偷偷退回文本协议）。

理由与 ADR-0011 §2 同源：一旦有一步经过字符串，NULL 与空串的区分就从**语法层**
降级回**约定层**，§2 那句「攻击面在构造上归零」当场作废。
这条与 §2 同级，是硬条款，不留给实现判断。

### 4. 连接：连接池 + 每条连接跑同一套「开连接仪式」

`sql_mode` 与字符集都是 **session 级**的，ADR-0011 §5 的「开连接断言」因此隐含了一个
没人回答过的问题：一个 run 期间 sink 用的是不是同一条连接？

**答案是不 pin**：用连接池，**仪式挂在连接池的连接创建钩子上，不是挂在业务代码开头**——
否则池子里第 2 条连接就是裸的。（切换事务显然在单条连接内完成，那是事务本身的要求。）

否掉「一个 run pin 一条连接」：暂存表是**普通表不是临时表**，跨连接可见，pin 没有正确性上的必要；
而 pin 会让「连接在 run 中途断掉」变成一类需要单独规定的失败（重连后 session 变量丢失，
且 sink 无 run 状态可依，见 [ADR-0012](0012-run-lifecycle-and-state-authority.md)）。**M1 不该为它写规格。**

### 5. 开连接仪式：四件事，一处成文

**一条新连接在可用之前必须做完的事**。本节是这件事的唯一权威，
ADR-0011 §5 的字符集断言并入此处（该节改为指向本节）。

| # | 动作 | 失败处置 |
|---|---|---|
| 1 | 显式配 `utf8mb4`，断言 `character_set_client` / `character_set_connection` / `character_set_results` 三个变量全为 `utf8mb4` | 整个 sink 不可用，翻成人话，点名是哪个变量、实际值是什么 |
| 2 | `SET SESSION sql_mode = 'STRICT_ALL_TABLES'`，随后 `SELECT @@SESSION.sql_mode` **回读断言相等** | 同上，点名期望值与实际值 |
| 3 | 断言 `@@max_allowed_packet >= 64 MiB` | 同上，点名实际值 |
| 4 | 以上任一不符 → 连接不交付给业务代码 | —— |

三条各自的理由：

**`sql_mode` 必须断言，因为 ADR-0009 的整套预检建立在「写入时会炸」之上。**
`ERROR 1264`（整数位溢出）/ `ERROR 1366`（字符集）**只在 strict 模式下为真**；
非 strict 下 MySQL 会**静默截断、静默改值**——正是 ADR-0009 §2「静默改值的地方从严」
要防的那类失效模式。**写死一个完整字符串，不做「在服务端默认值上追加」**：
追加意味着最终值取决于服务端配置，那就是「猜」。取 `STRICT_ALL_TABLES` 而非
`STRICT_TRANS_TABLES`，因为 ADR-0009 的原文前提就是它，且它是两者中更强的一个。

> **2026-08-13 增补（[#35](https://github.com/liumingjian/db-qbs/issues/35)）——这串写死值比 MySQL 默认串**少**两个 mode，是有意识的。**
>
> MySQL 8.0.46 的默认 `sql_mode` 还含 `NO_ZERO_DATE` / `NO_ZERO_IN_DATE`，本 ADR 这串没有。
> 后果已实测（spike §7.9 组 A）：`'0000-00-00 00:00:00'` 写进 `DATETIME` **会被接受**。
> **不补**——源端是 Oracle `DATE`，产不出零日期，补它防的是一条走不到的路，
> 而动这串就是动上面那条「写死完整字符串、不做追加」的形状。
>
> 同一次实测坐实了这条断言**买到的东西比原文写的更多**：域外日期（负年份、五位年）
> 在 `STRICT_ALL_TABLES` 下是硬 `ERROR 1292`，而非严格模式下**静默塌成 `0000-00-00`**
> 并只给 `Warning 1265`。也就是说，这条 `sql_mode` 断言同时是 `DATE` 值域的那道闸——
> [ADR-0009 §10](0009-m1-mapping-precheck-rules.md) 把「值域检查转 M3」正是架在它上面。

**`max_allowed_packet` 要断言，阈值就用 64 MiB、不另立数。**
第 1 节的子语句切分只在**宽表**上顺带压小了包（70 列 → 936 行/条 ≈ 2.8 MB）；
**窄表反过来**：3 列时 `floor(65535/3)` 远大于批次行数，切分不触发，
一条子 `INSERT` 就要扛下整批的 16 MiB 预算（ADR-0011 §6）。
服务端默认 64 MiB 够用，但它可配，客户现场调小过就会在运行期炸 `ERROR 1153`——那时数据已经在搬了。
复用 ADR-0010 §10 已有的那个 64 MiB（请求体断路器）之后，规格里关于
「一批最大能有多大」**只有一处定义**。**归类同 `PAYLOAD_TOO_LARGE`：这是环境配置错误，
不是数据问题**，措辞不能让人去查数据。

**三条都不进映射预检的逐列报告**：它们跟列无关，且一失败就是整个 sink 不可用，
发生时点早于预检。态度同 ADR-0011 §5、同 ADR-0003 对驱动漂移——
**正确性单点上宁可停机不要猜**。

### 6. 事务边界：每批一事务

该批的**全部子 `INSERT` 包在一个显式事务里**。

**否掉「整个 run 一事务」**：它要求跨多个 HTTP 请求持有一个未提交事务（分钟级、10 万行 undo），
并**强制第 4 节选 pin 连接**，把上面那类失败拉回规格里；而它想买的原子性在 ADR-0002 下
**本来就不需要**——暂存表失败即整张 `DROP`，没有半张表要清理。

**否掉「攒 N 批一事务」**：纯粹的调参，M1 不开这种旋钮
（态度同 ADR-0007 的「5000 行 / `fetch_array_size` 100 写死不可配」）。

每批一事务的正面收益，是把第 1 节引入的子语句切分**重新封成一个原子单位**：
`rows_written` 因此是「**已提交**的行数」而不是「写了一半的行数」，
与 [ADR-0013](0013-verification-gate-row-counting.md) §3 那条 source 侧逐批硬断言严丝合缝。
代价接近零——事务本来就要开一次。

### 7. `rows_written` = 该批全部子 `INSERT` 的 `affected_rows` 求和

多值 `INSERT` 且无 `ON DUPLICATE KEY UPDATE`，`affected_rows` 就是插入行数，无歧义。

**两侧各断言一次**：

- **sink**：提交后当场断言 `sum(affected_rows) == rows.len()`，不等即硬失败并**点名第 `seq` 批**。
  这兑现了 ADR-0010 对「当场能定位到第 n 批」的要求——只在当场断言时才兑现。
- **source**：照 ADR-0013 §3 再断言一次收到的 `rows_written` 等于自己发出的行数。

**负面条款：`rows_written` 的累加值不得被 sink 用于任何门禁判断。**
门禁那两组数是 `SELECT COUNT(*) FROM stg` 与 `total_batches`（ADR-0013 §2/§5）。
拿 `rows_written` 之和当门禁就是 ADR-0013 §1 否掉的「拿 sink 的数比 sink 的数」——自比自恒等。
**与 #29 不打架的正是这一点：两个数根本不在同一条算式里。**

## 后果

- **票面问的「列序重排怎么保证做对」失去了对象**——没有重排步骤可以做错。
  ADR-0010 §3.3 的「必然要做一次列序重排」被本 ADR 订正。
- **暂存表写入路径的全部形状定死**：`INSERT` 语句模板每 run 生成一次（列名清单 + `chunk`），
  每批开一个事务、跑 `ceil(rows / chunk)` 条子语句、求和断言、提交。
- **sink 多了一个「连接可用之前」的阶段**，四条断言全在那里，且是整个 sink 级别的失败，
  不是 run 级别的。
- **ADR-0011 §5 不再是字符集断言的权威**，改指本 ADR §5。
- **ADR-0002 的切换语句改为显式列名**，不再依赖 `SELECT *` 的列序。

## 代价

- **子语句切分让「一批」在 SQL 层不再是一条语句**，抓包/慢查询日志里看到的是若干条 `INSERT`。
  第 1 节的负面条款（不赋予语义、不进报文日志）是为了让这件事**只存在于 SQL 层**。
- **`STRICT_ALL_TABLES` 写死**意味着如果客户环境有某张目标表依赖非严格行为，M1 会拒绝跑。
  这是刻意的：那种依赖正是 ADR-0009 要拦的东西。
- **每批一事务**在 10 万行 / 20 批的规模下多出 20 次事务提交的开销，可忽略；
  但它确实放弃了「整个暂存表写入是一个原子单位」这个性质——依据是没人需要它。
- **`max_allowed_packet` 断言可能在客户现场卡住上线**，而它是一个 DBA 一行配置能解决的问题。
  代价换的是「不在搬到一半时炸」。

## 时效

第 1 节的 `chunk` 公式与第 5 节的 64 MiB 阈值都建立在 ADR-0011 §6 的批次预算之上；
批次预算若在台架验收后调整（见 #22 的 M1 验收雾），这两处要一起复审。
第 6 节「每批一事务」在 [ADR-0018](0018-delayed-batch-retry-model.md) 中保持为幂等单位，
但事务内容扩为同一 `__batch_no` 的 DELETE + 全部子 INSERT；两者必须一起提交或回滚。
